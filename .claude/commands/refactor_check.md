---
description: フェーズ完了時にリファクタ要否をメトリクスで判定し、必要なら小規模な提案書を起票する
---

現フェーズで変更したコードを対象に、リファクタリングの要否を判定してください。
必要と判定した場合のみ、小規模な提案書を `instructions/modified_proposal/` に起票します
（フォルダがなければ作成する）。
**このコマンドはリファクタを実行しません。判定と提案書の作成までです。**

## 実行タイミング

- フェーズ完了処理（正本反映タスク・実機目視 OK）の後、フェーズを完了扱いにする前に 1 回実行する
- 挙動不変が前提のフェーズ（デッドコード整理等）や、変更が docs のみのフェーズではスキップしてよい
  （スキップした場合もその旨を完了報告に 1 行書く）

## 手順

> **手順 1〜2 は `verifier` エージェントへ委任する**（`.claude/rules/agent_selection.md`）。
> `PHASE_BASE` と対象範囲を渡し、変更ファイル一覧 + M1〜M6 の測定値表
> + 閾値超過の候補列挙のみ受け取る（diff ダンプをメイン文脈へ載せない）。
> 判定（手順 3 以降）と提案書起票はメインセッションが行う。

### 1. フェーズ差分の特定

1. 直前フェーズの最終コミット（`current.md` / `decisions_archive` / `git log` から特定）を
   `PHASE_BASE` とする。特定できなければユーザーに確認する
2. `git diff --stat <PHASE_BASE>..HEAD -- src/` で変更ファイル一覧と増減行数を得る
   （パスはプロジェクトのソースルートに合わせる。以下同）
3. **判定対象はこの変更ファイルのみ**。フェーズで触っていないコードは対象外
   （既存の負債を見つけても提案書に含めず、`current.md` の「別タスク化候補」への追記に留める）

※ 本コマンドで「`current.md` の別タスク化候補へ追記」とある場合は、`current.md` の
`## 別タスク化候補` 節へ 1 行追記する（節がなければ新設する）。

### 2. メトリクス収集（変更ファイルごと）

| 記号 | 測るもの | 方法 |
|---|---|---|
| M1 | ファイル行数と増分 | `wc -l <file>` と diff --stat の増分 |
| M2 | 巨大関数の新規発生 | このフェーズで追加した関数、または 40 行以上変更した既存関数のうち、80 行超のもの（diff hunk を読んで特定） |
| M3 | 同型ブロックの増殖 | このフェーズで追加したコードが、既存の同型ブロックの「3 個目以降のコピー」になっていないか。機械的基準: 既存コードをコピペして修正したものは必ず該当。それ以外は「片方を直したらもう片方も直す必要があるか」で判定し、迷えば非該当 |
| M4 | 列挙型ボイラープレートの増加 | 全フィールド列挙の再構築・分岐の全モード列挙など、「フィールド/モード追加のたびに全箇所を直す」形の箇所が増えたか。測定はフェーズ前後の比較で行う（例: `git show <PHASE_BASE>:<file> \| grep -c "<型名>("` と `grep -c "<型名>(" <file>` を比較） |
| M5 | 申し送りコメントの新規追加 | `git diff <PHASE_BASE>..HEAD -- src/ \| grep -E "^\+.*(別タスク\|申し送り\|TODO\|将来.*統一\|暫定対応)"`（**必ずソースルートでパス限定する**。instructions/ や .claude_data/ の差分には「別タスク」等が正当に含まれるため、無限定だと毎フェーズ誤発火する） |
| M6 | 直値の重複追加 | 追加コードに、既存定数と同じ値のハードコード直値が入っていないか。照合範囲は変更ファイル内 + そのファイルが import している定数モジュール（`shared/constants.py` 等）に限る（コードベース全体は読まない） |

### 3. 判定（機械的に）

以下のいずれかに該当したら「**リファクタ推奨**」、どれにも該当しなければ「**不要**」:

- M1: ファイルが 600 行を超えており、**かつ**このフェーズで +100 行以上増えた
- M2: 80 行超の関数が新規発生した（既存の巨大関数は対象外）
- M3: 同型ブロックが 3 箇所以上になった
- M4: 列挙型ボイラープレートの箇所数が増えた
- M5: 申し送りコメントが新規に入った（← 最重要シグナル。「別タスク」と書いた瞬間がタスク化のタイミング）
- M6: 既存定数と同値の直値が追加された

**再提案の抑止（該当しても提案書に含めない）**: 該当箇所が以下のいずれかなら、提案書の項目に
せず、判定結果の報告に「既知（<参照先>）」と 1 行書くだけにする:

- 既存の提案書（`instructions/modified_proposal/*.md`）の未実施項目が既にカバーしている
  （その項目の実施までは常に「既知」扱いとする）
- `current.md` の「別タスク化候補」に記載済み
- 過去の /refactor_check で「保留」とユーザー判断済み（decisions 記録参照）

同一対象への提案書がフェーズごとに量産されるのを防ぐため、この抑止確認は判定より先に行ってよい。

**境界事例の定性判断材料**: M1〜M6 の該当が微妙（境界上）のときは、以下の 2 つを判断材料に
してよい。**どちらかに該当すれば「推奨」、どちらにも該当しなければ「不要」に倒す**
（定性材料は境界事例の tie-breaker 専用。単独のトリガにはしない = 判定の再現性を守る）:

- 対象ファイル内に「〜管理」「〜処理」「〜関連」のような**異なる責務のまとまりが 3 つ以上**
  見える（100 行のファイルでも責務が混在していれば分割対象になりうる）
- **AI への修正依頼で対象箇所を一言で説明しにくい**（「このファイルの◯◯の部分だけ」と
  修飾が必要になる構成は、意図しない変更・余計なコンテキスト消費の源になる）

どちらにも該当せず迷ったら「不要」に倒し、`current.md` の「別タスク化候補」に 1 行追記して
次フェーズ以降の再判定に委ねる（このコマンドは毎フェーズ走るので、悪化すれば次回引っかかる）。

### 4. 出力

**「不要」の場合**: 完了報告に以下の 1 行を含めて終了。提案書は作らない。

```
リファクタ判定: 不要（M1〜M6 該当なし。対象: <変更ファイル数> ファイル）
```

**「推奨」の場合**: `instructions/modified_proposal/NN_refactor_<phase名>.md`（NN は既存の次番号）
を作成し、ユーザーに提示して判断を仰ぐ。**ユーザー承認前に実装しない。**

提案書の必須構成:

- **項目数は 1〜3 個まで**。それを超える場合は効果×リスクで上位 3 個に絞り、残りは
  「別タスク化候補」として `current.md` に追記する
- 各項目に必ず含める: ID / 対象（ファイル:行）/ 何が問題か（該当したメトリクス記号を明記）/
  どう変えるか（変更前後のコードスケッチ）/ 完了条件（実行コマンドと期待結果）/
  リスクと戻し方 / 依存
- **安全網の確認**を項目 0 として置く: 既存テスト（テストスイート全パス +
  round-trip / smoke 等の特性テスト。コマンドは言語別ルール参照）が対象領域をカバーしているか確認し、
  カバーしていなければ特性テストの追加を先行項目にする
- 新ファイルの配置・命名・フォルダ化（親フォルダ方式）・昇格（Private → Feature Shared →
  Global Shared）は `.claude/rules/file_organization_rules.md` の判断手順に従う
  （同ファイル末尾の「本リポジトリへの適用注記」を含む）
- 挙動保存が原則。挙動変更が必要なら本コマンドの範囲外
  （`.claude/rules/spec_change_workflow.md` の仕様変更フローへ回す）

### 5. 記録

- 判定結果（不要 / 推奨 + 提案書パス / スキップ + 理由）をフェーズの完了報告に含める
- 「推奨」の場合、`decisions_archive/<phase>.md`（またはフェーズ進行中なら `decisions.md`）に
  判定と提案書パスを 1 行記録する
- ユーザーが提案を承認した場合の実施タイミングは、(a) 同フェーズ末の追加タスク
  （`task_NN_refactor` として起票）または (b) 次フェーズ前の独立ミニフェーズ、のいずれかを
  ユーザーに選んでもらう

## 禁止事項

- ユーザー承認なしにリファクタを実施すること
- フェーズで触っていないコードを提案書の項目に含めること
- 4 項目以上の提案書を作ること（大規模化の兆候。分割するか候補送りにする）
- 挙動・エラーメッセージ・保存ファイルのバイト列が変わる「修正」を提案書に混ぜること
- 判定のために本コマンドの範囲を超えてコードベース全体を読み込むこと（`python_rules.md` 準拠）
