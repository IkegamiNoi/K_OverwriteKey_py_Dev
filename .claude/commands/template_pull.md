---
description: template リポジトリで育った運用ルール・インフラをこのプロジェクトへ取り込む（逆同期。差分抽出 → 分類表で確認 → 適合化して反映）
---

このプロジェクトの生成元 template で発展した運用資産を、こちらへ取り込んでください。

**方向は template → このプロジェクト（逆同期）**。逆方向は template 側の `/template_sync` の責務。

## 前提（設計の中核）

- ソースは template リポジトリ 1 つ。パスと同期状態は `.claude/template_pull_state.md` に記録する
- **双方向に乖離している。template の差分をそのままコピーしない。** template は汎用
  （`EDIT REQUIRED` 前提・言語非依存・条件分岐で書かれている）で、こちらは具体化済み。
  取り込みは**汎用化の逆＝適合化**であり、こちらで確定している事実を汎用文言で上書きしてはならない
  （例:「python は必ずリポジトリルートの `.venv`」「Codex は python を実行できないので実測は `verifier`」）
- **template 側が正とは限らない。** こちらが先行している箇所・意図的に差分にしている箇所がある
  （マーカーの「意図的に差分にした箇所」を先に読む）
- template のパスは追加ワーキングディレクトリとして許可されている必要がある（`/add-dir` 等）。
  読み取りで止まる場合は、その旨を報告してユーザーに追加を依頼する
- 1 回の実行で扱う範囲は、確認ゲートで判断できる分量に保つ

## 引数

- `[<ref | range>]` — 省略時はマーカーの `last_pulled..HEAD`。単一ハッシュなら `<hash>^..<hash>`

---

## 手順

### 1. 範囲の決定

1. `.claude/template_pull_state.md` を読む（template のパス / `last_pulled` / 対応関係 / 除外メモ /
   意図的に差分にした箇所）
2. `git -C <template> rev-parse --show-toplevel` で git リポジトリであることを確認する
3. 範囲 = `<last_pulled>..HEAD`（引数があればそれを優先）。
   **`last_pulled` が空なら初回モード**（手順 2b）
4. `git -C <template> log --oneline <range>` で**コミット単位のタイトルを先に把握する**
   （手順 9 のコミット分割の単位になる）
5. 対象 0 件ならその旨だけ報告して終了（マーカーの日付のみ更新してよい）

### 2a. 候補抽出（差分モード。本文は読まない）

```bash
# ① 移動・改名を見る。pathspec は付けない（付けると rename 検出が効かない）
git -C <template> show --stat --summary -M <各コミット>
# ② 許可リストで絞った一覧
git -C <template> diff --stat -M <range> -- <許可リストのパス>
```

- **①の `--summary` を省略しない。** `--stat` だけだと rename は `{旧 => 新}/path` 形式で
  出るが**列幅で切れて見落とす**。`--summary` の `rename {旧 => 新}/path (NN%)` 行で確認する
- **①と②を必ず突き合わせる。** ②に pathspec を付けると移動元が範囲外になり、`-M` を付けても
  rename が検出されず**移動が「純新規」に見える**（実測: `-- .claude_data/modes/` で
  22 files / insertions のみ / deletions 0。移動元 `instructions/agent_mode/` が pathspec 外）。
  これを新規取込として丸コピーすると、旧パスの残置とパス階層のズレを持ち込む
- 名前変更・新規追加（template にありこちらに無い）も候補に含める
- 許可リスト外への移動は「削除」に見えるが、**こちら側ファイルの削除としては扱わない**（要判断へ）

### 2b. 候補抽出（初回モード）

許可リストのディレクトリ単位で内容比較し、**差異のあるファイルだけ**候補にする。

```bash
git diff --no-index --stat <template>/<path> ./<path>
```

- 同一内容のファイルはこの時点で候補から外れる（本文を読まない）
- マーカーの対応関係にあるファイルは、名前ではなく**対応先**と比較する

### 3. 候補ファイルの分類

候補ファイル**のみ**、必要な範囲で本文を取得して判定する（トークン制御）。

- 部分変更: `git -C <template> diff -M <range> -- <path>`
- 全面改訂・新規: `git -C <template> show <ref>:<path>`
- こちら側は現行ファイルを読む（無ければ「新規」）。**マーカーの対応関係を必ず確認する**
  （ファイル名が同じでも対応先が違う場合がある）

| ラベル | 条件 |
|---|---|
| 新規取込 | こちらに相当ファイル/節が無く、このプロジェクトでも意味がある |
| 更新反映 | こちら側が古い・不足している |
| 既反映 | こちらが同等以上（先行・具体化済みを含む）→ 触らない |
| 取込不要 | template 専用、または他言語・他構成向けで、適合化しても意味が残らない |
| 要判断 | 双方が同じファイルを別方向に育てており機械的に決められない |

原則 1 ファイル 1 ラベル。**行単位で採否が分かれる場合は「部分取込」として扱い**、
採る行と落とす行を確認ゲートで分けて示す（例: `.gitignore` は 2 行だけ採り、他は取込不要）。

### 4. 確認ゲート（**必ずここで停止する**）

以下を出力し、**ユーザーの承認を待つ**。承認前にファイルを変更しない。

```
## template_pull: 取込候補（range: <range> / <N> コミット）

### <template のコミットタイトル>（<hash>）
| 対象 | 分類 | 要旨 | 適合化 |
|---|---|---|---|
| .claude/rules/review.md | 更新反映 | レビュー観点を5観点へ整理 | 不要 |
| ...

**要判断**: <選択肢と推奨を1〜2行で>
**取込不要と判定**: <対象の列挙のみ>
```

- 表は **template のコミットごとに分ける**（手順 9 のコミット分割と対応させる）
- 「適合化」欄には、プロジェクト固有へ書き換える必要があるかを書く
- 候補が 15 件を超える場合はグループ（agents / commands / rules / modes / docs）ごとに承認を取る
- この分類作業をサブエージェントへ委任しない（許可リストで既に絞れているため。
  `.claude/rules/output_style.md` の委任量抑制）

### 5. 取込と適合化（同一ステップで行う）

承認された行のみ反映する。**取り込みながら適合化する**（後追いの修正工程を作らない）。

- `EDIT REQUIRED` ブロック → このプロジェクトの実値を入れる（`.venv` のパス等）
- 汎用化された条件分岐（「実行系がワークスペース外にある環境では…」等）
  → **こちらで確定している事実へ置き換える**（「Codex は python を実行できない」）
- 他言語・他フレームワーク向けの節・例示 → 落とす
- **モードの変種・新モードを取り込む場合、template のファイルをそのまま置かない。**
  こちら側の同系変種（例: 既存の `codex` 変種）をベースに、**モード固有部分だけを差し替える**。
  差替箇所を数えて確認ゲートの表に書く（例: 見出し / 冒頭の方針 1 行 / 対象節の 3 箇所）
- ファイル移動は `git mv`（履歴を保つ）。パス階層に依存する実装
  （`Path(__file__).parents[N]` 等）を**必ず見直す**

### 6. 残存チェック

- 汎用プレースホルダの残存: `EDIT REQUIRED` / 他言語・他フレームワーク名 / `py` ランチャ前提の記述
- **旧パス参照**（移動を伴う場合）: `.claude/` ・ `.claude_data/modes/` ・ `CLAUDE.md` ・
  `AGENTS.md` ・ `README.md` ・ `instructions/` ・ `.claude_data/state/` ・ `tests` を grep する
  （`.claude_data/modes/` の switch_files 変種とスクリプト docstring、および state・履歴側の
  取りこぼしが起きやすい）
- 意図的に残した場合は理由を報告に 1 行で書く

### 7. 波及チェック（**取り込みで最も漏れる箇所**）

メインセッションが実測する（タスクではないため `verifier` への委任は必須でない）。

- **モード切替**: 管理対象ファイルを触った / モードを追加した場合は
  `.claude_data/modes/README.md` の注意 1〜3 に従う（全変種への追随・`check` は非稼働モードの
  ズレを検知しない・参照側は中立に書く）
- **稼働側との差**: `check` が「登録ファイルのどれにも一致しない」と言う場合、稼働側にだけ入って
  いる改良がある。**登録ファイル側へ書き戻して一致させる**（放置すると `apply` で失われる）
- **`.gitignore` の根拠**: `git check-ignore -v` で確認する。グローバル設定や
  `.git/info/exclude` 由来のものは追跡ファイルに入っておらず、別マシンでは無効
- **実測**: python は `.venv`（`.claude/rules/python_rules.md`）。`compileall` と、モードを
  触った場合は `switch_*.py` の `check` を実行する。**自己申告で済ませない**

### 8. レビュー

複数コミットを跨ぐ差分になるため `deep-reviewer` を 1 回かける。観点に
「旧パス参照の残存」「適合化の漏れ（汎用文言のまま取り込んでいないか）」「取込不要判定の妥当性」
を明示する。事実主張は `ファイルパス:行` を実測で裏取りしてから採用し、採否はユーザー確認を経る。
タスク・フェーズではないため Codex 側レビューの併用は任意
（`.claude/rules/agent_selection.md` の「一方だけで完了判定を確定させない」はタスク完了判定の規定）。

### 9. マーカー更新とコミット

- `.claude/template_pull_state.md` を更新する
  - `last_pulled` = 今回の範囲の終端コミット / `date` = 実行日
  - 恒常的に「取込不要」となる**節**（ファイル単位で切ると template 側の改訂を取りこぼす）、
    ファイル対応関係のズレ、**template と意図的に差分にした箇所**を該当節へ追記する
    （意図的差分を記録しないと、template 側の `/template_sync` で毎回候補に出続ける）
  - template 側マーカー（`.claude/template_sync_state.md`）の記述が今回の取り込みで古くなった
    場合は、その旨をユーザーへ報告する（こちらからは直さない）
- 適合化の設計判断（何をベースにし何を差し替えたか）は、コミットメッセージに残す。
  仕様判断に当たるものがあれば `.claude_data/state/decisions.md` へも記録する
- コミットは template のコミットに 1:1 対応させ、メッセージに元ハッシュを書く
  （例: `モード切替機構を .claude_data/modes/ へ移動（template aa2f827 取込）`）。
  レビュー指摘の反映は別コミットにする
- フェーズタスクではないので `/task_commit` は使わない。**push はしない**

## 禁止事項

- 確認ゲート（手順 4）を経ずにファイルを変更すること
- template の汎用文言で、こちら側の確定済み記述を上書きすること（＝「既反映」判定の省略）
- 移動を新規取込として扱い、旧パス参照とパス階層のズレを残すこと
- template 側の未修正の不整合をそのまま持ち込むこと
  （**取り込んだ結果がこのプロジェクトで成立しているか**で判断する）
- モードを追加・変更したのに、変種追随と `check` 実測を省略すること
- 逆方向（このプロジェクト → template）の同期を行うこと
