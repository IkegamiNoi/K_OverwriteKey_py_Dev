---

`instructions/common/spec_detail/` の仕様書を変更する必要が生じた場合に使うコマンド。
`.claude/rules/spec_change_workflow.md` の「ユーザー判断後 (A) 仕様書更新」を実行する
（手順詳細は `instructions/common/rules_detail/spec_change_workflow.md`「ユーザー判断後の手順」）。

---

## 前提

このコマンドは **ユーザーが (A) 仕様書更新方針を選んだ後に呼ぶ**ことを想定している。
仕様変更の検出と方針判断は事前に済んでいる前提で動く。

検出フェーズが未完了の場合は実行しないこと。代わりに `spec_change_workflow.md` の検出基準に従い、ユーザーへの報告 → 方針判断を先に行う。

---

## 実行手順

以下を順に実施する。各ステップ完了ごとに進捗を簡潔に報告する。

### ステップ 1: 影響範囲の特定と提示

仕様変更によって影響を受けるファイル群をユーザーに提示する。**勝手に変更せず確認を取る**。

提示すべきリスト:
- 仕様書本体: `instructions/common/spec_detail/<file>.md`（複数あり得る）
- サンプル: `instructions/common/spec_detail/samples/<file>.json` 等（影響する場合のみ）
- タスクファイル: `instructions/phase/<NN_topic>/tasks/task_*.md`（対象範囲・検証項目・実装上の制約等が影響を受けるもの）
- 履歴: `.claude_data/state/decisions.md`（判断記録）/ `instructions/phase/current.md`（フェーズ / タスク状態）

ユーザーから「漏れている影響先がないか」の最終確認を得てから次へ進む。

### ステップ 2: 仕様書本体の更新

- 該当 `instructions/common/spec_detail/*.md` を最小差分で Edit
- 既存記述を**削除する場合は理由を明示**（変更前後の差分を会話に出す）
- 関連する別仕様書（`data_schema.md` ↔ 保存フォーマット仕様 等）の整合も同時にチェック
- キー順・型・必須/任意・制約・前方互換ルールを明記する場合は確定ルール表（別実装がある場合は実装間共通の表）に反映

### ステップ 3: サンプル更新（必要時のみ）

`samples/` 配下のファイルが新しい仕様に適合するように更新。

- 末尾改行・インデント・キー順・数値表記など仕様書の確定ルールに合わせる
- バイト一致テストの正本になるため**慎重に**

仕様書側でサンプル不要が確定した場合はこのステップをスキップしてよい。

### ステップ 4: decisions.md への判断履歴追記

`.claude_data/state/decisions.md` に以下を含めて追記:

```
### <変更内容の見出し>
- <選択肢 A> → **採用 / 修正して採用 / 保留 / 除外** のいずれか
- 理由: <なぜこの判断にしたか>
- 代替案 (<選択肢 B>) → **除外 / 保留** + 理由
- 影響範囲: <他タスク / 別実装 / テスト fixture 等>
```

凡例（採用 / 修正して採用 / 保留 / 除外）は既存の decisions.md 冒頭に従う。
**判断と理由をセットで残すこと**。後続セッションで「なぜそうしたか」を辿れるようにする。

### ステップ 5: タスクファイルの更新

影響を受けるタスクファイル `instructions/phase/<NN_topic>/tasks/task_*.md` の該当セクションを更新:

- **対象範囲**: 仕様変更で対象が広がる/狭まる場合
- **検証項目**: 新しい検証観点が増える場合
- **未適合項目テーブル**（検証結果セクション内）: 既存テーブルの記述変更
- **実装上の制約**: 新ルールが既存実装を制約する場合
- **推奨実装順序**: ステップ追加・順序変更
- **検証結果**: 既に reviewer 検証済みの項目は再検証フラグを立てる

複数タスクが影響を受ける場合は**すべて更新**。漏れがないかチェックリスト形式で確認する。

### ステップ 6: 再検証タスクの起票判断

仕様変更が以下のいずれかに該当する場合、再検証タスクを起票する:

- 既に reviewer 検証完了済みのタスクの前提が変わった
- スコープ変更により未検証領域が発生した
- 別実装（Python 版等）との互換性確認が必要

起票する場合の命名規則: `task_<親NN>_<連番>_<topic>_recheck.md`
（例: `task_01_01_domain_scope_recheck.md`）

ファイル配置は親タスクと同じディレクトリ。`phase.md` の tasks 一覧にも追記。

### ステップ 7: current.md の更新

`instructions/phase/current.md` の該当フェーズ記載に対して（進捗記録は current.md へ一本化）:

- 既に完了になっていたタスクを再開する場合 → 進行中へ戻し、再検証要の旨を併記
- 新規再検証タスクを追加した場合 → 該当フェーズ項に簡潔に追記
- 仕様変更そのもののエントリを該当フェーズ項（または次フェーズ候補）に追加

### ステップ 8: 完了報告

実施した内容を簡潔にまとめてユーザーに報告:

- 更新したファイル一覧
- decisions.md の追記項目
- 起票した再検証タスク（あれば）
- 次に取るべきアクション（reviewer 再検証 / implementer 再実装 等）

---

## 禁止事項

- ユーザー方針確認なしの仕様書修正（このコマンドが呼ばれた = ユーザー承認済み、それ以外は禁止）
- 影響範囲リスト提示（ステップ 1）の省略
- decisions.md への記録省略（重要な判断は必ず残す）
- タスクファイル更新の漏れ（ステップ 5 でチェックリスト化）
- 「あとで直す」を前提とした仮置きの仕様書記述
