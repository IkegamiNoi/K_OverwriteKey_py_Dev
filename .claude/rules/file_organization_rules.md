# ファイル構成・肥大化対策ルール（要点版）

ファイル肥大化・構造劣化を防ぎ、保守性・発見性を維持するための配置ルール。
言語・アーキテクチャに依存せず適用する。
例・図・詳説は `instructions/common/rules_detail/file_organization_rules.md`（必要時のみ読む）。

## ■ 基本原則

1. **共通化より局所化** — 責務を持つ機能・ファイルの近くに置く。再利用されたという理由だけで
   共通フォルダへ移さない。本当に共通概念と判断できた場合のみ共通化する
2. **肥大化したら分割** — 理解・修正・レビューしにくくなったら責務ごとに分割する
   （機能単位のまとまりは維持）
3. **所有者中心に構造化** — 特定ファイルからしか使われない補助は、そのファイル専用フォルダにまとめる
4. **分類の判断順序** — まず種類（責務カテゴリ）別 → 馴染まないものは所有者中心。
   種類別フォルダと所有者フォルダは入れ子にしてよい

## ■ フォルダ化（単一ファイル肥大化の分割時）

- **推奨**: 親ファイル専用フォルダを作り、親ごと入れる（`user_page/user_page.ext` + 補助群）
- **非推奨**: 親をフォルダ外に残し補助だけフォルダへ（親子関係・発見性が悪化）
- 検討タイミング: 分割ファイルが2個以上 / 今後増える見込み / 責務群として管理したい

## ■ 昇格ルール（使用範囲で配置決定）

- **Private**（利用1箇所 = 親専用フォルダ）→ **Feature Shared**（機能内共有 = `feature/common/`）
  → **Global Shared**（複数機能から利用 = `shared/`）。逆方向への移動は原則禁止
- 共通フォルダを雑多な置き場にしない（`utils` / `helper` / `misc` 禁止）。責務ごとに分類する

## ■ 移行

- 一時的なラッパー / re-export は移行期間のみ可。**恒久的な互換レイヤーは禁止**。
  削除予定コメントや Deprecated 指定を付与する

## ■ 判断手順とデフォルト

判断順: ①種類 → ②所有者 → ③利用箇所数 → ④最も狭いスコープへ置けるか → ⑤共通化の必然性 →
⑥フォルダ化で発見しやすくなるか → ⑦保守性。
迷ったら: **共通化しない・近くに置く・昇格は後回し・発見しやすさと保守性を優先**。

## ■ 本リポジトリへの適用注記（EDIT REQUIRED — プロジェクトの言語・構成に合わせて書き換える）

> 以下は Python / オニオン構成（レイヤ first）での読み替え例。

- Private = 親ファイル専用パッケージ（例: `src/presentation/input_controller/`）/
  Feature Shared = レイヤフォルダ直下（「機能」=レイヤと読み替え）/ Global Shared = `src/shared/`
- パッケージ `__init__.py` の再輸出（公開面の定義）は互換レイヤー禁止の**対象外**。
  禁止対象は「移動前の旧パスに残す横流し専用モジュール」
- `shared/` 配下にオニオン層名（`domain` 等）を使わない。補助モジュールにも雑多名を付けず
  内容を表す名前にする（例: `pick_helpers.py` = 候補選定純関数群）
- **正本ドキュメントの例外**: `spec_detail/` の分割は親（INDEX）を直下に残し節を同名フォルダへ
  （非推奨構成だが「ファイル名 + 節番号」参照の安定を優先）。手順は `/spec_split`
- 数値閾値は `/refactor_check` の M1〜M6（本ルール=どこへ置くか / refactor_check=いつ直すか）。
  実装時の予防目安（関数30行・新規300行）は `.claude/rules/implementation.md`
