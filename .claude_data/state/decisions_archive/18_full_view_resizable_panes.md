## 問題

フル表示のメイン領域（キーマップ管理 | トリガー一覧 | 出力シーケンス）は、ウィンドウ幅を変えると**出力シーケンスが伸縮**し、
枠の幅をユーザーが変える手段も保存もなかった。

## 確定した設計判断

| # | 判断 | 採らなかった案と理由 |
|---|---|---|
| 1 | **ウィンドウ幅の増減はトリガー一覧が受ける**・境界線 2 本のドラッグで両端を変え差分はトリガー一覧が吸収 | — |
| 2 | **`tk.PanedWindow`** に 3 枠（両端 `stretch="never"`） | 案 B（grid + 自前の仕切り）= 押し出し制御は同じで可動部が増える |
| 3 | **サッシュのドラッグを個別バインドで処理し `"break"`**（可動範囲の制限・中ボタン無効） | 標準バインド = 隣が `minsize` に達すると**反対側の枠まで押し縮める**（実測） |
| 4 | **ウィンドウ最小幅 = 両端の表示幅 + トリガー最小幅** | 3 枠の最小幅の合計 = 両端が潰れる |
| 5 | **最小幅は部品の並びに応じて算出**（縦並び = max / 横並び = 合計）（v0.3） | 減算式 = チェックボックスが最広の枠で切れる幅を許す |
| 6 | **希望幅と表示幅を分ける**。ドラッグで表示幅が変わったときだけ、接する側の希望幅を更新（v0.2 / v0.3） | 表示幅をそのまま保存 = 自動で広げた幅が保存される |
| 7 | **収まらない場合は最終値を先に全部計算して 1 回で適用**（v0.3） | 逐次適用 = 一時的に画面外まで広がる |
| 8 | **ウィンドウ幅も保存**（v0.4 = 案 A）。**既定幅は既定ウィンドウ幅 780 基準で算出**（ユーザー案） | Codex 案「希望幅も常に保存」= 既定幅を保存しない方針と衝突 |
| 9 | **ドラッグ中は移動イベントを `after_idle` で間引く**（v0.4 = 案 L） | 案 P プロキシ表示 = 離すまで幅が変わらない / 案 S ボタン列を枠外区画へ = 見た目が変わる |
| 10 | **アプリが自動で決めた幅は保存しない**（v0.4 再レビュー） | 狭い画面で起動して閉じるだけで保存幅が上書きされる |
| 11 | **ウィンドウ幅はリサイズごとに 500ms 間引いて保存・終了時は保存しない**（v0.5 = ユーザー案） | A = 通常時の幅を記録して終了時保存 / B = Win32 `GetWindowPlacement`（presentation に OS 専用コード）/ 終了時保存の併用 = 間引き中の取りこぼし防止だけで人の操作では不要（ユーザー判断） |
| 12 | **判定は予約の実行時**・ユーザーが幅を変えたら自動決定幅を無効化（状態条件で書かないときは無効化しない）（v0.5 敵対的レビュー） | 自動決定幅を固定 = 手で起動時の幅へ戻すと保存されない |
| 13 | **`write_startup` の失敗表示中はフック停止**（v0.5 敵対的レビュー・`key_input.md` §7.2 への適合・既存呼び出し元にも効く） | 呼び出し元ごとに停止 = 抜けが残る |

## 受容した制約

- 最後の幅変更から 500ms 以内に閉じる・最大化する・省略表示へ切り替えた変更は保存されない。
- 保存失敗が続く環境では幅を変えるたびに失敗ダイアログが出うる。
- ヘッダ領域が要求幅より狭くなったときの切れは既存の挙動のまま（→ idea_21）。
