  **`hotkey_presets_individual` が OFF でもパスは「参照あり」**（意図的 superset）。

### 【§4-A〜F の確定】（ユーザー 2026-09-06）

- **A = 読めなかった参照側があっても警告のうえ隔離・削除とも許す**（推奨の「抑止」から変更）。

### 【確定前レビュー】`codex-adversarial-reviewer` = needs-attention（High 3 / Medium 1）

- **High 1（不完全な走査のまま隔離 → 削除で恒久損失）= 除外**（ユーザー判断）。
  **degraded 方式**（走査が不完全な実行単位は削除だけ恒久拒否）を検討したが、
  **消せない隔離物が残ると結局ユーザーがエクスプローラで直接削除することになり、そちらが事故りやすい**
  ため不採用。代わりに**警告 + 「実行 / キャンセル」の 2 択**を規定し、**残存リスクを暫定仕様 §3-12-5 に明記**。
  あわせて**「見つからなかった指定ディレクトリ」を危険信号にしない**ことも確定
  （既定外ディレクトリの移動・削除は日常的で、**それ自体は参照集合を欠けさせない**）。
- **High 2 = 採用**: マニフェストを**移動前に原子書込み**（書けなければ 1 件も動かさない）。
  後追い記録だと中断時に「隔離先にファイルはあるがマニフェストが無い」＝復元対象外の状態が生まれる。
- **High 3 = 採用**: 削除 API は**実行単位 ID のみ**を受け取り 4 つを検証。
  `is_path_within` は docstring どおり**同一パスも配下と判定する**（`__init__.py:686`）ため、
  それだけでは**隔離ルート自身の再帰削除**を防げない。
- **Medium = 採用**: `external_keyboard_layouts` は**両基準で解決した superset**を参照集合へ入れる。
  既存実装は「config_root 基準で解決 → 親基準の相対表記で runtime 保持 → その値をそのまま保存」
  という非対称があり、**ファイル内の値がどちらの基準か一意に決まらない**。
  **非対称そのものの是正は本フェーズ対象外** →
  [idea_13](../../instructions/backlog/idea_13_external_layout_path_base_asymmetry.md) へ分離。

### 【その他の確定】

  `send2trash` 等の**新規依存を追加しない**。
  ※ 検討中に「phase 10 でゴミ箱送りの削除機能を作った」との想起があったが、**事実ではない**

### 【task_06b 起票時】§3-8 検証④の緩和 = **強い確認付きで削除を許す**（ユーザー確定 2026-09-06）

**検出**: 暫定仕様の**条項間の矛盾**（`.claude/rules/spec_change_workflow.md` 検出基準 B）。
§3-8 検証④「有効な `manifest.json` を持つ」を絶対条件にすると、マニフェストが壊れた実行単位は
**§3-7 により復元もできない**ため、**アプリからは復元も削除もできない残骸**になる。
これは §4-A の判断（degraded 方式を不採用にした理由 = **消せない隔離物が残ると結局ユーザーが
エクスプローラで直接消すことになり、そちらが事故りやすい**）と真逆に働く。

**判断**: **§4-A を優先し、検証④のみ「強い確認」で上書きできる**ようにする（暫定仕様 **v0.5**）。

- **①②③は緩和しない**（隔離ルート直下に実在 / 実行単位の名前形式 / 隔離ルート自身でない）。
  `is_path_within` は**同一パスも配下と判定する**（`__init__.py:738`）ため③は必須のまま。
- API は「④を満たさない単位の削除を明示的に許可する」**引数を要求**する（既定は拒否）。
- UI は通常の削除と**文言を分ける**（「中身を確認できない」「ディレクトリごと削除する」+ 全件提示）。
- 一覧の「マニフェスト不正」表示と **§3-7 の復元不可は不変**。

**却下した案**: (a) 仕様どおり削除させない → §4-A と矛盾したまま残骸が残る。
(b) task_06b では保留 → 不可逆機能の設計を後から緩めることになり
`spec_change_workflow.md` の不変原則（**実装してから仕様を後追いで緩めない**）に反する。

**発生源の状況**: task_05b で `manifest.json.tmp` が残る経路は塞いだため、**新規の残骸は生まれにくい**。
既存分・手で壊された分への対処としての規定。

### 【task_06b 完了時】敵対的レビューの High 2 件（TOCTOU）= **両方ともコード修正せず受容**（ユーザー確定 2026-09-07）

`codex-adversarial-reviewer` が task_06b の差分に対して **needs-attention（High 2 件）** を出した。
どちらも「検証してから実際に消すまでの間に外部が状態を変えられる」という TOCTOU 系。
**ユーザー判断 = 両方とも修正不要**。**idea も起票しない**（backlog は修正予定のものを置く場所のため）。
残存リスクとして**暫定仕様 §3-12-6 / §3-12-7 へ記録**した（**v0.6**。task_08 で正本へ昇格）。

- **High 1「確認後に追加された未提示ファイルも消える」= 受容**。
  Codex の指摘自体は事実。ただし**削除の粒度は実行単位ディレクトリ**（§4-B）で、ユーザーは
  実行単位 ID を選んで「この単位を消す」と指示している。**一覧は情報提供**であり、
  中身が全部消えること自体は仕様どおり。塞ぐには「削除計画を保持して実行時に再照合」が必要で、
  task_06b の対象範囲を超える。→ **§3-12-6**。
- **High 2「検証後に隔離ルートをジャンクションへ差し替えると外部の実体を消し得る」= 受容**。
  **Codex は窓を過大評価している**。`delete_quarantine_unit` は **UI 確認の後に**呼ばれて
  ①②③をやり直すため、窓は `_delete_directory` → `_read_manifest` → `shutil.rmtree` の
  **関数内（マイクロ秒）**であり、「確認画面を見ている間」ではない。
  塞ぐには削除完了まで実体を固定する仕組み（Windows のハンドル保持等）が要り、
  **§3-8 の「新規依存を足さない」と衝突する**。加えて隔離ルートを差し替えられる権限があれば
  **アプリを介さず直接削除できる**ため、脅威モデル上の上積みが小さい。→ **§3-12-7**。

**却下した案**: (a) idea 起票 → 修正予定ではないので backlog の意味が濁る（ユーザー指摘）。
(b) decisions.md だけに書く → 製品の性質が正本へ昇格せず、将来この機能を触る人が読めない。
→ **性質は §3-12（正本へ昇格）/ 判断経緯は decisions.md** と書き分ける。

### 【task_06b 実装時】ゼロ埋め連番 `_02` は拒否しない（メイン判断 2026-09-07）

**パターン一致が基準であること自体を固定した**。
