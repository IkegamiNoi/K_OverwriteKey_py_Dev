## 確定した設計判断（ユーザー）

| # | 判断 | 採らなかった案と理由 |
|---|---|---|
| 1 | 読込はワーカー（デーモンスレッド）・完了は **UI 側の 50 ms 確認タイマー**（ワーカーは Tk を呼ばない） | ワーカーから `after(0)` = 終了間際の例外吸収と上限用の別タイマーが要る |
| 2 | 上限 **5 秒固定**（超えたら実行時エラー。遅いだけのパスもエラーになる＝受容） | 上限なし / 10 秒 / 設定項目化（JSON スキーマ変更） |
| 3 | 同じ読込キー（正規化パス, encoding）のワーカーは同時 1 本。走っていれば**待ち合わせ**（前の結果は使わない）。上限超過で残った読込の間は同じキーを即エラー | 相乗り（v0.4）= 書き換え直後の押下に古い内容を送る（Codex 敵対的 2 回目）/ 放置の即エラーを取り消し・一時停止にも適用 = 遅いだけのパスで再押下がエラー |
| 4 | **読込結果のキャッシュ**（ユーザー要望・案 A: 実行ごとに stat のサイズと更新日時をワーカーで確認）。世代つき全破棄は構成セットの読込等 | 案 B（契機でだけ読み直す）= エディタで直しても古い行を送る事故 |
| 5 | 連続実行の読込中の一時停止 = 結果を捨て再開時に読み直す（1 ステップ・1 段） | 結果を保持して再開時に送る = 保持状態が増える |
| 6 | 連続実行の読込中の位置変更・編集 = **待機と同じく続行**（v0.7・統合レビュー H1） | 停止 = 待機の挙動と揃わない |
| 7 | **構成セットの読込等で連続実行を常に停止**（待機中・通常も・既存挙動の変更・v0.8） | 読込中だけ停止 / 位置変更と同じく続行 = 新しい構成のまま前の連続実行が続く |
