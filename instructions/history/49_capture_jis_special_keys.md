## §1 目的 / 背景

キーの取得（Tk のキーイベントで 1 キーを記録する入口）で、JIS の特殊キー（無変換・変換・半角/全角・かな）を取れない。IME に横取りされ、Tk には「IME が処理中のキー」（VK 229・名前 `??`）で届き、どのキーか判別できない。また押すと IME の ON/OFF が切り替わる。
**取得の間だけ keyboard のフック（物理の走査コードが分かる）で、選んでいるレイアウトの行に当たるキーを読み、フックの実行時と同じ名前で記録する。**

### 現状監査（2026-10-21・codex-explorer の調査をメインが裏取り）

- 取得の入口は正本 `key_input.md` §7.4「取得の入口」の 8 つ（#1 停止 / トグルキー `key_capture.py`・#2 トリガー `trigger_dialog.py`・#3 切替キー `keymap_edit_dialog.py`・#4 複数キーマップの切替キー `keymap_switch_batch_dialog.py`・#5 アクションの hotkey `action_dialog.py`・#6 key_hold の「1 キーを記録」`action_key_hold_fields.py`・#7 キーボードUI の編集 `keyboard_window.py`・#8 画面の枠の編集の窓 `grid_editor_window.py`）。名前は Tk のイベントから作り（`tk_keys.normalize_tk_key_event` 等・#7 と #8 は VK → 走査コード → レイアウト）、`??` は全入口で記録しない（`tk_keys.is_unresolved_capture_key`）
- 取得の開始 / 終了は全入口が `key_capture_ime.begin_key_capture(owner, window)` / `end_key_capture(owner)` を呼ぶ（取得中のアプリの IME を OFF・`KeyCaptureImeTracker` が owner → window を持ち、窓の `<Destroy>` でも終わる・`key_capture_ime.py:32-60`）
- **取得中は通常のフックが外れている**: 入口（またはその親ダイアログ）が `suspend_hook_for_dialog` を呼び、フックは `HookCoordinator.uninstall_input_event_hook` → `InputGateway.unregister_hook` で外れる（`hook_coordinator.py:73-80`）。停止キー / トグルキー専用の別フックは無い（`register_key_hook` は未使用）。**取得中に動いているフックは無い**
- 実測（2026-10-16〜17・idea_50）: 4 キーとも Tk には keysym `??`・VK 229 で届き、IME が OFF でも同じ。Tk のイベントは物理の走査コードを持たない。2026-10-21 の確認で、合成の入力（`keyboard.send('ime nonconvert')`）も Tk には `??` で届いた
- フックの実行時の名前は `LayoutController.resolve_key_name_from_scan_code`（写し `_active_layout` の行の `scan_code` → `extra_scan_codes` の順・`layout_controller.py:375-379`）。見本の jis.json で `scan_code` を持つ行は 4 キーだけ（`zenkaku_hankaku` 41 / `muhenkan` 123〔extra 241〕/ `henkan` 121〔extra 242〕/ `kana` 112）
- 正本: `key_input.md` §7.4「判別できないキー」（JIS の特殊キーは全入口で取得できない・idea_50）・「取得の入口」「取得中の IME」/ §7.1「フックの実行時のキー名の出どころ」

## §2 確定事項（ユーザー 2026-10-21）

- **対象の入口 = 取得の 8 入口すべて**（§7.4「取得の入口」と同じ範囲）

- **対象のキーは抑止する**（アプリの窓が前面のときだけ・押下中は離し / 一定時間まで・余韻つき・§3-3〜§3-5）
- **押下中は「最後の押下から一定時間、押下が来ない」ときだけ外す（離しは見ない）**。一定時間 = OS のキーリピートの開始の待ち + 200 ms / 余韻の上限 = 取得の終了から 5 秒（task_01 の実測・§7a・2026-10-21 ユーザー確定）

## §3 取得用のフック（presentation + infrastructure の既存の口）

1. **登録の期間**: 取得中の owner が 0 → 1 になったとき `InputGateway.register_global_hook(callback, suppress=True)` で登録する（UI スレッド）。外すのは「owner が 0」かつ「余韻（§3-5）が無い」とき（`unregister_hook`）。owner の数え方は `KeyCaptureImeTracker` と同じ（重複の開始・未開始の終了は何もしない・窓の破棄で終わる）。登録が残っている間に取得が再び始まったら、登録し直さずそのまま使う（keyboard は callback を辞書のキーにするため二重に登録しない）
2. **対象のキー**（フックのスレッドで判定。実行時の名前の解決 §7.1 と同じ順）:
   1. **アプリのプロセスの窓が前面でなければ対象外**（`win32_window.is_own_process_foreground()`・キーリピートと同じ判定）。他のアプリでは 4 キーが今どおり効く
   2. `numpad_name_from_event(scan_code, is_keypad)` が名前を返すキーは対象外（テンキー・§7.8）
   3. `LayoutController.resolve_key_name_from_scan_code(scan_code)` が名前を返さないキーは対象外（選んでいるレイアウトの行の `scan_code` / `extra_scan_codes` に当たらない）
   4. その名前が `esc` または修飾キー（`domain/key_hold.MODIFIER_KEY_NAMES`）なら対象外（Esc のキャンセル・#5 の修飾キーの記録を Tk に残す）
   5. 残りが対象（jis.json では 4 キーだけ。コードにキーの表は持たない・phase 62 の方針）
3. **抑止と受け渡し**: 対象のキーは押下も離しも抑止する（callback が False を返す。対象外・例外のときは **True を明示して返す**〔None は抑止になる〕）。押下のときだけ、§3-4 の重複を除いたうえで名前を UI スレッドへ渡す（`after(0, ...)`・既存の `hook_controller.py` と同じ）。`after` が失敗したとき（終了中 等）は抑止したまま捨てる
4. **重複の除去**: フックは対象のキーの「押下中」の走査コードと最後の押下の時刻を覚え、押下中の 2 回目以降の押下（押し続けのリピート・押下だけのキーの続く押下と離したときの 2 回組・半角/全角の「離し → 押下」の組）は渡さない。**押下中は、最後の押下から一定時間押下が来ないときだけ外れる**（離しでは外さない。半角/全角は押し続けの間も押下のたびに離しが先に届くため・§7a）。取得が続いているかどうかに関係なく外れる（#8 のように取得が続く入口でも、一定時間の後は同じキーをもう一度取得できる）
   - **一定時間 = OS のキーリピートの開始の待ち + 200 ms**（`input_gateway.keyboard_repeat_timing()` の待ち。実測は 500 ms → 700 ms）。押し続けの最初のリピートまでの間（待ちの長さ）で外れないため。判定は UI スレッドのタイマー（`after`）か、次のイベントの時刻との比較で行う（実装の選択）
5. **余韻**: 取得が終わっても（owner が 0）、押下中（§3-4）の対象のキーがある間はフックを残し、そのキーのイベントだけ抑止し続ける（他のキーは素通し・受け渡しはしない）。押下中が無くなり owner が 0 なら外す。**余韻の上限 = owner が 0 になってから 5 秒**。上限で押下中が残っていても外す（かなのように押下が止まらないキーがあるため・§7a）
6. **渡し先**: UI スレッドで、フォーカスを持つウィジェットの最上位の窓（`focus_get().winfo_toplevel()`）と、取得中の owner の窓の最上位が一致する入口へ名前を渡す。一致が複数なら最後に取得を始めた入口。一致が無い・フォーカスが無い・`focus_get()` が例外（ttk.Combobox の一覧が開いている 等）のときは捨てる（キーは抑止済み）
   - **古い名前を渡さない（世代）**: tracker は `begin_key_capture` の呼び出しのたび（取得中の owner の再度の開始〔#7 の編集中の別の元キーのクリック〕も含む）と実際の終了のたびに世代を 1 進める。フックのスレッドは名前を渡すときにその時点の世代を添え、UI スレッドで世代が変わっていれば捨てる（予約から実行までの間の取り消し・対象の切替・取り直しで、前の取得で押したキーを新しい取得に記録しない）。取得の対象を変える入口は begin を通す（#4 は end → begin・#7 は begin の再呼び出し）
7. **入口へ渡す口**: `begin_key_capture(owner, window, on_hook_key=None)` に、名前を受け取る関数を任意で渡せるようにする（渡さない入口は対象にならない＝渡し先の候補から外す）。各入口の関数は、**Tk の KeyPress から作った名前と同じ後続の処理**（修飾キー単独・禁止のキー・重複の判定・案内の更新・取得の終了・確定後の検査）を通す。Tk のイベントから名前を作る部分と、名前を受けて記録する部分を分け、両方の道筋が後者を呼ぶ形にする
   - #5 hotkey: 押している修飾キー（Tk で記録中）と組み合わせて確定する（`ctrl+muhenkan` 等）
   - #8: 選んでいる枠への割り当て（取得は窓を閉じるまで続く）
8. **構成**: 取得用のフックの登録・判定・余韻・受け渡しは、`key_capture_ime` の tracker と同じ単位（モジュールに 1 つ）の隣のモジュールが持ち、`App` が起動時に gateway・レイアウトの解決・`after`・前面の判定を設定する。設定されていなければフックを登録しない。tests_ui は tracker を差し替えて App を作るが、App がその tracker に設定するので取得のテストでは本物のフックが登録され得る（既存の tests_ui も通常のフックを本当に登録している。テストの既定のレイアウトは対象のキーを持たないので全キーが素通しになり実害は無い。入口のテストは tracker の設定を外してから受け取りの関数を直接呼んでよい）

## §4 取得用のフックと他のフック

- 取得中は通常のフックが外れているので（8 入口とも・§1）、通常は取得用のフックだけが動く
- 抑止は登録の順に評価され、偽が出たら後ろのフックは呼ばれない（keyboard の `__init__.py:236`）。idea_48 の穴で取得中に通常のフックが付け直されると後ろに付くので、対象のキーは通常のフックに届かない。余韻の間に通常のフックが再開しても同じ
- 逆に、#1・#7 の取得の開始から通常のフックの停止までのごく短い間（`key_capture.py:63` → :71・`keyboard_window.py:480` → :482）は通常のフックが前にいて、そちらが抑止すれば取得用のフックは見ない（受容）

## §5 受容

- **特殊キーを書いていないレイアウト（既定の US TKL 等）を選んでいると、今と同じく `??` で取得できない**（フックの実行時も名前にならないので、取れても意味が無い・§7.1）
- 取得中に、アプリの窓が前面で、取得の入口のない窓・欄（ラベル欄 等・#8 では別の窓のパネルの段 / 列の Spinbox）にフォーカスがあると、特殊キーは抑止されて捨てられる
- 取得中（と余韻の間）は対象のキーが OS（IME）へ届かないので、アプリの窓が前面の間は特殊キーで IME を切り替えられない
- 押下中が外れるまで（最後の押下から一定時間）に同じキーをもう一度押しても渡さない（素早い 2 度押しは 1 回の取得）
- 余韻の上限（5 秒）を過ぎても押し続けていると、そのキーは OS へ流れ、IME が切り替わり得る
- `after(0)` を UI スレッドが処理するまでフックのスレッドは待つ（既存の通常のフックと同じ）。UI が詰まると Windows の低レベルフックの時間切れで抑止が外れ、IME が切り替わり得る
- 対象のキーの離しを抑止しても keyboard の押下の表には残らない（抑止は表の更新の前に返る・`__init__.py:236-250`）

## §7 受け入れ条件（ドラフト）

1. jis.json を選んでいるとき、取得の各入口（8 入口すべて・§2）で無変換・変換・半角/全角・かなを押すと、フックの実行時と同じ名前（`muhenkan` / `henkan` / `zenkaku_hankaku` / `kana`）で記録される（§3）
2. 取得中に特殊キーを押しても、押下だけで届くキーボードでも、長押ししても、IME の ON/OFF が切り替わらない（§3-3〜§3-5）
2a. #8 で無変換を割り当てた後、離して一定時間（§3-4）の後に別の枠を選んで無変換を押すと、その枠にも割り当てられる（押下だけで届くキーボードでも・§3-4）
2b. 取得の取り消し・対象の切替の直前に押した特殊キーが、次の取得に記録されない（§3-6）
3. 特殊キー以外のキーの取得の名前・挙動は今と同じ（テンキー・Esc でのキャンセル・修飾キーを含む・§3-2）
4. 取得用のフックは取得の間（と余韻の間）だけ登録され、全入口の終了・窓の破棄の後に外れる（§3-1・§3-5）
5. 取得中でも、他のアプリの窓が前面なら特殊キーは今どおり効く（§3-2-1）
6. 既定の US TKL を選んでいるときは今と同じ（`??`・§5）
7. tests / tests_ui / smoke が通る（§3-8）
8. 実機目視: jis.json を選び、トリガー・key_hold の「1 キーを記録」・hotkey（`ctrl+無変換`）・キーボードUI の編集で無変換・変換を記録できる / 記録の後に IME の状態が変わっていない / 記録したトリガーが実行時に動く / 取得中に Esc でキャンセルできる

## §7a 実測（task_01・2026-10-21・Windows 11・JIS・MS-IME・押下だけで届くキーボード）

測定用の窓（Tk・keyboard の `hook(suppress=True)`・走査コード 41 / 112 / 121 / 123 / 241 / 242 だけを対象）で、方式ごとに 4 キーを「1 回押して離す」×2〜3 と長押し。

| キー | 押したとき | 押し続けたとき | 離したとき |
|---|---|---|---|
| 半角/全角（41） | 「離し → 押下」の組（1〜3 ms 差） | その組が約 33 ms ごと | 何も届かない |
| 無変換（241）・変換（242） | 押下 1 回 | 約 500 ms 後から押下が約 33 ms ごと | 押下の 2 回組（1〜10 ms 差） |
| かな（112） | 押下 1 回 | 約 500 ms 後から押下が約 33 ms ごと | 何も届かない（押下が約 12 秒続いた） |

- このキーボードでは無変換・変換は 241 / 242 で届き、123 / 121 は届かなかった（123 / 121 で届くキーボードは未実測）
- IME の開閉: 素通しでは 半角/全角・無変換・変換で切り替わった（かなでは開閉は変わらない）。**「押下と離しを抑止」「押下だけ抑止」のどちらでも一度も切り替わらなかった**（半角/全角の離しを通しても切り替わらない）
- OS のキーリピートの待ち 500 ms・間隔約 33 ms（Windows の設定どおり）
