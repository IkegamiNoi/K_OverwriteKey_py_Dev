## §1 目的 / 背景

**ダイアログ（grab 保持者）を開いたままアプリを最小化すると、アプリを二度と復元できない。**
ユーザーは Win+D（デスクトップ表示）で遭遇した。**アプリが操作不能になる**ため実害が大きい。

### 現状監査（2026-09-16・`.venv` の python で実測）

**症状の機序が実測で確定している。** 診断スクリプトで root（App 相当）+ child + grand
（grab 保持者）の 3 段を作り、Win+D とタスクバー復元を観測した:

| 局面 | 観測 |
|---|---|
| Win+D 直後 | `grand<Unmap>` → `child<Unmap>` → `root<Unmap>` の順で届く。**root = `iconic` / 子 2 つ = `withdrawn`**。**grab は grand が保持したまま** |
| タスクバーをクリック（2 回試行） | **`root<FocusOut>` + `grand<FocusIn>` だけが届く**。**root に `<Map>` は一度も来ず、状態は `iconic` のまま**（20 秒間変化なし） |

→ **シェルの復元要求は root ではなく grab 保持者（`withdrawn` で非表示）へ向かう**。
grab 保持者は表示されずタスクバーにも存在しないため、**誰も復元できない**。

**対策候補の A/B も実測済み**（同スクリプトの `fix` モード）:

| 局面 | 観測 |
|---|---|
| `root<Unmap>` で `grab_release()` | grab = None になる |
| タスクバーをクリック | **`root<Map>` が届き、root / child / grand の 3 窓とも `normal` へ戻る**（復元成功） |
| `<Map>` ハンドラ内で `deiconify()` + `grab_set()` | 再 grab は成功するが、**`deiconify()` が窓を再配置し、最終的に中間の child が `withdrawn` のまま残った** |

→ **grab を外せば復元できる**。ただし **`<Map>` の時点で WM が 3 窓とも復元済み**であり、
**アプリ側から `deiconify()` してはならない**（実測で中間窓が消えた）。

### 再現手順（診断スクリプトの構成・v0.2 で転記）

**production と同じ 3 段の窓構成**を最小コードで組んで観測した（`.venv` の python）:

- `root = tk.Tk()`（App 相当）/ `child = Toplevel(root)` + `child.transient(root)`（プリセット編集 相当）/
  `grand = Toplevel(root)` + `grand.transient(child)`（上書き確認 相当。**master は root** = 役割 1）
- `grand.grab_set()` の後、**①Win+D ②タスクバーのアイコンで復元を試す**
- 観測は 300〜500ms ごとの `wm_state()` / `winfo_viewable()` / `grab_current()` と、
  `<Map>` `<Unmap>` `<Visibility>` `<FocusIn>` `<FocusOut>` の各イベント

**この構成は production の `transient` チェーン（App → 呼び出し元ダイアログ → 内側）と一致する**
（phase 16 で確定した形）。**スクリプトはフェーズ資材として phase 17 のフォルダへ置く**（§8）。

### 最小化中の窓の状態（v0.2 で追加・`iconify()` での実測）

| 局面 | 実測 |
|---|---|
| `root.iconify()` 中 | **子 2 つとも `winfo_viewable()` = 0**（grab 自体は保持者が持ったまま） |

## §3 設計（案）

### §3-1 方針: 最小化の間だけ grab を「預かる」

**App が unmap（最小化）されたら grab を解除し、App が map（復元）されたら同じ窓へ張り直す。**

- **解除しないと復元できない**（§1 実測）。**解除している間は全窓が非表示**のため、
  背面を操作できてしまう危険は無い（モーダル性の実質的な穴にならない）。
- **復元時は再 grab のみを行い、`deiconify()` / `lift()` はしない**（§1 実測。WM が既に戻している）。

### §3-2 結線と条件（v0.2 でガードを追加）

1. **App の `<Unmap>`**（`event.widget is app` のときだけ）:
   `grab_current()` が `None` 以外で、**かつその保持者が既に非表示**（`winfo_viewable()` が 0）なら、
   記録して `grab_release()` する。**既に預かり中なら何もしない**（二重発火の防止）。
   - **表示されたままの保持者は預からない**（v0.4・実測根拠は §1）。`transient` を持たない窓や
     **呼び出し元を先に破棄された子**（正本 §4.6 の「前面維持の指定が戻らない」ケース）は
     最小化でも隠れず、**シェルの復元要求はその表示中の窓へ届く**ため、本件の症状が起きない。
     ここで外すと**表示中のモーダルから grab を奪う**（`features.md:92` 違反）だけになる。
   - **順序は実測で担保されている**: Win+D では `<Unmap>` が**子 → 親の順**で届くため、
     App の `<Unmap>` 時点で隠れる窓は既に `viewable` = 0 になっている（§1 の events ログ）。
2. **App の `<Map>`**（同上）: 預かり中なら、以下を**すべて**満たすときだけ `grab_set()` する。
   いずれかを満たさなければ**張り直さずに預かりだけ解除する**:
   - **現在の `grab_current()` が `None`**（**別の窓が既に grab を持っていたら上書きしない**。
     phase 14 の `modal.py:31-38` と同じガード。最小化中に `after` 経由で新しいダイアログが
     開いた場合に、**内側のモーダル性を奪わない**ため）
   - 記録した窓が **`winfo_exists()` かつ `winfo_viewable()`**
     （**`withdrawn` な窓への `grab_set()` は成功してしまう**＝見えない窓が入力を握り、
     元の症状を再現する。§1 実測）
3. **復元時に `deiconify()` / `lift()` / `focus_force()` を呼ばない**（§1 実測。WM が既に戻している）。
4. **`<Unmap>` / `<Map>` はウィジェット単位でも飛ぶ**ため、**必ず `event.widget` で App 自身に限定する**
   （実測: `Frame.pack_forget()` が toplevel のバインドへ `<Unmap>` を届ける。
   **FullView / CompactView の切替が実運用の発火源**になるのでガードは必須）。
5. **例外の扱い**: `grab_current()` は **`tk.TclError` に加えて `KeyError` も吸収**する
   （tkinter 管理外の保持者＝ stdlib ダイアログが grab 中だと `KeyError` になる。`modal.py:13-18` と同じ）。
   ただし **「保持者なし（`None`）」と「保持者を解決できない（例外）」を別状態として扱う**（v0.4）:
   - `<Unmap>`: 解決不能なら**預からない**（stdlib ダイアログが grab 中。§2 で対象外と確定済）。
   - `<Map>`: 解決不能なら**再 grab しない**（「保持者なし」と同一視すると、
     **stdlib ダイアログが持っている grab を記録窓へ奪ってしまう**）。
   - イベントハンドラ内の未捕捉例外は `report_callback_exception` を経由し、
     **既存テスト（`tests_ui/test_nested_modal_grab.py:40-42`）を落とす**ため握り潰しの範囲を明示する。
6. **記録した保持者が最小化中に破棄されていた場合**は、**生存かつ表示中の最内モーダルへ張り直す**
   （§3-5・ユーザー確定）。放置すると**外側ダイアログが開いたままアプリが非モーダルになる**。
7. **預かり中に新しいモーダルが開いた場合**（`after` 経由等）は、**`grab_modal` がその窓の
   「直前の保持者」として預かり中の窓を使い、預かりを解除する**（v0.4 追加）。
   - こうしないと、新窓の `previous` が `None` になり、**新窓を閉じたときに誰も grab を持たない**
     （= 表示中の外側ダイアログが非モーダルになる）。
   - 実装上、**預かりの状態は `grab_modal` から見える位置に置く**（どちらも `modal.py`・§3-3）。

8. **復元がスキップされたときの預かりへの差し戻し**（v0.5・ユーザー確定 2026-09-16）:
   `grab_modal` の `<Destroy>` 復元は、記録した `previous` が**非表示なら復元しない**
   （phase 14 の viewable ガード・`modal.py`）。**最小化中は全窓の `viewable` が 0 になる**ため、
   (7) で預かりを引き継いだ新モーダルが**復元より前に破棄されると、預かりも復元も行われず
   grab 保持者がゼロになる**（phase 17 task_03 の実測で確認。§6-10 後半が満たせない）。
   → **最小化中に限り、復元できなかった `previous` を預かりへ戻す**（`_custody_window` へ再設定）。
   - **最小化中かどうかを `modal.py` が知るためのフラグを 1 つ持つ**
     （App の `<Unmap>` で立て `<Map>` で下ろす）。**フラグ無しで無条件に戻してはならない**:
     最小化していないときに非表示の窓が預かりへ入ると、**次の最小化で (1) の「既に預かり中なら
     何もしない」ガードに引っかかり、本来の預かりを阻害する**。
   - 差し戻すのは**預かりが空のときだけ**（現に預かっている窓を上書きしない）。
   - **`previous` が破棄済みでも差し戻す**（v0.6）。**復元できなかった理由（非表示 / 破棄済み）で
     区別しない**。破棄済みの窓を預かりへ入れても、`<Map>` の候補ループが
     「記録窓が使えなければ**台帳の最内**（生存かつ表示中）」へ落とすため正しい窓が掴む（§3-5 と同じ規則）。
     - **区別すると穴が残る**: 最小化中に**預かり窓と新モーダルの両方**が破棄された場合、
       差し戻しが起きず `<Map>` が `_custody_window is None` で即 return するため
       **台帳フォールバックへ到達しない**（v0.5 の残穴・実測で再現）。
   - これにより **§6-8（保持者が破棄されてもモーダル性を失わない）と §6-10 後半が
     同じ機構で満たされる**（どちらも「最小化中に保持者が居なくなる」事故の一形態）。

### §3-3 置き場所（案 A 推奨）

- **案 A（推奨）: `presentation/modal.py` に `install_minimize_grab_custody(app)` を追加**し、
  App の初期化で 1 度だけ呼ぶ。**grab に触る処理を 1 ファイルへ集約する**現行方針
  （`grab_set` / `transient` を直呼びしない）と一致する。
  **引数の型注釈に `App` を使わない**（`modal.py` は現在 tkinter のみ依存。App を import すると
  `modal.py` → `app.py` の循環になる）。**`tk.Misc` で受ける**。
- 案 B: `app.py` に直接結線する。集約が崩れるため非推奨。
- 案 C: 新コントローラを作る。対象が 2 ハンドラのみで過剰。

**検討して落とした代替**（v0.2・後段で再検討しないため記録する）:

- **(a) ダイアログ側で自窓の `<Unmap>` / `<Map>` を拾う**（App を触らない）→ **不成立**。
  実測で **`root.iconify()` では子 Toplevel に `<Unmap>` が飛ばない**（Win+D では飛ぶ）ため、
  **通常の最小化と Win+D で挙動が割れる**。
- **(b) 記録せず、`<Map>` の時点で生存・表示中の最内ダイアログを再導出して grab を張る** →
  規模は同等で、**§5-6（保持者が消えていた場合）の対策としてはむしろ有利**。§5-6 の判断次第で本線になりうる。

### §3-4 phase 14 / 15 との関係（v0.2 で訂正）

- **phase 15（フック停止・`suspend_hook_for_dialog`）とは独立**。最小化でダイアログは破棄されず、
  `hook_controller` は `<Destroy>` にしか結線していない（実測）。**変更しない**。
- **phase 14（`<Destroy>` での grab 復元）とは独立ではない**（v0.1 の記述は誤り）。
  **最小化中は全窓の `winfo_viewable()` が 0 になり、`modal.py:40` の viewable ガードにより
  phase 14 の復元が発火しない**（§1 実測）。したがって**最小化中に保持者が破棄されると、
  復元後に grab を持つ窓が誰も居なくなる**。対処は §3-2(6) / §5-6。
- **ネストが複数段でも、預かるのは最内の 1 つだけ**（`grab_current()` が返すもの）。
  外側の記録はクロージャに残るため LIFO 復元は壊れない見込み。**受け入れ条件で固定する**（§6-4）。

### §3-5 保持者が破棄されていた場合の張り直し（v0.3・ユーザー確定）

復元時に記録した窓が消えていたら、**生存かつ表示中の最内モーダルへ grab を張り直す**。
そのためには「いま開いているモーダルの順序」を知る必要がある。

- **案 (i)（推奨）: `modal.py` にアクティブなモーダルの台帳を持つ** — `grab_modal` で追加し、
  `<Destroy>` で取り除く。復元時は**末尾から「`winfo_exists()` かつ `winfo_viewable()`」を探す**。
  **phase 14 の「記録はクロージャに持ちウィジェット属性を増やさない」方針と緊張する**
  （モジュール状態が増える）が、**順序を知る手段が他に無い**。台帳は
  **`grab_modal` を通った窓だけ**を持ち、stdlib ダイアログは載らない（§2 の対象外と整合）。
- 案 (ii): 復元時に `app.winfo_children()` から Toplevel を走査して再導出する →
  **どれがモーダルだったかを判定できない**（`grab_modal` を通っていない窓と区別できない）ため不採用。

**台帳の一貫性**（実装時の注意）: 追加は `grab_modal` の中、削除は `<Destroy>`。
**`grab_modal` を通らない窓は載らない**ので、載っていない窓へ grab が渡ることはない。

## §4 テスト方針（案）

- **Win+D は自動テストで再現できない**（シェル操作）。`iconify()` / `deiconify()` は `<Unmap>` /
  `<Map>` を発生させるため、**結線と預かり動作の検証には使える**
  （症状そのものは `iconify` では再現しないことも実測済 = テストは症状ではなく**結線を固定する**）。
- 固定する観点: ①`<Unmap>` で grab が外れる ②`<Map>` で同じ窓へ戻る ③保持者が破棄済みなら
  戻さない ④他ウィジェットの `<Unmap>` では何もしない ⑤**`<Map>` ハンドラが `deiconify` を
  呼ばない**（`deiconify` を patch して呼び出し 0 回を固定）。
- **変異検査**: 預かり処理を無効化したらテストが落ちること。
- **ハーネスの注意**（v0.2）: `tests_ui` は `setUpClass` で App を共有する
  （`tests_ui/test_nested_modal_grab.py:26-33`）。**iconify したまま tearDown すると
  iconic 状態が後続モジュールへ漏れる**ため、**新規モジュール + cleanup での `deiconify()` 復帰**を必須にする。
- **書けることは実測済み**（v0.2）: `root.iconify()` → `<Unmap>`(widget=root) 発火 /
  `root.deiconify()` → `<Map>`(widget=root) 発火 / `<Map>` 時点で記録窓は `viewable` = 1 で
  `grab_set()` 成功 / `Frame.pack_forget()` が toplevel へ `<Unmap>` を届ける（観点 ④ の書き方）。

残る 2 件（保持者が破棄された場合の張り直し / 正本 `:92` の限定）も推奨どおり確定した。

## §6 受け入れ条件（ドラフト・v0.2 で追補）

1. **ダイアログを開いたまま Win+D → タスクバーから復元でき、復元後もモーダル性が保たれる**
   （実機目視。§3-1）。
2. 最小化 → 復元の後、**中間のダイアログも含めて全窓が表示されている**（§1 の副作用の再発防止）。
3. `suspend_hook_for_dialog`（phase 15）は**無変更**。`modal.py` の既存 `grab_modal` と
   `<Destroy>` 復元は、**§5-6 の判断で必要になった場合のみ変更を許す**
   （v0.1 の「無変更」は §5-6 の対策を先回りで縛るため v0.2 で緩めた）。
4. **3 段ネスト**（アクション編集 → プリセット編集 → 上書き確認）で最小化 → 復元しても、
   その後の LIFO 復元が phase 14 どおり働く（§3-4）。
5. 既存の `tests` / `tests_ui` が全て pass し `smoke_app` が通る。**既存アサーションを弱めない**。
6. `<Map>` ハンドラが `deiconify()` を呼ばないことがテストで固定されている（§4）。
7. **ガード 3 種がテストで固定されている**（v0.2 追加）: ①別窓が grab 中なら上書きしない
   ②非表示の窓は掴まない ③App 以外の `<Unmap>`（`Frame.pack_forget()` 等）では何もしない。
8. **最小化中に保持者が破棄されても、復元後にモーダル性が失われない**
   （生存かつ表示中の最内モーダルへ張り直す。§3-5）。
9. **表示されたままの保持者からは grab を外さない**（v0.4）。
   `transient` を持たない窓を開いた状態で最小化しても grab が保たれること。
10. **預かり中に新しいモーダルが開き、それを閉じたとき、預かっていた窓へ grab が戻る**（v0.4・§3-2(7)）。
    復元前にその新窓が閉じられた場合も、復元時に正しい窓が grab を持つこと
    （**後半は §3-2(8) の差し戻しで満たす**。v0.5 で機構を追加）。
11. **`grab_current()` が解決不能なときに `grab_set()` を呼ばない**（v0.4・§3-2(5)）。
    テストでは `grab_current` が `KeyError` を送出する状況を作り、`grab_set` の呼び出し 0 回を固定する。
12. **App 以外の `<Unmap>`（`Frame.pack_forget()` 等）では預かりが発生しない**
    （FullView / CompactView の切替が実運用の発火源）。
