## §1 目的 / 背景

子JSON（keymap / trigger_set / sequence）に記録した**参照元 `_parent_refs`**（正本
`data_schema.md` §5.8.1）は **best-effort 更新**で、上位ファイルの移動・削除を検知しない。
そのため**実体の無い参照元がリストに残り続ける**。本フェーズは、それをユーザー操作で
まとめて回収する**保守機能**を追加する。

**掃除しないと何が起きるか**（v0.2 で明確化。受け入れ条件を検証可能にするため）:

- **誤警告**: 保存時の共有状況判定（§5.8.4）が「共有中」のままになり、
  実体の無い上位まで数えた **「N 個の上位で共有中・全てに影響します」** が出続ける。
- **余分な確認**: 「単独所有」へ落ちないため、§5.8.5 の**依存確認 4 択**が本来不要な場面で出る。

影響レイヤは **application（検査・除去のロジック）+ presentation（メニュー・確認 UI）**で、
**保存フロー（§5.8.3〜§5.8.6）と JSON スキーマは変更しない**（`_parent_refs` の**値**だけを書き換える）。

### 現状監査（2026-08-16・`Explore` + `deep-reviewer` 実測）

- **`_parent_refs` の読み書き**:
  - 読み = `ConfigService.read_parent_refs(path) -> list[str] | None`（**専用の公開 API**。
    読めない / dict でない / **値が list でない** / キー無し は**すべて `None`**）+
    `_normalize_parent_refs`（**`None`＝所有元不明 / `[]`＝既知の空**を区別。
    **strip・完全一致の重複除去・非 str 除去**を行う）。
  - 書き = `save_{keymap,sequence,trigger_set}_file(..., parent_ref=)` の内部で
    **`_parent_refs_for_save`**（マージの起点は**保存先ファイルの現在値**）→ **`_merge_parent_ref`**
    （`to_config_relative_or_absolute` で表記化し `canonical_path` で重複判定して append）。
  - **追加専用で、除去する API は存在しない**（本フェーズで新設する）。
- **【重要】子ファイルの実体を知るのは runtime の source_path 3 種**
  （`INTERNAL_KEYMAP_SOURCE_PATH` / `INTERNAL_TRIGGER_SET_SOURCE_PATH` /
  `INTERNAL_SEQUENCE_SOURCE_PATH`）。
  - **`resolve_child_save_targets` を検査の入力にしてはならない**。同 API が返すのは
    **「次に保存するとしたらどこへ書くか」**であり、①source_path を持たない子には**既定パスが割り当てられる**
    （そこに無関係な既存ファイルがあると**他人のファイルを書き換える**）②同じ source_path を持つ子が
    2 つあると 2 件目は**別パスへ再割当**される。
  - `keymaps[].path` / `trigger_set_path` / `triggers[].sequence_path` は **ファイル側のスキーマ**であり
    **runtime には存在しない**。
- **パス**: 記録は §5.7 表記（config 配下は相対・区切り `/`）。**実在確認は
  `resolve_config_path(path, config_root)` で解決してから行う**（相対値をそのまま
  `os.path.exists` へ渡さない＝2 度踏んだ罠）。比較専用は `canonical_path`。
- **sequence の親は trigger_set**（keymap_set ではない）。したがって
  **trigger_set が未保存 / 削除済みなら、現に使用中の sequence の参照元が全滅し得る**（§4-A の根拠）。
- **子ファイルの置き場所は `config/user/{keymaps,trigger_sets,sequences}` に限らない**
  （別名保存の任意ディレクトリ / `split_base_dir` 指定 / 既存 `source_path` の尊重）。
  → **ディレクトリ走査をしても全網羅は原理的に不可能**。
- **keymap_set を列挙する手段が無い**（`keyseq/` に `os.listdir` / `glob` / `os.walk` が **1 箇所も無い**）。
- **メニュー**: `views/menu_bar.py` の `build_menu_bar(app)` に 1 行追加。
  「一覧 → 確認 → 実行 → 結果通知」の先例は `app.layout.delete_keyboard_layout`。
- **ダイアログの流儀は配置先で異なる**（v0.2 で訂正）:
  `controllers/config_io/`（`ChildSaveDialog`）= **Toplevel を継承しない薄いオブジェクト + `finally` で resume** /
  `presentation/dialogs/`（`LayoutDeleteDialog` 等）= **`tk.Toplevel` 継承 + `__init__` で suspend +
  `destroy()` override で resume**。
  **コードベースの必須作法は「フックの suspend / resume を必ず対で行う」ことであり、
  対にする手段は配置先の流儀に従う**。
- **テストの土台**: `tests/test_child_save_rows.py` / `tests/test_config_service.py` /
  `tests_ui/test_child_save_dialog.py`（**`_replace_parent_refs(path, refs)` が
  ファイルの refs を直接書き換えるヘルパ**＝陳腐化を仕込む用途にそのまま使える）。

## §2 確定事項（ユーザー 2026-08-16）

- **検査範囲は「現在の構成セット（開いている keymap_set）が参照している子」のみ**とする。
  - 根拠: ①**子は config 外にも置けるため、ディレクトリ走査でも全網羅にならない**
    ②keymap_set の列挙手段が無く、全走査は新規の走査コードを要する
    ③目的は「**実際に使っているものが余計な処理を抱えないようにする**」こと。
  - **全網羅ではないこと**を正本へ**既知の制約**として明記する。
- **起動口は `menu_bar` のメニュー項目**（idea_07 の β-f 回答）。
- **掃除は非破壊に閉じる**: 変更するのは `_parent_refs` の**値のみ**。
  **子ファイル自体を削除しない・他のキーを変えない**。
- **【v0.3】孤児（参照元が 0 件になる子）の削除は行わない**。
  **「この掃除で参照元が 0 件になる」ことを警告として表示するだけ**にとどめる。
  - 根拠: **この検査範囲では孤児判定が原理的に成立しない**（§4-A）。
- **【v0.3】確認 UI は 1 枚**（v0.1 の「ファイル単位で選択」から差し替え）。
  検査結果を**読み取り専用の一覧**で提示し（子ごとに**消える参照元のパスを全件列挙**）、
  **実行 / キャンセル**の 2 択。掃除が**非破壊・冪等**になったため行ごとの取捨選択は設けない。
- **【v0.3】掃除の結果を現在の runtime へ反映しない**（次回読み込みで揃う。dirty も汚さない）。
- **【v0.4】構成セットが未保存（`keymap_set_path` が空）のときは、先に保存の確認を出す**。
  **保存を実行して成功したら掃除へ進み、キャンセル / 失敗なら掃除ごと中止**する。
  - 理由: `parent_ref` が空のまま個別保存すると、`_parent_refs_for_save` が**保存先を読み直さず
    runtime の refs を返す**ため、**掃除前の陳腐化した参照元がファイルへ再書き込みされ、掃除が巻き戻る**。
    保存後は `parent_ref` が非空になり、以後の個別保存は保存先ファイルを読み直す経路に入る。
  - これにより **runtime へ反映しない（B1）ままで巻き戻りを防げる**。
- **【v0.3】「全検査（config 配下の走査）+ 孤児候補の検出」は本フェーズに含めない**。
  **逆方向検査（上位 → 子の索引走査）の新設**を伴うため、
  **[idea_12](../backlog/idea_12_orphan_child_file_sweep.md) として分離**し、
  本フェーズで作る検査・除去のコアを土台に**次フェーズ以降で載せる**（ユーザー方針: 段階的に両方作る）。

## §3 設計本文

### §3-1 検査（application）

- 入力 = **現在の runtime・`keymap_set_path`・`config_root`**。
- **対象の子は runtime の source_path 3 種で列挙する**（新しい走査を書かない・
  **`resolve_child_save_targets` は使わない**）。**source_path が空の子（未実体化）は対象外**。
  - **UI 上で削除したが未保存の子**は runtime から落ちているため**対象外**（ディスクには実体と
    索引が残るが、本機能では扱わない）。
- **同一ファイルへ解決される複数の子は 1 行に重複排除する**（判定は `canonical_path`）。
  共有 sequence（複数トリガーが同一ファイルを指す）で二重処理・二重計上しないため。
- 各子について `read_parent_refs(resolve_config_path(child_path, config_root))` を読み、
  各参照元を `resolve_config_path` で解決して **`os.path.exists` で実在確認**する。
- **【v0.4】保護対象は検査の時点で分離する**。**現在の keymap_set のパス**（keymap / trigger_set の
  参照元）と**現在の trigger_set のパス**（sequence の参照元）は、**実在しなくても除去対象にしない**
  （§3-2 の理由）。**「消えるパス」の一覧・件数・下記 `CLEANUP_ALL_STALE` の判定から除外する**
  （検査と実行で結果が食い違わないようにするため。表示するなら「保護のため残す」と別枠にする）。
- **判定名**（分岐は判定名で行い、表示文言で分岐しない）:
  - **`CLEANUP_TARGET`** … **保護対象を除いて**実在しない参照元が 1 件以上ある（＝一覧に出す）
  - **`CLEANUP_ALL_STALE`** … 除去すると**残る参照元が 0 件になる**（警告表示の対象。
    **保護対象が残る場合は該当しない**）
  - **`CLEANUP_PROTECTED`** … 実在しないが**保護対象**のため除去しない参照元を持つ
  - **`CLEANUP_SKIP`** … 対象外（`None`＝所有元不明 / `[]`＝既知の空 / 実体なし / 読めない）
- **戻り値は表示都合を持たない検査結果**とする（子の種別 / 実体パス / 実在する参照元 /
  実在しない参照元 / 判定名）。**application は presentation の行モデルを返さない**
  （表示用の整形は presentation 側で行う。既存の `child_save_rows` と同じ依存方向）。

### §3-2 除去（application）

- **`_merge_parent_ref` の逆操作を新設する**（例: `prune_parent_refs`）。
- **除去してはならない参照元**（v0.2 で追加・**実在有無にかかわらず除外**）:
  - **現在の keymap_set のパス**（keymap / trigger_set の参照元）
  - **現在の trigger_set のパス**（sequence の参照元）
  - 理由: アプリを開いたまま上位ファイルが移動・削除された場合、これらを除去すると
    **次回保存で全子が「所有元不明」→ 既定が別名保存へ倒れ**、余計なファイルが増える
    （§5.8.4 / §5.8.5 の保護が空振りする）。
- **【v0.4】除去の直前に、対象ファイルの JSON を丸ごと読み直す**（`_parent_refs` だけでなく**全体**）。
  その場で実在判定をやり直し、**読み直した内容の `_parent_refs` だけを差し替えて書く**。
  - 理由: 書き込みは**ドキュメント全体の置換**なので、**検査時に読んだ内容を書き戻すと、
    確認ダイアログの表示中に外部（別実装・手編集）が加えた変更を消す**。
  - **保護対象の判定も読み直し時に同じ規則で再適用する**（検査時の結果をそのまま適用しない）。
  - **読み直しに失敗した場合は書かずに「失敗」として報告する**（`None` を「refs 無し」と解釈して
    書き戻すと**他のキーを壊す**）。
  - 残る競合の窓は**読み直しから書き込みまで**に縮む。これは §5.8.3 / §5.10.3 で既に
    「競合は対象外」と規定している水準と同じ（**版情報の照合は行わない**）。
- 残す参照元は**記録されていた表記のまま**書き戻す（`canonical_path` を保存値へ混入させない）。
  ただし `read_parent_refs` を通す都合で、**strip・完全一致の重複除去・非 str 除去は同時に起こる**
  （既存の読み出し規則。許容する）。
- **全件が実在しない場合は `[]` を書く**（**キーごと削除しない**）。
  §5.1「既存キーの削除禁止」に従い、`None`（所有元不明＝旧形式）と `[]`（掃除済み）を区別するため。
  **§5.8.4 の判定はどちらも「所有元不明」なので、保存フローの分岐は変わらない**。
- **`_parent_refs` 以外のキーを書き換えない**（読んだ JSON を保ち、当該キーだけ差し替える）。
- **書き込みは子ファイル 1 つずつ**。**1 ファイルの失敗で全体を中止しない**が、
  **失敗したファイルは結果に明示する**。
- **確認と書き込みの間に別プロセスがファイルを変える競合は対象外**（§5.8.3・§5.10.3 と同水準）。

### §3-3 UI（presentation）

- **メニュー**: `build_menu_bar` に 1 項目追加（**「設定」メニュー**が自然。保守機能のため）。
  **Import 直後など子に source_path が無い状態では結果 0 件**になる
  （＝起動できることと結果が出ることは別）。
- **【v0.4】未保存（`keymap_set_path` が空）で起動した場合**は、検査の前に
  **「掃除するには構成セットの保存が必要です。保存しますか？」の確認**を出す。
  - **はい** … 通常の保存経路（パスが空なので**別名保存**。§5.4）を実行し、
    **成功したら検査へ進む**。保存がキャンセル / 失敗したら**掃除も行わない**。
  - **いいえ / キャンセル** … **何もせずに終了**する。
  - 保存経路そのものは変更しない（子の保存計画ダイアログ等は従来どおり）。
- **確認 UI は 1 枚**（v0.3 確定）:
  - **【v0.5】「消える参照元がある子」（`CLEANUP_TARGET` / `CLEANUP_ALL_STALE`）が 0 件なら、
    一覧を出さずに「掃除する項目はありません」と通知して終了**する
    （検査結果そのものが 0 件の場合を含む）。
    **保護対象だけの子（`CLEANUP_PROTECTED`）は要約行の「対象ファイル」件数に数えない**
    （1 ファイルも書かれないため）。他に消えるものがある子で「保護のため残す」と併記するのはよい。
  - 1 件以上なら**読み取り専用のスクロール可能な一覧**を出し、**実行 / キャンセル**の 2 択。
    **行ごとの選択は設けない**（掃除が非破壊・冪等のため）。
  - **除去されるパスの実文字列を全件提示する**（件数だけにしない）。
    理由: **一時的に到達不能な媒体**（外付け / ネットワークドライブ未接続。config 外の絶対パスは
    §5.7 で許容されている）を掃除すると、**生きている参照元を恒久的に消す**。
    件数表示だけではユーザーが検知できない。
  - **`CLEANUP_ALL_STALE`（参照元が 0 件になる）子は警告を明示**する
    （**削除は行わない**。孤児かどうかはこの検査範囲では判定できない旨も添える）。
  - **キャンセルで 1 ファイルも書かない**。
  - **フックの suspend / resume を必ず対で行う**（手段は配置先の流儀に従う。§3-4）。
  - **`grab_set` は配置先の既存ダイアログと同じ作法に揃える**（ネストしたモーダルの grab 復元は
    [idea_10](../backlog/idea_10_nested_modal_grab_restore.md) の課題であり、**本フェーズでは触らない**）。
- 実行後は**結果を通知する**（除去した参照元の件数 / 対象ファイル数 / **失敗したファイル**）。
- **runtime・dirty を変更しない**（設計判断）。掃除はファイル側の整理に閉じ、
  runtime の内部キーは**次回読み込みで揃う**。runtime 更新の入口を増やさないため。

### §3-4 配置（設計判断）

- **検査・除去は application 側の新規モジュール**（例 `config_service/parent_refs_cleanup.py`）。
  **`config_service/__init__.py` は 737 行で M1 該当（分割保留中）**のため、
  **本体へロジックを足さない**（公開が要るなら 1 行委譲まで）。
  兄弟モジュールの規約どおり **`service` を第 1 引数に取る**モジュール関数とし、
  **兄弟から `__init__` を import しない**。
- **表示用の整形（検査結果 → 提示テキスト）は presentation の純関数**とする
  （Tk 非依存にしてテストしやすくする。`format_preset_manager_source_labels` と同じ流儀）。
  **行モデルの新規モジュールは作らない**（D1 で行ごとの選択が無くなったため）。
- **ダイアログは `presentation/dialogs/` に 1 クラス 1 ファイル**（計画07 でパッケージ化した流儀）。
  本機能は**保存フローの一部ではなく、メニューから独立起動する保守機能**のため。
  したがって **`tk.Toplevel` 継承 + `destroy()` override で resume**（同フォルダの流儀）に揃える。
- **`ChildSaveDialog` の描画ヘルパは流用しない**（読み取り専用の一覧で足りるため。
  共有ヘルパの抽出も本フェーズでは行わない＝不要な共通化を避ける）。

### §3-5 既知の制約（v0.5 で明記・**実装は変えない**）

- **sequence の掃除は trigger_set が実体化していることが前提**。
  sequence の親は trigger_set なので、**trigger_set が未実体化のまま sequence を個別保存すると
  `parent_ref` が空になり、掃除前の参照元が再書き込みされる**（＝掃除が巻き戻る）。
  §2 の保存確認は **keymap_set のパスが空のときにしか働かない**ため、この経路は塞がない。
  再現条件は限定的（保存計画で trigger_set を「保存しない」にした場合など）で、
  **データ損失は起きない**（掃除の効果が消えるだけ）。
- **確認ダイアログの表示中に上位ファイルが消えると、提示していない参照元も除去され得る**。
  除去直前に**同じ規則で再判定する**（§3-2）ため、提示時点では実在していた参照元が
  実行時に「実在しない」と判定される。**外部変更を消さないこと（安全側）を優先した結果**であり、
  受入条件 9「消える参照元を全件提示」とはこの窓でのみ両立しない。
- **再判定で対象外になった子は結果通知に出ない**（更新にも失敗にも数えない）。
  一覧に出ていた子が黙って落ちるが、**書き込みが起きていない**ことは
  「更新したファイル」の件数から分かる。
- **未保存時に呼ぶ保存経路は「掃除の一部」ではない**。本フェーズが保証するのは
  **「掃除による書き込みが 1 件も発生しない」**ことであり、**前提として実行する保存は
  正本 §5.8.6 の best-effort に従う**（**子 → 上位 → keymap_set → 起動設定**の順で書くため、
  **途中で失敗すると子だけが書かれた状態が残り得る**）。掃除はその場合 `prune` を呼ばずに終了する。
  保存経路のトランザクション化は §6 のとおり**スコープ外**。

## §4 確定の記録（旧・確認事項）

v0.1〜v0.2 で挙げた確認事項は**すべて確定**し §2 へ移した。**判断の根拠と却下案**を残す。

### A. 孤児（参照元がすべて実在しなくなる子）の削除 → **(A4) 削除せず警告表示のみ**

**v0.1 で「削除も選べる」と確定していたが、レビューを経て差し戻し、v0.3 で (A4) に確定した。**

- **孤児判定はこの検査範囲では原理的に成立しない**:
  - 検査対象は**現在のセットの索引に載っている子**＝**使用中**。参照元が 0 件になっても
    「どこからも参照されない」ことを意味しない。
  - **`_parent_refs` は best-effort 記録であり「どこからも参照されていないこと」の証明にならない**
    （旧形式・別経路保存では、現に使用中の子でも `None` になる）。
  - 具体例: **sequence の親は trigger_set** なので、**trigger_set が未保存 / 削除済みなら、
    使用中の sequence の参照元が全滅する**。
  - → 孤児検出は **逆方向（上位 → 子の索引走査）を根拠にしないと成立しない**（本書 §6 でスコープ外）。
| 案 | 採否 | 理由 |
|---|---|---|
| **(A4) 削除せず、参照元が 0 件になる子を警告表示** | **採用** | 掃除が**非破壊・冪等**に閉じる。「孤児かもしれないものを知りたい」動機は表示で満たせる |
| (A1) 削除も警告表示もしない | 却下 | (A4) の下位互換（情報が減るだけ）|
| (A2) 既定 3 ディレクトリを走査し、そこでのみ削除 | **本フェーズでは却下 → [idea_12](../backlog/idea_12_orphan_child_file_sweep.md) へ分離** | **削除は不可逆**で、規定外の場所に置かれた keymap_set が参照する子を消し得る（**データ損失**）。成立させるには**逆方向検査 + 削除の安全策**（隔離・全列挙）が要り、実質もう 1 フェーズ分 |
| (A3) v0.1 のまま削除を提供 | 却下 | **現在使用中の子を「孤児」として消せてしまう** |

### D. 確認 UI の形式 → **(D1) 確認 1 枚**

| 案 | 採否 | 理由 |
|---|---|---|
| **(D1) 読み取り専用の一覧 + 実行 / キャンセル** | **採用** | (A4) で掃除が非破壊・冪等になり**行ごとの取捨選択の価値が下がる**。**消えるパスの全件提示**を同時に満たせ、行モデル・ヘルパ抽出が不要になる |
| (D2) 行ごとのチェックボックス（v0.1 の「ファイル単位で選択」）| 却下 | 部分実行の具体的な理由（例: 到達不能な媒体の参照元だけ残す）が現時点で無い。UI とテストが増える |

### B. 掃除を現在の runtime へ反映するか → **(B1) 反映しない**

**(B1) 反映しない**（採用・次回読み込みで揃う / dirty も汚さない / runtime 更新の入口を増やさない）/
**(B2) 掃除した子の内部キーも更新する**（却下）。

### E. 敵対的レビュー（v0.4）の指摘と採否 — **High 3 件をすべて採用**

| 指摘 | 採否 | 対応 |
|---|---|---|
| **保護対象が「消えるパス」として提示され、表示と実行結果が食い違う** | **修正して採用** | **検査時点で保護対象を分離**（§3-1 の `CLEANUP_PROTECTED`）。一覧・件数・0 件警告から除外 |
| **未保存セットでは個別保存が掃除前の refs を再書き込みし、掃除が巻き戻る**（`parent_ref` が空だと `_parent_refs_for_save` が保存先を読み直さない）| **修正して採用**（ユーザー案）| **起動時に保存の確認を出し、保存成功時だけ掃除する**（キャンセルなら中止）。**runtime 反映（B2）は不要のまま** |
| **全体置換なので、確認中の外部変更を消し得る** | **修正して採用**（案 1）| **除去直前に JSON 全体を読み直す**。残る数ミリ秒の窓は §5.8.3 / §5.10.3 と同水準の既知の性質として**除外**（**版情報の照合は行わない**）|

### C. ダイアログの置き場所 → **`presentation/dialogs/`**（§3-4）

保存フローの一部ではなく独立起動の保守機能のため。**配置先の流儀（`tk.Toplevel` 継承 +
`destroy()` override で resume）に揃える**（`controllers/config_io/` の薄いオブジェクト方式ではない）。
