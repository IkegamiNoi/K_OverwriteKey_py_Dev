## §1 目的 / 背景

フル表示のヘッダ領域（**フック | 表示 | ファイル**）は、ウィンドウを狭めると切れる（ファイルの枠の中身が見えなくなる）。
phase 18 でウィンドウ最小幅を**メイン領域だけ**から算出したため、ヘッダの要求幅は考慮されていない。
①**ウィンドウ最小幅にヘッダの要求幅を含める** ②**文言が切り替わるボタンの幅を固定し、切替でヘッダの要求幅が変わらないようにする**
③**キーボード選択のドロップダウンを狭める**。

### 現状監査（2026-09-17・メインで直読み + deep-reviewer 実測）

## §2 確定事項（ユーザー 2026-09-17）

1. **案 A**: フル表示のウィンドウ最小幅を **max(メイン領域から算出した値, ヘッダの要求幅から算出した値)** にする。**ヘッダの配置は変えない**（案 B = 折り返し等の配置変更は不採用）。
2. **フックの枠の、文言が切り替わるボタンはすべて、取りうる文言の最大幅で固定する**（取得ボタン 2 つ・フック開始・通常トリガー切替）。
   切替でボタン幅・ヘッダの要求幅が変わらない。
3. **キーボード選択のドロップダウンを今の 2/3 の幅（`width` 18 → 12）にする。フル表示と省略表示の両方**。
4. **起動時にヘッダに合わせてウィンドウが自動で広がることを受け入れる**（標準 +19px / ＋3 で約 +223px）。既定ウィンドウ幅 780・780 基準の既定幅は変えない。
5. **幅を固定するのはフル表示のヘッダのボタンだけ**。省略表示のフック開始 / 通常トリガー切替は固定しない（固定すると幅 270 で常に切れるため）。
6. **保存したウィンドウ幅がウィンドウ最小幅より狭くて起動時に広げた場合は、広げた幅で保存値を更新する**（§3-5）。

## §3 設計

### §3-1 ヘッダの要求幅（測定）

- **ヘッダから算出したウィンドウ幅** = `header_area.winfo_reqwidth()` + ヘッダの外側の余白（ウィンドウ幅 − `header_area` の実幅）。
  **`update_idletasks()` の後に読む**（ボタンの要求幅は `configure` 直後に変わるが、`header_area` の要求幅は idle 処理の後でしか変わらない・実測）。
- **測る契機はメイン領域の最小幅と同じ**（初回適用 / フォント変更後 / 省略表示中にフォントを変えてフル表示へ戻ったとき）。§3-3 のボタン幅の固定が**先に済んでいる**こと。
- 測定は `controllers/pane_layout/`（`pane_measure.py` と同じ責務の範囲）に置き、**測った値をコントローラが保持**する。
  ドラッグ後の最小幅の更新（`_update_window_min_size`）は再測定せず、保持した値を使う。FullView は生成と配置のみのまま。

### §3-2 ウィンドウ最小幅と収まらない場合（phase 18 §3-7 の拡張）

- `resolve_layout` に**ヘッダから算出したウィンドウ幅**（int）を入力として追加する（tkinter 非依存のまま）。
  **既存の呼び出し・テストを壊さない形**（キーワード引数・既定値 0 等。`tests/test_pane_width_rules.py:224` は位置引数で呼んでいる）にする。`MinWidths` には足さない。
  - **必要幅（メイン）** = 従来どおり（両端の表示幅 + トリガー最小幅 + サッシュ + 余白）。
  - **ウィンドウ最小幅** = max(必要幅（メイン）, ヘッダから算出したウィンドウ幅)。
  - **最終ウィンドウ幅** = max(現在のウィンドウ幅, ウィンドウ最小幅)。
  - **画面幅を超える場合の縮小**（出力シーケンス → キーマップ管理の順に、表示幅を最小幅まで）は、**必要幅（メイン）を `max(画面幅, ヘッダから算出したウィンドウ幅)` 以下にする目標**で行う
    （ヘッダは縮められないため、ヘッダより狭くなるまで両端を縮めても無駄に狭くなるだけ）。
    ヘッダから算出した幅が画面幅を超える場合は、ウィンドウが画面からはみ出す（保証の範囲外・phase 18 と同じ扱い）。
- **ドラッグ後の最小幅**（`_update_window_min_size`）は、**画面超過の縮小規則を通さず** `max(実際の両端の表示幅 + トリガー最小幅 + サッシュ + 余白, 保持したヘッダ幅)` とする
  （`resolve_layout` を通すと、ウィンドウが画面幅より広いときに「縮めた仮の両端幅」から最小幅を出し、実際の表示より小さい最小幅を当ててしまう。v0.2 敵対的レビュー）。
  縮小規則を使うのは起動時・フォント変更後・フル表示へ戻ったときの一括適用だけ。
- ウィンドウ最小幅が上がって広がった分は、従来どおり**トリガー一覧が受ける**（両端の枠は変わらない）。
- **自動で広がった幅は保存しない**（phase 18 の規則のまま。geometry を変えたときに自動決定幅として記録される）。

### §3-3 文言が切り替わるボタンの幅の固定

- **対象**: フル表示の停止キー取得 / トグルキー取得（「キー入力で取得」「取得中…（Escで停止）」）/
  フック開始（「開始（フックON）」「停止（フックOFF）」）/ 通常トリガー切替（「通常トリガー無効化」「通常トリガー有効化」）。
  **省略表示の同じボタンは固定しない**（§2-5）。`HookController` は登録済みのボタンの組のうち**フル表示のものだけ**に幅を当てる（登録時に区別できる形にする）。
- **幅の決め方（純関数）**: `width = ceil(max(各文言の font.measure) / font.measure("0"))`。フォントは **TButton のスタイルのフォント**。
  実測で要求幅は各文言の自然な要求幅以上になる（不足なし）。動作中のボタンの文言を仮に切り替えて測ることはしない。
- **担当**: ボタンを登録している制御側（取得ボタン = `SingleKeyCaptureController`、フック開始 / 通常トリガー切替 = `HookController`）が幅を当てる。
  - 起動時: 登録時（`register_widgets` / `register_hook_buttons`）に当てる。
  - フォント変更時: `App._apply_font_delta` から、**`pane_layout.on_font_changed()` より前に**呼ぶ（省略表示中も当てる。幅配分の再計算だけが後回しになる）。
- **文言の定義を 1 か所にする**: 文言は **presentation 直下の中立なモジュール**（views からも controllers からも import してよい位置。例 `presentation/hook_button_texts.py`）の定数にし、
  View の初期文言・制御側の切替・幅の算出がそれを参照する。**views → controllers の import を新しく作らない**。
- 固定後は、文言を切り替えても**ボタンの要求幅が変わらない**。

### §3-4 キーボード選択のドロップダウン

- フル表示・省略表示の `ttk.Combobox` を `width=12` にする（定数 1 か所）。
- 表示名が長い外部レイアウトは欄内で切れる（ドロップダウンの一覧も同じ幅）。**受容**（§6）。

### §3-5 起動時の幅への影響

- ヘッダから算出したウィンドウ幅は **標準 799px（既定 780 より +19）/ ＋3 で 1054px（メインより +223）/ −3 はメインが勝つ**（§1 の見積もり）。
  → 既定ウィンドウ幅 780 のまま起動すると、標準フォントでも初回適用で**ウィンドウが自動で 19px 広がる**（§2-4）。**この幅は保存しない**（保存値が無いため。自動決定幅の規則）。
- phase 18 の「既定幅は 780 基準で算出」は変えない（広がった分はトリガー一覧が受ける）。
- **保存値の更新**（§2-6）: 初回適用の直後に、次を**すべて**満たすときだけ、適用後のウィンドウ幅で `full_view_window_width` を書く（`write_startup` 1 回）:
  ①`full_view_window_width` が有効な保存値として読めた（phase 18 の検証を通った）②**画面幅への切り詰め前の保存値 < 適用後のウィンドウ幅**
  （= ウィンドウ最小幅に届かず広げた。原因がヘッダかメイン領域〔フォント拡大等〕かは問わない）③適用後のウィンドウ幅がメモリ上の保存値と異なる。
  - **書かない**: 保存値が無い / 不正 / 画面幅への切り詰めだけが起きた（保存値 > 画面幅。phase 18 の「1600 は残る」を維持）/ 広げていない。
  - 書いた幅を自動決定幅として記録したまま残してよい（保存値と同じなので、その後の保存予約でも重複して書かない）。
  - 起動時以外（フォント変更後・フル表示へ戻ったとき）に広がった幅は、従来どおり保存しない。

## §5 受け入れ条件（ドラフト）

1. **ヘッダが切れない**: フォント −3 / 標準 / ＋3 のそれぞれで、フル表示のウィンドウを最小まで縮めても、`header_area` と**子の 3 枠（フック / 表示 / ファイル）それぞれの実幅 ≥ 要求幅**。
   **取得中の状態でも同じ**（§3-1・§3-2・§3-3）。値は固定ピクセルではなく要求幅との比較で書く。
2. **ウィンドウ最小幅** = max(メインからの必要幅, ヘッダからの幅)（純関数の単体テストで、メインが大きい / ヘッダが大きい / 等しい の 3 通り）。
   ヘッダ幅を渡さない既存の呼び出しは従来と同じ結果（§3-2）。
3. **画面幅超過の縮小**（純関数テスト）: ヘッダだけが画面幅を超える → 両端は縮まない / メインだけが超える → 従来どおり縮む /
   **両方が超える**（例: 画面 1000・メイン 1200・ヘッダ 1100）→ 両端はメインが 1100 になるところまでしか縮まない（§3-2）。
   **ドラッグ後の最小幅**: ウィンドウが画面幅より広い状態（例: ＋3 でヘッダに合わせて広がった後にフォントを標準へ戻す）でサッシュを限界まで動かして離すと、
   ウィンドウ最小幅 = max(実際の両端の表示幅 + トリガー最小幅 + サッシュ + 余白, ヘッダ幅)。続けてウィンドウを縮めても両端の枠は縮まず、トリガー一覧は最小幅を保つ（§3-2）。
4. **ボタン幅の固定**: 対象ボタンそれぞれで、文言を切り替えても `winfo_reqwidth()` が変わらず、要求幅 ≥ 各文言の自然な要求幅。フォント −3 / 標準 / ＋3 で成立。
   幅の算出は純関数の単体テストでも固定（§3-3）。
5. **取得中にヘッダの要求幅が変わらない**: 停止キー取得を開始 → `update_idletasks()` 後の `header_area.winfo_reqwidth()` が開始前と同じ（§3-3）。
6. **ドロップダウン**: `full_view.display_frame.keyboard_layout_combo` と `compact_view.display_frame.compact_keyboard_layout_combo` の `width` が 12（§3-4）。
7. **フォント変更**: フォントを上げるとウィンドウ最小幅がヘッダに合わせて上がり、戻すと**最小幅は**下がる（ウィンドウ幅は縮まない・phase 18 の規則）。
   省略表示中に変えた場合、ボタン幅はその場で当たり、ウィンドウ最小幅はフル表示へ戻ったときに反映（§3-1・§3-3）。
8. **自動で広がった幅を保存しない**: キー無しで起動 → 何もせず保存予約を実行しても `full_view_window_width` が書かれない（§3-5）。
   **旧保存値の更新**: 保存値 790（ヘッダから算出した幅より狭い）で起動 → 起動直後に適用後のウィンドウ幅で 1 回だけ書かれる /
   保存値が画面幅より広い（切り詰めのみ）→ 書かれない / 保存値が十分広い → 書かれない / 省略表示のフック開始ボタンの `width` は固定されない（§3-5・§2-5）。
9. **期待値が変わる既存テスト**（本仕様の条項で説明できる更新のみ。**それ以外のアサーションは弱めない**。完了報告に列挙する）。見込み:
   - `tests_ui/test_full_view_panes.py:96`（既定ウィンドウ幅 780）/ `:105`（トリガー一覧の幅 = 要求幅）→ ヘッダ分（標準 +19px）
   - `tests_ui/test_pane_window_width_persistence.py:100`（`expected_width = DEFAULT_WINDOW_WIDTH`）を使うキー無し / Bool / 文字列 / 0 の起動テスト
   - `tests_ui/test_pane_drag_and_window_min.py:116-121` の `_expected_window_min`（メインのみの式）→ test_07 / 08 / 09 / 12
10. 既存の `tests` / `tests_ui` が全て pass し `smoke_app` が通る。実 `config/config.json` を書かない。
