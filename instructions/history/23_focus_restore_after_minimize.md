## §1 目的 / 背景

モーダルダイアログを開いたままアプリを最小化し、復元すると、**モーダル性（grab）はダイアログへ戻るが
キーボードフォーカスはメイン窓に残る**。クリックしない限り **Escape などのキーがダイアログへ届かない**
（Escape はメイン窓へ行く）。**復元時にフォーカスも最内の表示中モーダルへ戻す**。

**対象レイヤ = presentation のみ**（`keyseq/presentation/modal.py`）。スキーマ・domain / application の変更なし。

### §1.2 実測（2026-09-23・`.venv` python で probe）

**測定 1**（API による模擬: `iconify` → `ShowWindow(SW_RESTORE)` + `SetForegroundWindow` を同一スレッドで → 実 Escape を `keybd_event`）:

| 条件 | 復元直後の `focus_get` | 前面の窓 | 実 Escape の行き先 |
|---|---|---|---|
| 何もしない（現状） | **`.`（メイン窓）** | メイン窓 | **メイン窓**（C② を再現） |
| `<Map>` 内で即 `focus_set` | 一巡後 **ダイアログの Entry** | **ダイアログ** | **ダイアログ** |
| `<Map>` から `after_idle` で `focus_set` | 同上 | ダイアログ | ダイアログ |

**測定 2**（キュー経由の復元: `iconify` → `PostMessageW(WM_SYSCOMMAND, SC_RESTORE)`。**3 段ネスト**〔root → d0 → d1 → d2・transient 連鎖〕）:

| 条件 | App のイベント順 | 復元後の `focus_get` | 3 窓の表示 | 実 Escape の行き先 |
|---|---|---|---|---|
| 何もしない | **`<FocusIn>` → `<Map>`** | `.` | 3 窓とも表示 | **メイン窓** |
| `<Map>` 内で即 `focus_set` | 同上 | **最内の Entry** | **3 窓とも表示** | **最内** |
| `<Map>` で印 → 次の `<FocusIn>` で戻す（レビューの代替案） | 同上 | `.` | 3 窓とも表示 | **メイン窓（戻らない）** |

- **キュー経由の復元では App の `<FocusIn>` が `<Map>` より先に届く**。そのため `<FocusIn>` を待つ方式は**戻らない**
  （反証）。`<Map>` 内で即時に `focus_set` する方式は両測定で成立し 3 段ネストでも中間窓は消えなかったが、**実 App では外側の窓が戻らない退行が出た**（測定 3。v0.4 で `after_idle` へ訂正）。
- **`<Map>` の時点で `focus_lastfor()` は最小化前のフォーカス先を返す**（表示済みの窓の記録。phase 28 の「未マップ時は保留」とは別）。
- **`focus_set` が別の Toplevel をアクティブにするのは、アプリが OS の入力フォーカスを持つときだけ**。持たないとき
  （測定 2 の 1 段構成で、プロセスが前面を取れなかった回）は `focus_get` が `None` のままで、何も奪わない
  （phase 28 の機序 3 と整合）。→ **他アプリで作業中のユーザーから入力を奪わない**のは Tk / OS の側で保たれる。
- ※ いずれも API による模擬。**タスクバー・Win+D・Alt+Tab での実際の復元は実機目視で確定する**（§6-6）。

**測定 3**（v0.4・task_01 の実装で既存テスト a2 / a3 が落ちたため実 App で再測定。アクション編集 → プリセットマネージャ →
上書き確認〔`confirm_overwrite`〕の 3 段・`app.iconify()` → `app.deiconify()`）:

| 条件 | 復元後の表示（アクション / マネージャ / 確認） |
|---|---|
| フォーカス復帰なし | **1 / 1 / 1** |
| `<Map>` 内で即時 `focus_set` | **0 / 1 / 1**（**アクション編集が非表示のまま**。1.3 秒後も戻らない） |
| `after_idle` / `after(0)` / `after(50)` / `after(200)` で `focus_set` | **1 / 1 / 1**・フォーカスは最内（確認ダイアログ） |

- **実 App では、Windows が所有窓を順に戻している途中で `focus_set` が割り込むと外側の窓が戻らない**（素の Tk の probe では
  再現しなかった）。**`after_idle` へ後ろ倒しすると解消**する。測定 1 でも `after_idle` はダイアログへ Escape を届けていた。
- `<FocusIn>` を待つ方式（測定 2 で反証）とは別物。`after_idle` は `<Map>` の処理が一巡した直後に走る。

## §3 設計

### §3.1 規範（実装が従う条項）

1. **アプリを最小化から復元したとき、モーダルダイアログが開いていれば、キーボードフォーカスをそのモーダルへ戻す**。
   戻し先の widget は**そのモーダルの中で最後にフォーカスがあった widget**（`focus_lastfor()`。記録が無い・`None` なら
   モーダル自身）。
2. **戻し先の窓の定義（1 つ）**: **復元処理（grab の返却）を終えた時点の grab 保持者**（`app.grab_current()`）が
   **台帳 `_active_modals` に同一性（`is`）で含まれ、かつ表示中**なら、その窓。
   - 預かりあり → 返却した窓 / 預かりなし → もともとの保持者 / 別の窓が既に grab 中 → その窓（台帳にあれば）、を
     **この 1 つの定義で覆う**（経路で分けない）。
   - **grab 保持者が解決できない（stdlib ダイアログ）/ いない / 台帳に無い / 表示されていない場合は触らない**。
3. **使うのは `focus_set` のみ**。`focus_force` / `lift` / `deiconify` は呼ばない（既存テスト a4 の固定を維持）。
4. **App 自身の `<Map>` で grab を返却した後、フォーカス復帰は `after_idle` で予約する**（v0.4。grab の返却は `<Map>` 内で即時のまま。
   既存ガード `event.widget is app` を流用）。**戻し先（§3.1-2）は予約が実行された時点で決める**（その間に窓が閉じられても安全）。
   **即時に `focus_set` してはならない**（§1.2 測定 3: 実 App の 3 段ネストで外側の窓が戻らない）。
5. **失敗は `TclError` / `KeyError` を握る**（破棄中の窓、`focus_lastfor()` の名前解決失敗）。復元・終了を妨げない。
6. **最小化中に開いたモーダルには復帰を行わない**（v0.3）。その窓の初期フォーカス要求は未マップのため Tk 内で保留中で
   `focus_lastfor()` から読めず、`focus_set(窓自身)` を出すと**開いたときの明示指定を奪う**（正本の初期フォーカス条項 `features.md:174-178` に反する）。
   `grab_modal` が `_app_minimized` の間に呼ばれた窓を記録し（台帳と同じモジュール状態。破棄時に除く）、
   §3.1-2 の窓がそれに当たる場合は `focus_set` しない（保留中の要求が復元時に解決される）。
   **記録の寿命はその回の復元まで**（v0.4）: 予約したフォーカス復帰の処理を終えた時点で記録を空にする。以後の最小化 → 復元では
   その窓も通常どおり戻す（初期フォーカス要求はその回の復元で解決済みのため）。

### §3.2 実装方式

- `modal.py` にフォーカス復帰の関数を切り出す（例: `_restore_modal_focus(app)`）。§3.1-2 の定義で窓を決め、
  `target = window.focus_lastfor() or window` へ `focus_set()`。台帳の判定は `restore_grab` と同じく **`is` による同一性**。
- `return_custody` は**どの経路でも最後にフォーカス復帰を `after_idle` で予約する**（v0.4。預かりが空の早期 return もこの予約を通る形へ
  整理する）。`return_custody` は現在 27 行のため、**戻し先の決定は別関数に出して 30 行目安を守る**。
- `focus_lastfor()` は Tk の仕様上、**同じ Toplevel 内の widget か、その Toplevel 自身**を返す（別の Toplevel は返さない）。

### §3.3 閉じた後のフォーカス（参考・変更しない）

ネストの内側を閉じた後は、Tk の既定の動作で外側へフォーカスが戻る（phase 28 の probe 3 の H・実機目視 C① で確認済）。
**本フェーズでは規定を追加しない**（§4-2）。
phase 28 の「フォーカスを `grab_modal` の外で設定しない」（22 §3.1-3）は**初期フォーカス**の条項であり、本件の復元時の
フォーカス復帰とは範囲が異なる（衝突しない）。

## §4 確認事項（→ 2026-09-23 ユーザー確定。§2 へ移した・経緯として残す）

1. **既存条項「復元の際、アプリは窓の表示・前面を操作しない」との関係**。`focus_set` で**アクティブな窓がダイアログに変わる**
   （§1.2）。**これは「前面（アクティブな窓）を操作しない」を意図的に緩める判断**になる。
   - **提案（API 単位で書く）**: 「復元の際、アプリは **`deiconify` / `lift` / `focus_force` を呼ばない**（OS が戻した表示状態のまま）。
     **キーボードフォーカスは `focus_set` で最内の表示中モーダルへ戻す**（それに伴うアクティブな窓・重なり順の変化は許容する）」。
     初期フォーカスの条項（「窓の前面化・フォーカス強制は行わない」）も同じ言い回しに揃える。
   - 理由: 「重なり順は変えない」と書くと、`transient` を失った窓（呼び出し元を先に閉じた子。`features.md:200-202`）では
     アクティブ化で重なり順が変わりうるため偽になりうる（起票時レビュー H2・未実測）。**呼ぶ API で書けばテスト a4 の固定と一致する**。
2. **「閉じた後」のフォーカスも規定するか**。
   - **提案: 規定しない（現状維持）**。Tk の既定で外側へ戻っており（C① OK）、実装を足す理由が無い。
     正本の一文は「**最小化から復元した後**は戻す／**閉じた後**は規定しない」に分ける。
3. **最小化を伴わないアプリの再アクティブ化**（Alt+Tab で最小化されていない窓へ戻る・クリック）も対象にするか。
   - **提案: 対象外**。App の `<Map>` が来ないため別の結線が要り、範囲が広がる。実機目視で挙動だけ記録し、
     フォーカスが外れる事象があれば idea 起票。
   - ※ **Alt+Tab で最小化中の窓を選んで復元する**のは `<Map>` が来る経路なので**本フェーズの対象内**（§6-6）。

## §5 テスト

- **決定論的な単体検査**（`tests_ui/test_minimize_grab_custody.py` に追加）。既存の最小化 → 復元の組み立てで、
  **戻し先の widget の `focus_set` が 1 回呼ばれる**ことを `patch.object(..., wraps=...)` で固定する。
  **期待値はダイアログごとの具体 widget で固定**する（例: `ActionDialog` なら phase 28 の初期フォーカス先。
  `focus_lastfor()` の戻り値をそのまま期待値にしない＝実装をなぞるだけの検査にしない）。経路:
  ①預かりあり ②預かりなし ③別の窓が既に grab 中（a6 相当）④最小化中に新しいモーダルを開いて閉じた（a9 相当 → 元の窓へ）
  ⑤預かった窓と新しいモーダルを両方閉じた（a10 相当 → 外側へ）⑥grab 保持者が解決不能（stdlib 相当）→ `focus_set` 0 回
  ⑦台帳に無い窓 → 0 回 ⑧**最小化中に `grab_modal` した窓**（`_app_minimized` を立てた状態で開く）→ 復元時の `focus_set` 0 回・
  開いたときに指定した `focus=` の widget への要求が残る ⑨**最小化前に初期フォーカス先とは別の widget へフォーカスを移してから**
  最小化 → 復元 → **その別の widget へ** `focus_set`（例: `ActionDialog` で `value_entry` ではなくラベル欄。毎回初期フォーカス先へ戻す
  誤実装を落とす）。
- **a4（`deiconify` / `lift` / `focus_force` が 0 回）は変更しない**。
- **ネスト 3 段**（既存 a2 の組み立て）で、復元後に**3 段とも表示されたまま**・**最内へ `focus_set`** が出ること。
  **注記**: テスト環境ではアプリが OS フォーカスを持たないことが多く、その場合 `focus_set` は記録だけでアクティブ化の経路を
  通らない。**中間窓が消えないことの最終確認は実機目視（§6-6②）で行う**。
- **実 Tk の到達検査**（`focus_get()` 依存）を置く場合は phase 28 の skip ガード方式にし、**修正前に落ちることを確認する**
  （落ちなければ参考扱いとし、受け入れの根拠にしない）。skip 件数は完了報告に記す。

## §6 受け入れ条件（ドラフト）

1. 最小化 → 復元の後、**§3.1-2 の窓の最後のフォーカス先**へ `focus_set` される。**初期フォーカス先と別の widget にいた場合もその widget へ戻る**（§5 ①②⑨）。
2. 別の窓が grab 中 / 最小化中の開閉（a6・a9・a10 相当）でも §3.1-2 の定義どおりに戻す（§5 ③④⑤）。**最小化中に開いた窓には復帰を行わず、開いたときの初期フォーカス要求が残る**（§3.1-6・§5 ⑧）。
3. **stdlib ダイアログ・台帳外・非表示では触らない**（§5 ⑥⑦）。
