## §1 目的 / 背景

構成セット（keymap_set）の「保存」が**子ファイル（keymap / trigger_set / sequence）をまとめて無条件上書き**する
現挙動を、**変更のある子ファイルごとに保存方法を選べる確認ダイアログ**へ置き換える。あわせて、子ファイルが
どの上位ファイルに属するかを記録し、**他所の keymap_set に属する子ファイルの誤爆上書きを防ぐ**。
本フェーズは**挙動変更を伴う**。

解決する不満（ユーザー討議 2026-07-26〜27・点3/4）:

- keymap_set の「保存」で子ファイルがまとめて保存されるが、**保存対象が何か分からず、上書き確認も飛ばされる**。
- 保存対象を一覧提示し、項目ごとに **保存/別名保存/保存しない** をラジオで選びたい。
- **利用している上位ファイルを記録**し、**上位が一致しない/複数のときは別名保存をデフォルト**にしたい。
  ただし「意図的に共有したいファイル」もあるため、共有を**可視化**して選べるようにしたい。
- トリガー一覧からの出力シーケンス保存も同様（**シーケンスの直接の上位はトリガー一覧**、keymap_set は間接）。

### 現状監査（2026-07-27・v0.2 で配置を修正）

**子ファイルの一括保存（無条件上書き）**:

- keymap_set の「保存」→ `KeymapSetIo.save_keymap_set_to`（`keymap_set_io.py:68-92`）→
  `config_service.save_runtime_data`（`config_service.py:200-252`）が、**keymap_set / trigger_set / keymaps / sequences /
  hotkey_presets / startup を一括で・無条件に上書き**する（`:227-246`）。個別の上書き確認・対象提示は無い。
- config_root 内へ保存する場合、trigger_set / hotkey_presets は**全セット共通の固定パス**
  （`user/trigger_sets/default.json` / `user/hotkey_presets/default.json`）へ書かれる（`_build_split_save_payloads:468-476`）。
  → 複数 keymap_set が同じ子ファイルを共有・上書きする（Phase α §9 の制約の根拠）。

**子ファイルの既定配置（v0.2 修正・指摘④）**:

- **keymaps**: `user/keymaps/` に **label / id 基準**で命名（`keymap_file_io.py` の suggest）。
- **trigger_set**: config_root 内では **固定 `user/trigger_sets/default.json`**（`_build_split_save_payloads:468-471`。
  keymap_set 名基準ではない ＝ 複数セットで衝突する唯一の子）。
- **sequences**: config_root 内では **`user/sequences/`**（`_is_default_trigger_set_area` 判定時。
  ※ v0.1 の「`<trigger_set>/sequences/` に置く」は**誤り**。config_root 内は `user/sequences/`）。
- hotkey_presets: `user/hotkey_presets/default.json`（**本フェーズでは触らない**・プリセットは暫定 07 でグローバル化）。

**変更（dirty）管理は子単位で存在する**（`dirty_state.py`）: keymap ごと `INTERNAL_KEYMAP_DIRTY` / trigger_set 全体
`trigger_set_dirty` / sequence ごと `INTERNAL_SEQUENCE_DIRTY` / keymap_set 全体 `config_dirty`。
`has_individual_dirty()`（`:47-57`）が走査判定。

**source_path**: keymap `INTERNAL_KEYMAP_SOURCE_PATH` / sequence `INTERNAL_SEQUENCE_SOURCE_PATH`（対称）/
trigger_set は**読み書き分断**（[idea_05](../backlog/idea_05_trigger_set_source_path_inconsistency.md)・本フェーズで接続）。

**参照元（上位ファイル）の記録は現状なし**。参照階層: **keymap→keymap_set / trigger_set→keymap_set / sequence→trigger_set**
（keymap_set は sequence の間接上位。`config_service.py:421` トリガーが `sequence_path` を持つ）。

## §2 確定事項（ユーザー 2026-07-26〜27 / 2026-07-27 確定）

- **概念は「子（下位）ファイルの保存」**。keymap_set 側の「保存」で、**変更（dirty）のある子ファイルごと**に一覧を提示し、
  項目ごとに **保存 / 別名保存 / 保存しない** のラジオで選ばせる。粒度は**ファイル単位**。
- **親 keymap_set.json は常に保存**（ラジオ対象にしない・索引として最後に書く）。変更のある子が無ければダイアログを出さない。
- **参照元を子JSONに記録する（案A・軽量）**。keymap / trigger_set は **keymap_set** を、sequence は **trigger_set** を記録。
  パスは config_root 内=相対 / 外=絶対（`to_config_relative_or_absolute`）。外部移動での参照不能は許容し
  掃除は [idea_07](../backlog/idea_07_reference_link_cleanup.md)。
- **【指摘①】未知の参照元（既存子JSONに `_parent_refs` 無し）は安全側で「別名保存」を既定にする**
  （共有を否定できるまで上書きしない）。
- **【指摘②③】保存は「保存計画」として原子的に扱う**:
  - 保存計画は **presentation が行ごとの指示（保存/別名パス/スキップ）を集め、application が実行**する。
  - **依存関係**: 子のパスが変わる（別名保存・新規パス）ときは、**その子を索引する上位（trigger_set / keymap_set）の
    保存を必須化**する（その上位は「保存しない」を選べない）。例: sequence を別名保存 → 親 trigger_set の保存必須。
  - **事前検証 → 書き込み**の順で行い、途中失敗時は**旧索引を維持**できるようにする（部分成功で親索引だけ旧状態に
    取り残さない）。個別 save API 再利用時も、**行ごとの粒度**（選んだ子だけ書く・他 sequence を巻き込まない）を守る。
- **【指摘④】既定命名の変更は trigger_set のみ**（現状 `default.json` に落ちる唯一の子）。keymap_set 名基準の名前にする。
  **keymaps / sequences は現状の命名ルールのまま**（衝突は上記①の安全既定＋既存の衝突ダイアログ
  `choose_save_path_with_collision` で守る）。**複数 trigger_set を持つ対応は将来課題**（本フェーズは 1 keymap_set:1 trigger_set）。
- **共有の可視化とデフォルト選択規則**（§5）: 保存ダイアログ内でのみ表示。
- **trigger_set の source_path 分断を接続する**（idea_05 内包）。
- 影響レイヤ: presentation（ダイアログ・保存計画の収集・参照元記録）+ application（保存計画の実行・事前検証・
  参照元永続化・trigger_set 既定命名）+ スキーマ（子JSONに参照元の内部キー追加・後方互換）。

### v0.3 の変更（2026-07-29・実機目視フィードバック）

- **【A】再解決後の一覧再表示を廃止する**（v0.2 の「提示した保存先と実際に書く先を必ず一致させる」を緩和）。
  trigger_set の保存先が変わってシーケンスの保存先が再計算された場合でも、**一覧で選んだ操作
  （保存 / 別名保存 / 保存しない）をそのまま適用**し、再確認しない（§3-3）。
  **緩和の理由**: 別名保存は「その保存先へ書く」というユーザーの明示操作であり、その帰結として
  子の保存先が追随することは同一操作の一部とみなせる。再確認は冗長で、確定操作の反復を強いていた。
  **残す安全網**: §5 の既定選択規則（未知・別の上位は別名保存が既定）と、別名保存時の
  `asksaveasfilename` による上書き確認は変更しない。加えて、**再計算で保存先が変わった行が
  既存ファイルを上書きする場合だけ、行単位の小ダイアログで確認する**（§3-3・敵対的レビュー
  2026-07-29 の critical 指摘への対応。一覧の再表示・選び直しは発生させない）。
- **【B】config_root の内外判定・既定領域判定は「ケース非依存」で行う**（§6 末尾）。
  Windows でパス文字列の大文字小文字が食い違うと、config_root 内のパスが「外」と誤判定され、
  ①デフォルト配下なのに「デフォルト外に保存されます」確認が出る ②参照元・起動設定が相対化されず
  絶対パスで記録される ③その絶対パスが source_path に載ると次回保存でシーケンスが
  `user/trigger_sets/sequences/` へ落ちる、というカスケードが起きる（2026-07-29 実機で発生・再現確認済）。
  **実際の発生経路**: VS Code の ▶ 実行（デバッグ構成）はドライブ文字を小文字（`c:\`）で渡すことがあり、
  `config_root` が `c:\...` になる一方、tkinter のファイルダイアログは `C:/...` を返すため食い違う。
- **【C】一覧ダイアログのレイアウト要件**を定める（§3-5）。dirty な子が多いときに横方向へはみ出し、
  縦にも収まらない問題への対応。

### v0.4 の変更（2026-07-30・2 回目の実機目視フィードバック）

- **【D】依存確認ダイアログ（「トリガー一覧の保存が必要です」）の提示条件を絞る**。
  子のパスが変わって上位（trigger_set）の保存が必須になったとき、**上位の共有状況（§5）が
  「単独」または「新規作成」なら確認を出さず自動で保存**し、**保存完了メッセージで事後通知**する
  （索引の更新は別名保存という明示操作の一部と見なす）。
  **「所有元不明」「別の構成に属します」「N 個の上位で共有中」のときだけ**ダイアログを出す。
  **廃止の理由**: 単独所有のときは答えが常に「保存」であり、確認が冗長だった（実機目視 2026-07-30）。
- **【E】依存確認ダイアログを 4 択にする**: **保存 / 別名保存 / 保存しない / キャンセル**
  （従来の「はい」＝保存 /「いいえ」＝別名保存 のラベル変更 ＋「保存しない」の追加）。
  **既定ボタンは「別名保存」**（従来の `default=NO` を踏襲。安全側）。
  **「保存しない」の意味**: 上位を書かず、**索引は旧パスのまま維持**する。子は選んだ操作どおり書かれるため、
  新しいパスは**この保存では索引されない**。
  **上位は、保存前の dirty 状態に関係なく dirty 化する**（非 dirty だった上位も dirty にする。
  さもないと次回の一覧に何も出ず「次回保存で追随」が成立しない ← 敵対的レビュー high 指摘）。
  子の dirty はクリアされ `source_path` は新パスへ更新されるため、**次回保存で上位を書けば索引が追随**する。
  旧ファイルは旧内容のまま残るので、この保存の直後に再起動すると**旧状態が読まれる**（許容する帰結）。
  → §2【指摘②③】の「パスが変わる子の上位は『保存しない』を選べない」条項は、
  **ダイアログを出す条件（共有状況が単独 / 新規作成以外）に限り緩和**する。
  自動保存に倒すケースでは従来どおり保存必須（選択肢を出さない）。
- **【F】v0.3-A2（再計算先の上書き確認）は維持する**（廃止案を検討したが不採用）。
  理由: A2 の対象は**「保存」を選んだ行**であり `asksaveasfilename` を通らないため、
  **ファイルダイアログの上書き確認では代替できない**（v0.3 の critical 指摘の本体）。
  対象 0 件なら出ない設計であり、通常フローでの追加ダイアログにはならない。
- **【G】新規の子の既定保存先で「ディスク上の既存ファイルを避けて連番にする」案は不採用**
  （ユーザー判断 2026-07-30）。既定保存先はラベル由来の名前のままとし、既存ファイルとの衝突は
  **§5 の既定選択規則**（下記【I】を含む）で守る。
  ＝ `_allocate_unique_*` の「同一保存バッチ内の衝突のみ回避する」現挙動を変更しない。
- **【I】`source_path` を持たない子（新規）の保存先に既存ファイルがあるときは、共有状況にかかわらず
  既定を「別名保存」にする**（§5 に条項追加・ユーザー確定 2026-07-30）。
  **理由**（敵対的レビュー critical）: 新規の子はラベル由来の既定名で既存ファイルと衝突し得るが、
  その既存ファイルの `_parent_refs` が現在の上位のみだと §5 は「単独」＝安全と判定し、既定が「保存」になる。
  同一保存バッチ内の衝突は `used_paths` で回避されるため、実際に踏むのは**現在の runtime にオーナーがいない
  既存ファイル**（削除済みトリガーの孤児 / 同名 keymap_set の前バージョンが書いたファイル）に限られるが、
  無確認で内容が失われるため既定を安全側へ倒す。表示は「同名の既存ファイルあり・安全のため別名」。

## §3 子ファイル保存の確認ダイアログ（点3/4）

keymap_set の「保存」で:

1. **変更のある子を収集**（dirty フラグ）: dirty な各 keymap / dirty な trigger_set / dirty な各 sequence。無ければ
   ダイアログを出さず親 keymap_set.json のみ保存。
2. **一覧ダイアログ**を表示。各行 = 1 子ファイル。列: 種別 / 対象名 / 保存先パス / **共有状況**（§5）/ **ラジオ（保存/別名保存/保存しない）**。
   各行のデフォルトは §5 の規則（未知の参照元は別名保存）。
3. ユーザー確定後、**保存計画**（§2・行ごとの指示＋依存関係）を作り、**事前検証してから**実行:
   - **保存**: source_path（または既定パス）へ上書き。**別名保存**: `asksaveasfilename`。**保存しない**: スキップ。
   - パスが変わる子の親（trigger_set / keymap_set）は保存必須（依存関係）。
   - **【v0.3-A】trigger_set の保存先が変わり、シーケンスの保存先が再計算される場合も一覧を再表示しない**。
     一覧で選んだ操作を再計算後の保存先へそのまま適用する（保存＝再計算後のパスへ保存 /
     別名保存＝ユーザーが選んだパスのまま / 保存しない＝スキップ）。
     再計算が起きたことは**保存完了時のメッセージで事後通知**する（確認は求めない）。
     依存確認ダイアログ（trigger_set の保存が必須になったとき）は**廃止しないが、v0.4-D で提示条件を絞る**。
   - **【v0.4-D/E】依存確認ダイアログの提示条件と選択肢**:
     - 対象は「子のパスが変わり、それを索引する上位（trigger_set）の保存が必須になった」場合。
     - **上位の共有状況（§5）が「単独」「新規作成」なら確認を出さず自動保存**し、完了メッセージで事後通知する。
     - **「所有元不明」「別の構成に属します」「N 個の上位で共有中」のときだけ**ダイアログを出し、
       **保存 / 別名保存 / 保存しない / キャンセル**の 4 択にする（**既定ボタン = 別名保存**）。
     - **「保存しない」**: 上位を書かず**索引は旧パスのまま維持**する。子は選んだ操作どおり書かれるが、
       新しいパスはこの保存では索引されない。**上位は保存前の dirty 状態に関係なく dirty 化**し
       （非 dirty だった上位も dirty にする）、次回保存で索引を追随させる。
       この状態で再起動すると旧ファイル・旧索引が読まれる（許容）。
       application 側の事前検証はこの場合だけ**必須依存の例外**として通す（§8）。
     - **「キャンセル」**: 一覧から選び直す（従来どおり）。
   - **【v0.3-A2】再計算先の上書き確認**（A の安全弁）: 再計算で**実体パスが変わった「保存」行**のうち、
     **新しい保存先に既存ファイルがあり、かつ §5 の共有状況が「単独（現在の上位のみが所有）」以外**の行を
     集め、**1 枚の小ダイアログ**で対象行（種別 / 対象名 / 新しい保存先 / 共有状況）を列挙して確認する。
     - 選択肢は **「はい」= そのまま上書き / 「いいえ」= 対象行を別名保存（行ごとに `asksaveasfilename`）/
       「キャンセル」= 保存を中止**（既存の依存確認ダイアログと同じ 3 択の作法に揃える）。
     - **一覧の再表示・選び直しは行わない**（A の趣旨）。対象行が 0 件なら**このダイアログも出さない**
       （別名保存先が新規領域なら通常は 0 件になる）。
     - 判定は §6 の canonical identity で行う（パス文字列の表記差で誤検出しない）。
4. 子の保存完了後、**親 keymap_set.json を索引として保存**（子の最終パスを反映）。途中失敗時は旧索引を維持。
5. **【v0.3-C】一覧ダイアログのレイアウト要件**:
   - **固定の初期サイズ**で表示し、**ユーザーが端をドラッグしてリサイズできる**（`resizable(True, True)`）。
   - 行が入りきらない場合は**縦スクロール**できる（横スクロールは持たない）。
   - **対象名・保存先パスは省略表示**（末尾省略ではなくパスは中央省略が望ましい）とし、
     **ツールチップで全文**を見せる。ウィンドウが横方向へはみ出さないことを最優先する。
   - 種別・共有状況・ラジオ（操作）は省略しない（判断に直結するため）。
   - **【v0.4 追記】OK / キャンセルはスクロール領域の外に置き、縦を最小サイズまで詰めても必ず見える**
     （縮小時に押し出されないレイアウト順にする）。
   - **【v0.4 追記】対象名・保存先パスの列はダイアログ幅に追随して伸縮する**（省略量が幅に応じて変わる）。
     種別・共有状況・ラジオは固定幅とし、**幅が足りないときは可変列を詰めてラジオの完全表示を優先**する。
     最小サイズでも 5 列すべてが見えること。

- **単体操作ではダイアログを出さない**（本ダイアログは keymap_set 一括「保存」経路にのみ挟む）。
- **既存の個別保存ボタン（各 box）は本フェーズでは統合しない**（§11）。
- **変更のある子が無いとき**は子ファイル保存ダイアログを出さないが、**親 keymap_set.json・起動設定・
  未作成の子は従来どおり書かれ、保存完了ダイアログも出る**（従来挙動の維持。回帰ではない）。

## §4 参照元記録（案A・軽量・参考表示）

- 子JSON に内部キー（例 `_parent_refs`）で**直接の上位ファイルパスの集合**を記録（keymap/trigger_set→keymap_set /
  sequence→trigger_set）。パスは `to_config_relative_or_absolute`。
- **更新（best-effort）**: 子を保存/別名保存した際、現在の上位パスを集合へ追加。上位の移動・削除は検知せず残置（→ idea_07）。
- **後方互換**: 既存子JSON に `_parent_refs` は無い → **未知**として扱い、**§5 で「別名保存」を既定**にする（指摘①・安全側）。
  既存キーは削除しない（追加のみ）。

## §5 共有の可視化とデフォルト選択規則（指摘①反映）

| 保存先ファイルの参照元状態 | 既定のラジオ | ダイアログ表示 |
|---|---|---|
| **未知（`_parent_refs` 無し）** | **別名保存** | 「所有元不明・安全のため別名」 |
| 現在の上位のみ（単独所有） | **保存（上書き）** | 「単独」 |
| 現在の上位を含み、かつ複数（共有） | **保存（上書き）** | 「N 個の上位で共有中・全てに影響します」警告 |
| 保存先が**別の上位に属す**（現在の上位が参照元に無い） | **別名保存** | 「別の構成に属します」注意 |

- **【v0.4-I】上表より優先する条項**: **`source_path` を持たない子（新規）**の保存先に**既存ファイルがある**ときは、
  参照元状態が「単独」「共有」であっても**既定は別名保存**とし、「同名の既存ファイルあり・安全のため別名」を表示する。
  新規の子の既定名はラベル由来で、同一保存バッチ内の衝突しか回避しないため（§6【v0.4-G】）、
  現在の runtime にオーナーがいない既存ファイル（孤児 / 前バージョンのファイル）を「単独」と誤認し得る。
- いずれもデフォルトであり、ユーザーは上書き/別名/しない を選び直せる。共有情報は**保存ダイアログ内でのみ**表示。

## §6 子ファイルのデフォルト命名（trigger_set のみ・指摘④反映）

- **trigger_set**: source_path が無い場合の既定名を **keymap_set の stem** にする
  （例 keymap_set `gaming.json` → `user/trigger_sets/gaming.json`）。現状の固定 `user/trigger_sets/default.json`
  （`config_service.py:468-471`）を keymap_set 名基準へ変更 ＝ **複数 keymap_set の trigger_set 衝突を回避**。
- **keymaps / sequences**: **現状の命名ルールのまま**（keymap=label/id、sequence=`user/sequences/` の個別名）。
  衝突は §5 の未知→別名既定と既存の衝突ダイアログ（`choose_save_path_with_collision`）で守る（追加の命名変更はしない）。
- **【v0.4-G】既定保存先はディスク上の既存ファイルを避けない**（`_allocate_unique_*` は同一保存バッチ内の
  衝突のみ回避する現挙動を維持）。既存ファイルとの衝突に対する安全網は **§5【v0.4-I】の既定選択規則**が担う。
- hotkey_presets は**触らない**（暫定 07 でグローバル化）。
- **複数 trigger_set を 1 keymap_set に持つ運用は将来課題**（そのとき trigger_set の命名名前空間を再検討）。
- **【v0.3-B】パスの同一性は canonical identity で判定する**。
  **canonical identity の定義**: 対象パスを config_root から解決して絶対パス化し、
  `os.path.normpath` → `os.path.normcase` を適用した文字列。**比較専用**であり、
  **JSON へ保存する表記（config_root 内=相対 / 外=絶対）は §4 のまま変更しない**。
  既に絶対パスで記録済みの参照元も、**比較時に解決して相対表記と照合**する（後方互換）。
  **適用箇所（すべてに適用する）**:
  1. config_root の内外判定（`config_paths.is_within_config_root`）
  2. legacy `settings/` 配下の判定（`config_paths.is_within_legacy_settings`）
  3. trigger_set の既定領域（`user/trigger_sets/`）判定（`config_service._is_default_trigger_set_area`）
  4. 相対化の可否判定（`config_service.to_config_relative_or_absolute`）
  5. §5 の所有判定（`_parent_refs` と現在の上位の照合）
  6. `_parent_refs` の重複排除（絶対で記録済みの参照元と相対表記の同一パスを二重登録しない）
  7. 保存計画の保存先重複検出（現状は区切り文字しか正規化しておらず、ケース違いの `source_path` を
     別ファイル扱いして同一ファイルへ複数 payload を順に書く余地がある）
  **背景**: `os.path.commonpath([p, root]) == root` のような素の文字列一致は、Windows で
  パス文字列の大文字小文字が揺れると config_root 内のパスを「外」と誤判定する。

  `dirty_tracker.trigger_set_source_path` と `trigger_set_dirty` を初期化し、
  `data[INTERNAL_TRIGGER_SET_SOURCE_PATH]` との一致を保つ（変更の入口は `dirty_state` の 2 メソッドのまま）。

## §8 application 層の保存計画（指摘②③反映）

- 現状 `save_runtime_data` は子を無条件書き出しする。これを、**presentation が集めた保存計画（子ごと: 保存/別名パス/スキップ
  ＋依存関係）を application が実行**する形へ変更する。
- **実行契約**:
  - **事前検証**: 全対象の書込み可能性（パス妥当・依存関係の充足）を先に確認する。
  - **依存関係の強制**: パスが変わる子の親（trigger_set / keymap_set）保存を必須化し、スキップを禁止する。
  - **【v0.4-E】唯一の例外＝deferred index（索引更新の先送り）**: 依存確認ダイアログで**明示的に「保存しない」を
    選んだ trigger_set** のみ、パスが変わる子があってもスキップを許可する（現状の事前検証は同条件で
    `SavePlanError` を投げるため、**この例外を通すよう検証契約を更新する** ← 敵対的レビュー high 指摘）。
    許可の条件と不変条件:
    1. 例外は**ユーザーが 4 択で明示選択した場合のみ**（既定・自動判定では発生させない）
    2. 子は選んだ操作どおり書く。**親索引（trigger_set の `sequence_path`）は旧パスのまま**にする
       ＝ 親を新パスへ進めない（従来の「親索引を先に進めない」方針と同方向）
    3. **keymap_set（親の親）と起動設定は従来どおり保存する**。keymap_set が索引する trigger_set のパスは
       変わらないため不整合は生じない
    4. `_parent_refs` は**実際に書いた子**にのみ現在の上位を追加する（書かない trigger_set の参照元は触らない）
    5. presentation は**上位を dirty 化**して未反映を残す（§2【v0.4-E】）。次回保存で索引が追随する
    6. 書込み失敗時は従来どおり旧索引維持（例外の有無で失敗時の扱いを変えない）
  - **粒度の厳守**: 選んだ子だけを書く（trigger_set 保存が全 sequence を巻き込まない）。
  - **失敗時**: 旧索引（keymap_set / trigger_set の子パス参照）を維持できる順序・復元手順にする（完全なトランザクションは
    tkinter/ファイル系では困難なため best-effort。少なくとも親索引を新規パスへ進める前に子の書込み成功を確認する）。
- presentation オーケストレーションで個別 save 経路（`keymap_io` / `trigger_set_io` / `sequence_io`）を子ごとに呼ぶ場合も、
  上記契約（粒度・依存・検証）を満たすよう保存計画駆動にする（idea_06 の共通ドライバをここで実現）。
