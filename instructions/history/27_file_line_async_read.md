## §1 目的 / 背景

file_line のファイル読込を UI スレッドの外で行い、**遅い・応答しないパス（UNC・切断されたドライブ等）でも UI・停止操作・待機の取り消しが止まらない**ようにする。
あわせて読込に**時間の上限**を設け、応答しない読込でシーケンスが無期限に止まらないようにする。**JSON スキーマ変更なし**。

## §2 確定事項（ユーザー 2026-09-27）

- **file_line の読込を UI スレッド外で行う**（idea_38）。**phase 38 で最初に対応**する。
- 含まない: file_line 以外の種別の非同期化（idea_38 の想定スコープ）。
- **読込時間の上限 = 5 秒固定**（設定項目にしない）。5 秒超かかる遅いパスは従来の成功からエラーに変わる（受容）（旧 Q1・§5）
- **放置された読込の重複防止を入れる。対象は上限超過で放置したもののみ**（取り消し・一時停止で捨てた読込は対象外）（旧 Q2・§6）
- **連続実行の読込中の一時停止は、結果を捨てて再開時に読み直す**（戻す履歴は読み直しを含めて 1 段）（旧 Q3・§3.4）
- **完了の受け取りは UI 側の確認タイマー（50 ms ごと）**。ワーカーは Tk を呼ばない（旧 Q4・§3.2）
- **v0.4 の内容（同じ読込キーは同時に 1 本・読込と行の選択の分離・結果を上限より優先）を了承**（2026-09-27）。相乗りは v0.6 で待ち合わせへ改めた（§6.1）
- **読込結果をキャッシュする。実行のたびにサイズと更新日時をワーカーで確認し、変わっていなければキャッシュを使う**（案 A・2026-09-27。
  用途 = ループで同じファイルを繰り返し使う。書き換えは次の実行で反映）（§6.2）

## §3 実行モデル（読込中の保留）

### 3.1 準備・読込・送信の分担

1. file_line の行に達して実行するとき、**準備**（オプションの正規化・カウンター名の検証・コールバックの確認・encoding / out_of_range / 行番号の型の検証・
   カウンター値の取得・パス解決）は UI スレッドで行う。**準備のエラーはその場で実行時エラー**（保留にしない・文言と検査の順は従来どおり）。
2. **読込**（更新の確認〔§6.2〕・ファイルのサイズ確認・読込・復号・行への分割 = I/O を含む部分）をワーカースレッドで行う。ワーカーは**デーモンスレッド**。結果は**行の一覧またはエラー**で、行番号に依らない（キャッシュ §6.2 のため）。
3. **行の選択**（行番号・範囲外の扱い）と**送信**（text と同じ経路・send guard）は UI スレッドで行う。行の決定・エラー文言は従来の `read_file_line` と同じ。
4. 行番号は**読込開始時点**のカウンター値（読込中に他のトリガーがカウンターを変えても反映しない）。
5. 分担の境界: executor は file_line を「準備」と「行の送信」に分けた口を持ち、runner は種別が file_line のとき非同期の経路を使う
   （runner がワーカーの起動と完了の確認を受け持つ）。`execute()` に file_line を渡したときの同期実行は**残さない**
   （既存の同期前提のテスト `tests/test_action_executor_file_line.py`・`tests/test_sequence_runner.py` の file_line を扱う箇所は新しい口に合わせて書き換える）。
   ワーカーの起動は差し替え可能にする（テストで同期実行・停止を再現するため）。

### 3.2 完了の受け取り（UI 側の確認タイマー方式）

- ワーカーは結果（行 / エラー）を置くだけで、**Tk を一切呼ばない**。UI スレッドが **50 ms ごと**に `after` で「完了したか・上限を超えたか」を確認する。
- この確認タイマーが保留の `after_id`（単発 = `PendingStep.after_id` / 連続実行 = `run_to_end_after_id`）になり、**取り消し・一時停止・停止でタイマーも止まる**。
- 各読込に**読込トークン**（読込ごとに一意）を付け、確認時にトークンが今の保留と一致しなければ何もしない（取り消し・一時停止の後の古い結果を使わない）。
  連続実行の世代番号は一時停止で進まないため、それとは別に守る。
- 確認のたびに、**結果が届いていれば上限より優先して使う**（成功・エラー）。届いていなければ、読込開始（単調時計）からの経過が 5 秒以上なら上限超過（§5）。
  上限の判定は最大 50 ms 程度遅れ得る（受容）。

### 3.3 読込中の保留（単発）

- そのステップは**保留中**になる（単発の待機と同じ扱い・`features.md` §4.2.5）:
  - 同じトリガーの押下は無視する（他のトリガーは動く）。
  - 戻す・先頭への対象なら「対象のトリガーが待機中のため操作できません」（文言は流用）。
  - 位置は file_line の行（一覧の「次に実行」も file_line の行）。ステップ開始時の snapshot と、それまでのカウンター操作（file_line より前の system・保留の反映分）を保留に持つ。
- 完了したら同じステップの続きとして:
  - **成功**: 行を送信し、通常アクションの実行後と同じく位置を進めて先行処理（§4.2.2）をする。空の行・`empty` の範囲外は何も送らず成功（従来どおり）。
  - **エラー / 上限超過（§5）/ 放置中（§6）**: 実行時エラー（§5.11.8）。通知し、位置は file_line の行に残る。
  - いずれも**そのステップを戻す履歴に 1 段積む**（従来と同じく、状態が変わっていれば 1 段・`commit_step` は 1 回だけ）。
- **直前のトリガー**は、完了（または取り消し）したときに更新される（押した順ではなく完了した順。受容）。

### 3.4 連続実行

- 読込中は次のステップの予約をしない。完了後は通常アクションの後と同じく間隔を置いて次へ（成功時）/ 停止（エラー・上限超過・放置中）。
- **一時停止**: 読込の結果を捨て、確認タイマーを止める。**ステップの snapshot と途中までのカウンター操作は持ち越す**（待機の一時停止が `_run_to_end_resume` を保持するのと同じ）。
  再開は通常の間隔の後に **file_line の行から読み直し**（捨てた読込がまだ走っていれば §6.1 の待ち合わせ）、読み直しの完了までを**同じ 1 ステップ**として扱う（戻す履歴は 1 段だけ）。
- **停止**（フック停止・キーマップ一時停止・UI 編集の一時停止・その他の停止契機）: 結果を捨て、そのステップを戻す履歴に 1 段積み、位置は file_line の行に残す（待機の停止と同じ）。
- エラー・上限超過で停止するときも**戻す履歴は 1 段だけ**（エラー時の `commit_step` と停止処理で二重に積まない）。
- **読込中に一覧で位置を変えた / シーケンスを編集した**（`features.md` §4.2.3 の張り直しの契機）: 読込の結果を捨て、**通常の間隔の後に新しい位置から連続実行を続ける**
  （待機中に位置を変えたときの既存の挙動と同じ。履歴・保留は §4.2.3 の規則どおり消える）。
- 読込の完了時に、そのトリガーが無い / アクティブなトリガー一覧が読込開始時と違うなら、**送らずに**連続実行を停止する（単発の §3.3 と対称）。

## §4 取り消し（単発）

- 取り消し契機は**単発の待機と同じ**（`features.md` §4.2.5 の列挙: フック停止〔UI 編集中の一時停止を含む〕/ キーマップ一時停止 / キーマップの切替 /
  一覧で位置を変えた / シーケンスの編集・トリガーの削除 / 構成セットの読込等 / 他のトリガーの連続実行の開始）。
- 取り消したら結果を捨て、確認タイマーを止める。位置は file_line の行に残り、そのステップを戻す履歴に 1 段積む（位置変更・編集で履歴を消す規則が優先）。何も送らない。
- ワーカースレッド自体は止められない（OS の読込を中断できない）。**取り消しは「結果を使わない」ことを意味する**。

## §5 読込時間の上限

- 読込開始から **5 秒**（固定・設定項目にしない）以内に結果が届かなければ、**実行時エラー**「ファイルの読込が 5 秒以内に終わりませんでした（ファイル: …）」
  として扱う（§5.11.8 と同じ: 通知・そこで止まる・位置は file_line の行。連続実行は停止）。その後に届いた結果は捨てる。
- 単発・連続実行の両方に掛かる。計時は §3.2 の確認タイマーで行う。連続実行の一時停止をまたいだ読み直しは、読み直しの開始から 5 秒。

## §6 読込の共有・キャッシュ

### 6.1 同じ読込キーの待ち合わせと放置（ワーカーの積み上がり防止）

- 走っている読込を**読込キー = (同じパス, 文字コード)** ごとに登録簿で管理し、**同じ読込キーのワーカーは同時に 1 本まで**とする。
  「同じパス」は解決済みパスを `os.path.normcase(os.path.normpath(...))` で比べる（大文字小文字・区切り文字の揺れを同じとみなす）。
- file_line の読込を始めるとき（および §3.2 の確認タイマーのたびに、まだワーカーを起動していない要求について）、同じ読込キーの登録があれば:
  - **上限超過の印が付いている** → 新しいワーカーを起動せず**即座に実行時エラー**「前回のファイル読込が終わっていません（ファイル: …）」（§5.11.8 の扱い・§3.3 の 1 段）。
  - **印が無い**（取り消し・一時停止で捨てた読込 / 他のトリガーが読込中）→ 新しいワーカーを起動せず**待ち合わせる**。前の読込の**結果は使わない**。
    前の読込が終わって登録が外れたら、自分のワーカーを起動して登録する（§6.2 の更新確認から始めるため、前の読込で更新されたキャッシュがあれば確認だけで済む）。
    複数の要求が待っていれば、先に確認タイマーが来た要求から起動する。上限 5 秒は**この要求の開始（待ち合わせを含む）から**数える。
    **起動の前に上限を判定する**（既に 5 秒以上なら起動せず上限超過のエラーだけ返し、印は付けない）。
  - 登録が無ければワーカーを起動して登録する。
- 登録簿はワーカーと UI スレッドの両方から触るため**1 つのロックで守り**、次を**同じロックの中で**行う:
  - ワーカーの終了（成功・失敗を問わない）: 結果を置き、キャッシュを更新し（§6.2）、登録を外す。
  - 上限超過: その要求のワーカーが**まだ終わっていなければ**上限超過の印を付ける。終わっていれば（結果が届いていれば）§3.2 のとおり結果を使い、印は付けない。
    待ち合わせ中（ワーカー未起動）の要求の上限超過は印を付けない（その要求のエラーだけ）。
  - 読込の開始: 登録の有無と印の確認、待ち合わせまたは起動・登録。
- これにより、走り続けるワーカーは**読込キーごとに 1 本**を超えない（一時停止→再開・取り消し→再押下の繰り返しでも増えない。待ち合わせはスレッドを使わない）。
  各要求は**自分の開始以降に起動したワーカーの結果**だけを使うため、書き換え直後の押下に古い内容を送らない。別の読込キーは影響しない。

### 6.2 読込結果のキャッシュ

- 読込キー（§6.1）ごとに、**行の一覧**と、読んだときの**サイズと更新日時**（`os.stat` の `st_size` / `st_mtime_ns`）を保持する。**起動中だけ**持ち、保存しない。
- 実行のたびに、ワーカーが `os.stat` でサイズと更新日時を取り:
  - キャッシュと**両方一致** → ファイルを読まずキャッシュの行の一覧を結果にする。
  - `os.stat` が失敗（`OSError` / `ValueError`）→ キャッシュを捨てて読む側へ進む（エラー文言は従来の読込の文言になる）。
  - 不一致・キャッシュ無し → 従来どおり読む（1 MB 上限・復号・分割）。成功したらキャッシュを置き換える（保持するサイズと更新日時は**読む前の** `os.stat` の値。
    確認と読込の間に書き換わっても、次の実行で不一致になり読み直すだけで、古い内容を使い続けない）。
  - **エラー**（ファイルが無い・読めない・1 MB 超・復号できない）→ その読込キーのキャッシュを捨てる。
- 更新の確認もワーカーで行うため、キャッシュがあっても実行は §3 の保留を経由する（確認の分だけ最大 50 ms 程度待つ・受容）。上限 5 秒・待ち合わせも同じ。
- **構成セットの読込等**（実行位置を消す契機・`features.md` §4.2.3）でキャッシュを全部捨てる（使わなくなったファイルを持ち続けないため）。
  全破棄では**キャッシュの世代**を進め、ワーカーは起動時の世代を持つ。**世代が違うワーカーの結果はキャッシュへ書かない**（全破棄の後に古い読込が書き戻さない）。
  その結果を待っている要求への受け渡しは通常どおり（全破棄は保留の取り消し契機でもあるため、通常は受け手がいない）。
- キャッシュはワーカーと UI スレッドから触るため、§6.1 の登録簿と**同じロック**で守る。
- 既知の制約（受容）: サイズも更新日時も変わらない書き換え（更新日時を戻す等）は検出しない /
  キャッシュの後に**読取権限だけ**を失っても、`os.stat` が成功し一致すればキャッシュの行を送る（ファイルは開かない）。

## §7 確認事項（ユーザー判断）

なし（Q1〜Q4 は v0.3 で §2 へ移した）。

## §8 受け入れ条件（ドラフト）

1. 応答しない読込（ワーカーの起動を差し替えて止める）の間も UI スレッドが塞がらず、他のトリガー・停止操作が動く（§3・§4）
2. 単発: 読込中の同じトリガーの押下は無視され、完了後に行が送られ、先行処理まで進む（§3.3）
3. 単発: 取り消し契機ごとに結果が捨てられ、位置は file_line の行・戻す履歴に 1 段（§4）
4. 連続実行: 読込中は次を予約せず、完了後に間隔を置いて進む / 一時停止 → すぐ再開しても古い結果が使われず、読み直しを含めて戻す履歴は 1 段 / 停止の扱い（§3.4）
5. 5 秒の上限で実行時エラーになり、後から届いた結果は使われない（§5）
6. 上限超過で放置中の同じ読込キー（パスの表記揺れを含む）は即エラー・別の読込キーは動く・ワーカーの終了で解除（§6）
6a. 捨てた読込がまだ走っている間の再押下・一時停止→再開は新しいワーカーを起動せず待ち合わせ、前の読込の終了後に自分の確認をする（応答しないパスで繰り返してもワーカーは 1 本 / 読込中に書き換えた直後の押下は新しい内容を送る）（§6.1）
6b. 2 回目以降の実行で、サイズ・更新日時が同じならファイルを読まずに同じ行が送られ、書き換え後は次の実行で新しい内容が送られる / エラーでキャッシュが捨てられる / 構成セットの読込等で全部捨てられ、その前に起動した読込の結果は書き戻されない（§6.2）
6c. 上限の直前に結果が届いた場合は結果を使い、上限超過の印も付かない（ワーカーの終了と上限超過が競合しても同じパスが拒否され続けない）（§3.2・§6）
7. 読込中に他のトリガーがカウンターを変えても、行番号は読込開始時点の値（§3.1-4）
8. 読込完了後に戻すと、手前のカウンター操作まで打ち消される / エラー・上限超過でも戻す履歴は 1 段（§3.3・§3.4）
9. 戻す・先頭への対象が読込中なら拒否メッセージ（§3.3）
10. 行の決定・エラー文言は従来の `read_file_line` と同じ（`read_file_line` の既存テストが通る。executor・runner の同期前提テストは新しい口へ書き換え）（§3.1-5）
11. 実機目視: UNC 等の応答しないパスで UI が止まらない / 読込中にアプリを終了しても例外が出ない

## §9 スコープ外（本フェーズでやらない）

- file_line 以外の種別の非同期化 / 読込中の表示（ステータス・一覧の印）/ 上限の設定項目化
- カウンター条件分岐（[idea_37](../backlog/idea_37_counter_conditional_branch.md)）・制御アクション第 2 弾（暫定 26 §13）
