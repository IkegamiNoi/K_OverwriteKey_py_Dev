## §1 目的 / 背景

構成セット（keymap_set）を開き直す手段は現在**ファイル選択ダイアログのみ**で、アプリ内に
「過去に開いたもの」の記録が無い。OS のファイル履歴に頼らず、**アプリ側で履歴を持ち、
ユーザーが分類して残せる**ようにする。

## §2 確定事項（ユーザー 2026-09-21）

- **保存先 = config.json とは別の JSON**。パスは**固定**（config.json にキーを増やさない）。
- **UI = `ttk.Treeview`**（分類＝親 / 履歴＝子）。**`ui_font_delta_pt` に追従させる**。
- **分類は 1 階層のみ**。**表示は名前順で自動整列**。
- **記録の契機 = 読込または保存が成功し、空でないパスが確定したとき**（§4.1）。
- **`recent` の先頭が既に同一パスなら、ファイルへ書き込まない**（§4.2）。
  これにより通常の起動ではディスクに触らず、遅延作成の方針（§1-13）と実質衝突しない。
- **履歴ファイルが読めないときは退避してから作り直す**（§4.4）。**上書きで消さない**。
- **孤児ファイルの棚卸しは、履歴のパスを「参照」と見なさない**（走査範囲・孤児判定を変えない）。
- **分類の操作 = 追加 / リネーム / 削除**。削除時は配下のエントリも消える（確認あり）。分類名の重複は禁止。
- **エントリに任意の表示名（ラベル）は付けない**。**`loaded_at` も持たない**。
- 既定として採用（ユーザー提示 2026-09-21・異議なし）:
  - パス表記は正本 §5.7 に従う（config 配下は相対 / 外は絶対）。**同一性判定も §5.7 準拠**。
  - 直近履歴の上限は **20 件固定**（不在エントリも枠を数える）。分類配下は**上限なし**。
  - 不在ファイルは**自動削除しない**。一覧に残して「見つかりません」と表示する。
  - 「履歴から削除」は**一覧から消すだけ**。実ファイルには触らない。
  - 分類へのコピーは「選択 →『分類へコピー…』ボタンで分類を選ぶ」。**D&D は入れない**。
  - 同一分類内にパスの重複を作らない。別分類に同じパスが入るのは可。
  - 読込はダブルクリック /「読み込む」ボタン。未保存変更の確認は**既存経路へ合流**させ二重化しない。
  - JSON の型不正は正本 §5.1「型不正の共通規則」に従う。

## §3 データモデル（新規 JSON）

**ファイル = `config/keymap_set_history.json`**（`config.json` と同階層。クラス定数
`KEYMAP_SET_HISTORY_RELATIVE_PATH = "keymap_set_history.json"` を `ConfigService` に置く）。

`user/` 配下を避ける理由: `user/` は子ファイルの置き場で、**参照側の走査ディレクトリ**として
指定され得る（§1-11）。なお**候補側**（孤児判定の対象）は固定 4 ディレクトリで設定不可のため、
配置場所にかかわらず履歴ファイルが孤児候補になることはない。

```json
{
  "recent": [
    { "path": "user/keymap_sets/default.json" }
  ],
  "categories": [
    { "name": "仕事用", "entries": [ { "path": "D:/sets/work.json" } ] }
  ]
}
```

- `recent` — 新しい順の配列。**先頭が最新**。最大 20 要素（不在エントリも枠を数える）。
- `categories` — 分類の配列。保存順は問わない（表示時に名前順で整列。§5.2）。
- `path` — 正本 §5.7 のパス保存ルールに従う（config 配下は相対 / 外は絶対。**小文字化しない**）。
- **`version` キーは持たない**（既存の別ファイル JSON〔hotkey presets〕に揃える）。
- **履歴ファイルも遅延作成**。起動時のディレクトリ骨格作成（正本 §5.4・`ensure_split_config_dirs`）の
  対象に**加えない**。最初に記録が発生した時点で作る。
- 型不正（§5.1）:
  - `recent` / `categories` / `entries` が list でなければ空扱い。
  - 要素が dict でなければ除去。`path` が非文字列 / trim して空なら**要素ごと除去**。
  - 分類の `name` が非文字列 / trim して空なら**分類ごと除去**。重複していたら**先に現れた方を残す**。
  - `recent` が 21 件以上あったら**読込時に先頭 20 件へ切り詰める**。
- **「ファイルが無い」と「あるが読めない」は区別する**（§4.4）。型不正の除去は**読めた**場合の話であり、
  読めなかった場合に空扱いで上書きしてはならない。

## §4 記録・永続化の規則

### §4.1 記録する契機

**構成セットの読込または保存が成功し、その結果として `keymap_set_path` に空でないパスが
確定したとき**、その**実保存先（正規化後の値）**を記録する。判定と呼び出しは **presentation 側**で行う。

| 呼び出し点 | 記録 |
|---|---|
| `keymap_set_io.py:545` 読込成功（メニュー「読込（構成セット）…」） | する |
| `keymap_set_io.py:651` 起動セット指定の読込成功 | する |
| `startup_io.py:30` 起動時の自動読込成功 | する |
| 履歴ダイアログからの読込成功 | する |
| `keymap_set_io.py:132` **保存成功**（別名保存 / 新規作成後の初回保存 / 上書き保存） | する |
| `app.py:76` の初期代入 / `new_config` / `import_config` / `restore_default` | **しない**（明示的除外） |

- **保存の種別で分岐しない**。`normalize_keymap_set_save_path` が保存先を書き換えるため
  （§1-2）、「上書きだからパスは同じ」とは限らない。**成功した保存の実保存先**を常に渡す。
- **同一パスの再読込・上書き保存でも呼んでよい**。§4.2-2 の先頭一致で自動的に no-op になる。
- **未保存確認（`confirm_save_if_dirty`）の中で保存が走った場合も、その保存の成功として記録される**
  （§1-3）。これは正しい挙動（そのファイルを開いている状態になったため）。

**application の下位ローダー（`load_runtime_data_from_keymap_set_path`）には記録を入れない。**
同関数はテストから約 20 箇所直接呼ばれており（§1-4）、副作用を足すとテスト実行で履歴ファイルが
書かれる。また phase 26 と同じ分担（**presentation は事実 / application は規則**）に揃う。

**記録は差し替え可能な単一の口に閉じる。** presentation 側の入口を 1 メソッド
（例 `app.keymap_set_history_io.record(path)`）に限定する。§1-6 のとおり既存 characterization
テストが `config_root` に `os.getcwd()` を入れるため、**テスト側で 1 箇所を patch すれば
リポジトリを汚さずに済む**形にしておく必要がある。

### §4.2 積み方

1. 履歴を**ディスクから読む**（§4.4 の結果が「書き込み禁止」なら以降を行わない）。
2. 保存表記へ正規化した `path` を作る（§5.7。`ConfigService` / `ConfigPaths` の責務）。
3. **`recent` の先頭が既に同一パスなら、何もしない**（書き込まない）。
   判定は**永続化済みの内容**に対して行う（メモリだけ先行更新しない）。
4. そうでなければ `recent` から**同一パス**の要素を**すべて**取り除く。
5. 先頭へ新しい要素を挿入する。
6. 21 件目以降を末尾から捨てる（**不在エントリも枠を数える**）。
7. ファイルへ書き出す（`json_repository.save_json` の原子的置換）。

**同一性判定は正本 §5.7 に従う**（解決 → `normpath` → `normcase` の比較専用表記）。
**シンボリックリンクは辿らない**（§5.8.9 の方針に合わせる）。

手順 3 により、起動エントリを指定済みで前回もそれを使っていた**通常の起動ではディスクに触らない**。
履歴が空のとき・前回別のセットを開いていたときだけ書き込みが発生する（遅延作成。§3）。

### §4.3 永続化の失敗

- **永続化に成功してから UI を確定する。** 分類の追加・リネーム・削除、エントリの削除・コピーは
  **書き込みが成功した場合のみ**一覧へ反映する。失敗したら変更を取り消し、理由を表示する
  （メモリだけ更新して見かけ上成功させない）。
- 履歴の読み書きの失敗で**構成セットの読込・保存を巻き戻さない**。書き込み失敗はステータスバーへ
  通知するにとどめ、例外は握りつぶさず理由を残す。
- **既存経路の通知を上書きしない**（例: `set_startup_keymap_set` は起動設定の保存失敗時に
  flash を出して return する〔`keymap_set_io.py:661-663`〕。この通知が優先で、履歴の失敗通知は出さない）。

### §4.4 履歴ファイルが読めないとき

| 状態 | 扱い |
|---|---|
| ファイルが**無い** | 空の履歴として扱い、**通常どおり書き込む**（遅延作成） |
| **あるが読めない**（壊れた JSON / 権限エラー / 型が dict でない） | **退避してから空で作り直す** |

退避は `config/keymap_set_history.broken.json` へのリネーム。既に存在する場合は
`keymap_set_history.broken2.json`、`broken3.json` … と連番を増やす。
**連番が 5 に達したら退避せず、そのセッションは書き込みを行わない**（無制限に増やさない）。

- **退避に失敗したら書き込まない**。そのセッションは履歴を**読み取り専用**として扱い、
  履歴ダイアログに「履歴ファイルを読み込めませんでした」と表示して編集操作を無効にする。
- `config/quarantine/` は**使わない**。隔離ルートは棚卸しの所有領域で、中身は
  実行単位ディレクトリ + `manifest.json` を前提とし（§1-12）、正本 §5.4 は
  「隔離を 1 度も実行していない環境に作らない」と規定しているため。

## §5 UI（履歴ダイアログ）

### §5.1 入口

ファイルメニューに **「履歴から読み込む…」** を追加する。位置は
**「読込（構成セット）…」の直後**（`views/menu_bar.py:12` の次行）。アクセラレータは付けない。

### §5.2 ダイアログ

既存作法に従う（`Toplevel` / `suspend_hook_for_dialog` / Escape で閉じる /
`protocol(WM_DELETE_WINDOW)` / `modal.grab_modal()`）。手本 = `dialogs/orphan_sweep_dialog.py`。

一覧は **`ttk.Treeview`（2 列: 名前 / パス）**。

- ルート直下に固定ノード **「直近（最大 20 件）」** と、**各分類のノード**を並べる。
- 分類ノードは**名前の昇順**（比較は `casefold()`。同値なら保存順）。
- 子ノード = 履歴エントリ。名前列 = ファイル名（拡張子なし）、パス列 = 保存表記のパス。
- 不在ファイルは名前列へ **「（見つかりません）」** を付す。
- 既定で「直近」は展開、分類は折り畳み。
- **`ui_font_delta_pt` に追従させる**（`ttk.Style` へフォントを指定する。Treeview は
  他ウィジェットの指定が効かないため別途必要）。
- **リポジトリ初の `ttk.Treeview`**（§1-9）。`Listbox` 前提のテスト作法が使えないため、
  `tests_ui` では `tree.get_children()` / `tree.item()` / `tree.selection_set()` で操作する。

### §5.3 ボタン

| ボタン | 対象 | 動作 |
|---|---|---|
| 読み込む | エントリ 1 件 | 未保存確認 → 読込を実行し、**成功したときだけ閉じる**（ダブルクリックも同じ） |
| 履歴から削除 | エントリ 1 件 | **選択したノードのみ**を除去（実ファイルは消さない）。確認あり |
| 分類へコピー… | **「直近」配下の**エントリ 1 件 | コピー先の分類を選んで追加（分類 → 分類のコピーは不可。§10） |
| ＋分類を追加 | — | 分類名を入力して作成 |
| 分類名を変更 | 分類 1 件 | リネーム |
| 分類を削除 | 分類 1 件 | **配下ごと削除**。確認あり |
| 閉じる | — | ダイアログを閉じる（保存は伴わない。編集は都度永続化済み） |

選択の種類（エントリ / 分類 / 未選択）に応じてボタンの有効・無効を切り替える。
§4.4 で読み取り専用になっている場合は、読込以外を無効にする。

## §6 操作の規定

- **書き込みは即時**。分類・エントリの編集は**操作ごとにその場で**書き出し、
  **成功した場合のみ**一覧へ反映する（§4.3）。「閉じるときにまとめて書く」方式は採らない。
- **読込**: 未保存変更の確認は既存の `confirm_save_if_dirty` へ合流させる（二重化しない）。
  - 確認でキャンセルされた場合・読込に失敗した場合は、**ダイアログを開いたまま**にし、
    そのエントリを履歴から自動削除しない。
  - **未保存確認の中で保存が走ると履歴が更新され得る**（§1-3）。したがってダイアログは
    **自分が持つ表示内容を正としない**。読込・編集のたびに**永続化済みの履歴を読み直して再描画する**
    （選択と展開状態は可能な範囲で復元する）。
- **同一パスが「直近」と分類の両方にある場合**: 「履歴から削除」は**選択したノードだけ**を消す。
- **分類へコピー**: コピー先に同一パス（§4.2 の比較）が既にあれば何もしない（メッセージのみ）。
  コピーしても「直近」側は消えない。
- **分類の追加 / リネーム**: 空名・空白のみは不可。既存分類と**同名は不可**
  （trim 後の完全一致で判定する。表示名なので大文字小文字は区別する）。
- **不在ファイル**: 存在確認は**再描画のたびに行う**（開きっぱなしの間に確認し直さない、という
  規定は置かない。再描画の契機は上記のとおり読込・編集時）。

## §8 受け入れ条件（ドラフト）

1. メニュー「ファイル」に「履歴から読み込む…」があり、「読込（構成セット）…」の直後に並ぶ（§5.1）。
2. **読込 4 経路**（メニュー読込 / 起動セット指定 / 起動時の自動読込 / 履歴ダイアログ）と
   **保存成功**で `recent` の先頭に積まれ、**同一パスは 1 件に統合**される（§4.1 / §4.2）。
3. **`app.py:76` の初期代入・新規作成・Import・例の復元では記録されない**（§4.1）。
4. **記録されるのは正規化後の実保存先**である。`normalize_keymap_set_save_path` が保存先を
   書き換えるケースでも、履歴のパスが実際の保存先と一致する（§4.1 / §1-2）。
5. **保存計画がキャンセルされた場合・保存が途中で失敗した場合は記録されない**（§4.1・成功時のみ）。
6. **`recent` の先頭が既に同一パスのとき、`save_json` が呼ばれない**（mtime 不変だけでなく
   呼び出し自体が無いことで確認する）。起動エントリを指定済みで前回もそれを使っていた起動では
   **履歴ファイルが書かれない**（§4.2）。
7. 履歴が空の状態で記録が起きると**そのとき初めてファイルが作られる**（遅延作成。§3）。
8. `recent` は **21 件目で最古が落ちる**。不在エントリも枠を数える（§4.2）。
9. **失敗した起動読込そのものでは記録されない**（同一セッション内の後続の読込・保存は記録される）（§4.1）。
10. **履歴ファイルが壊れているとき、元のバイト列が `*.broken*.json` として保全される**。
    退避に失敗した場合は**書き込みが行われない**（§4.4）。
11. 連番が 5 に達した状態では退避も書き込みも行わず、読み取り専用として動作する（§4.4）。
12. **永続化に失敗した編集操作が一覧へ反映されない**（分類追加・削除・コピー・エントリ削除。§4.3）。
13. 分類の追加・リネーム・削除ができ、削除で配下のエントリも消える。**同名の分類は作れない**（§6）。
14. 分類は**名前順で表示**される（§5.2）。
15. 「直近」のエントリを分類へコピーでき、「直近」側は残る。**同一分類内に重複を作らない**（§6）。
16. 同一パスが「直近」と分類の両方にあるとき、「履歴から削除」は**選択した側だけ**を消す（§6）。
17. 「履歴から削除」で一覧から消えるが、**実ファイルは残っている**（§6）。
18. 不在ファイルのエントリが「（見つかりません）」と表示され、**自動削除されない**（§6）。
19. **読込に失敗した場合・未保存確認でキャンセルした場合、ダイアログが開いたまま**で、
    そのエントリが残る。**成功したときだけ閉じる**（§5.3 / §6）。
20. **未保存確認の中で保存が走って履歴が更新された場合、ダイアログの表示がその結果へ追従する**
    （再描画で永続化済みの内容を読み直す）（§6）。
21. 履歴 JSON の型不正（`recent` が list でない / `path` が非文字列 / 分類名が空 /
    `recent` が 21 件以上）を入れても例外にならず、§3 の規則どおり処理される（§3）。
22. 記録されるパスが**§5.7 の保存表記**（config 配下は相対 / 外は絶対・小文字化しない）である（§4.2）。
23. **ダイアログ作法の回帰**: Escape / ✕ / 読込ボタンのいずれで閉じても grab が親へ戻り、
    hook の suspend / resume が対称であること（§5.2）。
24. **孤児棚卸しの候補側の分類結果（`ORPHAN_*`）が本機能の前後で変わらない**（§2・§1-11）。
25. **履歴自体の永続化処理では `config/config.json` を書かない**（§3。未保存確認から派生する
    keymap_set 保存が config.json を書くのは既存挙動であり、本条件の対象外）。
26. 既存テスト（`tests` / `tests_ui` / smoke）が緑のまま。ただし以下は**本フェーズで更新する**
    （§9 の作業表）: `INTERNAL_MODULE_NAMES` / `DIALOG_FILES`。
27. **既存の characterization テスト（`tests_ui/test_config_io_characterization*.py`）が
    リポジトリルートへ履歴ファイルを生成しない**（§4.1 の単一の口を patch して担保する）。
