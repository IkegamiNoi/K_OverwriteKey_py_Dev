## §1 目的 / 背景

IME が ON のままキーの取得をすると、Tk にはどのキーも「IME が処理中のキー」（`VK_PROCESSKEY`・名前 `??`）で届き、押したキーを取得できない。
**取得の間だけアプリ自身の IME を OFF にし、終わったら元へ戻す**。あわせて、`??` を記録しない扱いを全入口に揃える。

## §2 確定事項（ユーザー 2026-10-16）

* **方式 = 開閉を記録して OFF・終了で復元**（入力コンテキストを外す方式〔`ImmAssociateContext`〕は採らない）
* **`??` は全入口で記録せず、取得を続ける**
* 組み込み方: **取得の寿命だけを持つ小さな共通部品**を作り、各入口の既存の開始・停止の関数から呼ぶ。キーの解釈（修飾キー・Esc の意味・KeyRelease 等）は各入口に残す（取得処理の丸ごとの共通化はしない。8 入口の差が大きく過剰な共通化になるため）
* **API = 自スレッド向けの `ImmGetContext` / `ImmGetOpenStatus` / `ImmSetOpenStatus`**（`WM_IME_CONTROL` は使わない・§4.1）
* **`??` の案内の文言 = 「このキーは取得できません。別のキーを押してください。（Escでキャンセル）」**（§5）
* **取得中に手で ON にされても OFF にし直さない**（§5 の受容）
* **取得中のフック再開（#1・#7）は本フェーズのスコープ外**。別 idea として起票する（§4.3）

## §3 取得の期間

* #1〜#7: **各入口の既存の開始の関数で始まり、既存の停止の関数で終わる**（§1 の表）。経路（取得できた・Esc・ボタン・種類 / 対象の切替・排他・右クリック・閉じる）を個別に列挙せず、停止の関数の中で終了を呼ぶことで全経路を覆う。窓の破棄で停止の関数を通らない入口は §4.2 の `<Destroy>` で覆う
* #8: 画面の枠の編集の窓を**開いている間**（開いたら開始・`<Destroy>` で終了）
* 期間そのものは変えない

## §4 取得中の IME

### 4.1 対象と API

* 対象 = **アプリ自身の UI スレッドの入力コンテキスト**（Tk の窓はすべて共有・§1 probe）。HWND は取得を受ける窓の `winfo_id()` を使う（どの Tk の HWND でも同じ結果）
* API = **`ImmGetContext` → `ImmGetOpenStatus` / `ImmSetOpenStatus` → `ImmReleaseContext`**（自スレッドの直接呼び出し・時間制限不要）。送信用の `WM_IME_CONTROL`（別プロセス向け）は使わない
  ※§2 の「開閉を記録して戻す」方式は変えず、自アプリ向けに直接の API を使う（deep-reviewer M7）

### 4.2 開始と終了

* **開始**: 取得中でない入口の開始のたびに開閉を問い合わせ、**ON なら OFF にする**。OFF にしたら「アプリが OFF にした」印を立てる（立っていれば立てたまま）
* **開始の冪等**: 取得中の入口の開始が終了を挟まずに再び呼ばれたとき（#7 の編集中の別の元キーのクリック `keyboard_window.py:442-470`）は**何もしない**（数を増やさず、開閉の問い合わせも OFF もしない。手で ON にした変換中に OFF にして確定した文字を記録しないため）
* **終了（冪等）**: 取得中の入口の終了だけが数を減らす（取得中でない・終了済みの入口の終了は何もせず、印にも触らない）。**数が 0 になったときだけ**、印が立っていて、その時点で OFF なら ON へ戻し、印を下ろす（取得中にユーザーが手で ON にしていれば触らない）。**数が残る終了では印に触らない**。戻すのは即時
* **窓の破棄**: 取得の部品は窓の `<Destroy>` で終了を呼ぶ。トップレベルの `<Destroy>` は子の破棄でも発火するため **`event.widget is window` で絞る**（既存の例 `hook_controller.py:57-64`）
* **アプリの終了**: 戻さない（入力コンテキストはアプリのスレッドのもので、終了とともに消える。他のアプリへは影響しない）

### 4.3 重なり

* 開閉の状態は共有の入力コンテキストが持つため、取得が重なる（#7・#8 の長く続く取得の間に他の入口の取得 等）ときは §4.2 の数と印で扱う。2 番目以降の開始も ON なら OFF にする（例: #7 の編集中にラベル欄で手で ON にしてから #3 を始めても取れる）
* **受容**: #7・#8 の取得の間は、アプリの他の入力欄（ラベル欄・名前欄 等）も IME が OFF で始まる（手で ON にはできる）。#8 の操作パネルの `ttk.Spinbox`（数字 1〜9・`grid_editor_panel.py:112`）は OFF で支障ない
* 送信時の IME の制御（§7.7・`ImeController`）とは状態を分ける。取得の開始で全入口ともフックを止めるが、**#1（メイン窓）と #7（非モーダル）の取得中はフック開始ボタンで再開できる**（`hook_frame.py:21` → `toggle_hook`・`start_hook` は停止の数を見ない `hook_controller.py:120-145`。Codex 敵対的レビュー指摘・メイン実測）。再開した場合、自窓へ文字の送信が来ると送信側が同じ入力コンテキストを問い合わせ・切替え得る（送信側は自分が OFF にしたときだけ戻すため、取得側が OFF にした後なら何もしない）。**この相互作用は受容**とし、取得中のフック再開そのもの（IME と無関係な既存の穴）は別 idea で扱う（§7 確認事項 4）
* **受容（実機確認の対象）**: 他の入力欄で手で ON にして変換中のまま別の入口の取得を始めると、開始の OFF で変換中の文字が確定し、その確定から作られた KeyPress が取得され得る（Tk のイベントの順序に依存・未実測）

### 4.4 失敗

* 入力コンテキストが取れない・API が失敗したときは **IME に触らず取得はそのまま続ける**（通知しない・ログのみ）。Windows 以外では何もしない

## §5 `??` の扱い（全入口で統一）

* 名前が `??` のキーは**記録せず、取得を続ける**（Esc 待ちのまま）。判定は `presentation/tk_keys.py` の関数 1 つに寄せる（各入口で `== "??"` を書かない）
* **案内の欄がある入口（#2・#3・#4・#6）は理由を出す**。欄のない入口（#1・#5・#7・#8）に欄を新設しない
* 案内の文言: IME は自動で OFF になるため、「IME が ON の場合は OFF に」を外し **「このキーは取得できません。別のキーを押してください。（Escでキャンセル）」** に改める（`hook_button_texts.UNKNOWN_CAPTURE_KEY_HINT_TEXT`・§7 確認事項 2）
* **挙動の変更**: #1 は `??` でエラーのダイアログ（見込み）→ 黙って無視になる。#2・#5〜#8 は `??` の記録 → 無視になる
* **受容**: 取得中にユーザーが手で IME を ON にすると、以降の打鍵は `??` で無視される。変換が確定すると確定した文字から作られた KeyPress（`??` ではない）が記録され得る（`features.md:481` と同じ受容）。Esc → 取り直しで回避する

## §6 構成

* **infrastructure**: 自アプリの IME の開閉を読む・変える**状態なしの薄い口**を新設する（`ime_control.py` は送信用で既に 338 行のため別モジュール。例: `infrastructure/own_ime_status.py` に `get_open(hwnd) -> bool | None` / `set_open(hwnd, is_open) -> bool`。Windows 以外・失敗は `None` / `False`）
* **presentation**: 取得の寿命の部品を新設（例: `presentation/key_capture_ime.py`。複数の入口が使う presentation 内の共有）
  * 数と印（§4.2）は**この部品が持つ**（取得は UI スレッドだけで完結するためロック不要）。開始 / 終了 / 窓の `<Destroy>` の連動
  * infrastructure の口を**直接 import** する（前例: `keymap_panel_controller.py:13`・`grid_overlay_window.py:6`）。テストでは口を差し替えられるようにする
* 各入口は既存の開始・停止の関数からこの部品を呼ぶ（入口の構造は変えない）。`??` の判定は `tk_keys.py`
* application は経由しない（自アプリの IME は UI の都合で、業務の状態ではない）。JSON スキーマ不変

## §8 受け入れ条件（ドラフト）

1. 8 入口のいずれも、IME ON の状態で取得を始めると押したキーがそのまま取得できる（§3・§4）
2. 取得の終了（停止の関数のすべての経路・窓の破棄）で IME が元の ON に戻る。元が OFF なら OFF のまま。取得中に手で ON にしたら終了で触らない（§4.2）
3. 取得の重なりで、最後の取得が終わるまで OFF・終わったら戻る。2 番目の入口の開始でも ON なら OFF にする。取得中の入口の再開始・重複した終了・数が残る終了は印と開閉を変えない（§4.2・§4.3）
4. 8 入口のいずれも `??` を記録しない。#2・#3・#4・#6 は案内を出す（§5）
5. IME の API が使えない・失敗しても取得は従来どおり動く（§4.4）
6. 自動テスト: infrastructure の口（API の偽物）・presentation の部品（口の差し替えで数・印・冪等・重なりの状態遷移・`<Destroy>` の絞り込み）・各入口の UI テスト（開始 / 停止で部品が呼ばれる・`??` の無視）。**実機で IME を ON にした取得はユーザーの目視**で確認する（#7 の編集中の別の元キーのクリック・他の欄で変換中に取得を始める場合を含む）
