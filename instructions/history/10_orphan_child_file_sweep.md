## §1 目的 / 背景

**どの keymap_set からも参照されていない子ファイル（孤児）を検出し、可逆な「隔離」を経て削除できるようにする。**

phase 10（正本 `data_schema.md` §5.8.1）で作った「参照元の掃除」は**現在の構成セットが参照している子だけ**を
検査対象とし、**孤児判定は原理的に成立しない**として警告表示にとどめている。本フェーズは
**逆方向検査（上位 → 子の索引走査）**を新設してこの制約を部分的に解く。

**対象レイヤ**: application（走査・参照集合の構築・孤児判定・隔離 / 復元 / 削除の実行）+
presentation（メニュー・確認 UI・走査ディレクトリ設定）。
**スキーマ変更**: あり（`config/config.json` に走査ディレクトリ設定のキーを**追加**。既存キーの削除・意味変更はしない）。

## §2 確定事項（ユーザー 2026-09-06）

- **到達範囲 = 検出 + 隔離 + 復元 + 隔離済みの削除**。削除は**隔離ディレクトリ内のファイルのみ**を対象とする
  （元の場所から直接削除はしない）。
- **走査範囲（参照している側）= 既定ディレクトリ + ユーザー指定ディレクトリ**。
  - ユーザー指定ディレクトリは**設定として記録し、次回以降の再指定を不要**にする。
  - **指定ディレクトリが見つからないときはスキップ**し、**走査完了後に「見つからなかった」旨をパスとともに表示**する。
- **ユーザー指定ディレクトリは「参照している側（keymap_set を探す場所）」にのみ使う**。
  **孤児候補になるのは config 配下の既定ディレクトリにあるファイルだけ**。
- **孤児候補の種別 = keymap / trigger_set / sequence + 個別 hotkey_presets の 4 種**。
  **`hotkey_presets_individual` が false（OFF）でも `hotkey_presets_path` は「参照あり」として数える**。
- **復元機能を本フェーズに含める**（隔離マニフェストの記録は必須）。

**§4-A〜F の確定（同日・v0.3。根拠と経緯は §4）**

- **A = 読めなかった参照側があっても、警告を出したうえで隔離の実行を許す**（§3-5）。
- **B = 復元 / 削除は隔離の実行単位ごと**（§3-7 / §3-8）。
- **C = 設定メニューに 2 項目**。走査ディレクトリの追加 / 削除は棚卸しダイアログ内（§3-9 / §3-10）。
- **D = 隔離ルートは `<config_root>/quarantine/`**（`user/` の外・§3-6）。
- **E = 候補側に種別の形状検証を入れる**（§3-4）。
- **F = フェーズを分割しない**。ただし phase.md のタスク分割で
  **「検出までを先に green にする」段取りを明記**し、隔離 / 復元 / 削除はその後のタスクに積む。

## §3 設計本文

### §3-1 用語と全体フロー

- **参照側** = keymap_set ファイル、およびそこから辿った trigger_set ファイル。
- **参照集合** = 参照側から辿れた子ファイルパスの集合（比較は canonical 表記で行う）。
- **候補側** = 孤児候補になり得るファイル（§3-4 の既定ディレクトリにあるもの）。
- **孤児候補** = 候補側にあり、参照集合にも保護対象にも含まれないファイル。

フローは 3 つの独立した操作に分ける。

1. **棚卸し（検出）**: 走査 → 参照集合の構築 → 孤児候補の判定 → 結果を一覧提示 →（実行を選べば）**隔離**。
2. **復元**: 隔離マニフェストを読み、元の場所へ戻す。
3. **削除**: 隔離ディレクトリ内のファイルを削除する（不可逆）。

### §3-2 走査範囲（参照側）

参照側として読むのは次の 4 つ。いずれも**読み出し専用**で、走査は**書き込みを一切行わない**。

1. **既定ディレクトリ** = `<config_root>/user/keymap_sets/` 直下の `*.json`（**非再帰**）。
2. **起動エントリが指す keymap_set**（`<config_root>/config.json` の keymap_set パス）。
   既定ディレクトリの外にあっても含める。
3. **現在開いている keymap_set**（`app.keymap_set_path`）。**必須**（H1）。
   `load_keymap_set_from` は `config.json` を書かないため、2 では代替できない。
   既定外・config 外にあっても**ファイルとして読む**（コストはほぼゼロで、純粋に安全側にしか働かない）。
4. **ユーザー指定ディレクトリ**（§3-10）の直下の `*.json`（**非再帰**）。

- 走査は**シンボリックリンクを辿らない**。
- 読取不可・JSON として解析できないファイルは **「読めなかった参照側」として記録**して継続する（§3-5-2）。
- **keymap_set として解釈できない JSON は「対象外」として扱い、参照集合に寄与させない**。
  **判定基準**: §3-3 が挙げる子キー（`trigger_set_path` / `keymaps` / `active_keymap_path` /
  `hotkey_presets_path`）が **1 つも存在しない**こと（**キーの有無で判定し、値の空・非空では判定しない**。M2）。
  **対象外と判定した JSON は、件数だけを結果に出す**（無音の誤判定経路を作らない。M2）。

### §3-3 参照集合の構築（2 段辿り）

参照側 1 件ごとに次のキーからパスを取り出す。取り出した値は
**`resolve_config_path` で解決 → `canonical_path` で比較用に正規化**して集合へ入れる
（**canonical 値は集合の照合にだけ使い、表示・保存には stored 表記を使う**。正本 §5.7）。

- keymap_set から: `trigger_set_path` / `keymaps[].path`（**要素が素の文字列の旧形式も受ける**）/
  `active_keymap_path` / `hotkey_presets_path`（**`hotkey_presets_individual` の値に関わらず参照ありとする**。§2）。
- 上で得た **trigger_set をさらに読み**、`triggers[].sequence_path` を集合へ入れる（2 段目）。
- **グローバルプリセット**: `<config_root>/config.json` の `hotkey_presets_path` も参照集合へ入れる。
- **`external_keyboard_layouts[].path` も参照集合へ入れる**（L2）。既定の登録先は候補側と交差しないが、
  ユーザーが候補側ディレクトリのファイルを登録することは阻止されていないため、**入れる方が安全側**。
- **このキーだけは「両基準で解決した superset」を入れる**（Codex Medium）。既存実装は
  **読み込み時に `config_root` 基準で解決**したうえで（`split_loading.py:526`）、
  **runtime へは `dirname(config_root)` 基準の相対表記で保持**し（`:529-531`）、
  **保存はその runtime 値をそのまま書く**（`split_payloads.py:342`）。
  そのため**ファイル内の値がどちらの基準かは一意に決まらない**。片方だけで解決すると
  候補側に置かれたレイアウトへの参照を取りこぼし、**その子を孤児と誤判定する**。
  → **`config_root` 基準と `dirname(config_root)` 基準の両方で解決し、両方を参照集合へ入れる**
  （余分に保護されるだけで、誤って隔離する方向へは働かない）。
  **既存の非対称そのものの是正は本フェーズのスコープ外**
  （[idea_13](../backlog/idea_13_external_layout_path_base_asymmetry.md) として分離）。
- **相対パスの解決基準は config ルート**（正本 §5.7。上記 1 キーの例外を除く）。
  **config 外を指す参照は集合に入れてよい**（候補側が config 配下だけなので実害はなく、集合に入れる方が安全側）。
- **`hotkey_presets_path` を無条件に参照ありとするのは意図的な superset**（M7）。
  正本 §5.5 / §5.10.1 の移行規則（フラグキーを持たない keymap_set は `hotkey_presets_path` を引き継がない）は
  **読み込み時の適用規則**であり、本節は**孤児判定を安全側に倒すための別規定**である。昇格時にこの旨を明記する。

### §3-4 孤児候補の判定（候補側の範囲と保護対象）

候補側は **config 配下の既定ディレクトリ直下の `*.json`**（**非再帰**）に限る。

| 種別 | 候補側ディレクトリ |
|---|---|
| keymap | `<config_root>/user/keymaps/` |
| trigger_set | `<config_root>/user/trigger_sets/` |
| sequence | `<config_root>/user/sequences/` |
| hotkey_presets（個別） | `<config_root>/user/hotkey_presets/`（**直下のみ**） |

- **`user/hotkey_presets/global/` は候補側から除外**する（グローバル専用の予約ディレクトリ。正本 §5.10）。
- **隔離ルートは `<config_root>/quarantine/`**（§4-D 確定）で `user/` の外にあるため、
  **候補側 4 ディレクトリと構造的に交差しない**（隔離物を再び候補として拾う経路が原理的に無い・L6）。
  隔離ルートは参照側の走査対象にも含めない。
- **候補側に種別の形状検証を行う**（§4-E 確定・M3）。トップレベルが `dict` であり、
  **ディレクトリに対応する種別のキーを正しい型で持つ**ことを条件とし、
  通らないものは `ORPHAN_EXCLUDED` として**隔離しない**（件数は結果に出す）。
  基準は**既存の読み手が要求するキーに合わせる**:

  | 種別 | 必須キー（トップレベル） | 読み手 |
  |---|---|---|
  | keymap | `mappings`（`dict`） | `split_loading.py:411-413` |
  | trigger_set | `triggers`（`list`） | `split_loading.py:458-460` |
  | sequence | `actions`（`list`） | `split_payloads.py:399-409` |
  | hotkey_presets（個別） | `hotkey_presets`（`list`） | `split_loading.py:84-87` |

  壊れた子ファイルは真に孤児でも隔離されないが、**誤隔離を避ける安全側へ倒す**。
- **保護対象**（孤児候補にしない。phase 10 §5.8.1 の保護対象と同じ考え方）。
  **application 側は「保護対象パスの集合」を引数で受け取る**（表示都合と同様に、
  presentation / controller 側が集めて渡す。M4 / §3-11）。集合に入れるのは:
  - **`app.keymap_set_path`**（runtime には keymap_set の source_path が無い）
  - **runtime の子 source_path 3 種**（keymap / trigger_set / sequence）
  - **`runtime["hotkey_presets_path"]`**（個別プリセット。source_path ではなく通常キーで、
    条件付きで載る・`split_loading.py:290`）
  - いずれも**実在しなくても保護**し、**config 外にあっても保護**する。
- **未保存の変更がある構成セット**を開いている場合は、**棚卸しの前に保存を確認**する。
  未保存だと現在の参照が走査結果へ反映されず、**使用中の子を孤児と誤判定し得る**ため。
  **既存の `KeymapSetIo.confirm_save_if_dirty` は再利用しない**（「保存しない = 続行」で意味が逆・H5）。
  本フェーズは **「保存する / 中止する」の 2 択**とし、**保存しない選択は棚卸しごと中止**する。
- 判定結果は **判定名**で表現し、**分岐は判定名で行い表示文言で分岐しない**（正本 §5.8.4 / §5.8.1 の規律）。
  判定名は 4 つ:
  - `ORPHAN_CANDIDATE` — 孤児候補（隔離の対象）
  - `ORPHAN_REFERENCED` — 参照集合に含まれる
  - `ORPHAN_PROTECTED` — 保護対象
  - `ORPHAN_EXCLUDED` — 候補側ディレクトリにあるが対象外
    （`user/hotkey_presets/global/` 配下 / 隔離ディレクトリ配下 / §4-E を採る場合の形状検証で落ちたもの）

### §3-5 走査の不完全性の扱い

次の 4 つは**握りつぶさず、結果に必ず出す**。

1. **見つからなかった指定ディレクトリ**: スキップし、**完了後にパスとともに一覧表示**（§2 確定）。
   設定からは**自動で消さない**（一時的に外付けドライブが未接続の場合があるため）。
2. **読めなかった参照側ファイル**（keymap_set / trigger_set の読取・解析失敗）: パスと理由を一覧表示する。
   **その参照側が指していた子は参照集合に入らない**ため、孤児候補が過大になり得る。
3. **対象外と判定した JSON の件数**（§3-2 最終項）。
4. **走査範囲外の keymap_set から参照され得る**旨は、**孤児候補の一覧に必ず併記**する（§3-12-1）。

**2 が 1 件以上あっても隔離の実行は許す**（§4-A 確定）。ただし代償として:

- **孤児候補の一覧の先頭に警告を置く**（MUST）。内容は「読めなかった参照側が N 件あり、
  **それらが参照していた子を孤児と誤判定している可能性がある**」旨と、該当ファイルのパスと理由。
- **ユーザーの選択は「このまま隔離を実行する / キャンセル」の 2 択**とする。
  **読めなかった親を確認するための UI は作らない**（パスを提示するだけで、確認は
  エクスプローラ等でユーザーが行う）。
- 孤児候補が 0 件でも、この警告は通知へ含める（§3-9）。
- **隔離した実行単位は、走査が不完全だったかに関わらず復元も削除もできる**
  （走査の完全性で削除可否を分けない。理由と残存リスクは §4-A / §3-12-5）。

### §3-6 隔離

- **隔離ルート = `<config_root>/quarantine/`**（§4-D 確定。`user/` の外）。
  **隔離先** = `<config_root>/quarantine/<YYYYMMDD_HHMMSS>/`（**実行単位 = 1 ディレクトリ**）。
  **同一秒に 2 回実行した場合は `<YYYYMMDD_HHMMSS>_2` のように連番を付す**（L4）。
- **隔離ルートは遅延作成**とし、`ensure_split_config_dirs`（正本 §5.4 の起動時作成リスト）には**加えない**（L3）。
  隔離を 1 度も実行していない環境にディレクトリを作らない。
- **元の相対構造を保って移動**する（例: `<実行単位>/user/keymaps/foo.json`）。
  これにより**同名 stem の衝突を避け**、マニフェストが失われても手で戻せる。
- **マニフェスト** `manifest.json` を実行単位ディレクトリ直下に書く。

  ```json
  {
    "created_at": "2026-09-06T10:15:00",
    "entries": [
      {"kind": "keymap", "original_path": "user/keymaps/foo.json",
       "quarantined_path": "quarantine/20260906_101500/user/keymaps/foo.json"}
    ]
  }
  ```
  パスは**正本 §5.7 の表記**（config 配下は相対 / 区切りは `/`）で記録する。
- **隔離するのは〔ユーザーへ提示した孤児候補〕∩〔隔離直前の再判定でも孤児候補〕に限る**（H2 / §3-12-3）。
  **再判定で新たに孤児になった候補は隔離しない**（提示していないものを破壊的に動かさない）。
  再判定で対象外になった分・新たに孤児になった分は、いずれも件数を結果に出す。
- **マニフェストは移動より先に、原子書込みで作る**（Codex High 2・MUST）。手順は:
  ①これから動かす全件を**計画**として `manifest.json` へ書く（一時ファイルへ書いて `os.replace` で置換）
  →②**書けなければ 1 件も動かさない**（隔離を中止する）→③移動を 1 件ずつ行い、成功のつど
  そのエントリの状態を `moved` へ更新する。
  これにより**移動の途中で中断しても計画が残り、アプリから復元できる**
  （後追い記録だと、中断時に「隔離先にファイルはあるがマニフェストが無い」＝
  §3-7 で復元対象外になる状態が生まれる）。
- **移動は 1 件ずつ**行い、**失敗しても継続**する（成功件数と失敗件数 + 理由を結果に出す）。
  失敗したエントリは状態を `failed` として残す（計画から消さない）。
- 隔離は**元ファイルを削除しない**（移動のみ）。**runtime / dirty 状態は変更しない**。

### §3-7 復元

- 隔離ルート配下の**実行単位を一覧**し、選んだ単位のマニフェストに従って元の場所へ戻す。
- **`original_path` は候補側ディレクトリ（§3-4 の 4 種）の配下でなければ復元を拒否する**（M5）。
  `is_path_within` で検証する。マニフェストの破損・手編集で任意パスへ書き込ませない
  （削除に課しているガードと対称にする）。
- **復元先に同名ファイルが既にある場合は上書きせずスキップ**し、結果に「スキップ（既に存在）」として出す。
- **復元先ディレクトリが無い場合は作成する**（MUST）。
- **部分失敗を許容**（1 件ずつ・失敗は理由付きで記録して継続）。
- **全件が戻った実行単位は、マニフェストと空ディレクトリを削除する**（MUST。L9 / M9。
  中途半端に残さない）。1 件でも残っていれば実行単位を残す。
- **マニフェストが読めない実行単位は復元対象にしない**（一覧には「マニフェスト不正」として出す）。
  **削除は §3-8 の「強い確認」経路でのみ可能**（v0.5。復元はできないが、残骸を残さないため削除は許す）。
  - **「読めない」の定義**（**v0.7 で明記・判定は不変**）: **JSON として解析できない**、または
    **トップレベルが object でない**、または **`entries` が配列でない**、のいずれか。
    **エントリ単位の妥当性（必須キーの有無・値の形）は検査しない**。
    したがって `{"entries": [{}]}` のような**空要素だけのマニフェストは「有効」**として扱い、
    一覧は「残り 0/N 件」、復元は**中止せず各エントリをスキップ**として報告する（§3-12-8）。

### §3-8 隔離済みの削除

- **削除 API はパスを受け取らない。実行単位 ID（`20260906_101500` 等）だけを受け取る**
  （Codex High 3・MUST）。UI から渡された文字列を信用しない。
- **API 側で次の 4 つを検証**してから削除する（**①②③は 1 つでも満たさなければ拒否**）:
  ①隔離ルート**直下**に実在するディレクトリである ②名前が実行単位の形式
  （`YYYYMMDD_HHMMSS` または `_<連番>` 付き）に一致する ③canonical 表記が**隔離ルート自身と一致しない**
  ④**有効な `manifest.json` を持つ**。
- **④だけは「強い確認」で上書きできる**（**v0.5 で緩和**）。マニフェストが読めない実行単位は
  §3-7 により**復元もできない**ため、④を絶対条件にすると**アプリからは復元も削除もできない残骸**が残る。
  これは **§4-A の判断（消せない隔離物を残さない）と矛盾する**ので、**§4-A を優先**する。
  - **API は「④を満たさない単位の削除を明示的に許可する」引数を要求する**
    （既定は拒否。呼び出し側が意図して渡したときだけ通る）。**①②③は緩和しない**。
  - **UI は通常の削除と文言を分ける**（MUST）。**「マニフェストが読めないため中身を確認できません」**と
    **「ディレクトリごと削除します」**を明記し、**削除されるパスを全件提示**する。
  - 一覧では引き続き**「マニフェスト不正」**と表示する（§3-7 の復元不可は不変）。
  **`is_path_within` だけでは不十分**である点に注意する
  （同関数は docstring のとおり**同一パスも「配下」と判定する**〔`__init__.py:686`〕ため、
  空値や不正値で隔離ルート自身が渡ると**全実行単位が再帰削除される**）。
- **削除の実体は「実行単位ディレクトリの再帰削除」**（M8）。`manifest.json` も一緒に削除する。
  **OS のゴミ箱へは送らず、通常のファイル削除とする**（隔離が可逆層を兼ねるため。新規依存を増やさない）。
  **シンボリックリンクは辿らず、リンク自体を削除する**（隔離ルート外への脱出を防ぐ）。
- **削除前に対象パスを全件提示**して確認する（UI は §3-9）。**不可逆である旨を確認画面に明記する**。
- 部分失敗を許容し、結果を件数 + 理由で出す。
- **粒度 = 隔離の実行単位ごと**（§4-B 確定）。実行単位を選んで削除する（§3-9 のリスト選択 UI ①）。

### §3-9 UI

- **設定メニューに 2 項目を追加**する（§4-C 確定。`features.md` §4.6 の並びに追随）:
  「**孤児ファイルの棚卸し…**」（検出 → 隔離）と「**隔離の管理…**」（復元 / 削除）。
- **確認・結果表示は `ReferenceCleanupDialog` を再利用するが、そのままでは使えない**（H3）。
  **本文ヘッダ文言と実行ボタンのラベルを引数化する最小改修**を行う。
  ボタンラベルは **隔離 =「隔離する」/ 復元 =「復元する」/ 削除 =「削除する」**（いずれも右は「キャンセル」）。
  改修時は `tests_ui/test_reference_cleanup_flow.py`（9 件）を壊さないこと。
- **孤児候補の「行ごとの選択 UI」は作らない**（差分と誤操作を抑える。実行するかしないかの 2 択）。
- **リスト選択 UI は 2 箇所だけ作る**（H4。上の「行ごとの選択」禁止の対象外）:
  ①**隔離の実行単位の選択**（§4-B。「隔離の管理」側）、
  ②**走査ディレクトリの一覧と追加 / 削除**（§4-C。「棚卸し」側）。
- **孤児候補が 0 件のときはダイアログを出さず通知のみ**（phase 10 の「消える参照元が 0 件なら一覧を出さない」に揃える）。
  ただし §3-5 の 1〜3 に該当する項目があるときは**通知でその旨を必ず伝える**。
- 表示文言の生成は**純関数**（`presentation/` の text モジュール）に置き、application 側は
  **表示都合を持たない判定結果**を返す（phase 10 task_05 の依存方向の指摘を踏襲）。

### §3-10 走査ディレクトリ設定の永続化

- 記録先は **`<config_root>/config.json` に新キーを追加**する（例: `orphan_sweep_scan_dirs`: `list[str]`）。
  **既存キーの削除・意味変更はしない**（正本 §5.4 / 後方互換）。
- **書き込みは起動設定の書き出し経路 1 本を通す**（H6・MUST）。`config.json` を直接書かない。
  正本 §5.10.1 のとおり `config.json` は保存時に**丸ごと書き直され**、未知キーの保全は
  **起動時スナップショット `_startup_settings`** に依存するため、**直接書くと次の保存で無言で失われる**。
  設定を変更したら **`_startup_settings` も更新する**。
- 値は**正本 §5.7 の表記**（config 配下は相対 / 外は絶対 / 区切りは `/`）で保存する。
- **重複は canonical 表記で排除**して保存する。**読み出し時に非文字列要素は除去**する
  （壊れた設定で起動不能にしない。プリセット読み出しの正規化と同じ規律）。
- 追加・削除の UI は**棚卸しダイアログ内**に置く（§4-C 確定。§3-9 のリスト選択 UI ②）。

### §3-11 配置と依存方向

- **走査・参照集合の構築・孤児判定・隔離 / 復元 / 削除の実行 = application**
  （`keyseq/application/config_service/` 配下の新規モジュール。`parent_refs_cleanup.py` とは別ファイル）。
  **移動・削除という破壊的 I/O を application が直接行う**のは前例踏襲
  （`relocate_individual_hotkey_presets` が `shutil.copyfile` を直呼び・L10）。
- **application の入力は明示的に受け取る**（M4）: `config_root` / 走査ディレクトリの一覧 /
  **保護対象パスの集合** / 起動エントリと現在のセットのパス。**application から `app` を参照しない**。
- **表示文言 = presentation の純関数** / **入口 = `presentation/controllers/config_io/` の新規 IO クラス**
  （`reference_cleanup_io.py` と同型）。
- **`ConfigService` にはファサードの薄い委譲（1 行委譲）を置く**
  （`tests/test_parent_refs_cleanup.py` の「ファサードとモジュール関数の等価性」の方針に揃える）。
  `config_service/__init__.py` は **767 行**で分割保留中のため、**実ロジックを置かない**（L9）。
- **presentation から `config_service` の内部モジュールを直参照しない**
  （phase 10 の未対応指摘 H8 を新規コードで繰り返さない）。

### §3-12 既知の制約（正本へ昇格する）

1. **全網羅ではない**。走査は §3-2 の 4 経路に限られ、**`user/keymap_sets/` のサブディレクトリ**・
   **config 配下の非既定ディレクトリ**・**config 外の任意ディレクトリ**へ別名保存された keymap_set は
   走査できない（`normalize_keymap_set_save_path` は任意パスを許す・`config_paths.py:62-72`）。
   そこから参照されている子を**孤児候補として提示し得る**。だから**削除ではなく隔離**を既定とする（M1）。
2. **候補側は既定ディレクトリ直下のみ**（非再帰）。サブディレクトリに置かれた子は棚卸しの対象外。
3. **走査と隔離の間に外部変更があり得る**。**隔離の直前に孤児判定をやり直し**、
   **〔提示済み〕∩〔再判定でも孤児〕だけを隔離する**（H2）。
4. **`_parent_refs` は参照しない**。best-effort であり孤児判定の根拠にできない（正本 §5.8.1）。
5. **壊れた親があると、無傷の子を恒久的に失い得る**（§4-A の決定に伴う残存リスク）。
   `user/keymap_sets/` 直下などの keymap_set が破損して読めない場合、**その親が参照していた子は
   参照集合から抜け落ち、無傷でも孤児候補になる**。警告は出るが隔離・削除とも許すため、
   ユーザーが警告を読まずに削除まで進めると復旧できない。
   **壊れているのは親（多くは手で直せる小さなファイル）で、消えるのは子**である点に注意。
6. **削除の粒度は実行単位ディレクトリであり、確認画面の一覧は情報提供にすぎない**。
   `collect_unit_paths` が一覧を作ってから確認ダイアログを閉じるまでの間に、外部プロセスが
   その実行単位へファイルを追加すると、**一覧に出ていない中身も一緒に消える**。
   ユーザーは実行単位 ID を選んで「この単位を消す」と指示しているため挙動は意図どおりだが、
   **一覧を「消える物の全部」と読むと期待とずれる**。§3-9 の対象外とした
   「行ごとの選択 UI」を将来入れる場合は、ここを削除計画の再照合として作り直す必要がある。
7. **検証と `shutil.rmtree` の間の TOCTOU は許容する**。`delete_quarantine_unit` は UI の確認後に
   ①②③をやり直すため窓は関数内に限られるが、その間に隔離ルートを外部へのジャンクションへ
   差し替えられれば、外部の実体を消し得る。塞ぐには削除完了まで実体を固定する仕組み
   （Windows のハンドル保持等）が要り、**§3-8 の「新規依存を足さない」と衝突する**。
   隔離ルートを差し替えられる権限があればアプリを介さず直接削除できるため、
   **脅威モデル上の上積みも小さい**と判断した。
8. **マニフェストの妥当性をエントリ単位では検査しない**（v0.7 で明記。§3-7 の定義）。
   手編集などで**well-formed だが実体を指さないマニフェスト**にすると、その単位は
   **「有効」として一覧に出る**（「マニフェスト不正」にならない）。隔離側に実体が残っていても
   **復元は 0 件**になり（スキップ理由「隔離側にファイルがありません」・パス欄は空）、
   削除は**通常経路**で進む。ただし削除の確認画面は `collect_unit_paths` が**実体を全件列挙**するため、
   **消せない残骸にはならない**（§4-A は満たす）。アプリ自身の書込みは原子的でこの形を作らないため、
   **発生源は手編集に限られる**と判断し、エントリ単位の検証は入れない。

## §4 確認事項の決着（ユーザー確定 2026-09-06）

**未確定はゼロ**。以下は決定の記録（§2 に要約、§3 に規定を反映済み）。

- **§4-A: 読めなかった参照側がある場合の扱い**（§3-5-2）
  → **警告を出したうえで隔離の実行を許す。削除も許す**（v0.4 で最終確定）。
  - `deep-reviewer` / Codex の推奨は「抑止」だったが、**壊れた JSON が 1 件あるだけで棚卸しが使えなくなる**
    運用上の不都合を避ける判断。
  - Codex High 1 を受けて **degraded 方式**（走査が不完全な実行単位は削除だけ恒久拒否）も検討したが、
    **不採用**。理由 = **消せない隔離物が残ると、結局ユーザーがエクスプローラで直接削除することになり、
    そちらの方が事故を起こしやすい**（ユーザー判断）。
  - **見つからなかった指定ディレクトリを危険信号として扱わない**ことも確定。既定外のディレクトリは
    ユーザーが移動・削除するのが日常的で、**それ自体は参照集合を欠けさせない**ため
    （指定先に keymap_set が実在しないなら誤判定の原因にならない）。
  - 代償として **①一覧先頭の警告表示を MUST 化 ②「このまま隔離を実行する / キャンセル」の 2 択
    ③残存リスクを §3-12-5 に明記**（§3-5）。確認用 UI は作らない。
- **§4-B: 復元 / 削除の粒度**（§3-7 / §3-8）
  → **隔離の実行単位ごと**。マニフェスト単位で一貫し、古い隔離だけを消せる。
  実行単位のリスト選択 UI を 1 箇所作る（§3-9 ①）。
- **§4-C: メニュー構成と走査ディレクトリ設定の入口**（§3-9 / §3-10）
  → **設定メニューに 2 項目**（「孤児ファイルの棚卸し…」「隔離の管理…」）。
  走査ディレクトリの追加 / 削除は**棚卸しダイアログ内**（§3-9 ②）。
- **§4-D: 隔離ルートの位置**（§3-6）
  → **`<config_root>/quarantine/`**（`user/` の外）。候補側（`user/` 配下）と**構造的に交差しない**ため、
  「隔離ディレクトリを候補側から除外する」規定が不要になり、隔離物を再走査する事故が原理的に起きない。
- **§4-E: 候補側の形状検証**（§3-4）
  → **入れる**。既定ディレクトリに手で置いた無関係な JSON を隔離しない。基準は §3-4 の表。
- **§4-F: フェーズの分割**（`deep-reviewer` M10）
  → **分割しない**。ただし phase.md のタスク分割で**「検出までを先に green にする」段取りを明記**し、
  隔離 / 復元 / 削除はその後のタスクへ積む。

## §5 受け入れ条件（ドラフト）

> §4-A〜F は確定済み（§4）。対応する条件を 17〜19 に追記した（L7）。

1. `user/keymap_sets/` 直下の複数 keymap_set と、2 段目の trigger_set → sequence を辿って
   参照集合が構築される（§3-3）。旧形式の `keymaps[]`（素の文字列）でも辿れる。
2. `hotkey_presets_individual` が **false でも** `hotkey_presets_path` が参照ありと数えられる（§2 / §3-3）。
3. **既定ディレクトリの外・config 外にある「現在開いている keymap_set」が走査され、その子が孤児候補にならない**
   （§3-2-3 / H1）。`config.json` を書き換えずに keymap_set を開いた状態で成立すること。
4. 候補側は 4 種の既定ディレクトリ直下のみで、**`user/hotkey_presets/global/` が除外**される（§3-4）。
5. **現在開いている構成セットが参照する子は、config 外にあっても孤児候補にならない**（§3-4 保護対象）。
6. 未保存の変更があるときは**「保存する / 中止する」の 2 択**になり、保存しない選択で棚卸しが中止される（§3-4 / H5）。
7. 見つからない指定ディレクトリは**スキップされ、完了後にパス付きで表示**される（§2 / §3-5-1）。
8. 読めなかった参照側・対象外と判定した JSON の件数が結果に出る（§3-5-2 / §3-5-3）。
9. 隔離により**元の相対構造を保ったまま移動**され、`manifest.json` が書かれる（§3-6）。
10. **隔離直前の再判定で新たに孤児になった候補は隔離されない**（§3-6 / §3-12-3 / H2）。
11. 復元でマニフェストどおりに戻り、**同名ファイルがある場合はスキップして報告**される（§3-7）。
    **`original_path` が候補側ディレクトリ配下でなければ拒否**される（§3-7 / M5）。
12. 削除は**隔離ルート配下でなければ拒否**される（§3-8）。
13. 孤児候補 0 件ならダイアログを出さず通知のみ。§3-5 の該当項目は通知に含まれる（§3-9）。
14. 走査ディレクトリ設定が **起動設定の書き出し経路を通して** `config.json` へ保存され、
    **アプリ内の別操作（keymap_set 保存など）の後も失われない**（§3-10 / H6）。既存キーも失われない。
15. **棚卸し（検出）そのものによるファイル書き込みが 1 件も発生しない**（§3-2）。
    ※ §3-4 の保存確認で保存した場合と §3-10 の設定保存は本条件の対象外（正本 §5.8.1 と同じ切り分け。M6）。
16. `compileall` clean / `tests` `tests_ui` が既存件数（`tests` 267 / `tests_ui` 238）を減らさず pass /
    smoke pass / 実行後にリポジトリルートへ `user/` が生成されない。
    **隔離を 1 度も実行していない環境に隔離ルートが作られない**（§3-6 / L3）。
17. **読めなかった参照側があるとき、孤児候補一覧の先頭に警告が出る**（件数・パス・理由）。
    孤児候補が 0 件でもこの警告は通知に含まれる。**選択は「実行 / キャンセル」の 2 択**で、
    走査が不完全でも隔離・削除とも行える（§3-5 / §4-A）。
18. **候補側の形状検証**で、必須キーを欠く JSON が `ORPHAN_EXCLUDED` になり隔離されない（§3-4 / §4-E）。
19. **復元 / 削除が隔離の実行単位ごとに行える**（実行単位を選び、その単位のファイルだけが対象になる）
    （§3-7 / §3-8 / §4-B）。
20. **マニフェストが移動より先に書かれる**。書けない状況では**ファイルが 1 件も移動しない**。
    移動の途中で中断しても、残った計画から復元できる（§3-6 / Codex High 2）。
21. **削除 API に隔離ルート自身・ルート外・実行単位の形式に合わない値・マニフェストの無い単位を渡すと拒否される**
    （§3-8 / Codex High 3）。**削除は OS のゴミ箱へ送らず通常削除**である。
22. **候補側ディレクトリに置かれた外部キーボードレイアウトが、どちらのパス基準で記録されていても保護される**
    （§3-3 / Codex Medium）。
