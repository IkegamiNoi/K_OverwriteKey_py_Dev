## §1 目的 / 背景

キーボードUIの各キーの文字を、キーの幅に収まる大きさで 1 行に出す（単語の途中で折り返さない）。
改行と、キー置換の送信先の表示名をレイアウトの JSON で指定できるようにする。
最小サイズを「窓の幅」ではなく「キー 1 個の大きさ」で決め、JIS も US TKL と同じキーの大きさまで縮められるようにする。
利用者が変えた窓の幅をレイアウトごとに記録し、次に開くときその幅で開く。
既定の US TKL（コードに内蔵）と同じ内容の見本の JSON を置く。

## §2 確定事項（ユーザー 2026-10-25）

1. **文字はキーの幅に合わせて小さくし、単語の途中で折り返さない**
2. **改行は `label` に `\n` を書いて指定する**（例: `"半角\n全角"`。JSON の普通の書き方で、書式は変わらない）。`\n` が無ければ改行しない
3. **キー置換の送信先の表示名は、レイアウトの JSON に足す「キー名 → 表示名」の別の表で指定する**（`keys` とは別。配列に無いキーにも名前を付けられる）
4. **最小サイズは `w = 1.0` のキー 1 個 = 27px**（US TKL の今の最小とほぼ同じ。JIS 見本はさらに縮められる）
5. **既定の US TKL と同じ内容の見本 `config/user/keylayout/us_tkl.json` を置く**（`layout_id` は内蔵と重ならない別の id）
6. **最小の大きさでの文字の余白 = 左右・上下 1px ずつ、下限 = 主の文字 7px・下の文字 6px**（v0.2 の Q6。起票時レビューの実測で今の余白では 4〜5 文字の 1u のキーが収まらないため）
7. **下限の幅に上限は付けない**（v0.2 の Q4）。座標の尺度が大きい外部レイアウトで下限が画面を超える場合は保証の範囲外（受容）
8. **新規に開く大きさ = 最小。利用者が変えた大きさはレイアウトごとに幅を記録し、次に開くときその幅で開く**（v0.2 の Q1 への回答・高さは比率から）。**位置は記録しない**
9. 小さいレイアウトに追加の下限は設けない（v0.2 の Q2）/ jis.json に表の例 `{"zenkaku_hankaku": "半角\n全角"}` を足し、その行の `label` も `"半角\n全角"` にする。us_tkl.json は空の表 `{}` を書く（Q3）/ 内蔵の US TKL に表は持たせない（Q5）

## §3 文字の大きさを合わせる

対象 = 各キーの主の文字（`display`）と、物理キー名の表示中の下の小さい文字（`sub_display`）。

- **単位は px にそろえる**: フォントの大きさは負の値（px 指定）で持ち、上限・下限・計測をすべて px で扱う（正の値は pt で、DPI により px が変わるため）
- **行に分ける**: 文字を `\n` で行に分ける（§2-2）。**それ以外では改行しない**（`create_text` に `width` を渡さず、Tk の自動の折り返しを使わない）
- **大きさの上限**（px）: 主の文字 = `unit × 0.37`（今の 0.28pt × 96dpi の 1.333 ≒ 0.37px）/ 物理キー名の表示中は 主 = `unit × 0.27`・下 = `unit × 0.19`。
  今の「4 文字超で 0.22」の段はやめる（実測で縮めるため）。このため普通の大きさの窓では 5 文字以上の文字（Enter・Shift・Space 等）が今より大きく出る（受容・実機目視で確かめる）。文字の大きさはキーごとに違ってよい（揃えない）
- **収まるまで縮める**: 上限から小さくして、**いちばん長い行の幅 ≤ キーの内側の幅** かつ **主と下の文字の行の高さの合計 ≤ キーの内側の高さ** になる最大の大きさにする。幅・高さは Tk のフォントで実測する（`tkfont.Font.measure` / `metrics("linespace")`）。
  主と下の文字は同じ割合で縮める（下 = 主 × 0.19 / 0.27）が、**下限は主・下それぞれに個別に当て、下限が上限より優先する**（下限に達した側は比例をやめて下限に留め、もう一方だけ縮める。上限が下限を割るとき〔unit 27 の下の文字 5.13px 等〕は下限）。
  丸め（整数 px）と下限を当てた後の大きさで幅・高さを測り直して収まりを判定する
  - キーの内側 = 枠（`x1`〜`x2`・`y1`〜`y2`）から左右・上下に **1px ずつ**引いた範囲（§2-6）
  - 探し方は実装の判断（1 ずつ下げる / 比率で見積もって確かめる等）。**同じ（文字・枠の大きさ）の結果は描き直しの間で使い回すことを推奨**（Configure ごとに描き直すため）
- **縦の配置**: 主の文字の行と下の文字の行を上から積み、その塊をキーの内側の縦の中央に置く（各行は横の中央揃え）。今の固定のずらし（`unit × 0.12`・`y2 − max(8, unit × 0.18)`）はやめる
- **下限**: 主の文字 7px・下の文字 6px（§2-6）。下限でも収まらなければ下限の大きさで出し、はみ出しは受容（`\n` 以外では折り返さない）。
  実測（Yu Gothic UI・96dpi・7px bold）: 1u のキーは最小で内側 21px に `Home` 19・`MODE` 20・`Pause` 19・`PgUp` 17px が収まり、2 行（行の高さ 10px × 2）も収まる。長い送信先のキー名（`zenkaku_hankaku` 58px 等）は最小ではみ出す（受容・表で短い名前を付けられる）

## §4 キー置換の送信先の表示名の表（レイアウトの JSON）

### §4.1 書式

レイアウトの JSON の最上位に任意キー **`key_display_names`**（object・キー名 → 表示名）を足す。

```json
{
  "layout_id": "jis",
  "display_name": "JIS",
  "key_display_names": {"zenkaku_hankaku": "半角\n全角", "backspace": "BS"},
  "keys": [ ... ]
}
```

- **読込**: 無い・`null` → 空 / object でなければ読込エラー / 値が文字列でなければ読込エラー /
  キーは `normalize_key_name` で正規化して持つ（空になるキーは読込エラー）/ 正規化後に重なるキーは後に書いた方（読込で拒否しない）/ 値は空文字も可（空なら表にないものとして扱う）
- 値に `\n` を書けば改行する（§3）
- 既存キーの意味は変えない（後方互換。表が無い JSON は今と同じ）

### §4.2 使い方

- **キー置換の枠**の文字（送信先のキー名）だけに使う: 送信先のキー名（正規化済み）が表にあれば表の値、無ければ**今どおりキー名**
- トリガーの番号・`KM<n>`・`MODE`・`STOP`・割り当ての無い枠（`label`）には使わない
- 内蔵の US TKL の表は空（今と同じ表示）

## §5 最小サイズ

- **最小のキャンバス = `w = 1.0` のキーが 27px 以上になる最小の大きさ**: キャンバス幅の下限 = `ceil(27 × max(x + w))`・キャンバス高の下限 = `ceil(27 × max(y + h))`。
  縦横比の固定と合わせ、窓の下限 = 「キャンバス幅の下限から比率で決めた大きさ」と「キャンバス高の下限から比率で決めた大きさ」の大きい方（どちらの辺も下限を割らない）+ 余白 10 × 2。
  検査は `unit ≥ 27 − 0.1`（比率の四捨五入の誤差を許す）で判定してよい
  - 例: US TKL ≒ 515 × 188 / JIS 見本 ≒ 399 × 188（今は 510 × 187 / 510 × 237）
- `KEYBOARD_WINDOW_MIN_WIDTH` の固定値（510）をやめ、レイアウトごとの下限にする。`minimum_size` / `corrected_size` は比率だけでなく下限（または `max(x + w)` / `max(y + h)`）を受け取る形にする。縦横比の固定の補正の「下限を割ったら最小へ」も同じ下限を使う
- **レイアウトの切替**（開いている間）: **`layout_id`・比率・下限のいずれか**が変わったら当て直す。目標の幅 = そのレイアウトの記録の幅（§8）、無ければ下限の幅。いずれも下限を割らない（`max(目標, 下限)`）から比率で決める
  （小さく縮めた後に下限の大きいレイアウトへ替えて、OS の頭打ちで比率がずれるのを防ぐ）。**同じ `layout_id` で比率も下限も変わらないとき**（同じレイアウトの選び直し・読み直し）だけ大きさに触らない（今どおり）。
  配置が同じ別のレイアウト（内蔵の `us_tkl` と見本の `us_tkl_sample` 等）でも、それぞれの記録の幅へ替わる
- 下限に上限は付けない（§2-7）。下限が画面より大きい場合は既存の受容「補正の目標が画面の大きさを超えると OS が頭打ちにし、比率のずれた大きさが残る」に含める
- キーが無いレイアウト（`ratio is None`）は今どおり 510 × 210（補正しない・記録もしない）
- px は Tk の座標（プロセスはシステム DPI 対応）
- Windows の窓の最小の幅（タイトルバーのボタンの分）で OS が頭打ちにする場合も同じ受容に含める

## §8 大きさの記録（`config/config.json` の `keyboard_window_widths`）

- **書式**: `config/config.json` の任意キー **`keyboard_window_widths`** = `{"<layout_id>": <int px>, ...}`（窓の幅・余白込み）。高さは記録しない（比率から決める）
  - 読込: dict でなければ全体を無視 / **値ごとに判定**し、bool を含む非 int・1 未満は無視（エラー表示なし・ファイルは書き換えない）
  - 登録されていないレイアウトの id の値も残す（消さない）
  - 書き込みは起動設定の書き出し経路 1 本（`StartupIo.write_startup`）を通す（構成セットの保存で config.json が書き直されても残る）。今の辞書に今のレイアウトの値を 1 つ足し / 置き換えて全体を書く
- **開くとき**: 今のレイアウトの記録の幅があればその幅、無ければ下限で開く。高さは比率から。記録の幅が下限を割っていれば表示だけ下限にする（記録は書き換えない）。画面より大きい値は OS の頭打ちに任せる（受容）
- **書き込み契機**: 利用者の操作で大きさが変わり、縦横比の補正（約 150ms・ボタンが離れた後）が確定したとき、その幅が今のレイアウトの記録と違えば書く。
  **自分が当てた大きさ**（開く・レイアウトの切替・比率の当て直し・下限への引き上げ）では書かない。最大化中・最小化中は書かない（通常へ戻った後の基準の取り直しでも書かない）
- 新しいキーなので後方互換（キーが無ければ今と同じく下限で開く）。正本 `data_schema.md` §5.4（config.json の UI の保存値）へ足す
- 受容: 補正が確定する前にアプリを終了・窓を閉じた場合、その変更は記録されない

## §6 見本 `config/user/keylayout/us_tkl.json`

- 内容 = 内蔵の `_DEFAULT_US_TKL_KEYS` と同じ行（`id`・`label`・`x`・`y`・`w`・`h`。省略していた `w` / `h` = 1.0 も明記）。`scan_code` は書かない（内蔵と同じ）
- `layout_id` = **`us_tkl_sample`**・`display_name` = **`US TKL（見本）`**（内蔵の `us_tkl` と重なると読込エラーになるため）
- `key_display_names` は空の `{}` を書く（§2-9・書式の見本）。jis.json には表の例を足し `zenkaku_hankaku` の `label` を `"半角\n全角"` にする
- 追跡は jis.json・de.json と同じ（`git add -f`）。検査 `tests/test_keyboard_layout_files.py` に「内蔵と行が一致する」ことを足す（内蔵を変えたら見本も直す前提を固定する）

## §9 受け入れ条件（ドラフト）

1. 最小まで縮めた JIS / US TKL で、どのキーの文字も単語の途中で折り返さない（`Backspace`・`Home`・`PgUp`・`Scroll`・`Pause`・`Down`・`Right`・`MODE`・`STOP` 等）。自動テストは text の item に `width` が無いこと・行の数で確かめ、読めるか・はみ出しは実機目視で確かめる（§3）
2. `label` / 表の値の `\n` の位置でだけ改行する（§3・§4）
2a. 普通の大きさの窓で文字の大きさが今と比べて不自然でない（5 文字以上の文字が大きくなる点を含む・実機目視）（§3）
3. JIS 見本でキー置換の送信先 `zenkaku_hankaku` が表の値で出る。表に無い送信先はキー名のまま（§4.2）
4. `key_display_names` の読込の検証が §4.1 どおり（不正は読込エラー・無ければ今と同じ）（§4.1）
5. JIS 見本も US TKL も `w = 1.0` のキーが 27px になる大きさまで縮められ、それ以下には縮まない（`unit ≥ 26.9` で判定）。JIS を最小まで縮めてから US TKL へ切り替えても比率がずれない（§5）
6. `us_tkl.json` を登録すると内蔵の US TKL と同じ配置で出る・行が内蔵と一致する検査がある（§6）
6a. 記録が無ければ最小で開く。大きさを変えて閉じ、開き直すと同じ幅で開く（レイアウトごと）。開く・切替では書き込まれない。内蔵の US TKL と見本に別の幅を記録し、開いたまま切り替えるとそれぞれの幅になる（§5・§8）
6b. unit 27 で物理キー名を表示しても、主の文字 ≥ 7px・下の文字 ≥ 6px（§3）
7. tests / tests_ui / smoke が通る・件数が減らない
