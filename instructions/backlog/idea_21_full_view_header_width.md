# idea_21_full_view_header_width.md

## 概要

**フル表示のヘッダ領域（フック / 表示 / ファイル操作）の幅を、メイン領域の幅・ウィンドウ最小幅と一緒に考慮する**。
ウィンドウを狭めると**ファイル操作の枠の中身が見えなくなる**ことがある。あわせて、**サイズが変わるボタンは最大サイズで作って
枠のサイズに影響させない**・**キーボード選択のドロップダウンを今の 2/3 の幅にする**。

## 起票経緯（2026-09-17）

出所: phase 18 task_05 の実機目視（ユーザー）。phase 18 の暫定仕様 16 §6 でヘッダはスコープ外（既存の挙動のまま）としたため分離。

## 現状

- ヘッダ = `keyseq/presentation/views/full_view/hook_frame.py` / `display_frame.py` / `file_frame.py`（`full_view.py` で配置）。
- phase 18 のウィンドウ最小幅は**メイン領域だけ**から算出（暫定仕様 16 §3-4 / `controllers/pane_layout_controller.py`）。
  ヘッダの要求幅が上回ると切れる。
- フックの枠の停止キー / トグルキーの「キー入力で取得」ボタン（`hook_frame.py:30,39`）は、取得中に文言が変わりボタン幅が変わる
  （ユーザー観察。文言の切替箇所は未確認）。
- キーボード選択のドロップダウン = `display_frame.py:28-32`（`ttk.Combobox(width=18)`）。

## 提案（方向性・要設計）

- ウィンドウ最小幅を max(メイン領域から算出した値, ヘッダの要求幅 + 余白) にする（案 A）。
  または、ヘッダの配置を狭い幅でも切れない形へ変える（案 B・配置変更を伴う）。
- 文言が変わるボタンは、取りうる文言の最大幅で `width` を固定する（切替で枠の要求幅が変わらない）。
- `keyboard_layout_combo` の `width` を 18 → 12 程度（2/3）にする。レイアウト名が長い場合の見え方を確認する。

## 想定スコープ

- presentation のみ。JSON の変更なし。
- 最小幅の算出に入れるなら暫定仕様 16（または昇格後の正本 `features.md` §4.6）の改訂が要る → 仕様変更フロー。
