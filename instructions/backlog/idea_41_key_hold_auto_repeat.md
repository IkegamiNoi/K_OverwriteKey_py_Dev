# idea_41_key_hold_auto_repeat.md

## 概要

**key_hold で押したままにした通常キー（`a` 等）を、離すまでキーリピートさせる**。
今は押下（keydown）を 1 回送るだけなので、メモ帳などの文字入力では 1 文字しか出ない。
押下中は一定間隔で keydown を送り直す仕組みを加え、実キーボードの長押しと同じ連続入力にする。

## 起票経緯（2026-10-10）

phase 51 task_05 の実機目視で判明（ユーザー）。`a` を押したままにしてメモ帳で実行すると、
離すまで `a` が入り続けると想定していたが、実行の最初と、シーケンスが先頭へ戻ったとき
（先頭へ戻ると離し、次の実行で押し直す）にしか入らなかった。
key_hold としては問題なし（押下中の状態を読むアプリ・修飾キーには有効）とユーザーが判断し、リピートを別ネタとして分離した。

## 現状

- `InputGateway.press_key`（`keyseq/infrastructure/input_gateway.py`）は `keyboard.press` で keydown を 1 回だけ送る。
- Windows は合成入力（SendInput / keybd_event）にタイプマティックリピートを付けない。実キーボードの連続入力は
  キーボード側が keydown を送り直して作っている。
- OS 上の押下状態は離すまで「押されている」になるため、状態を問い合わせるアプリ（ゲームの移動・
  修飾キー・スペース + ドラッグ等）には有効。押下の合図の数で入力するアプリ（文字入力）には効かない。
- 仕様: 暫定仕様 [35](../history/35_key_press_release_actions.md)（phase 51）はリピートを約束していない。

## 提案（方向性・要設計）

- 押下中のキーごとに、遅延（初回）→ 間隔で keydown を送り直すタイマー（スレッドまたは UI の `after`）を持つ。
  離す・自動で離す（止まる経路すべて）でタイマーも止める。
- 対象: 修飾キー（shift / ctrl / alt / windows）は対象外にする案が有力（実キーボードでは修飾キーもリピートするが、効き目は変わらない）。
- 遅延・間隔: OS の設定（`SystemParametersInfo` の SPI_GETKEYBOARDDELAY / SPI_GETKEYBOARDSPEED）に合わせるか、
  行ごと・全体の設定にするか。
- 有効化: key_hold の行にリピートの有無を持たせるか（JSON の新キー・後方互換）、常にリピートするか。
- 送り直しの keydown が自分のフックに届く（再入）ことへの対策（既存の送信ガードとの整合）。
- text / file_line の送信中は押下中のキーを離す（暫定 35 §2-14）ため、その間はリピートも止める。

## 想定スコープ

- 含む: 押下中の通常キーのリピート送信・止まる経路での停止・設定の要否判断。
- 含まない: マウスボタンの連打。
- 影響レイヤ: infrastructure（送信）/ application（押下中の集合 `HeldInputs`・タイマーの寿命）/
  presentation（設定 UI を作る場合）。JSON に設定を足すなら data_schema の更新を伴う（仕様変更あり・暫定仕様先行の見込み）。
