# idea_12_orphan_child_file_sweep.md

## 概要

**`config` 配下を全走査し、「どの構成セットからも参照されていない子ファイル（孤児）」を検出する棚卸し機能。**
phase 10（暫定仕様 09）で作る「現在の構成セットの参照元掃除」の**上位版**にあたり、
**逆方向検査（上位 → 子の索引走査）**を新設する。削除まで行うかは着手時に判断する。

## 起票経緯（2026-08-16）

出所: **phase 10 の暫定仕様 09（v0.1〜v0.3）の設計議論**。
ユーザー方針は「**全検査と現在のセットのみ、それぞれ作る**」で、
**段階的に進める**（まず現在のセットのみ = phase 10 / 全検査 = 本 idea）と確定した。

## なぜ分けたか（phase 10 に入れなかった理由）

- **孤児判定は `_parent_refs` を根拠にできない**。参照元記録は **best-effort**（正本
  `data_schema.md` §5.8.1）で、**「どこからも参照されていないこと」の証明にならない**
  （旧形式・別経路保存では、現に使用中の子でも参照元が空 / 不明になる）。
  - 具体例: **sequence の親は trigger_set**。trigger_set が未保存 / 削除済みなら、
    **使用中の sequence の参照元が全滅**する。
- したがって孤児検出には **上位（keymap_set → 子）の索引を走査して「参照されている子の集合」を作る**
  逆方向検査が要る。これは新規実装:
  - **`config/user/keymap_sets/` の走査**（現状 `keyseq/` に `os.listdir` / `glob` / `os.walk` が **1 箇所も無い**）
  - keymap_set ファイルから子パスを取り出す**読み出し専用の経路**
    （`build_runtime_data_from_split` は読み込みと正規化が一体で、そのままは使えない）
- **削除は不可逆**。かつ **keymap_set も子も `config` 外に置ける**（別名保存の任意ディレクトリ /
  `split_base_dir` / `source_path` の尊重）ため、**走査しても全網羅にならない**。
  規定外の場所にある keymap_set が参照している子を「孤児」と誤判定すると**データ損失**になる。

## 提案（方向性・要設計）

1. **検出のみ（推奨の出発点）**: 孤児候補を一覧で提示するだけ。削除はユーザーが手で行う。
2. **削除するなら安全策を必須にする**:
   - **削除ではなく隔離ディレクトリへ移動**（可逆にする）
   - **対象パスの全列挙**を実行前に提示
   - **「走査範囲外の keymap_set からは参照され得る」旨の明示**
3. **phase 10 の成果を土台にする**: 検査結果の型・`prune_parent_refs`・確認 UI（読み取り専用の一覧 +
   実行 / キャンセル）はそのまま再利用できる。**孤児候補の判定だけを足す**形にできると差分が小さい。

## 想定スコープ

- **含む**: `config/user/keymap_sets/` の走査、keymap_set → 子パスの読み出し、
  参照されている子の集合の構築、孤児候補の提示、（採るなら）隔離 / 削除と確認 UI。
- **含まない**: 参照元記録（`_parent_refs`）の仕組み変更、保存フローの改変。
- **影響レイヤ**: application（走査・逆方向検査）+ presentation（メニュー・確認 UI）。
- **仕様変更**: あり（新機能）。**前提: phase 10（暫定仕様 09）の完了**。
- **優先度**: 中〜低（棚卸し機能）。**削除まで含める場合はリスクが上がる**ため、
  着手時に「検出のみ / 隔離 / 削除」を先に確定すること。
