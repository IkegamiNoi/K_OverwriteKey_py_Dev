# idea_68_shift_layer_replacement_source.md

## 概要

**キー置換の置換元に `Shift+キー` を指定できるようにし、同じキーマップに「Shift を押している間の面」を持たせる。** 例: `2` はそのまま、`Shift+2` だけ `@` にする（配列の違いの吸収）/ `Shift+1` → `1`（Shift を効かなくする）/ `Shift+Space` → `Enter`。いまは置換がキー名だけで一致し、Shift の有無を見ないため作れない。

## 起票経緯（2026-11-25）

出所: idea_62 の意図確認（ユーザー 2026-11-25）からの分離。idea_62 の当初案（置換元に修飾キー付きの組み合わせ）がこれに当たる。idea_62 は置換先に大文字を置く案へ書き直した。

## 現状

- 置換もトリガーもキー名だけで一致し、修飾キーは素通しになる（`keyseq/application/input_router.py:138` 以降）。`a → b` の置換で `Shift+A` を押すと、物理の Shift が残っているため OS には `Shift+b` が届く。
- 置換元の記録（`keyseq/presentation/keyboard_window.py:618` の `_record_key`）は修飾キーを読み飛ばす（idea_57 と同じ箇所）。

## 提案（方向性・要設計）

- 置換元を `shift+<キー>` で持つ（`mappings` の str → str のまま足せる見込み）。
- 一致の条件は、押されている修飾の組がちょうど一致すること（完全一致）。一致したら物理の Shift を離してから置換先を送り、まだ押されていれば押し直す（ユーザー 2026-11-25 の方向性）。
- Shift の面に置換が無いキーは、従来どおり通常の面の置換に Shift が付いて届く。
- 単一キーのトリガー A と `Shift+A` の置換が重なったときの優先順位（修飾付きの置換を優先する案 / トリガーを優先する案 / 重なりを禁止する案）。
- キーボードUI の記録と表示（Shift の面への切替のボタンで面を選んで表示・編集する案 等）。
- **Shift 以外の修飾キー（Ctrl / Alt、macOS の Command / Option）** の面も同じ枠組みで扱うか（ユーザー 2026-11-25: まず Shift、他の修飾は別途検討）。

## 想定スコープ

- 含む: キーマップの保存形式（後方互換で項目を足す）・フックの判定・送信（物理の Shift の打ち消しと押し直し・Windows / macOS）・重なり判定・キーボードUI の記録と表示。
- 含まない: hotkey・key_hold の変更。
- 仕様変更あり（`data_schema.md` / `key_input.md` / `features.md` に跨る見込み → 暫定仕様先行）。関連: idea_62（置換先に大文字）・idea_57（置換先に修飾キー）・idea_53（送信中の物理入力）。
