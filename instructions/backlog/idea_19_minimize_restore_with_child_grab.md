# idea_19_minimize_restore_with_child_grab.md

## 概要

**子ダイアログが grab を持つ状態で Win+D（全ウィンドウ最小化）を行うと、アプリを再表示できない**。
タスクバーから戻そうとしても操作できる窓が現れず、**実質的に操作不能になる**。
App が grab を持っている場合（ダイアログを開いていない場合）は再表示できる。
**原因は未確定**（最小化で隠れた grab 保持者へ入力が向いたままになる、という仮説のみ）。

出所: [phase 16](../phase/16_dialog_transient_parent/phase.md) task_04 の実機目視 §5-6。

**grab 中は背面 App の最小化ボタン自体が押せず**、代替として Win+D を使った際に本現象を観測した。
ユーザー判断（2026-09-15）で別 idea へ分離した。

## 現状

- モーダル化は `keyseq/presentation/modal.py` の `grab_modal()` のみ。
  `window.transient(parent)` + **ローカル grab**（`grab_set()`）で、
  破棄時に直前の保持者へ戻す（`<Destroy>` バインド）。
- **最小化・復元に関する結線は存在しない**。`keyseq/` 全体で `iconify` / `withdraw` /
  `<Map>` / `<Unmap>` の使用は 0 件、`deiconify()` は
  `controllers/layout_controller.py:43`（キーボードウィンドウの再表示）のみ。
  つまり**全最小化からの復帰は OS 任せ**で、アプリ側の復元処理は何もない。
- 影響範囲は「grab を持つ子ダイアログが開いている間」に限られる（通常操作時は再現しない）。
- 再現手順: 入れ子ダイアログを開く → Win+D → タスクバーのアイコンからアプリへ戻ろうとする。
  **プリセット編集 → プリセット追加でも、プリセット編集 → 上書き確認でも再現する**
  （特定の経路の問題ではない）。

## 提案（方向性・要設計）

- **案 A（推奨）: 復元時に grab 保持者を明示的に出す** — App 側で `<Map>` を拾い、
  `grab_current()` が生存していれば `deiconify()` + `lift()` する。
  `modal.py` は既に `grab_current()` を使っており、**追加は小さい**。
  ただし「入れ子の全段」を出す必要があるか（保持者だけで足りるか）は要確認。
- **案 B: 最小化されたら grab を一時解除し、復元時に張り直す** — 復元経路は OS 任せのままにできるが、
  **grab の一時解除中に背面を操作できてしまう**ため、モーダル性の保証が崩れる。採りたくない。
- **案 C: そもそも最小化させない** — 子ダイアログを持つ間は最小化を抑止する。
  OS の全最小化は抑止できないため**解決にならない**。
- **着手時にまず行うこと**: 最小化中のウィンドウ状態（`wm_state()` が root / 子でそれぞれ何になるか、
  grab 保持者が生存しているか）を `.venv` の python で実測し、**仮説を確定させる**。
  案の選定はその後。

## 想定スコープ

- **含む**: `modal.py` と App の復元結線、対応する `tests_ui` の受け入れテスト。
- **含まない**: `transient` の相手の設計（phase 16 で確定済）、grab の復元規則そのもの
  （phase 14 で確定済）。
- **影響レイヤ**: presentation のみ。**仕様変更の見込みあり**（正本 `features.md` /
  `key_input.md` のモーダル挙動に「最小化・復元」の条項が無いため、着手時は
  `.claude/rules/spec_change_workflow.md` に従い暫定仕様先行が要りそう）。
- **優先度**: 中（**再現手順は簡単で、起きるとアプリが操作不能になる**が、
  Win+D を押さない限り遭遇しない）。
