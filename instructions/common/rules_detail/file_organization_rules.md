# ファイル構成・肥大化対策ルール（詳細版）

> 本書は `.claude/rules/file_organization_rules.md`（要点版・毎セッション自動読込）の詳細版。
> 規範の正は要点版。ルール変更時は要点版を先に直し、本書を追従させる。
> 本書は自動読込の対象外であり、例・図・背景説明が必要なときのみ読む。

## 目的

コードベースの成長に伴うファイル肥大化や構造劣化を防ぎ、保守性・可読性・発見性を維持することを目的とする。

本ルールは言語やアーキテクチャ（オニオンアーキテクチャ、クリーンアーキテクチャ、ヘキサゴナルアーキテクチャなど）に依存せず適用する。

---

# 基本原則

## 1. 共通化より局所化を優先する

コードは可能な限り、その責務を持つ機能やファイルの近くに配置する。

再利用されたという理由だけで安易に共通フォルダへ移動してはならない。

共通化は「本当に共通概念である」と判断できた場合のみ行う。

---

## 2. 肥大化したら分割する

ファイルが大きくなり、

* 理解しにくい
* 修正しにくい
* レビューしにくい

状態になった場合は責務ごとに分割する。

ただし機能単位のまとまりは維持すること。

---

## 3. 所有者を中心に構造化する

分割したコードが特定ファイルからしか利用されない場合、そのファイル専用のフォルダにまとめる。

例：

```text
user_page/
    user_page.ext
    header.ext
    list_view.ext
    action_panel.ext
```

補助ファイルは親ファイルの責務に属するものとして扱う。

---

## 4. フォルダ分類の判断順序

フォルダへ分類する際は、次の順で判断する。

1. **まず種類（責務カテゴリ）別に分類する。**
   `controllers/`、`views/` のように、同種の役割を持つ独立したファイル群は種類別フォルダへ配置する。
2. **種類分類に馴染まないものは所有者中心に分類する。**
   特定の親ファイルからしか利用されない派生ファイル群（単一ファイルの肥大化を分割した結果など）は、種類別フォルダではなく、親ファイルごと専用フォルダにまとめる（フォルダ化ルールの「推奨構成」）。

種類別フォルダと所有者フォルダは入れ子にしてよい
（例：`views/full_view/` = 種類別フォルダの中に、FullView 専用の派生ファイル群を所有者フォルダとして置く）。

---

# フォルダ化ルール

※本節（推奨構成／非推奨構成）は、**単一ファイルが肥大化して派生ファイルへ分割する場合**のルールである。役割が独立したファイル同士の分類には、基本原則 4 の「種類別分類」を先に適用する。

## 推奨構成

ファイルが肥大化して複数ファイルへ分割する場合は、親ファイル専用フォルダを作成する。

```text
user_page/
    user_page.ext
    user_header.ext
    user_list_view.ext
    user_action_panel.ext
```

---

## 非推奨構成

```text
user_page.ext
user_page/
    user_header.ext
    user_list_view.ext
```

理由：

* IDE上で親子関係が分かりにくい
* ファイルとフォルダが離れて表示される
* 関連ファイルの発見性が低下する

---

## 判断基準

以下の状態になったらフォルダ化を検討する。

* 分割ファイルが2個以上になった
* 今後さらに増加する可能性が高い
* ひとつの責務群として管理したい

---

# 昇格ルール

コードの配置は使用範囲によって決定する。

---

## 第1段階：Private（専用）

利用箇所が1つのみ。

配置場所：

```text
feature/
    target_file/
```

または同等のローカルフォルダ。

---

## 第2段階：Feature Shared（機能共有）

同一機能内の複数箇所から利用される。

配置場所：

```text
feature/
    common/
```

例：

```text
trade/
    common/
        price_formatter.ext
        trade_validator.ext
```

---

## 第3段階：Global Shared（全体共有）

複数機能から利用される。

配置場所：

```text
shared/
```

例：

```text
shared/
    validation/
    formatting/
    ui/
    domain/
```

---

# 共通フォルダの制約

共通フォルダを雑多な置き場にしてはならない。

禁止例：

```text
common/
    utils.ext
    helper.ext
    misc.ext
```

推奨例：

```text
shared/
    validation/
    formatting/
    ui/
    domain/
    infrastructure/
```

責務ごとに分類すること。

---

# 移行ルール

コードを移動する際、

* 一時的なラッパー
* export
* re-export

の利用は許可する。

ただし移行期間のみとする。

恒久的な互換レイヤーを作ってはならない。

削除予定コメントや Deprecated 指定を付与すること。

---

# 依存関係ルール

コードは使用範囲に応じて上位へ昇格する。

```text
Private
    ↓
Feature Shared
    ↓
Global Shared
```

逆方向への移動は原則禁止とする。

---

# AIの判断手順

コードを新規作成または修正する際は以下の順で判断する。

1. どの種類（責務カテゴリ）のフォルダに属するか（基本原則 4。種類別が先、馴染まなければ所有者中心）
2. このコードの所有者は誰か
3. 利用箇所は何箇所か
4. 最も狭いスコープへ配置できないか
5. 共通化する必然性はあるか
6. フォルダ化した方が発見しやすくならないか
7. 将来的な保守性は向上するか

---

# デフォルト判断

判断に迷った場合は以下を優先する。

* 共通化しない
* 近くに置く
* 昇格を後回しにする
* 発見しやすさを優先する
* 保守性を優先する

短期的な便利さよりも長期的な管理容易性を重視すること。

# 本リポジトリへの適用注記（Python / オニオン構成・レイヤ first）

> 本リポジトリは `keyseq/` 配下に `domain` / `application` / `infrastructure` /
> `presentation` のレイヤ first 構成。

## スコープの対応

- **第1段階 Private** = 親ファイル専用パッケージ（例: `keyseq/presentation/xxx/`）
- **第2段階 Feature Shared** = レイヤフォルダ直下（例: `keyseq/domain/` 直下のモジュール）。
  本リポジトリの「機能」単位はレイヤと読み替える
- **第3段階 Global Shared** = `keyseq/shared/`（現状は存在しない。必要になった時点で作成）

## Python での親フォルダ方式

- 「親ファイル専用フォルダ」はパッケージで実現する:
  `xxx/`（`__init__.py` + `xxx.py` + 補助モジュール）
- **パッケージの `__init__.py` による再輸出（公開面の定義）は「恒久的な互換レイヤー禁止」の
  対象外**とする。Python の標準作法であり互換レイヤーではない。
  禁止対象は「移動前の旧パスに残す横流し専用モジュール」（例: 移動済み定数を再輸出するだけの
  旧モジュールを削除予定なしで残すこと）

## 命名の注意

- `shared/` 配下のサブフォルダ/ファイル名にオニオン層名（`domain` / `infrastructure` 等）を
  使わない（ルール本文の推奨例はレイヤ first 構成では名前衝突するため）
- パッケージ内の補助モジュールでも `helpers.py` / `utils.py` のような雑多名は避け、
  内容を表す名前（例: `pick_helpers.py` = 候補選定純関数群）を付ける

## 正本ドキュメントの例外（親フォルダ方式の読み替え）

`instructions/common/spec_detail/` の正本仕様書を分割する場合は、**親（INDEX）ファイルを
`spec_detail/` 直下に残し、分割した節を同名フォルダ配下に置く**
（例: `spec_detail/key_input.md`〔INDEX〕 + `spec_detail/key_input/5_13_move_mode.md`）。
ルール本文の「非推奨構成」（親がフォルダ外）に該当するが、正本は凍結文書から
「ファイル名 + 節番号」で参照されており、親のパス安定が発見性より優先するため例外とする。
分割の判定・手順は `/spec_split`（`.claude/commands/spec_split.md`）に従う。

## 「肥大化したら」の数値解釈

判定の数値閾値は `/refactor_check`（`.claude/commands/refactor_check.md`）の
M1〜M6（ファイル 600 行超 + フェーズで +100 行 / 関数 80 行超 / 同型ブロック 3 箇所 等）を
用いる。本ルールは「どこへ置くか」、/refactor_check は「いつ直すか」を担当する。
実装時の予防目安（関数 30 行超で抽出検討・新規ファイル 300 行以内）は
`.claude/rules/implementation.md` に定める。
