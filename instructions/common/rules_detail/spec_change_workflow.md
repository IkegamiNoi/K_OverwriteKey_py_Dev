# 仕様変更ワークフロー（詳細版）

> 本書は `.claude/rules/spec_change_workflow.md`（要点版・毎セッション自動読込）の詳細版。
> 規範の正は要点版。ルール変更時は要点版を先に直し、本書を追従させる。
> 本書は自動読込の対象外であり、報告テンプレート・手順詳細が必要なときのみ読む。

---

## ■ モードの選択（詳説）

**直接改訂モード**を使う — 次を **すべて** 満たすとき:

- 変更が単一 spec_detail ファイル・少数条項に閉じる（局所的）
- 最終文言が着手前に確定している（探索不要）
- タスクが少ない（目安 1〜2）
- 例: キーリバインド 1 件、制約文言の微修正、合意済みの小変更

**暫定仕様先行モード**を使う — 次の **いずれか** に該当するとき:

- 複数の spec_detail ファイルに跨る／多数の条項を変える（多岐・目安 2 ファイル以上）
- **設計が未確定で、ユーザーと反復して詰める必要がある（探索的）** ← **強いトリガ。規模が小さくてもこれに該当すれば暫定仕様先行を採る**
- タスクが複数（目安 3 以上）で、実装中の設計微修正が仕様へ跳ね返りうる
- 新機能フェーズ／別実装同期があり、正本を一度・原子的に変えたい

**迷ったら暫定仕様先行に倒す**（正本を中途半端な状態で長く晒すリスクを避ける）。規模判断に迷う場合はユーザーへ確認する。

## ■ 検出基準の詳細（フラグを立てるべき状態）

### A. 仕様書 vs 実装の乖離
- 仕様書に書かれた挙動と現実装が一致しない
- 仕様書のサンプル（`samples/` 配下等）と実装出力がバイト一致しない
- 仕様書の制約（型・必須・キー順等）を実装が満たしていない

### B. 仕様書の不備
- 仕様書に未定義の挙動を実装で決める必要がある
- 仕様書に矛盾する記述がある
- 仕様書に書かれた要件が実装上不可能・非現実的
- 仕様書のサンプルが仕様本文と矛盾している

### C. 設計判断の波及
- レビューで「仕様書側で再検討推奨」項目が出た
- スコープ変更（task の対象範囲拡張等）に伴い仕様書の解釈が変わる必要がある
- 別実装との整合上、仕様書を厳密化／緩和する選択が必要

### D. 危険な誘惑
- 「実装が楽になるから仕様書を緩めたい」という選択肢が頭をよぎる
- 「仕様書のこの記述は無視しても大丈夫だろう」という判断をしようとしている

→ D が出た時点で必ず止める。これが最も事故を起こす経路。

## ■ 検出時の報告フォーマット

ユーザーへの報告は以下を含めること。

```
## 仕様変更フラグ

**検出した状態**: A / B / C / D のどれか
**該当箇所**:
- 仕様書: instructions/common/spec_detail/<file>.md:<line>
- 実装: <path>:<line>（または該当タスク）

**ズレの内容**: 仕様書はこう書いてあるが、実装/レビューはこうなっている

**選択肢**:
- (A) 仕様書を <方向> に更新する
- (B) 実装を <方向> に修正する
- (C) 保留（追加調査）

**推奨**: <理由付きで A/B/C のどれか>
**影響範囲**: <他タスク / 別実装 / テスト fixture 等>
```

報告後は **ユーザーの判断を待つ**。勝手に進めない。

---

## ■ ユーザー判断後の手順

ユーザーが (A) 仕様書更新を選んだ場合:

`/spec_update` コマンド（`.claude/commands/spec_update.md`）を呼び出して以下の手順を実行する。

1. 影響範囲の特定と提示（ユーザー確認を取る）
2. 仕様書本体（`instructions/common/spec_detail/*.md`）の更新
3. サンプル（`samples/` 配下）の更新（必要時のみ）
4. `.claude_data/state/decisions.md` への判断履歴追記
   - **採用 / 修正して採用 / 保留 / 除外** の区分を明示
   - **理由** と **代替案を不採用にした根拠** を残す
5. 影響を受けるタスクファイルの更新
   - 「対象範囲」「検証項目」「未適合項目テーブル」「実装上の制約」「推奨実装順序」など該当セクション
6. 必要に応じた再検証タスクの起票
   - 命名: `task_NN_NN_<topic>_recheck.md`（例: `task_01_01_domain_scope_recheck.md`）
7. `instructions/phase/current.md` の更新

詳細手順は `.claude/commands/spec_update.md` を参照。

ユーザーが (B) 実装修正を選んだ場合:

1. 仕様書は無修正
2. 既存のタスクワークフロー（`task_execution.md`）に従って実装エージェントへ修正依頼（選択基準・既定エージェントは `.claude/rules/agent_selection.md`）
3. `decisions.md` への記録は任意（重要な判断のみ）

## ■ 分割後の正本構造（INDEX 化）の運用詳細

正本が肥大化した場合は INDEX 化して分割できる。分割後は**実体が同名フォルダ配下の子ファイル**
（親を開けば判別できる: 本文がリンク + 1 行要約なら INDEX。例: `features.md`〔INDEX〕+
`features/4_18_multi_select.md`〔実体〕）。

- 仕様更新は該当子ファイルを編集する。節の趣旨が変わったら親 INDEX の 1 行要約も追従させる。
- 新しい節は子ファイルを新規作成し親 INDEX に 1 行追加する（命名は `/spec_split` の規則）。
- 別実装との同期メモは正本本文に追記せず、専用のノートファイルへ分離する。
- 節番号と見出しテキストは既存参照の互換のため変更しない。

分割の経緯・対象ファイルの記録は `.claude_data/state/decisions.md` に残す。
