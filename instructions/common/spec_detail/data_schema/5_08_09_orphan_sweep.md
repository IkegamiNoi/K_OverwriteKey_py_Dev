#### 5.8.9 未使用ファイルの整理（検出 → 退避 → 復元 → 削除）

**どの構成セットからも参照されていない子ファイル（未使用の候補）を検出し、可逆な「退避」を経て
削除できるようにする保守機能**（起動口は設定メニューの 2 項目。UI は `features.md` §4.6）。
§5.8.1 の「参照元の掃除」が**現在の構成セットしか見ない**のに対し、本機能は**親ファイル → 子の
逆方向検査**を行う。**両者は別機能**であり、§5.8.1 の検査範囲は本節によって変わらない。

**検出（走査と判定）そのものは、ファイルを 1 件も書き換えない**（読み出しのみ。
書き込みが起きるのは退避・復元・削除と、走査フォルダ設定の保存だけ）。

**未保存の変更があるときは、走査の前に保存する** — 選択肢は**「保存する / 中止する」の 2 択**とし、
**保存しない選択・保存の失敗・別名保存のキャンセルはいずれも整理ごと中止**する
（保存が成功したときだけ走査へ進む）。未保存の編集内容は参照側の実体に反映されておらず、
**使用中の子を未使用の候補と誤判定し得る**ため。
§5.8.1 の「参照元の掃除」の保存確認とは**意味が逆の 2 択にならないよう**注意する
（掃除側の既存 API は「保存しない = 続行」であり、本機能では再利用しない）。

**走査範囲（参照側）** — 次の 4 経路の構成セットを読む。

走査した JSON が構成セットかどうかは、**`trigger_set_path` / `keymaps` /
`active_keymap_path` / `hotkey_presets_path` のいずれかのキーを持つか**で判定する
（**キーの有無**で見る。値が空かどうかは問わない）。ただし **`mappings` キーを持つ JSON はキーマップファイルとして
構成セットと判定しない**（phase 34 でキーマップファイルも `trigger_set_path` を持つため。旧形式で `trigger_set_path` しか持たない
構成セットは従来どおり拾う）。**走査はリンク / ジャンクションを辿らない**。

1. `config/user/keymap_sets/` **直下**
2. `config/config.json` の `keymap_set_path`（起動エントリ）
3. **現在開いている構成セット** — 通常読込も保存も `config.json` の起動エントリを書かない（§5.4）ため、
   **起動エントリでは代替できない**。落とすと**既定外のセットを開いている間にその子が退避される**
4. **ユーザー指定フォルダ**（§5.4 の `orphan_sweep_scan_dirs`。config 外でもよい・**非再帰**）

**参照集合の構築（3 段辿り・phase 34）** — 構成セットからキーマップ/ 個別 hotkey_presets のパスを読み、
**キーマップファイルの内容を読んでその `trigger_set_path` からトリガーセット**、**トリガーセットの `triggers[].sequence_path` から出力シーケンス**を読む
（構成セット→ キーマップ→ トリガーセット→ 出力シーケンス）。`keymaps[]` に加え **`active_keymap_path` の参照先も内容を読む**。
**旧形式の構成セットにある `trigger_set_path` もトリガーセットへの参照として数え続ける**（未移行の構成セットのトリガーセットを未使用にしない）。
読めなかったキーマップは既存の「読めなかった参照側（理由コード付き）」として扱い、そのキーマップが指すはずのトリガーセットは参照集合に入らない。
キーマップファイルは参照収集のために 1 回だけ読む（形状検証のために再読込しない）。
`external_keyboard_layouts[].path` は、**`config_root` 基準と、その親
（`dirname(config_root)`）基準の両方で解決した superset** を入れる。
登録・読込・表示は phase 64 で §5.7 どおり `config_root` 基準の相対へそろえたが、それ以前は親基準の相対表記
（例 `config\user\keylayout\jis.json`・旧既定の置き場所から登録した `keylayout\jis.json` など）で記録していた。
**旧表記の値は移行しない**（構成セットの読込でも単一 JSON の取り込みでも、読み込めず一覧から外れるだけで、利用者が JSON を手で直す）ため、**手で直していない旧表記の値が指すレイアウトも誤って退避しない**よう両基準を残す。
**`config/config.json` が指す共通プリセット（§5.10.1）も参照集合へ入れる**
（走査した構成セットからは辿れないため。個別指定と違い親ファイルを持たない）。

**候補側（退避し得るもの）** — config 配下の既定 4 フォルダの**直下のみ**（非再帰）:
`user/keymaps` / `user/trigger_sets` / `user/sequences` / `user/hotkey_presets`。
**形状検証**を通ったものだけを候補にする（`mappings` は dict / `triggers` は list /
`actions` は list / `hotkey_presets` は list）。
**`user/hotkey_presets/global/` は候補側から除外する**（予約フォルダ。§5.10.1）。

**保護対象** — **編集中の構成が使っているパスは、参照集合の判定によらず候補にしない**:
現在の構成セット自身（**アプリが保持する現在のパス**）/ 各キーマップ/ **全キーマップの**トリガーセット/ その各出力シーケンス（共有実体は重複を除く）/
構成セット専用プリセット（**この 4 種は runtime が持つ保存表記**）。
**実在しなくても保護する**（存在確認をしない）。**config 配下でなくても保護する**。

**判定名**（§5.8.4 と同じく、**分岐は判定名で行い表示文言で分岐しない**）:
`ORPHAN_CANDIDATE`（未使用の候補）/ `ORPHAN_REFERENCED`（参照あり）/ `ORPHAN_PROTECTED`（保護対象）/
`ORPHAN_EXCLUDED`（形状検証などで対象外）。

**走査の不完全性の扱い** — 次の 5 つは**握りつぶさず結果に含める**
（未使用の候補が 0 件でも該当があれば通知に含める）:
①**読めなかった参照側**（JSON として壊れている）②**リンク / ジャンクションのため読まずにスキップした参照側**
③**`listdir` に失敗した走査フォルダ** ④**見つからない指定フォルダ**
⑤**構成セットとして解釈できなかった JSON**。
**警告は一覧の先頭に出し、警告があっても実行は許す**（「実行 / キャンセル」の 2 択。
**行ごとの選択 UI は設けない**）。
**走査範囲外の構成セットから参照され得る旨は、警告の有無にかかわらず常に併記する**
（制約 1 を利用者へ伝えるため）。

**退避** — 退避先フォルダは **`config/quarantine/`**（`user/` の外＝候補側と構造的に交差させない）。
  **遅延作成**（§5.4）。回は **`<YYYYMMDD_HHMMSS>`**（衝突時は `_<連番>`）で、
その下に**元の相対構造を保って移動**する。

* **退避の記録は移動より先に、原子書込みで作る**: ①これから動かす全件を**計画**として
  `manifest.json` へ書く → ②**書けなければ 1 件も動かさない**（退避を中止する）→
  ③1 件ずつ移動し、成功のつどそのエントリの状態を更新する。
  後追い記録だと、中断時に**実体はあるが退避の記録が無い**＝復元できない退避物が残る
* `manifest.json` は `created_at` と `entries[]`（`kind` / `original_path` / `quarantined_path` /
  `state`）を持つ。`state` は **`planned` / `moved` / `failed`**
* 退避するのは**〔ユーザーへ提示した未使用の候補〕∩〔退避直前の再判定でも未使用の候補〕**に限る
  （提示していないものを破壊的に動かさない）。再判定で増減した分は件数を結果に出す
* **移動のみ**（元ファイルを削除しない）。1 件ずつ行い、**失敗しても継続**する（件数 + 理由を出す）
* **runtime / 未保存マークは変更しない**
* 退避先フォルダが**リンク / ジャンクション**のときは中止する（実体を退避先フォルダ外へ出さない）
* **回のフォルダの作成に失敗したときも中止する**（1 件も動かさない）。
  作成は**既存フォルダへの再利用を許さない**（同名がすでにあれば失敗として扱う）
* 退避の記録に書くパスは **§5.7 の保存表記**（config 配下は相対）とし、復元時に解決する

**復元** — 回を選び、退避の記録に従って元の場所へ戻す。

* **`state` は信用せず、`quarantined_path` の実体の有無で判定する**
  （進捗書込みが失敗すると `state` が `planned` のまま実体は移動済みになり得る）
* **`original_path` が候補側 4 フォルダの配下でなければ拒否する**。
  **`user/hotkey_presets/global/` 配下は無条件に拒否する**（予約フォルダ。§5.10.1）。
  **§5.7 の `is_path_within` は同一パスも「配下」と判定する**ため、それだけに頼らない
  （フォルダそのものへの復元・退避先フォルダ外への書き込みを防ぐ）
* **復元先に同名ファイルがあれば上書きせずスキップ**し、結果に「復元先に同名ファイルがあります」と出す。
  **復元先フォルダが無ければ作成する**
* **部分失敗を許容**（1 件ずつ・失敗は理由付きで記録して継続）
* **全件が戻った回は、退避の記録と空フォルダを削除する**（中途半端に残さない）。
  1 件でも残っていれば回を残す
* **退避の記録が読めない回は復元対象にしない**（一覧に**「記録が正しくありません（復元できません）」**と出す）。
  この回も**削除だけは可能**（下記の検証④の緩和。消せない残骸を残さないため）

**「退避の記録が読めない」の定義** — ①**JSON として解析できない** ②**トップレベルが object でない**
③**`entries` が配列でない** ④**`manifest.json` 自体がリンク / ジャンクションである**、のいずれか。
④は**内容以前のパス安全性のガード**で、中身が妥当な JSON でも読まずに不正扱いにする
（退避先フォルダ外の実体を復元の入力にしない）。
**エントリ単位の妥当性（必須キーの有無・値の形）は検査しない**（下記の既知の制約 8）。

**削除（不可逆）** — 粒度は**退避の回ごと**。

* **API はパスを受け取らず、回の IDだけを受け取る**（UI から渡された文字列を信用しない）。
  **API 側で 4 つを検証**する: ①退避先フォルダ**直下**に実在するフォルダである
  ②名前が回の形式（`YYYYMMDD_HHMMSS` または `_<連番>` 付き）に一致する
  ③canonical 表記が**退避先フォルダ自身と一致しない** ④**有効な `manifest.json` を持つ**
* **④だけは「退避の記録が不正な回の削除を明示的に許可する」引数で上書きできる**（既定は拒否）。
  ④を絶対条件にすると**復元も削除もできない残骸**が残るため。**①②③は緩和しない**
* **UI は通常の削除と文言を分ける**。退避の記録が不正な回のときは
  **「退避の記録が読めないため、中身を確認できません。」**と**「フォルダごと削除します。」**を
  **別行で**明記する
* **削除前に対象パスを全件提示**し、**不可逆である旨を確認画面の先頭に書く**
* 実体は**回のフォルダの再帰削除**（`manifest.json` を含む）。
  **OS のゴミ箱へは送らない**（退避が可逆層を兼ねる・新規依存を足さない）。
  **リンクは辿らず、リンク自体を削除する**（**シンボリックリンクの場合**。
  ジャンクションは下記の制約 10）
* **途中で失敗した場合は中止とし、「一部が削除されている可能性がある」旨を通知する**。
  退避・復元のような 1 件ずつの継続は行わない（**削除の粒度が回のフォルダ**であり、
  ユーザーは「この回を消す」と指示しているため）
* **最後の回を削除したら退避先フォルダ自体も片付ける**（他の回が残っていれば残す）

**既知の制約**（いずれも**実装を変えず契約として明記**する）

1. **全網羅ではない**。走査は上記 4 経路に限られ、**`user/keymap_sets/` のサブフォルダ**・
   **config 配下の非既定フォルダ**・**config 外の任意フォルダ**へ別名保存された構成セットは
   走査できない。そこから参照されている子を**未使用の候補として提示し得る**。
   だから**削除ではなく退避を既定**とする
2. **候補側は既定フォルダ直下のみ**（非再帰）。サブフォルダに置かれた子は対象外
3. **走査と退避の間に外部変更があり得る**。退避の直前に判定をやり直し、上記の積集合だけを退避する
4. **`_parent_refs` は参照しない**（best-effort であり未使用の判定の根拠にできない。§5.8.1）
5. **壊れた親があると、無傷の子を恒久的に失い得る**。読めない 構成セットがあると、
   **その親が参照していた子は参照集合から抜け落ち、無傷でも未使用の候補になる**。
   警告は出るが退避・削除とも許すため、警告を読まずに削除まで進めると復旧できない。
   **壊れているのは親（多くは手で直せる小さなファイル）で、消えるのは子**である点に注意
6. **削除の確認画面の一覧は情報提供にすぎない**。一覧を作ってから確認を閉じるまでの間に
   外部プロセスがその回へファイルを追加すると、**一覧に出ていない中身も一緒に消える**
   （ユーザーは回の IDを選んでいるため挙動は意図どおり）
7. **検証と再帰削除の間の TOCTOU は許容する**。窓は削除 API の内部に限られるが、
   その間に退避先フォルダを外部へのリンクへ差し替えられれば外部の実体を消し得る。
   塞ぐには削除完了まで実体を固定する仕組みが要り、**新規依存を足さない方針と衝突する**。
   退避先フォルダを差し替えられる権限があればアプリを介さず直接削除できるため上積みも小さい
8. **退避の記録の妥当性をエントリ単位では検査しない**。手編集などで**well-formed だが実体を
   指さない退避の記録**にすると、その回は**「有効」として一覧に出る**。退避側に実体が残っていても
   **復元は 0 件**になり（各エントリは「退避先にファイルがありません（復元済み等）」でスキップ）、削除は通常経路で進む。
   ただし削除の確認画面は**実体を全件列挙**するため**消せない残骸にはならない**。
   アプリ自身の書込みは原子的でこの形を作らないため、**発生源は手編集に限られる**
9. **一覧に出ない残骸はアプリから扱えない**。退避先フォルダ直下でも、名前が回の形式でないもの・
   リンク / ジャンクションであるもの・フォルダでないファイルは、**一覧にも出ず復元も削除もできない**
   （エクスプローラ等で片付ける）
10. **削除 API 単体では、回のフォルダ自身のリダイレクト検査を課していない**。
    退避先フォルダ外へ向くリンクは実体基準の境界検証で拒否されるが、**退避先フォルダ内の別の回を指す
    ジャンクションに対しては、削除でその別の回の中身まで消え得る**。
    ただし**UI からは到達しない**（一覧がリダイレクトされた回を弾くため、選択肢に出ない＝制約 9）。
    **API を直接呼ぶ経路にだけ残る性質**として記録する
11. **空になった退避先フォルダの後始末は削除と復元で非対称**。削除は最後の回を消した時点で
    退避先フォルダも片付けるが、**復元で全ての回が空になった場合は退避先フォルダが残る**（実害はない）
12. **候補側フォルダ直下のリンク / ジャンクションは、候補にせず件数にも出さない**
    （参照側と違い理由付きで報告しない＝無音で落ちる）。実体を移動する破壊的操作の入力に
    リンクを載せないための扱いで、**候補側は「実体のファイルだけ」を対象とする**
