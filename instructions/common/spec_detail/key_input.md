# key_input.md — キー入力・フック仕様

## 7. キー入力・フック

### 7.1 グローバルフック

* keyboard によるグローバルフックを必須とする
* `suppress=True` を使用する（元入力を抑制して置換する）
* suppress の副作用を常に考慮する

* **左右の修飾キーの名前**（phase 59・keyboard ライブラリの名前の表と正規化による）: 左 = `ctrl` / `shift` / `alt` / `left windows`、右 = `right ctrl` / `right shift` / `right alt` / `right windows`。レイアウトの修飾キーの行に `scan_code` を書かない限り（`features.md` §4.6）、修飾キーの名前は走査コードでの解決では決まらず `event.name` で決まる。キーマップ・トリガーの照合は名前の完全一致（左右・別名を同一視しない）
* **AltGr 配列の右 Alt**（phase 59）: Windows は偽の左 Ctrl（走査コード 541）と右 Alt の 2 つを送り、keyboard ライブラリは偽の左 Ctrl を `alt gr` としてアプリへ届け、**押下では続く右 Alt をアプリへ見せずに OS へ通す**（アプリは抑止できない・解放の順は未確認）。このため `alt gr` は割り当て禁止（`features.md` §4.3）。押下状態の記録は `alt gr` を `alt` にまとめる（既存）
* **フックの実行時のキー名の出どころ**（phase 62）: 順に テンキー（§7.8）→ **選んでいるレイアウトの `scan_code` だけで引く**（`features.md` §4.6。名前がテンキーのキー名なら採らない）→ keyboard の `event.name`。
  コードに直書きした特殊キーの表は持たない（phase 62 で削除）。トリガー・直接置換の元・切替 / 停止 / トグルキー・押下状態・重なり判定と、画面の枠の編集の窓が同じ名前を使う
  * 受容: 特殊キーを書いていないレイアウト（既定の US TKL 等）では、JIS の特殊キーは `event.name`（keyboard が OS から得た名前。JIS の Windows では `半角/全角` 等）になり、`muhenkan` 等にならない / US 入力配列の「`」（走査コード 41）は `event.name`（「`」の見込み・未確認）になり、`zenkaku_hankaku` にはならない（キーボードUI の取得の `grave`〔§7.4〕とは一致しない）
  * 受容（2026-10-18 実測・Windows 11・JIS）: キーボードによっては、無変換・変換が **押下（`VK_IME_OFF` / `VK_IME_ON`・走査コード 241 / 242）だけで約 60 ms の間に 3 回**届き、離しが届かない（MS-IME のキーの割り当てをオフにしても起きる・キーボード本体が LANG2 / LANG1 で送る見込み）。
    このキーは扱えない（割り当てると 2 回目の押下が送信ガードの最中に届いて素通りし、二重送信にもなる）。対応は idea_52

### 7.2 フックの停止制御

* 停止キー（hook_stop_key）でフックを停止できる。停止トリガーも単キー
* UI 編集中（キャプチャ・ダイアログ等）はフックを停止する（**ネスト対応**: 多重に
  停止要求が重なっても、すべて解除されるまで再開しない）
* **停止要求は閉じ方によらず解除される**（OK / キャンセル / Escape / 閉じるボタン /
  プログラムからの破棄のいずれでも、ちょうど 1 回）
* **停止要求が残っている間は置換もアクション実行も行わない**（停止が間に合わず届いた入力は**元のまま素通しする**。飲み込まない）
* **アプリの終了が確定した後はフックを再開しない**

### 7.3 トリガー・入力判定の優先順位・重複（phase 34）

* トリガーは単キーのみ。トリガー一覧はキーマップに従属し（`data_schema.md` §5.13）、入力判定・表示はアクティブキーマップのものを扱う
* **入力判定の優先順位**: **停止 > トグル > 直接切替 > トリガー > 置換**（トリガー・置換はアクティブキーマップのもの）。
  「キーマップ一時停止」中は停止 / トグル以外（直接切替・トリガー・置換）はすべて無効。
  **アクションが空のトリガーは無いものとして扱う**（置換元キーと重なれば置換が動く。キーボード表示はトリガーを上に出すため、この場合だけ表示と動作が食い違う = 受容）
* **画面の枠**（phase 56・57・`features.md` §4.7）: 枠の表示中は**直接切替の後・トリガーの前**で枠の操作を判定する。
  ctrl / alt / windows の押下中と修飾キー単独は素通し、**suppress する集合のキーは枠の操作として suppress**、それ以外は素通し（**トリガー・置換へ進まない**）。
  フックのスレッドが見るのは、UI スレッドが状態の変化ごとに計算して不変の値として差し替えて公開する「表示中か・世代・suppress する集合（実効の集合 1 本）」と、キーを振り分けた時点の修飾キー（shift・ctrl・alt・windows・alt gr）の押下だけ
  （phase 57 で「深さ ≥1 の印」と Esc の特別扱いを廃止し、Esc・矢印の条件を集合の計算へ移した）
  * **UI スレッドでの判定の順**（phase 57）: 今の深さの枠のキー > 操作キー（付け替えた 8 操作 → 固定の esc = 戻る / num enter = クリック）。操作キーどうしは 深くする → 戻る → クリック → 次の画面へ → 上 → 下 → 左 → 右 の順
  * **枠のキーの予約**: 固定の予約キー = **修飾キー**（shift・ctrl・alt・windows の左右）だけ（phase 57 で enter / num enter / space / esc / backspace / tab を外し操作キーへ移した）。読込時も検査し、含む形は既定へ戻す（`data_schema.md` §5.6.1）。
    **操作キー（固定の esc / num enter を含む）との重なり**と設定で変わる予約キー（停止 / トグル / 全キーマップの直接切替キー）は**編集の窓の OK でだけ拒否**する
    （編集中の keymap 自身の元の切替キーは除き、ダイアログの切替キー欄の今の値は含める）。読込時・手編集の重なりは上の判定の順で解決する
  * **下の重複の表に枠のキー・操作キー（固定を含む）は足さない**（グレー表示・案内の対象にしない）。後から停止 / トグル / 直接切替キーを枠のキー・操作キーと同じにしても拒否せず、振り分けで上位が勝ってその枠・その操作は使えない（受容）。
    枠のキーはトリガー・置換元キーと重なってよい（枠の表示中はトリガー・置換が効かないため）
* **切替中の受け付け停止**: 判定（フックのスレッド）で直接切替を決めた瞬間に「切替中」の印を立て、印がある間に届いたキーは
  停止 / トグル以外を**処理せず素通しする**（元のキーのまま OS へ渡す・§7.2 と同じ扱い）。UI スレッドで切替が終わったら
  （アクティブの変更・再描画・重なりの表の作り直しまで。連続実行中などで拒否された場合も）印を下ろして受け付けを再開する。
  切替前の状態で判定されたキーが切替後の状態で実行されるずれを防ぐ
* **トリガーの押下のリピートの印**（phase 50）: トリガーに決まった down には、その down の前に同じキーが既に押下中だったか（押下状態の管理による）を
  「リピート」の印として添えて実行側へ渡す。suppress の決定は印に関係なく従来どおり。印は「確認して実行」の長押しの無視（`features.md` §4.2.11）にだけ使う
* **編集時の重複禁止**:

  | 登録するもの | 拒否する相手 |
  |---|---|
  | トリガーキー | 停止 / トグル / 全キーマップの直接切替キー / 同キーマップの既存トリガー / 同キーマップの置換元キー |
  | 置換元キー | 停止 / トグル / 直接切替キー / 同キーマップのトリガーキー |
  | 直接切替キー | 停止 / トグル / 全キーマップのトリガーキー / 全キーマップの置換元キー / 他キーマップの切替キー（このほか割り当て禁止のキーは切替キーにできない・`features.md` §4.3・phase 59） |
  | 停止 / トグルキー | 互い / 全キーマップのトリガーキー / 全キーマップの置換元キー / 直接切替キー |

  表は**追加・キー変更**のとき。キーを変えない編集（ラベル・suppress 等）では重複検査をしない（phase 43）。
  キーマップの追加・個別読込・貼り付けで切替キーをまとめて設定するときは、反映後の完成予定の状態に対してこの表を適用する（`features.md` §4.3）。
  別キーマップのトリガーと置換元キーの重複は許す（別モード）。共有しているトリガー一覧で別キーマップの置換と重なった場合は、
  そのキーマップではトリガーが動き置換が使えなくなる（キーボード表示でトリガーが上に出ることで分かる）
* **読込等で重なった場合（編集時の拒否をすり抜けた重なり）**:
  * トリガーが停止 / トグル / 直接切替キーと重なる → トリガー一覧で**グレー表示＋理由**（「停止キーと重複」/「一時停止/再開キーと重複」/「切替キーと重複」。
    複数なら上位の 1 つ）。入力判定では上位が動く。編集はできる
  * **同じトリガー一覧に同じキーの行が複数ある**（複製・貼り付け・読込。phase 43）→ **一覧で一番上の行が有効な行**、下の行は**グレー表示＋理由「上のトリガーと重複」**。
    理由の優先は 停止 > トグル > 切替 > 上のトリガー（複数なら上位の 1 つ）。入力判定・キーボード表示・重なりの判定は有効な行で引く。
    一番上の行のアクションが空なら、そのキーはトリガーとして無いものとして扱い、下の行も実行しない（置換が動く）。
    **この重なりでは「重なったキーを押したときの案内」を出さない**（有効な行が動くため）。実行中の状態と有効な行の交代は `features.md` §4.1
  * 直接切替キーが停止 / トグルと重なる → キーマップ一覧で**グレー表示＋理由**。キーでは切り替わらないが**一覧からの選択・編集はできる**
  * **置換元キーとの重なりではトリガーをグレーにしない**（トリガーが勝つ）
  * キーボード表示: トリガーを置換より優先して表示し、予約キー（停止 > トグル > 切替）が最後に上書きする
* **重なったキーを押したときの案内**（同じキーの行の重複は除く・上記）: グレー表示の割り当てに対応するキーが押され上位が働いたとき、**ステータスバー中央の一時メッセージ領域**に
  重複と変更の案内を出す（例「f12 は停止キーと重複しているため、トリガーは実行されません。トリガーのキーを変更してください」/
  「f9 は停止キーと重複しているため、キーマップ <名前> へ切り替えられません。切替キーを変更してください」/
  「f3 は切替キーと重複しているため、トリガーは実行されません。…」）。停止キーでフックが止まる場合は「停止しました」と併記する（上書きしない）。
  置換元キーと停止 / トグル / トリガーの重なりは案内しない。「キーマップ一時停止」中は重なりの案内を出さない
* **重なりの判定は 1 箇所**に置き（置き場は `codebase_map.md`）、グレー表示・案内・編集時拒否・開始検証が共有する。
  判定結果は**読み取り専用の表**として保持し、データが変わる契機（トリガー / 置換 / 切替キー / 停止・トグルキーの編集・読込・アクティブ切替・
  一覧の並べ替え・貼り付け・範囲削除〔phase 43〕）で作り直す。
  **キー入力時（フックのスレッド）は表を引くだけ**で全件走査しない。どの割り当てが動くか（上記の優先順位）はキー入力時に判定し、表は案内にだけ使う
* **フック開始を止める重複は「停止キーとトグルキーが同じ」だけ**。停止 / トグルとトリガー・置換元キー・直接切替キーの重なりでは開始を止めない。
  「トリガーが 1 件も無い」判定は全キーマップのトリガー・置換元キーで行う。**枠 ON（`grid.enabled` が真）の keymap があれば、トリガー・置換元キーが無くても開始・一時停止からの再開を止めない**（phase 56）

### 7.4 キーキャプチャ

* 停止キー / トグルキーのキャプチャは相互排他とする
  （`SingleKeyCaptureController` が担当。現状は `codebase_map.md` を参照）
* **画面の枠の編集の窓のキーの取り込み**（phase 56）: 押したキーを**フックの振り分けと同じ名前**にする。
  順に テンキー（`numpad_name_from_tk_event`）→ キーボード配列のスキャンコード（VK → `MapVirtualKeyW` でスキャンコード → 配列の解決）→ 修飾なしの文字（`MapVirtualKeyW` の `MAPVK_VK_TO_CHAR`。
  配列の定義がスキャンコードを持たないとき〔US TKL 等〕にフックの `event.name` と同じ `.` `,` 等になる）→ Tk の keysym の正規化。
  Tk の keysym の正規化だけでは記号キーが `period` / `comma` 等になりフックの名前と一致しないため。**既存のキー取得（トリガー・停止 / トグル・切替キー）はこの方法に変えていない**（idea_45）
* **キーボードUI の編集のキーの名前**（phase 61）: 順に テンキー（`numpad_name_from_tk_event`）→ Tk の keysym の表（`TK_KEYSYM_TO_KEYBOARD_NAME`）→ **VK を `MapVirtualKeyW` で走査コードへ変換し、選んでいるレイアウトの `scan_code` だけで引く**（フックの実行時と同じく、コードに直書きした特殊キーの表は無い・§7.1）→ Tk の keysym の小文字。
  変換できない（走査コード 0・Windows 以外）ときはレイアウトを引かず keysym へ。Tk の `keycode`（VK）をそのまま走査コードとして引くと F1 / F10 / F12 が `kana` / `henkan` / `muhenkan` になるため（phase 61 で修正）
  * 受容: JIS キーボードで jis.json 以外のレイアウトを選んでいると、キーボードUI では特殊キーが名前にならない（フックの実行時と同じ・§7.1）/ US 入力配列の「`」はキーボードUI では `grave`、フックの実行時は `event.name`（「`」の見込み・未確認）で、名前は揃っていない（idea_45 の領域）
  * レイアウトを引いた名前がテンキーのキー名なら採らず keysym へ落とす（フックの実行時と同じ・§7.8。外部レイアウトにテンキーの id と `scan_code` を書いても、拡張キー〔Insert 等〕がテンキーの名前に化けない。テンキーは先頭の判定が拡張ビットで決める）
  * 未対応: JIS の特殊キー（無変換・変換・半角/全角・かな）は**全入口共通で**取得できない（下の「判別できないキー」。#7 の上の解決は、これらが VK で届く環境のための経路として残る）
* **切替キーの取得**（phase 59）: Caps Lock は取得しない（`features.md` §4.3「割り当て禁止のキー」）。`??` の扱いは下の「判別できないキー」（全入口共通）
* **取得の入口**（phase 60）: キーを押して取得するのは次の 8 つ。#1 停止キー / トグルキー（メイン窓）/ #2 トリガーキー / #3 切替キー（キーマップの編集ダイアログ）/ #4 複数キーマップの切替キー（まとめて設定）/
  #5 アクションの hotkey の記録 / #6 key_hold の「1 キーを記録」/ #7 キーボードUI の編集（元キーの枠のクリック → 押したキーを割り当て）/ #8 画面の枠の編集の窓
  * 取得の期間: #1〜#7 は各入口の取得の開始から終了（取得できた・Esc・ボタン・種類 / 対象の切替・排他・右クリック・閉じる・窓の破棄のいずれか）まで。#7 は割り当てが拒否されたとき編集が続く。#8 は**窓を開いている間ずっと**
* **取得中の IME**（phase 60）: 取得の間だけ**アプリ自身の IME を OFF にし、終わったら元へ戻す**（IME が ON だと Tk にはどのキーも「IME が処理中のキー」〔`VK_PROCESSKEY`・名前 `??`〕で届き、取得できないため）
  * 対象 = アプリの UI スレッドの入力コンテキスト（Tk の窓はルート・Toplevel の外枠と中身・各ウィジェットとも同じ入力コンテキストを共有する〔2026-10-16 実測・Tcl/Tk 8.6.15〕）。ルートの窓の HWND で `ImmGetContext` → `ImmGetOpenStatus` / `ImmSetOpenStatus` → `ImmReleaseContext`（自スレッドの直接呼び出し・時間制限なし）。送信用の §7.7（`WM_IME_CONTROL`・別プロセスの窓）とは別の口で、状態も共有しない
  * 開始: 取得中でない入口の開始のたびに開閉を問い合わせ、**ON なら OFF** にして「アプリが OFF にした」印を立てる（OFF なら何もしない）。取得中の入口の開始が終了を挟まずに再び呼ばれたとき（#7 の編集中の別の元キーのクリック）は何もしない（手で ON にした変換中に OFF にして確定した文字を記録しないため）
  * 終了: 取得中の入口の終了だけが数を減らす（重複した終了・未開始の終了は何もしない）。**取得中の入口が 0 になったときだけ**、印が立っていてその時点で OFF なら ON へ戻し、印を下ろす（取得中にユーザーが手で ON にしていれば触らない）。数が残る終了では印に触らない。戻すのは即時。窓の破棄でも戻す（窓自身の破棄に限る・子の破棄では終わらない）。アプリの終了のための特別な復元はしない（窓の破棄の経路で戻ることはある。入力コンテキストはアプリのスレッドのもので、他のアプリへは影響しない）
  * 重なり: 取得が重なる（#7・#8 の長く続く取得の間に他の入口 等）ときは上の数と印で扱い、2 番目以降の入口の開始でも ON なら OFF にする
  * 失敗: 入力コンテキストが取れない・API が失敗したときは IME に触らず取得はそのまま続ける（通知しない・例外はログ）。Windows 以外では何もしない
  * 受容: #7・#8 の取得の間はアプリの他の入力欄（ラベル欄 等）も IME が OFF で始まる（手で ON にはできる）/ 他の欄で手で ON にして変換中のまま別の入口の取得を始めると、開始の OFF で確定した文字が取得され得る（Tk のイベントの順序に依存・未実測）/
    #1・#7 の取得中はフック開始ボタンでフックを再開できる既存の穴があり、再開して自窓へ文字が送られると送信側（§7.7）が同じ入力コンテキストを問い合わせ・切替え得る（送信側は自分が OFF にしたときだけ戻すため、取得側が OFF にした後なら何もしない。穴そのものは idea_48）
* **判別できないキー**（phase 59・60 で全入口へ）: 取得の名前が `??`（Tk が名前を判別できないキー。JIS の Caps 単独〔「英数」〕・取得中に手で IME を ON にしたときのキー・**JIS の特殊キー〔無変換・変換・半角/全角・かな〕**〔IME に横取りされ、IME が OFF でも VK 229 で届く・押すと IME の ON/OFF が切り替わり、以降の打鍵も `??` になり得る〔下の受容〕・Tk のイベントは物理の走査コードを持たないため判別できない・2026-10-17 に Windows 11 + MS-IME で実測・取得できるようにする話 = idea_50〕 等）は**全入口で記録せず、取得を続ける**（Esc 待ちのまま）。判定は `presentation/tk_keys.is_unresolved_capture_key` の 1 か所
  * 案内の欄がある入口（#2・#3・#4・#6）は「このキーは取得できません。別のキーを押してください。（Escでキャンセル）」を出す（取得を止める / 終えると従来の文言へ戻る）。欄のない入口（#1・#5・#7・#8）は黙って無視する（#1 は以前のエラーのダイアログを出さなくなった）
  * 受容: 取得中にユーザーが手で IME を ON にすると、以降の打鍵は `??` で無視される。変換が確定すると確定した文字から作られた KeyPress（`??` ではない）が記録され得る。Esc → 取り直しで回避する（OFF にし直すことはしない）

### 7.5 安全ルール

* フック暴走を起こさない（暴走防止最優先）
* keyboard の例外は必ず吸収する
* フック処理を UI と競合させない。UI 更新は `after()` で UI スレッドへ委譲する

### 7.6 停止/トグルキーの供給源

* 停止キー / トグルキーは**全体デフォルト（`config/config.json`）**と
  **keymap_set の個別指定**の 2 系統を持つ。データ側の規定は `data_schema.md` §5.9
* **フック実行層が見るのは解決済みの 1 値のみ**。供給源（全体 / 個別）による分岐を
  フック側に持たせない（解決は keymap_set を runtime へ載せる時点で確定する）
* **個別指定 OFF のときのキー取得 / クリアは全体デフォルトを編集する**
  （keymap_set は変更せず、未保存にもしない）。ON のときは keymap_set の個別値を編集する
* **キーの重複検証はカレント keymap_set 内に閉じる**（§7.3）。全体デフォルトは他の keymap_set の
  トリガーとは照合されないため、別の keymap_set でトリガーと重なり得る。
  重なった場合は**停止 / トグルがトリガーより優先**され、§7.3 のグレー表示と案内で知らせる（フック開始は止めない）
* 個別指定のチェックは **FullView で操作**する。CompactView は**状態表示のみ**
  （キー欄も readonly 表示）

### 7.7 キーの送信

* アプリが送るキー（出力シーケンスの hotkey アクション・キーマップの送信先キー）のうち、
  Windows の**拡張キー**は拡張キーとして送る（テンキーや左側のキーとして扱われないようにする。
  例: 拡張キーとして送らないと `shift+right` がテンキーの 6 と Shift の組み合わせとして扱われ、範囲選択にならない）
* 対象のキー名（別名は keyboard ライブラリの名前の正規化に従う）:
  up / down / left / right / home / end / page up / page down / insert / delete /
  right ctrl / right alt / windows・left windows・right windows / menu（アプリケーションキー）/ print screen / num lock
  * 左右を指定しない `windows` は左の Windows キーとして送る。`ctrl` / `alt` / `shift` は左側（非拡張）のまま
  * 主キーボードの Enter・`/` はこの対象に含めない。テンキーの名前（`num enter` 等）は §7.8 の規定で送る。`alt gr` は従来どおり
* 組み合わせは記述順に押し、逆順に離す（従来どおり）。拡張キーの規定は、テキスト入力（text・file_line）・マウス操作には適用しない
* hotkey の書式・検証（`codebase_map.md` の hotkey 文法）は変えない
* **キー名 → 走査コードの解決の順**（phase 62）: 送信（hotkey・キーマップの送信先・key_hold・キーリピート）・検査・同じキーの判定（§7.8）は、キー名ごとに次の順で決める
  1. テンキーの名前（§7.8）
  2. 上の拡張キー
  3. keyboard ライブラリが知る名前（`key_to_scan_codes` が成功し結果が空でない）
  4. **選んでいるレイアウトの行のうち、`id` を正規化した名前が一致し `scan_code` を持つ最初の行の `scan_code`**（1〜255 の範囲外は当たらない）
  5. どれにも当たらなければ「不明なキー」
  * 4 で決まったキーは `SendInput` の走査コード入力（`KEYEVENTF_SCANCODE`・拡張なし）で送る（§7.8 と同じ経路・send_guard の中・keyboard の押下記録に載せない）。
    hotkey は、全キーが 3 で決まるときだけ keyboard へまとめて渡す。それ以外は記述順に押し逆順に離す
  * 4 は**登録済みのレイアウト**（読込済みの値）を引く。ファイルの読み直し・UI の操作はしない（UI スレッドの外から呼ばれるため）。
    infrastructure はレイアウトを直接読まず、「キー名 → 走査コード」の関数を外から受け取る
  * **検査は選んでいるレイアウトで結果が変わる**。保存済みのキーマップ・出力はレイアウトを切り替えても再検査しない。
    送れない名前は実行時エラー（hotkey のアクションは保存時にキー名を検査しない・既存）
  * **レイアウトが変わる前に、押したままのキー・マウスのボタンをすべて離す**（key_hold・キーリピート。`held_inputs.release_all`）。
    - 対象: レイアウトの読み直し（起動・追加・削除・構成の読込〔phase 62 task_04b で構成の読込でも読み直すようにした〕）は登録済みの値を置き換える前に毎回 / 選ぶレイアウトの id が実際に変わるときは置き換える前
    - 離しの失敗は「すべて解放」の失敗と同じく通知し、切替は進める
    - 古い値で離さないと、4 で押したキーを新しいレイアウトで引き直して離せなくなるため
  * 受容:
    - keyboard が知る名前の `id` に別の `scan_code` を書くと、受け取りはレイアウトの名前・送信は keyboard の走査コードでずれる
    - 拡張キーの走査コードを書いた行は送信で拡張なしになる
    - 起動中に外部レイアウトの JSON を書き換えると、受け取り（呼ぶたびに読み直す）と送信（登録時の値）が読み直しまで食い違う（idea_51）
    - 離しに失敗したまま切り替えると、再試行は新しいレイアウトで引くため、別の走査コードへ離しを送って成功扱いになり、**元のキーが OS 上で押されたまま残り、記録も消える**ことがある（SendInput の失敗と切替が重なるときだけ・押したときの値を覚える形は idea_51）
    - 離してから登録済みの値を置き換えるまでの間に、実行用のスレッドが key_hold で押したキーは古い値のまま残り得る（ロックを持たない）
* **key_hold の送信**（phase 51・`features.md` §4.2.12）: キーボードの押す / 離すは `press_key` / `release_key`（拡張キーの規定は上と同じ）を send_guard の中で送る（フックが自分の送信を拾わない）。自動で離す送信も同じ（フック停止の後でも OS へ送る）。マウスのボタンの押す / 離すは座標があれば移動してから送り、**FAILSAFE を外す**（画面の隅で例外になり離し損ねないため・ドラッグと同じ）。マウス操作は send_guard の対象外
  * **keyboard ライブラリの押下記録に載せない**: keyboard は送信の前後に、フックが動いている間に記録した押下中のキーを離して修飾キーを押し直す（`stash_state` / `restore_modifiers`）。拡張キー（right ctrl 等）を記録に載せると、text の送信で左 ctrl として押し直され、右 ctrl を離しても左 ctrl が OS 上に残る（phase 51 task_01 の probe）。そのため拡張キーの送信は記録に載らない形で送る。**この処理は hotkey・直接置換の拡張キー送信にも効く**（押して離すまでが一瞬で実害はない）。記録に載らないごく短い間に届いた物理入力は keyboard のフックが拾わない（keyboard 自身の `send` と同じ既存の性質）
  * **text・file_line の送信で keyboard に修飾キーを押し直させない**（`restore_state_after=False`・phase 51 で変えた既存の挙動）: 手で右 ctrl を押している間に text が送られると左 ctrl が残る不具合を直した。手で修飾キーを押したまま text が送られると、送信後は OS 上離れた扱いになる（押し直したければ一度離して押す）＝受容。押したままの key_hold のキーは送る間だけ離して押し直す（`features.md` §4.2.12）
  * **キーリピートの送り直し**（phase 52・`features.md` §4.2.12「キーリピート」）: 押すと同じ `press_key` の経路で send_guard の中で送る（keyboard の記録にもアプリのフックにも載らない）。
    間隔は Windows のキーボード設定を `SystemParametersInfoW`（`SPI_GETKEYBOARDDELAY` = 0x16 を UINT・`SPI_GETKEYBOARDSPEED` = 0x0A を DWORD）で読み、
    待ち = 250 × (n + 1) ms（n = 0〜3）/ 間隔 = round(1000 / (2.5 + n × 27.5 / 31)) ms（n = 0〜31。n = 0 → 400 ms・n = 31 → 33 ms）に換算する。範囲外の値・取得失敗・Windows 以外は既定値（待ち 500 ms・間隔 33 ms）。
    リピート中は send_guard / replay の一瞬が毎秒数十回生じ、その間の物理入力を取りこぼす頻度が上がる（上の既存の性質の頻度が上がるだけ）＝受容
    **アプリの窓が前面かの判定**（phase 53・`features.md` §4.2.12「キーリピート」）: `GetForegroundWindow` の窓を `GetWindowThreadProcessId` でプロセス ID に引き、自プロセス（`os.getpid()`）なら前面とする。専用の `WinDLL("user32")` に型を設定して使う（共有の `windll` の属性は書き換えない）。
    前面の窓が NULL なら「前面（止める）」・プロセス ID が 0・呼び出しの例外・Windows 以外は「前面でない（止めない）」。例外のログは初回だけ（発火ごとに呼ばれるため）
* **文字の入力（text・file_line の行）の間は、送り先の IME をオフにする**（phase 41）。文字は 1 文字ずつ Unicode 文字として送るため、送り先の IME がオンだと変換前の入力として扱われ、カタカナがひらがなの変換待ちで入る（キーの取得中のアプリ自身の IME は §7.4「取得中の IME」・別の口で状態は共有しない）
  * 送り先 = 前面の窓のスレッドで**キーボードフォーカスを持つ窓**（`GetGUIThreadInfo`。取れなければ前面の窓）。その既定の IME 窓に `WM_IME_CONTROL` で状態を問い合わせ、オンならオフにしてから送る（オフなら何もしない）
  * 送り終えたら、**文字数に応じて待ってから**オンへ戻す（送った文字は送り先で後から処理されるため。待ち = 200 ms + 40 ms × 文字数）。待ちは別スレッドのタイマーで行い、UI を止めない
  * 戻す前に同じ IME 窓へ次の文字を送るとき: 状態を問い合わせ直し、オン（ユーザーが手でオンにした等）なら再びオフにしてから送る。
    戻す時刻は**前の戻す時刻と今回の送信からの待ちの遅いほう**にする（短い文字列を続けて送っても、前の長い文字列の処理中に戻さない）
  * 戻すとき: 状態を問い合わせ、**オフのときだけ**オンにする（既にオンなら触らない）
  * IME への問い合わせ・切替は**時間制限つき**（`SendMessageTimeoutW`・200 ms・応答しない窓は即打ち切り）で行い、共有の状態を守るロックの外で呼ぶ（送り先が応答しなくても UI・他の送り先を止めない）
  * 送り先の IME 窓が取れない・問い合わせが失敗した・時間切れのときは、IME に触らずそのまま送る（通知しない）。Windows 以外では何もしない
  * **アプリの終了時**は、戻す予約をすべてその場で戻してから終える（待ちの途中でも。戻した後に処理された文字はひらがなになり得る・受容）
  * 既知の制約（受容）:
    * 戻すまでの間（例: 50 文字で約 2.2 秒）にユーザーが打った文字も IME オフで入る / 処理の遅い送り先では待ちが足りずに末尾がひらがなになり得る（待ちの係数はメモ帳でのみ実測）
    * 送り先で変換途中の文字列があれば、オフにしたときに確定または破棄される（IME による）
    * 待っている間にユーザーが手で「オン → オフ」と切り替えても見分けられず、戻すときにオンへ戻す（状態は問い合わせ時点の値しか分からない）
    * 予約は IME 窓（送り先アプリのスレッドごとに 1 つ）の単位で持つ。戻すまでの間に同じアプリの別の入力欄・タブへフォーカスが移ると、戻す操作は移った先に効き、元の欄はオフのまま残り得る
    * 送信の途中で前面の窓が変わると、残りの文字は新しい窓へ IME の制御なしで入る（戻す操作は元の IME 窓に効く・元の窓が閉じていれば何も起きない）
    * IMM（`WM_IME_CONTROL`）が効かない送り先・管理者権限の窓（UIPI）では何もせずに送る
    * 強制終了したときは戻されない
  * 根拠の実測（2026-10-01・Windows 11 のメモ帳）: 前面の窓（外枠）への問い合わせは IME オンでも 0 を返し、フォーカスの窓（編集欄）なら正しく読める /
    文字の処理は 1 文字あたり約 20〜26 ms で、送った直後に戻すと途中からひらがなになる

### 7.8 テンキー（phase 54）

テンキーは専用の名前で、入力の判定・送信・記録のすべてで主キーボードと区別する。**既存の名前（`1` / `enter` / `end` / `home` / 矢印 / `.` 等）は入力の判定では主キーボード側のキーだけを指す**（phase 53 まではテンキーでも反応していた・データの移行はしない）。
  **出力側も変わる**: phase 53 までは keyboard の別名で `num 0`〜`num 9` が主キーボードの数字として送られていたが、phase 54 からはテンキーとして送る（NumLock オフなら End 等の動き）。既存の hotkey・直接置換の送り先・key_hold に `num 0`〜`num 9` があると、設定を変えずに数字入力がカーソル移動に変わり得る（自動移行しない）。従来どおり主キーボードの数字を送るには `0`〜`9` に書き換える

| 名前 | スキャンコード | 拡張 |
|---|---|---|
| `num 0`〜`num 9` | 82 / 79 / 80 / 81 / 75 / 76 / 77 / 71 / 72 / 73 | 非拡張 |
| `num decimal` | 83 | 非拡張 |
| `num multiply` / `num subtract` / `num add` | 55 / 74 / 78 | 非拡張 |
| `num divide` / `num enter` | 53 / 28 | 拡張 |

* **名前**: trim + 小文字で引く（`Num 1` も可）。`num` と数字 / 単語の間は半角空白 1 つ。`+` / `,` と衝突しないよう記号は単語で書く
  * **`_` を空白に置き換えた形が `num ` で始まり、表に無い名前は名前の検査でエラー**（`num +` / `num plus` / `num del` / `num_1` / `num_add` 等。keyboard ライブラリはこれらを主キーボード等に読み替えるため）。`num lock`（`num_lock` を含む）は従来どおり有効でテンキーの名前に含めない
  * keyboard の名前 `decimal` / `clear` / `separator` は従来どおり有効（送信は従来どおり）。入力ではテンキーが表の名前になるため、トリガー等に書いても反応しない
  * テンキーのカンマ（スキャンコード 126）等は対象外（従来の名前のまま）
* **NumLock に関係なく物理キーで同じ名前**: テンキーの 1 の位置は NumLock オン / オフとも `num 1`（トリガーは NumLock に左右されない。押している間に NumLock を切り替えても押下状態は `num 1` で対になる）
* **入力の判定**: フックのイベントの `is_keypad` が真で、スキャンコードが表にあれば表の名前にする（レイアウトのスキャンコードの解決・イベントの名前より優先）。
  テンキーでないイベントでは、レイアウトの `id` が表の名前でも採用しない（レイアウトはスキャンコードだけで引くため、本物の End が `num 1` になるのを防ぐ）。
  名前の決定は domain の 1 関数で、トリガー・直接置換の元・切替キー・停止キー・トグルキー・押下状態・重なり判定が同じ名前を使う
  * NumLock オンで shift を押したままテンキーを押すと、Windows が shift の up / down を差し込む（押下状態で一瞬 shift が離れた扱い・`shift` を停止キー等にしていれば反応し得る）＝既存の性質として受容
* **送信**: 表の名前は `SendInput` のスキャンコード入力（`KEYEVENTF_SCANCODE`・拡張は `KEYEVENTF_EXTENDEDKEY`）で送る（NumLock の状態で送り先の解釈が決まる＝物理キーと同じ。`num 1` は NumLock オフなら End の動き）。
  §7.7 と同じく send_guard の中・keyboard の押下記録に載せない。keyboard の名前の API には渡さない。表の名前を含む hotkey は記述順に押し、逆順に離す
  * **記号の名前（`*` / `+` / `-` / `/`）の送信は従来どおり keyboard の解決に任せる**（テンキーのキーで送られ得る。「主キーボードだけ」は入力の判定に限る）
  * **同じキーの判定**（押下中の集合・リピートの対象）は実際に送るキー: 表の名前は表のスキャンコード + 拡張 → §7.7 の拡張キーはそのスキャンコード + 拡張 → それ以外は keyboard の先頭のスキャンコード（`0xE0xx` の形は `xx` + 拡張に読み替える・テンキーに限らずすべてのキー名に効く）→ 選んでいるレイアウトの `scan_code` + 拡張なし（§7.7「キー名 → 走査コードの解決の順」）。`+` と `num add`、`/` と `num divide` は同じキー・`1` / `end` と `num 1` は別のキー
* **記録**（hotkey の記録・key_hold の「1 キーを記録」・トリガー / 切替キー / 停止キー / トグルキーの取得・キーボード表示の置換先の取得）: Tk の keysym はテンキーでも主キーボードと同じ（`KP_` が付かない）ため、
  **keycode（Windows では VK）と拡張ビット（`state & 0x40000`）**で判定する。VK 96〜105 / 110 / 106 / 109 / 107 / 111 → 表の名前・13 かつ拡張あり → `num enter`・
  拡張なしの 45 / 35 / 40 / 34 / 37 / 12 / 39 / 36 / 38 / 33 / 46 → `num 0`〜`num 9` / `num decimal`（NumLock オフ。拡張ありは本物の Insert / End / 矢印等）。該当しなければ従来どおり keysym で決める
* 組み込みのキーボード表示（US TKL）にテンキーは無い（外部レイアウトで足せる。`id` を表の名前にすれば色分けされる）
