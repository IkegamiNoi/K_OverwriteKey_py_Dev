## 5. JSON 仕様

### 5.1 重要ルール（後方互換）

* 後方互換必須
* 既存キーの削除禁止
* 既存キーの意味変更禁止
* 未定義キーは無視する

※設計変更タスクの場合は、指示された範囲でのみ変更可能。

**「削除禁止」の例外＝生成停止（能動削除ではない）**: 役目を終えたキーは
**payload の生成を止める**ことで、再保存時に自然に消える形にしてよい。
既存ファイルから**能動的に削除（`pop` 等）はしない**。
**現在、生成を止めているキーは無い**（keymap_set の `hotkey_presets_path` は
**個別プリセットの指定**として `hotkey_presets_individual` とともに**常に出力する**。§5.10.1）。
※ §5.9.1 の「hook 3 キーは値が空でも常に出力する」とは扱いが異なる（あちらは削除禁止の原則どおり）。

### 5.2 基本構造（単一JSON互換）

```json
{
  "triggers": [...],
  "hotkey_presets": [...],
  "hook_stop_key": "f12"
}
```

### 5.3 拡張キー

#### run_to_end

* 型: bool
* 連続実行

#### run_to_end_delay_ms

* 型: int
* デフォルト: 300

### 5.4 分離JSONの本流

| 機能 | 形式 |
| --- | --- |
| 保存 | split |
| 読込 | split |
| 起動 | split |
| Import | 単一JSON |
| Export | 単一JSON |

#### keymap_set の保存先と「ファイルなし」状態

* keymap_set の既定の保存先は**ディレクトリ `config/user/keymap_sets/`** とする。
  固定ファイル（`default.json`）を既定の保存ターゲットにしない
* 起動時に `config/user/{keymap_sets,keymaps,trigger_sets,hotkey_presets,hotkey_presets/global,sequences}`
  を作成する（`hotkey_presets/global/` はグローバルライブラリ専用の予約ディレクトリ。§5.10.1）。
  **隔離ルート `config/quarantine/` はこのリストに含めない**（§5.8.9 の遅延作成。
  隔離を 1 度も実行していない環境に作らない）。
  `config/config.json` 本体は起動時に作らず、**最初に設定が永続化された時点**で作成する
  （keymap_set の保存 / フォントサイズ変更 / 起動時に読む keymap_set の指定）
* **`config/config.json` は孤児ファイルの棚卸しの走査ディレクトリ設定
  `orphan_sweep_scan_dirs`（文字列の配列・既定は空）を持つ**（§5.8.9）。
  **書き込みは起動設定の書き出し経路 1 本を通す**（config.json は keymap_set の保存等で
  丸ごと書き直されるため、直接書くと次の保存で無言消滅する。§5.9.4 と同じ機構）。
  値は §5.7 の表記へ正規化し、**非文字列・空文字・重複を除いて保存する**（実在確認はしない）。
  **一覧の編集は棚卸しを実行せずダイアログを閉じた場合も保存する**（設定の編集と棚卸しの実行を分ける。
  UI にもその旨を表示する）
* アプリが保持する現在の keymap_set パスは、次の 3 経路で**空（＝ファイルなし）**になる:
  1. 新規作成した直後
  2. Import（単一JSON）に成功した直後
  3. 起動時に `keymap_set_path` が**未設定 / 不在 / 読込失敗**の場合（無言で空データ起動する）
* パスが空の状態で「保存」した場合は**別名保存**として扱う。
  別名保存ダイアログの初期ディレクトリは `config/user/keymap_sets/`、初期ファイル名は `keymap_set.json`
* パスが空でない場合の「保存」は従来どおり当該ファイルへ上書きする
* 保存に成功すると `config/config.json` の `keymap_set_path` は保存先へ更新される
* **trigger_set は既定名のレベルで keymap_set ごとに分離する**（§5.6・既定名が keymap_set の
  ファイル名由来）。ただし**既に source_path を持つ子はその保存先を使う**ため常に分離されるとは限らず、
  keymap_set が未設定のときは §5.6 のフォールバック名へ、別名の keymap_set が同一 stem へ丸まる場合は
  同一ファイルへ落ちる。
  **hotkey_presets は keymap_set の子ファイルにしない**（§5.8 の保存計画に載せない）。
  既定は `config/config.json` が指す**アプリ全体のライブラリ**だが、
  **keymap_set ごとの個別指定を持てる**（§5.10）。いずれの場合も
  **keymap_set の保存（保存カスケードを含む）ではプリセットの内容を書き込まない**
  （書き手はプリセットマネージャのみ）。ただし **keymap_set の別名保存では既存の個別ファイルを
  複製する**（内容の生成ではなくファイルのコピー。§5.10.3）。
  **keymap / sequence の既定保存先はセット横断で共有される**（`config/user/keymaps/` /
  `config/user/sequences/` 配下のラベル・id 由来のファイル名）。別々の keymap_set が同名の子を持つと
  保存先が衝突し得るため、誤爆上書きは §5.8 の参照元記録と共有状況判定で防ぐ
* **【実装未追従】** 別名保存でレガシー `<アプリ配置>/settings/` 配下を選んだ場合のみ、選択パスが
  `config/user/keymap_sets/default.json` へ差し替わる実装が残っている
  （[idea_09](../../backlog/idea_09_legacy_settings_save_path_fallback.md)）。**本節の規定が正**であり、
  実装側を追従させる

### 5.5 split 読込

* 通常読込では `keymap_set.json` を直接選択する
* `config/config.json` は起動時に読む `keymap_set_path` を保持する
* `keymap_set.json` は trigger_set / keymap の実体JSONをファイルパスで参照する。
  **hotkey preset は個別指定が ON のときだけ参照する**（`hotkey_presets_individual` が真なら
  `hotkey_presets_path` を個別ファイルとして読む。OFF＝既定では `config/config.json` 起点の
  グローバルを使う。§5.10.2）。
  **`hotkey_presets_individual` キーを持たない既存ファイルは常に OFF として扱い、
  残っている `hotkey_presets_path` も引き継がない**（§5.10.1 の移行規則）

### 5.6 個別JSON

#### trigger_set

* `config/user/trigger_sets/` 配下に保存する
* `triggers[]` は `key` / `suppress` / `sequence_path` を持つ
* `sequence_path` は出力シーケンスJSONへの参照

#### sequence

* `config/user/sequences/` 配下に保存する
* `label` / `run_to_end` / `run_to_end_delay_ms` / `actions` を持つ
* `run_to_end` / `run_to_end_delay_ms` は UI 上の「連続実行」「間隔(ms)」
* sequence の新規保存ファイル名は label 由来にし、日本語 label もそのまま候補に使う
* ファイル名では Windows 禁止文字のみ `_` に置換する
* trigger_set の新規保存ファイル名は現在の keymap_set ファイル名由来（拡張子を除いた stem）にする。
  stem は Windows 禁止文字を `_` に置換したうえで、連続した `_` の圧縮・前後の ` ._` の除去・
  予約名（`CON` 等）への `_` 付加を行う。**この処理の結果が空になる場合はフォールバック名**を使う
  （下記の経路別の名前）
* keymap_set が未設定（§5.4 の「ファイルなし」状態）のときのフォールバック名は**経路で異なる**:
  * **構成セットの一括保存**（keymap_set を保存する経路）… `default`（＝
    `config/user/trigger_sets/default.json`）
  * **個別「トリガー一覧を保存」**… `trigger_set.json`
* 既定保存先の決定は**既存ファイルの有無を考慮しない**（衝突を避けて別名へ逃がさない）。
  既存ファイルの保護は §5.8 の共有状況判定と既定選択規則が担う

#### 旧形式互換

* 旧形式の `triggers[].label` / `triggers[].run_to_end` / `triggers[].run_to_end_delay_ms` /
  `triggers[].actions` は読込互換を維持する
* 保存時は trigger_set + sequence の新形式へ寄せる

### 5.7 パス保存ルール

* `config` 配下のパスは `config` ルート基準の相対パスで保存する
* `config` 配下ではない外部パスは絶対パスで保存する
* 読込時は絶対パスをそのまま使い、相対パスは `config` ルート基準で解決する
* trigger_set / sequence / keymap 個別保存でも同じルールを適用する
* **記録用の表記（stored）と書き込み用のパス（resolved）を分離する**。runtime が保持する参照パスは
  本節の表記（`config` 配下なら相対）のまま保ち、**ファイルへ書き込む直前に `config` ルート基準で
  絶対パスへ解決する**。解決済みの絶対パスを runtime の参照パスへ書き戻さない
  （相対表記が絶対へ置換されると、次回以降の内外判定と索引が壊れる）
* config 外の絶対パスも**区切り文字は `/` に正規化**して記録する
* 本節は**保存経路・読込経路の両方**に適用する（個別読込で選んだファイルも、config 配下なら相対で記録する）
* **パスの同一性判定は正規化した比較専用の表記で行う**（解決 → `normpath` → `normcase`）。
  ドライブ文字の大小・区切り文字・相対/絶対の差で「`config` の外」と誤判定しないこと。
  正規化した文字列は**比較にのみ使い、保存値・表示・戻り値へ混入させない**

### 5.8 子ファイルの保存計画と参照元記録

構成セット（keymap_set）の「保存」は、**変更のある子ファイル（keymap / trigger_set / sequence）ごとに
保存方法を選べる**。子ファイルは複数の keymap_set から参照され得るため、他所に属する子の誤爆上書きを防ぐ。

#### 5.8.1 参照元記録 `_parent_refs`

* 子JSON に内部キー `_parent_refs` で**直接の上位ファイルパスの集合**を記録する
  （keymap / trigger_set → keymap_set、sequence → trigger_set）
* パス表記は §5.7 に従う
* **更新は best-effort**。子を保存・別名保存した際に現在の上位パスを集合へ追加する。
  上位の移動・削除は検知せず残置する。**残置した参照元は「参照元の掃除」でまとめて除去できる**（後述）
* **マージ元は保存先ファイルに実際に記録されている `_parent_refs`** とし、runtime が読み込み時に
  持っていた旧参照元は持ち込まない（別名保存で他所の所有記録を新しいファイルへ複製しないため）
* **後方互換**: `_parent_refs` を持たない既存の子JSON は**「所有元不明」**として扱う（§5.8.4）。
  既存キーは削除せず追加のみ行う。**「参照元の掃除」だけが値の除去を行う唯一の経路**で、これは
  `_parent_refs` の**値だけ**を書き換える（他のキーは変更せず、子ファイル自体も削除しない）。
  **§5.1 の「キー削除禁止」の例外ではない**（全件除去でも `[]` を書きキーは残す）

**参照元の掃除（保守機能）**

残置した参照元は §5.8.4 の共有状況判定を誤らせ（「N 個の上位で共有中」の誤警告）、
§5.8.5 の余分な確認を招く。これを**ユーザー操作でまとめて除去する**（起動口は設定メニュー）。

* **検査範囲は「現在の構成セット（開いている keymap_set）が参照している子」のみ**。
  列挙は **runtime の source_path（keymap / trigger_set / sequence の 3 種）**を根拠とする。
  * **既知の制約: 全網羅ではない**。子は config 配下の外にも置けるためディレクトリ走査でも
    全網羅にならず、keymap_set 自体の列挙手段も無い。**現在使っているものを軽くする**のが目的
  * **同一ファイルへ解決される複数の子は 1 件へ重複排除する**（判定は §5.7 の比較専用表記）。
    共有 sequence（複数トリガーが同一ファイルを指す）で二重処理・二重計上しないため
  * **source_path が空の子（未実体化）は対象外**（Import 直後・「例を復元」直後は結果が 0 件になる。
    起動できることと結果が出ることは別）。**UI 上で削除したが未保存の子**も runtime から落ちているため
    対象外（ディスクの実体と索引は残るが本機能では扱わない）
* **除去するのは「実体が無い上位パス」のみ**。実在する参照元は**記録された表記のまま**書き戻す
  （比較専用の正規化文字列を保存値へ混入させない。§5.7）。
  ただし読み出し規則を通す都合で、**前後空白の除去・完全一致の重複除去・非文字列要素の除去は
  同時に起こる**（既存の `_parent_refs` 読み出しと同じ。許容する）
* **判定名**（§5.8.4 と同じく、**分岐は判定名で行い表示文言で分岐しない**）:
  * **`CLEANUP_TARGET`** … 保護対象を除いて実在しない参照元が 1 件以上ある（＝一覧に出す）
  * **`CLEANUP_ALL_STALE`** … 除去すると**残る参照元が 0 件になる**（警告表示の対象。
    **保護対象が残る場合は該当しない**）
  * **`CLEANUP_PROTECTED`** … 実在しないが**保護対象**のため除去しない参照元を持つ
  * **`CLEANUP_SKIP`** … 対象外（`None`＝所有元不明 / `[]`＝既知の空 / 実体なし / 読めない）
* **保護対象**: **現在の keymap_set / trigger_set への参照は、実在しなくても除去しない**
  （消すと次回保存で「所有元不明」となり、既定が別名保存へ倒れるため）。**検査の時点で分離**し、
  **「消えるパス」の一覧・件数・0 件警告から除外する**（検査と実行で結果が食い違わないため）。
  **別枠で「保護のため残す」と併記してよい**
* **全件が除去対象になった場合は `[]` を書き、キー自体は残す**（§5.1 の後方互換。
  `None` と `[]` はいずれも §5.8.4 の「所有元不明」で判定は不変）
* **孤児（参照元が 0 件になる子）の削除は行わない**。**本機能の検査範囲（現在の構成セットが
  参照している子）だけでは孤児判定が成立しない**ため、**0 件になることを警告表示するだけ**に
  とどめる（**子ファイル自体は削除しないこと**を添える）。
  **孤児かどうかは §5.8.9「孤児ファイルの棚卸し」で判定する**（上位 → 子の逆方向検査による
  部分的な補完。**§5.8.1 の検査範囲は §5.8.9 によって変わらない**）
* **未保存（`keymap_set_path` が空）の構成セットでは先に保存が必要**。保存の確認を出し、
  **保存が成功したときだけ掃除へ進む**（キャンセル / 失敗なら掃除ごと中止）。
  * 理由: `parent_ref` が空のまま個別保存すると `_parent_refs_for_save` が保存先を読み直さず
    runtime の参照元を書き戻すため、**掃除が巻き戻る**
  * この保存は掃除の一部ではなく、**§5.8.6 の best-effort に従う**（掃除が保証するのは
    「掃除による書き込みが 1 件も発生しない」ことだけ）
* **除去直前に対象 JSON を丸ごと読み直し**、同じ規則で再判定してから `_parent_refs` を差し替える
  （検査時のスナップショットを書き戻して外部変更を消さないため）。
  1 件の失敗で中止せず、失敗を記録して継続する
* **除去 0 件なら書き込まない**（冪等）。**掃除の結果は runtime へ反映しない**
  （次回読み込みで揃う。未保存マークも付けない）
* **確認は読み取り専用の 1 枚**（実行 / キャンセルの 2 択。掃除が非破壊・冪等のため
  **行ごとの選択は設けない**）。**キャンセルすると 1 ファイルも書かない**
* **消える参照元は子ごとに全件提示**する（件数だけに丸めない）。理由: **一時的に到達不能な媒体**
  （外付け / ネットワークドライブ未接続。config 外の絶対パスは §5.7 で許容）を掃除すると
  **生きている参照元を恒久的に消す**ため、件数表示だけではユーザーが検知できない。
  ただし**保護対象は「対象」に数えず**、消える参照元が 1 件も無ければ
  **一覧を出さずに「掃除する項目はありません」**とする（書くものが無いため）
* **実行後は結果を通知する**（更新したファイル数 / 除去した参照元の件数 / **失敗したファイル**）

**既知の制約**（いずれも**実装を変えず契約として明記**する）

* **sequence の掃除は trigger_set が実体化していることが前提**。trigger_set が未実体化のまま
  sequence を個別保存すると `parent_ref` が空になり、掃除前の参照元が再書き込みされる（＝**巻き戻る**）。
  上記の保存確認は **keymap_set のパスが空のときにしか働かない**ためこの経路は塞がない。
  再現条件は限定的（保存計画で trigger_set を「保存しない」にした場合など）で、**データ損失は起きない**
* **確認ダイアログの表示中に上位ファイルが消えると、提示していない参照元も除去され得る**
  （除去直前に同じ規則で再判定するため）。**外部変更を消さないこと（安全側）を優先した結果**であり、
  「消える参照元を全件提示」とはこの窓でのみ両立しない
* **再判定で対象外になった子は結果通知に出ない**（更新にも失敗にも数えない）。
  書き込みが起きていないことは「更新したファイル」の件数から分かる
* **読み直しから書き込みまでの窓に残る競合は対象外**（書き込みはドキュメント全体の置換のため、
  この窓の外部変更は `_parent_refs` 以外も失われ得る）。**版情報の照合（mtime / ハッシュ）は行わない**
  ＝ §5.8.3 / §5.10.3 が既に規定している水準と同じ

#### 5.8.2 runtime の内部キー（永続化しない）

* 子ファイルの読込元・保存先（source_path）と未保存フラグ（dirty）は、runtime のデータに
  **内部キー**として保持する:
  * keymap … `INTERNAL_KEYMAP_SOURCE_PATH` / `INTERNAL_KEYMAP_DIRTY`（`keymaps[]` の各要素）
  * sequence … `INTERNAL_SEQUENCE_SOURCE_PATH` / `INTERNAL_SEQUENCE_DIRTY`（`triggers[]` の各要素）
  * trigger_set … **`INTERNAL_TRIGGER_SET_SOURCE_PATH`**（runtime データの直下）。
    dirty は runtime データではなく未保存状態の管理側が持つ
* 内部キーは**保存する JSON へ出力しない**（永続化されるのは `_parent_refs` と各ファイル本来のキーのみ）
* trigger_set の source_path は**単一の入口を通して更新し、runtime データ側の
  `INTERNAL_TRIGGER_SET_SOURCE_PATH` と常に一致させる**（読み手と書き手が別の場所を見る状態を作らない）

#### 5.8.3 保存計画（アクションと既定規則）

* 各子ファイルのアクションは **保存（上書き） / 別名保存 / 保存しない** の 3 種
* 決定の優先順位は 1 箇所に集約する: **確認ダイアログでの選択 > 確定済みエントリ > 既定規則**
* **既定規則**（＝ダイアログに出ない子の扱い）:
  **保存先に実体があれば「保存しない」・無ければ「保存」**。
  実体が無いのに保存しないと上位の索引が切れるため、**未実体化の子は未保存でなくても保存対象**とする
* **確認ダイアログの行として出るのは未保存（dirty）の子だけ**。非 dirty の子は
  ダイアログに現れないまま既定規則で決まる
* 保存計画は**表示層が決定し、アプリケーション層が実行する**（表示層のダイアログ都合を
  アプリケーション層へ持ち込まない）

#### 5.8.4 共有状況と既定選択規則

保存先ファイルの `_parent_refs` と現在の上位を比較し、共有状況を判定する。**判定名と画面表示の文言は別物**
であり、分岐は必ず判定名で行う。

| 判定 | 条件 | 既定のアクション | 画面表示 |
| --- | --- | --- | --- |
| 新規作成 | 保存先にファイルが無い | 保存 | 「新規作成」 |
| 単独所有 | 参照元が現在の上位のみ | 保存（上書き） | 「この構成のみが所有・既存を上書き」 |
| 共有中 | 参照元に現在の上位を含み、かつ複数 | 保存（上書き） | 「N 個の上位で共有中・全てに影響します」 |
| 別の構成 | 参照元に現在の上位が無い | **別名保存** | 「別の構成に属します」 |
| 所有元不明 | `_parent_refs` が無い / 空、**または現在の上位が未確定（空）** | **別名保存** | 「所有元不明・安全のため別名」 |

* **上表より優先する規則**: **source_path を持たない子（新規）**の保存先に**既存ファイルがある**とき、
  元の判定が「単独所有」「共有中」なら**既定を別名保存**へ倒す（表示「同名の既存ファイルあり・安全のため別名」）。
  * **対象は keymap / sequence のみ。trigger_set には適用しない**
    （trigger_set の既定名は keymap_set のファイル名由来＝ユーザーが別名保存ダイアログで確認済みの
    パスから決まるため。適用すると §5.8.5 の「単独所有なら確認を出さない」が常に空振りする）
  * 「別の構成」「所有元不明」には適用しない（既定は元から別名保存であり、具体的な警告文が失われるだけ）
* いずれも**既定**であり、ユーザーは行ごとに選び直せる。共有情報は保存ダイアログ内でのみ表示する
* **帰結**: 既存と同名の keymap_set を保存先に指定すると、**その stem 由来の trigger_set は上書きされる**
  （意図した挙動）。keymap / sequence 行は上記規則により既定が別名保存のままとなる

#### 5.8.5 確認ダイアログ

* **子ファイル一覧**: dirty な子を行として並べ、行ごとに 保存 / 別名保存 / 保存しない を選ぶ。
  dirty な子が無ければダイアログを出さない。キャンセルすると**1 ファイルも書かない**
* **依存確認**: 子の別名保存で上位の索引が変わり、上位の保存が必須になったとき
  （§5.8.6）に提示する。
  * 上位の共有状況が**「単独所有」「新規作成」なら確認を出さず自動保存**し、保存完了メッセージで事後通知する
  * **「所有元不明」「別の構成」「共有中」のときだけ 4 択**（保存 / 別名保存 / 保存しない / キャンセル）を
    提示し、**既定ボタンは別名保存**とする。キャンセルは一覧へ戻る
  * 依存が発生しない経路（上位の保存先が未作成で既定計画により普通に書かれる等）では通知しない
* **再計算先の上書き確認**: 上位の保存先が変わると子の既定保存先も再計算される。
  再計算後のパスに既存ファイルがあり、共有状況が「単独所有」以外の**「保存」行**だけを対象に、
  行単位で上書き確認を出す（0 件なら確認も出ない）。選択肢は
  **上書き / 別名保存（対象行を別名で保存し直す）/ キャンセル（保存を中止）** の 3 択で、
  **既定は別名保存**。**一覧の再表示・選び直しはしない**
* 別名保存は明示操作であり、その帰結として子の保存先が追随する。**再解決のたびに一覧を再表示しない**

#### 5.8.6 依存関係と索引の更新

* **子の保存先パスが変わるとき、その子を索引する上位の保存は必須**とする
  （keymap / trigger_set → keymap_set、sequence → trigger_set）。
  「パスが変わる」には**別名保存だけでなく、source_path を持たない子が新たに実体化する場合**も含む
  （旧形式のインライン sequence・「例を復元」直後の子など）
* **例外（deferred index）**: 依存確認の 4 択で「保存しない」を**明示選択**したときのみ、上位の保存を見送る。
  このとき上位の索引は**旧パスを維持**し、上位は**保存前の dirty 状態にかかわらず未保存にする**
  （次回保存で追随する）。keymap_set 本体と起動設定は従来どおり保存する。
  `_parent_refs` を更新するのは実際に書いた子のみ
* **書き込み失敗時の保証は best-effort**（完全なトランザクションは行わない）。
  **上位の索引を新しいパスへ進める前に、子の書き込み成功を確認する**書き込み順序とし
  （子 → 上位 → keymap_set → 起動設定）、子が書けなかった場合は**上位の索引と起動設定を
  旧内容のまま維持する**（部分的に壊れた索引を残さない）
* **「保存しない」を選んだ子は、保存後も未保存マークが残る**
* **「保存しない」を選んだ子の索引**は、**旧 source_path が実在すればそのパスを指し、
  無ければ空にする**。keymap の索引が空になった場合、その keymap は keymap_set の
  `keymaps[]` から落ちる（実体を指せないエントリを書かない）
* keymap_set の「保存」自体は明示操作のため、子の別名保存で索引パスが変わっても keymap_set の
  保存に追加の確認は求めない
* **変更が無い状態で保存した場合も**、keymap_set・起動設定・未実体化の子は書かれ、保存完了メッセージも出る

#### 5.8.7 個別保存経路

* 各パネルの個別「保存」「別名で保存」も §5.7 に従いパスを解決してから書き込む
  （相対表記のまま書き込み層へ渡さない）
* **個別「トリガー一覧を保存」も保存計画で実行する**。dirty な sequence があれば
  **sequence 行のみの一覧ダイアログ**を出し、計画にある子だけを書く（trigger_set 自身は行に出さない）。
  dirty な sequence が無ければダイアログを出さない
* 個別保存で子の保存先が変わったときは、**その子を索引する直接の上位を未保存にする**
  （sequence → trigger_set、trigger_set / keymap → keymap_set）。上位を自動保存はしない

#### 5.8.8 runtime データを新規化・置換する入口

* runtime データを差し替える入口では、**trigger_set の source_path と dirty 状態を必ず更新する**。
  更新方法は入口の種類で異なる:
  * **新規化する入口（「新規作成」「例を復元」）… 空へリセットする**
    （リセットせずに個別保存すると、前の構成のファイルへ無確認で書き込む）
  * **読み込む入口（「読込」「Import」「起動時に読む構成セットの変更」）… 読み込んだ値へ同期する**
    （keymap_set が指す trigger_set のパスを引き継ぐ）
* いずれの入口でも、**tracker が持つ trigger_set の source_path と runtime データ側の内部キーは
  常に一致させる**（更新の入口を 1 本に集約する）
* **「例を復元」は「中身のある新規作成」として扱う**。keymap_set のパスを引き継がず
  （＝次の保存は別名保存になる）、**復元前に未保存の確認を出す**。
  復元した子（trigger_set / 各 sequence）は**未保存（dirty）扱い**とし、
  §5.8.5 の一覧ダイアログと §5.8.4 の保護を通す

##### 入口台帳（全体デフォルトの供給）

`config/config.json` 由来の全体デフォルト（hook キー §5.9 / プリセット §5.10）は、
**runtime を新規化・置換した直後に 1 本の注入 API（`apply_global_defaults` 相当）で供給する**。
**全体デフォルトを増やすときは、この台帳の全経路について供給の要否を判断する**。

| 分類 | 入口 | 供給方法 |
| --- | --- | --- |
| E1 | App 初期化（起動直後の既定 runtime）| **注入 API** |
| E2 | 新規作成 | **注入 API** |
| E3 | 例を復元 | **注入 API** |
| E4 | 起動時の空データフォールバック | **注入 API** |
| E5 | Import（単一JSON。**split の通常読込を通らない**）| **注入 API**（**プリセットの個別指定は落としてから供給する**。下記）|
| L1〜L3 | keymap_set の読込 / 構成セットの変更 / 起動時の構成セット読込 | 通常読込（split 読込）が供給 |
| N1 | 新規作成直後の再正規化 | 供給不要（E2 の直後に同一 runtime を正規化するだけ）|
| P1 | **プリセットマネージャでの切替（ON / OFF の両方向）と、OFF でダイアログを開いた時点**の再読込（§5.10.3 の UI 契約）| **注入 API を使わない**。ダイアログ内で切替先（個別 / グローバル）を読み直して**表示を更新するだけ**で、runtime へ反映されるのは **OK を押したときの 1 本**（§5.10.3 の書き手）|

* **通常読込（L1〜L3）は注入 API を経由しない**。hook キーが §5.9.3 の移行判定を通す
  条件付き注入のため。ただし**供給規則は注入 API と一致させる**（§5.10 の `list | None` 規則）
* **hook キー単独の注入は別物**として残す（個別指定 **ON→OFF** の切替。§5.9.4）。
  束ねた注入 API を使うとキー切替だけでプリセットが再読込され、編集中の内容を取りこぼす
* **P1 は台帳の本体（runtime を新規化・置換する入口）ではない**。runtime を置き換えず、
  全体デフォルトの供給でもない**表示用の読み直し**だが、プリセットの供給点を数えるときに
  見落とされやすいため台帳へ併記する
* **プリセット単独の注入 API は増やさない**。P1 の読み直しは**ダイアログ内の表示更新**であり、
  runtime への反映はマネージャの確定（OK）に一本化する（§5.10.3）。
  読み直しには読み出し関数をそのまま使う
* **プリセットについては E1〜E4 が常にグローバルを供給する**（`apply_global_defaults` は
  keymap_set を引数に取らないため、個別指定は通常読込 L1〜L3 でのみ効く）。
  **E5（Import）は個別指定を強制的に OFF にしてから供給する**
  （`hotkey_presets_individual=false` / `hotkey_presets_path=""`。§5.10.2）

#### 5.8.9 孤児ファイルの棚卸し（検出 → 隔離 → 復元 → 削除）

**どの keymap_set からも参照されていない子ファイル（孤児候補）を検出し、可逆な「隔離」を経て
削除できるようにする保守機能**（起動口は設定メニューの 2 項目。UI は `features.md` §4.6）。
§5.8.1 の「参照元の掃除」が**現在の構成セットしか見ない**のに対し、本機能は**上位 → 子の
逆方向検査**を行う。**両者は別機能**であり、§5.8.1 の検査範囲は本節によって変わらない。

**検出（走査と判定）そのものは、ファイルを 1 件も書き換えない**（読み出しのみ。
書き込みが起きるのは隔離・復元・削除と、走査ディレクトリ設定の保存だけ）。

**未保存の変更があるときは、走査の前に保存する** — 選択肢は**「保存する / 中止する」の 2 択**とし、
**保存しない選択・保存の失敗・別名保存のキャンセルはいずれも棚卸しごと中止**する
（保存が成功したときだけ走査へ進む）。未保存の編集内容は参照側の実体に反映されておらず、
**使用中の子を孤児候補と誤判定し得る**ため。
§5.8.1 の「参照元の掃除」の保存確認とは**意味が逆の 2 択にならないよう**注意する
（掃除側の既存 API は「保存しない = 続行」であり、本機能では再利用しない）。

**走査範囲（参照側）** — 次の 4 経路の keymap_set を読む。

走査した JSON が keymap_set かどうかは、**`trigger_set_path` / `keymaps` /
`active_keymap_path` / `hotkey_presets_path` のいずれかのキーを持つか**で判定する
（**キーの有無**で見る。値が空かどうかは問わない）。**走査はリンク / ジャンクションを辿らない**。

1. `config/user/keymap_sets/` **直下**
2. `config/config.json` の `keymap_set_path`（起動エントリ）
3. **現在開いている keymap_set** — 通常読込は `config.json` を書かないため、
   **起動エントリでは代替できない**。落とすと**既定外のセットを開いている間にその子が隔離される**
4. **ユーザー指定ディレクトリ**（§5.4 の `orphan_sweep_scan_dirs`。config 外でもよい・**非再帰**）

**参照集合の構築（2 段辿り）** — keymap_set から keymap / trigger_set / 個別 hotkey_presets の
パスを読み、**trigger_set の `triggers[].sequence_path` から sequence** を読む
（**sequence のパスは keymap_set に無い**ため 1 段では集まらない）。
`external_keyboard_layouts[].path` は、**`config_root` 基準と、その親
（`dirname(config_root)`）基準の両方で解決した superset** を入れる。
読み込みが `config_root` 基準で解決するのに runtime は親基準の相対表記で保持する**既存の非対称**
（是正は [idea_13](../../backlog/idea_13_external_layout_path_base_asymmetry.md)）があり、
**どちらの基準で記録された値でも保護する**ため。
**`config/config.json` が指すグローバルプリセット（§5.10.1）も参照集合へ入れる**
（走査した keymap_set からは辿れないため。個別指定と違い上位を持たない）。

**候補側（隔離し得るもの）** — config 配下の既定 4 ディレクトリの**直下のみ**（非再帰）:
`user/keymaps` / `user/trigger_sets` / `user/sequences` / `user/hotkey_presets`。
**形状検証**を通ったものだけを候補にする（`mappings` は dict / `triggers` は list /
`actions` は list / `hotkey_presets` は list）。
**`user/hotkey_presets/global/` は候補側から除外する**（予約ディレクトリ。§5.10.1）。

**保護対象** — **編集中の構成が使っているパスは、参照集合の判定によらず候補にしない**:
現在の keymap_set 自身（**アプリが保持する現在のパス**）/ 各 keymap / trigger_set / 各 sequence /
個別プリセット（**この 4 種は runtime が持つ保存表記**）。
**実在しなくても保護する**（存在確認をしない）。**config 配下でなくても保護する**。

**判定名**（§5.8.4 と同じく、**分岐は判定名で行い表示文言で分岐しない**）:
`ORPHAN_CANDIDATE`（孤児候補）/ `ORPHAN_REFERENCED`（参照あり）/ `ORPHAN_PROTECTED`（保護対象）/
`ORPHAN_EXCLUDED`（形状検証などで対象外）。

**走査の不完全性の扱い** — 次の 5 つは**握りつぶさず結果に含める**
（孤児候補が 0 件でも該当があれば通知に含める）:
①**読めなかった参照側**（JSON として壊れている）②**リンク / ジャンクションのため読まずにスキップした参照側**
③**`listdir` に失敗した走査ディレクトリ** ④**見つからない指定ディレクトリ**
⑤**keymap_set として解釈できなかった JSON**。
**警告は一覧の先頭に出し、警告があっても実行は許す**（「実行 / キャンセル」の 2 択。
**行ごとの選択 UI は設けない**）。
**走査範囲外の keymap_set から参照され得る旨は、警告の有無にかかわらず常に併記する**
（制約 1 を利用者へ伝えるため）。

**隔離** — 隔離ルートは **`config/quarantine/`**（`user/` の外＝候補側と構造的に交差させない）。
**遅延作成**（§5.4）。実行単位は **`<YYYYMMDD_HHMMSS>`**（衝突時は `_<連番>`）で、
その下に**元の相対構造を保って移動**する。

* **マニフェストは移動より先に、原子書込みで作る**: ①これから動かす全件を**計画**として
  `manifest.json` へ書く → ②**書けなければ 1 件も動かさない**（隔離を中止する）→
  ③1 件ずつ移動し、成功のつどそのエントリの状態を更新する。
  後追い記録だと、中断時に**実体はあるがマニフェストが無い**＝復元できない隔離物が残る
* `manifest.json` は `created_at` と `entries[]`（`kind` / `original_path` / `quarantined_path` /
  `state`）を持つ。`state` は **`planned` / `moved` / `failed`**
* 隔離するのは**〔ユーザーへ提示した孤児候補〕∩〔隔離直前の再判定でも孤児候補〕**に限る
  （提示していないものを破壊的に動かさない）。再判定で増減した分は件数を結果に出す
* **移動のみ**（元ファイルを削除しない）。1 件ずつ行い、**失敗しても継続**する（件数 + 理由を出す）
* **runtime / 未保存マークは変更しない**
* 隔離ルートが**リンク / ジャンクション**のときは中止する（実体を隔離ルート外へ出さない）
* **実行単位ディレクトリの作成に失敗したときも中止する**（1 件も動かさない）。
  作成は**既存ディレクトリへの再利用を許さない**（同名が既にあれば失敗として扱う）
* マニフェストに書くパスは **§5.7 の保存表記**（config 配下は相対）とし、復元時に解決する

**復元** — 実行単位を選び、マニフェストに従って元の場所へ戻す。

* **`state` は信用せず、`quarantined_path` の実体の有無で判定する**
  （進捗書込みが失敗すると `state` が `planned` のまま実体は移動済みになり得る）
* **`original_path` が候補側 4 ディレクトリの配下でなければ拒否する**。
  **`user/hotkey_presets/global/` 配下は無条件に拒否する**（予約ディレクトリ。§5.10.1）。
  **§5.7 の `is_path_within` は同一パスも「配下」と判定する**ため、それだけに頼らない
  （ディレクトリそのものへの復元・隔離ルート外への書き込みを防ぐ）
* **復元先に同名ファイルがあれば上書きせずスキップ**し、結果に「スキップ（既に存在）」として出す。
  **復元先ディレクトリが無ければ作成する**
* **部分失敗を許容**（1 件ずつ・失敗は理由付きで記録して継続）
* **全件が戻った実行単位は、マニフェストと空ディレクトリを削除する**（中途半端に残さない）。
  1 件でも残っていれば実行単位を残す
* **マニフェストが読めない実行単位は復元対象にしない**（一覧に**「マニフェスト不正」**と出す）。
  この単位も**削除だけは可能**（下記の検証④の緩和。消せない残骸を残さないため）

**「マニフェストが読めない」の定義** — ①**JSON として解析できない** ②**トップレベルが object でない**
③**`entries` が配列でない** ④**`manifest.json` 自体がリンク / ジャンクションである**、のいずれか。
④は**内容以前のパス安全性のガード**で、中身が妥当な JSON でも読まずに不正扱いにする
（隔離ルート外の実体を復元の入力にしない）。
**エントリ単位の妥当性（必須キーの有無・値の形）は検査しない**（下記の既知の制約 8）。

**削除（不可逆）** — 粒度は**隔離の実行単位ごと**。

* **API はパスを受け取らず、実行単位 ID だけを受け取る**（UI から渡された文字列を信用しない）。
  **API 側で 4 つを検証**する: ①隔離ルート**直下**に実在するディレクトリである
  ②名前が実行単位の形式（`YYYYMMDD_HHMMSS` または `_<連番>` 付き）に一致する
  ③canonical 表記が**隔離ルート自身と一致しない** ④**有効な `manifest.json` を持つ**
* **④だけは「マニフェスト不正の単位の削除を明示的に許可する」引数で上書きできる**（既定は拒否）。
  ④を絶対条件にすると**復元も削除もできない残骸**が残るため。**①②③は緩和しない**
* **UI は通常の削除と文言を分ける**。マニフェスト不正のときは
  **「マニフェストが読めないため、中身を確認できません。」**と**「ディレクトリごと削除します。」**を
  **別行で**明記する
* **削除前に対象パスを全件提示**し、**不可逆である旨を確認画面の先頭に書く**
* 実体は**実行単位ディレクトリの再帰削除**（`manifest.json` を含む）。
  **OS のゴミ箱へは送らない**（隔離が可逆層を兼ねる・新規依存を足さない）。
  **リンクは辿らず、リンク自体を削除する**（**シンボリックリンクの場合**。
  ジャンクションは下記の制約 10）
* **途中で失敗した場合は中止とし、「一部が削除されている可能性がある」旨を通知する**。
  隔離・復元のような 1 件ずつの継続は行わない（**削除の粒度が実行単位ディレクトリ**であり、
  ユーザーは「この単位を消す」と指示しているため）
* **最後の実行単位を削除したら隔離ルート自体も片付ける**（他の単位が残っていれば残す）

**既知の制約**（いずれも**実装を変えず契約として明記**する）

1. **全網羅ではない**。走査は上記 4 経路に限られ、**`user/keymap_sets/` のサブディレクトリ**・
   **config 配下の非既定ディレクトリ**・**config 外の任意ディレクトリ**へ別名保存された keymap_set は
   走査できない。そこから参照されている子を**孤児候補として提示し得る**。
   だから**削除ではなく隔離を既定**とする
2. **候補側は既定ディレクトリ直下のみ**（非再帰）。サブディレクトリに置かれた子は対象外
3. **走査と隔離の間に外部変更があり得る**。隔離の直前に判定をやり直し、上記の積集合だけを隔離する
4. **`_parent_refs` は参照しない**（best-effort であり孤児判定の根拠にできない。§5.8.1）
5. **壊れた親があると、無傷の子を恒久的に失い得る**。読めない keymap_set があると、
   **その親が参照していた子は参照集合から抜け落ち、無傷でも孤児候補になる**。
   警告は出るが隔離・削除とも許すため、警告を読まずに削除まで進めると復旧できない。
   **壊れているのは親（多くは手で直せる小さなファイル）で、消えるのは子**である点に注意
6. **削除の確認画面の一覧は情報提供にすぎない**。一覧を作ってから確認を閉じるまでの間に
   外部プロセスがその実行単位へファイルを追加すると、**一覧に出ていない中身も一緒に消える**
   （ユーザーは実行単位 ID を選んでいるため挙動は意図どおり）
7. **検証と再帰削除の間の TOCTOU は許容する**。窓は削除 API の内部に限られるが、
   その間に隔離ルートを外部へのリンクへ差し替えられれば外部の実体を消し得る。
   塞ぐには削除完了まで実体を固定する仕組みが要り、**新規依存を足さない方針と衝突する**。
   隔離ルートを差し替えられる権限があればアプリを介さず直接削除できるため上積みも小さい
8. **マニフェストの妥当性をエントリ単位では検査しない**。手編集などで**well-formed だが実体を
   指さないマニフェスト**にすると、その単位は**「有効」として一覧に出る**。隔離側に実体が残っていても
   **復元は 0 件**になり（各エントリは「隔離側にファイルがありません」でスキップ）、削除は通常経路で進む。
   ただし削除の確認画面は**実体を全件列挙**するため**消せない残骸にはならない**。
   アプリ自身の書込みは原子的でこの形を作らないため、**発生源は手編集に限られる**
9. **一覧に出ない残骸はアプリから扱えない**。隔離ルート直下でも、名前が実行単位の形式でないもの・
   リンク / ジャンクションであるもの・ディレクトリでないファイルは、**一覧にも出ず復元も削除もできない**
   （エクスプローラ等で片付ける）
10. **削除 API 単体では、実行単位ディレクトリ自身のリダイレクト検査を課していない**。
    隔離ルート外へ向くリンクは実体基準の境界検証で拒否されるが、**ルート内の別単位を指す
    ジャンクションに対しては、削除でその別単位の中身まで消え得る**。
    ただし**UI からは到達しない**（一覧がリダイレクトされた単位を弾くため、選択肢に出ない＝制約 9）。
    **API を直接呼ぶ経路にだけ残る性質**として記録する
11. **空になった隔離ルートの後始末は削除と復元で非対称**。削除は最後の単位を消した時点で
    隔離ルートも片付けるが、**復元で全単位が空になった場合は隔離ルートが残る**（実害はない）
12. **候補側ディレクトリ直下のリンク / ジャンクションは、候補にせず件数にも出さない**
    （参照側と違い理由付きで報告しない＝無音で落ちる）。実体を移動する破壊的操作の入力に
    リンクを載せないための扱いで、**候補側は「実体のファイルだけ」を対象とする**

### 5.9 hook キーの全体デフォルトと個別指定

停止キー（`hook_stop_key`）とトグルキー（`hook_toggle_key`）は、**全体デフォルト（`config/config.json`）**と
**keymap_set ごとの個別指定**の 2 系統を持つ。新規作成のたびにキーを設定し直す手間をなくすための規定。
フック実行時の挙動は `key_input.md` §7.6。

#### 5.9.1 データモデル

* **`config/config.json`（全体デフォルト）**: `hook_stop_key` / `hook_toggle_key` を持つ。
  **正規化して保持**し、空文字を許す（**初期値は空**）。未設定のときは空として扱う
* **keymap_set（個別）**: `hook_keys_individual`（bool・**既定 false**）+ 既存キー
  `hook_stop_key` / `hook_toggle_key`
* keymap_set の保存では**この 3 キーを常に出力する**（値が空でも省略しない・§5.1 の既存キー削除禁止）

#### 5.9.2 解決順序（runtime へ載せる時点で確定する）

* 解決は **keymap_set を runtime データへ載せる時点の 1 回**で確定させる。参照するのは
  **§5.9.3 の移行判定を通して確定させた `hook_keys_individual`** であり、
  keymap_set のキーの有無をここで直接見ない
  * 確定値が**真** … keymap_set の個別値をそのまま使う
  * 確定値が**偽** … `config/config.json` の全体デフォルトを runtime の
    `hook_stop_key` / `hook_toggle_key` へ**注入**する
* **注入 API 側の既定**: 新規化・置換された runtime へ注入する経路では、**フラグを持たない runtime を
  OFF とみなす**（既定 `false` を補ってから注入する）。移行判定（§5.9.3）を適用するのは
  **保存済みの keymap_set を読み込む経路**であり、両者を取り違えないこと
  （フラグ無しの runtime へ移行判定を適用すると、注入した全体デフォルトが「個別値あり」と
  誤判定され keymap_set へ焼き付く）
* フック実行層は runtime の値を直読みするため、**常に解決済みの 1 値**だけを見る
  （供給源による分岐をフック側に持たせない）
* 注入は読込だけでなく、**runtime を新規化・置換するすべての入口**に適用する。
  対象経路は **§5.8.8 の入口台帳 E1〜E5**（App 初期化 / 新規作成 / 例を復元 /
  起動時の空データフォールバック / Import）で、**束ねた注入 API 1 本で供給する**。
  適用漏れがあるとその経路だけキーが空になり、フックが無反応になる
* **単独注入が残るのは個別指定 ON→OFF の切替だけ**（§5.9.4）。ここで束ねた API を使ってはならない
* 全体デフォルトの読み出しに失敗した場合は**空（`""` / `""`）へ縮退**する（起動は継続する）

#### 5.9.3 移行規則（後方互換）

`hook_keys_individual` を持たない既存 keymap_set は、次の規則で解釈する:

* フラグが**存在すれば**その値をそのまま使う（`false` とキー無しを区別する）
* フラグが**存在しなければ**、**正規化後**に stop / toggle の少なくとも一方が非空 → **ON**、
  両方空 → **OFF**
* 既存キーは**残す**（削除しない）
* 判定は**冪等**とする。既に ON で両キーが空の状態を OFF へ落とさない
  （§5.9.4 の「ON→OFF での内部保持」が壊れるため）

#### 5.9.4 編集と保存の契約

* **個別指定チェックの操作そのもの**は keymap_set を**未保存（dirty）にする**
  （`hook_keys_individual` は keymap_set に保存される値のため）。
  以下の「dirty にしない」規定は**キーの取得 / クリア**に対するもので、チェック操作は対象外
* **個別指定 ON**: キーの取得 / クリアは keymap_set の個別値を編集し、**値が変わる場合に**
  keymap_set を**未保存（dirty）にする**（クリアは旧値が空なら dirty にしない）
* **個別指定 OFF**: キーの取得 / クリアは **`config/config.json` の全体デフォルトを編集**する
  * 書き込みは**成否を返す**。**成功した場合のみ** runtime / UI 表示を確定する
    （失敗時は旧値を維持し、確定させない）
  * keymap_set は**未保存にしない**（OFF 前の未保存状態を記録し、操作後に復元する）
  * 全体デフォルトの書き込みは**起動設定の書き出し経路 1 本に集約する**。
    別経路で `config/config.json` を read-modify-write すると、次の起動設定書き出しが
    古い在メモリ値で hook キーを消す
* **ON→OFF の切替**: keymap_set の個別値は**内部保持**し、表示・挙動は全体デフォルトへ切り替える。
  **再 ON で復活するのは保存前の同一セッション内のみ**。保持値が無い状態で ON にした場合は
  両キーを `""` にする（全体デフォルト値を個別値として引き継がない＝焼き付きの防止）
* **OFF のまま保存**: 個別値を **`""` にクリア**し `hook_keys_individual: false` で保存する
  （キー自体は残す）。**保存を実行した時点**で内部保持していた個別値も破棄するため、
  保存後は再 ON しても空になる。保存を中止した場合は保持したままとする
* **内部保持の破棄条件**: 保持は**現在の runtime に紐づく**。保存の実行に加えて、
  **runtime を置換・新規化する操作（読込 / 新規作成 / 例を復元）でも破棄**する
  （別の keymap_set を読み込んだ後に前の構成の個別値が復活しないこと）

#### 5.9.5 契約上の制約（既知・実装は変更しない）

* **キーの衝突検証はカレント keymap_set 内に閉じる**。全体デフォルトは他の keymap_set の
  トリガーとは照合されないため、別の keymap_set を読み込むとそのトリガーと重なり得る
  （そのとき停止 / トグルが優先される。`key_input.md` §7.3 の重複禁止はカレント構成内の規定）
* **「明示 `false` + 非空の個別値」を持つ keymap_set** は、読込時に全体デフォルトで上書きされ、
  保存時に空文字化されるため**個別値が失われる**。本アプリはこの組み合わせを生成しないが、
  手編集・別実装由来のファイルでは起こり得る

### 5.10 hotkey プリセットの全体ライブラリと個別指定

hotkey プリセットは、**アプリ全体で共有する 1 つのライブラリ（グローバル）**を既定とし、
**keymap_set ごとの個別指定**を持てる。グローバルの参照は `config/config.json` が持ち、
個別指定の有無とパスは keymap_set が持つ。
**個別指定はグローバルの上書きであり、グローバルを置き換えない**（構造は §5.9 の hook キーと同型）。

#### 5.10.1 データモデル

* **`config/config.json`（グローバル）**: `hotkey_presets_path` を持つ。既定は
  **`user/hotkey_presets/global/default.json`**（config 相対）。
  **未設定 / 空文字 / 非文字列 / config.json 自体が読めない場合は、いずれも既定へ縮退する**
* **アプリはこのキーを書かない（読むだけ）**。値を変えたい場合は config.json を手編集する
  （書き手を作る場合は §5.10.3 の「唯一の書き手」規定と衝突しないこと）
* **手編集は必ずアプリの終了中に行う**。config.json は keymap_set 保存・起動設定の書き出しで
  **丸ごと書き直され**、未知キーの保全は**起動時に読んだスナップショット**に依存する
  （§5.9.4 の「全体デフォルトの書き込みは起動設定の書き出し経路 1 本に集約する」と同じ機構）。
  アプリ起動中に書き換えた値は、次の保存で無言で失われる
* **`user/hotkey_presets/global/` はグローバル専用の予約ディレクトリ**とする。
  グローバルライブラリはこの配下に置き（config.json の `hotkey_presets_path` はここを指す想定）、
  **個別ファイルはこの配下へ保存しない**（§5.10.3 の保存先ガードで拒否する）。
  名前空間を分けることで、生成される個別パスとグローバルが構造的に衝突しない。
  **孤児ファイルの棚卸し（§5.8.9）でも `global/` は候補側から除外する**
* **孤児判定では、`hotkey_presets_individual` が OFF でも `hotkey_presets_path` を
  「参照あり」と数える**（§5.8.9。**意図的な superset**）。読み出しでは OFF のパスを使わない
  （§5.10.2）が、**OFF はパスを保持して再 ON で復帰させる**規定（本節の移行規則・§5.10.3）で
  あるため、**参照されていない＝隔離してよい、とは扱わない**。
  §5.5 / 本節の「**フラグキー**を持たない keymap_set はパスを引き継がない」は**読み出し時の規則**であり、
  孤児判定は**フラグキーの有無を見ずに `hotkey_presets_path` を数える**。
  したがって**フラグキーが無くパスキーだけある keymap_set でも、そのパスは参照ありと数える**
  （読み出しでは使われないパスを保護する側に倒す。これが superset の本体）。
  `hotkey_presets_path` キー自体が無ければ数える対象も無い
* **keymap_set（個別指定）**: `hotkey_presets_individual`（bool・**既定 false**）+
  `hotkey_presets_path`（個別ファイルのパス）。**この 2 キーは保存時に常に出力する**
  （OFF でもパスを空文字化しない）。`hotkey_presets_path` は**出力時に §5.7 の表記へ正規化する**
  （config 配下は相対・区切りは `/`。手編集・別実装由来の表記をそのまま書き戻さない）
* **個別ファイルの既定パス**: **`user/hotkey_presets/<keymap_set の stem>.json`**（直下）。
  stem 規則とフォールバック名は §5.6（trigger_set）に準じる。
  既定保存先の決定は**既存ファイルの有無を考慮しない**（衝突を避けて別名へ逃がさない）
* **プリセットファイル**: 根キー `hotkey_presets` に配列を持つ
  （`{"hotkey_presets": [{"label": ..., "value": ...}, ...]}`）。
  **グローバルと個別で形は同じ**

**移行規則（後方互換）**

* **`hotkey_presets_individual` を持たない keymap_set は常に OFF**。フラグの判定は**値**で行う。
  §5.9.3 の「フラグ無し + 非空なら ON」は**採らない**（旧仕様の残置 `hotkey_presets_path` が
  個別指定として復活してしまうため）
* **`hotkey_presets_individual` キーを持たない keymap_set は、`hotkey_presets_path` も
  引き継がない**（runtime へ載せず未設定＝空文字として扱う。**この判定だけはキーの有無で行う**）。
  残置パス（旧グローバルパス `user/hotkey_presets/default.json`）が
  **個別指定としても保存先としても復活しない**ための規定。
  **フラグキーがあれば値が `false` でもパスは保持する**（OFF での保持＝再 ON での復帰。§5.10.3）
* **グローバル既定パスの移行は手動**とし、手順は **2 段**:
  1. `user/hotkey_presets/default.json` を `user/hotkey_presets/global/default.json` へ**移す**
  2. **config.json に `hotkey_presets_path` を明示保存している場合は、その値も新パスへ書き換える**
     （既定値の変更は明示値に効かないため、①だけでは旧パスを読み続け、
     マネージャの保存で旧パスが再生成される）
* **旧パスからのフォールバック読みは行わない**。移行しない場合は組込既定が表示されるだけで、
  **ファイルは失われない**
* **旧版アプリが本仕様のファイルを読んだ場合**は、`hotkey_presets_individual` が未知キーとして
  無視され、`hotkey_presets_path` も読込時無視のため**グローバルへ安全に倒れる**

#### 5.10.2 解決順序（読み出しと供給）

* 読み出しは **「読めたか」を区別する**:
  * **読めた** … ファイルが読め、根キー `hotkey_presets` が配列である（**空配列を含む**）
  * **読めない** … ファイルが無い / JSON が壊れている / dict でない / 根キーが配列でない
* **供給規則**（注入経路・通常読込で共通）:
  * **読めたらそれが唯一の正**として runtime のプリセットを**置き換える**。
    **空配列なら空にする**（利用者が全削除した意思を尊重する）
  * **読めなければ置き換えない**（runtime の既定を維持する）。
    **破損ファイルを既定値で黙って上書きしないため**
* **読み出しは正規化済みの値を返す**（`label` の trim / `value` の trim + 小文字化 /
  **非 dict 要素の除去** / **`label` または `value` が文字列でない要素の除去**）。
  **正規化はファイル単位で失敗しない**（壊れた要素だけを落とし、残りは採用する。
  手編集・別実装由来のファイル 1 つでアプリが起動不能にならないための規定）。
  **正規化は読み出しの 1 箇所に置く**。
  通常読込は互換化処理で再度正規化されるが**冪等**なので問題ない。
  **「読めたか」の判定は正規化の前に行う**（正規化の結果が空配列でも「読めた」として扱う）

**個別指定の解決順序**

* 解決は **keymap_set を runtime へ載せる時点の 1 回**で確定させる（§5.9.2 と同型）:
  1. `hotkey_presets_individual` が**真** … **個別パスから読む**。
     読めたら**それを採用** / 読めなければ**グローバルへフォールバックする**。
     グローバルも読めなければ**置き換えない**
  2. **偽（キー無しを含む）** … **グローバルから読む**（読めなければ置き換えない）
* **解決の入力は keymap_set に保存されたパス**とする（stem からの再導出はしない）。
  stem は**新規に保存先を決めるときの既定名算出**にだけ使う
* **個別パスが `config` 配下でなくても、読み出しではそのファイルを読む**
  （読めなければ 1. のフォールバックでグローバルへ倒れる）。**キーの値は書き換えない**。
  書き込みは §5.10.3 のとおり管理下の既定パスへ寄せるため、**読み書きで非対称なのは意図どおり**
  ＝ config 外のパスは「**初回に内容を拾うための移行導線**」であり、
  次に個別として保存が成功した時点で管理下の値へ置き換わる
* 供給経路は **§5.8.8 の入口台帳**に従う（E1〜E5 = 注入 API / L1〜L3 = 通常読込 /
  N1 = 供給不要 / P1 = 表示用の再読込）。
  **読み出し・正規化・`list | None` の規則は経路で変わらない**ため、
  **同じ供給元を読む経路どうしでは、読めた場合のプリセット集合が一致する**。
  ただし**個別指定が効くのは L1〜L3 だけ**なので、個別ファイルとグローバルの内容が異なるとき、
  **L1〜L3 と E1〜E5 の結果は一致しない**（意図どおり。下記）
* **個別指定が効くのは通常読込（L1〜L3）だけ**。**E1〜E4 は常にグローバル**を供給し、
  **E5（Import）は個別指定を強制的に OFF にしてから供給する**
  （`hotkey_presets_individual` を `false`、`hotkey_presets_path` を `""` にする。
  外部指定の任意パスへ書く経路を作らないため）

#### 5.10.3 編集と保存の契約

* **プリセットファイルの唯一の書き手はプリセットマネージャ**とする。
  **keymap_set の保存（保存カスケードを含む）はプリセットを書かない**
* プリセットマネージャの編集確定は**即時保存する**（keymap_set の保存に依存しない）。
  書込先は **個別指定 ON なら個別ファイル / OFF なら config.json が指すグローバル**
* **保存先の算出は application 側に置く**（presentation と二重化しない。
  子ファイルの既定パス算出と同じ流儀）
* 書き込みは**成否を返す**。**成功した場合のみ** runtime へ反映し、編集ダイアログを閉じる。
  **失敗時は編集内容を保持したままダイアログを閉じない**（再試行できる）
* **個別ファイルの実体はマネージャの確定（OK）で初めて作る**。
  個別指定を ON にしただけではファイルを作らない（実体が無い間はグローバルへのフォールバックが効く）

**書き込み前の判定（この順序で行う）**

1. **既定パスへの寄せ** … 書込先が個別で、記録されたパスが**書き込みに使えない**場合
   （**未設定 / 空文字 / 非文字列 / `config` 配下でない**）は、
   **既定パス `user/hotkey_presets/<stem>.json`（§5.10.1）を保存先にする**。
   **未設定・空も config 外と同じ分岐で扱う**（＝**初回 ON の主経路**。分岐を増やさない）。
   **これを理由にグローバルへ倒さない**（グローバルライブラリを破壊するため、書込先は必ず個別側に取る）。
   **config 外の元ファイルへは書かない・消さない**。対象は
   **その保存の実効的な書込先が個別のとき**だけで、**OFF での確定は対象外**
2. **保存先ガード（拒否）** … 寄せた後の最終的な保存先が
   **`user/hotkey_presets/global/` 配下**、または**グローバルの読み先と同一ファイル**
   （判定は §5.7 の比較専用表記）なら、**保存を拒否する**。
   理由を表示し、**ダイアログを閉じない・runtime を変更しない・dirty を汚さない・
   キーの値も書き換えない**。文言は 2 種に分ける
   （①`global/` は予約ディレクトリのため専用の保存先にできない /
   ②config.json の `hotkey_presets_path` を `global/` 配下へ直す案内＝移行手順②への誘導）。
   **同一ファイル判定は 1. だけでは防げない**（config.json が `user/hotkey_presets/` 直下を指し、
   その名前が構成セットの stem と一致すると、**専用プリセットとグローバルが同一ファイルの別名**になり、
   専用側の編集がグローバルへ漏れ続ける）。**読み出しは対象外**
3. **上書き確認** … 次の 3 条件を**すべて**満たすときだけ確認する:
   ① **個別として書き込む**（OFF ＝グローバルへの書き込みは対象外）
   ② **最終的な保存先に実体がある**
   ③ **その実体の内容が、ダイアログが直近に読み込んだ一覧と異なる**
   （＝開いた時点の一覧、または切替で差し替えた内容。**編集後の一覧とは比較しない**。
   **保存先が読めない場合も「異なる」として扱う**）。
   比較は **§5.10.2 の正規化を通した結果どうし**で行う（比較専用の別経路を作らない）。
   **出どころ（読み出し元パス）の比較にはしない**（別名保存でコピー先の実体を採用した場合に
   保存先と一致して素通りするため）
   * 選択肢は **上書きする / 既存を読み込む / キャンセル** の 3 択とする。
     **保存先が読めない（破損）ときは「既存を読み込む」を出さない**（読む対象が無いため 2 択）
   * **既存を読み込む** … 保存先の実体の内容へ**一覧と破棄確認の比較基準を差し替えるだけ**で、
     **保存せず、ダイアログも閉じない**（明示的な選択のため破棄確認は出さない）。
     差し替え後に改めて OK すると内容が一致するため確認は出ず、**既存の内容が保たれたまま保存が通る**。
     ただし**この判定は OK のたびに再評価する**（保存先を読み直し、比較基準と突き合わせる）。
     **保存先が外部から変更・削除・破損した場合は、本条項の規則どおり再び確認が出る**
     （差し替え時のスナップショットを信用して素通りさせない）。
     **差し替え後に一覧を編集した場合は確認が出ないまま編集後の内容が書かれる**
     （比較対象は編集後の一覧ではないため。既存の内容が保たれるのは編集しなかった場合）
   * **キャンセル** … 保存せず、ダイアログも閉じない。
     **runtime・dirty・ファイルのいずれも変更しない**（2. の拒否と同じ契約）
   * **通常運用では発火しない**: 初回 ON の新規作成（②で除外）/ 記録パスのある再 ON・
     ON のままの内容編集（③で除外）/ OFF での OK（①で除外）/ 内容が一致している共有（③で除外）
   * **発火するのは**: 記録パスが空のままの ON（別名保存で既存の構成セットを上書きした後など）/
     別名保存でコピー先の実体を採用した後の ON / config 外パスからの移行 / 保存先が破損して読めないとき
4. **書き込み**

**dirty と別名保存**

* **個別指定チェックの切替を確定した場合**は keymap_set を**未保存（dirty）にする**
  （`hotkey_presets_individual` は keymap_set に保存される値のため。§5.9.4 と同型）
* **`hotkey_presets_path` は値が実際に変化したときだけ** keymap_set を未保存にする
  （同じ値の再確定では立てない）。これにより
  「ON + 有効パスあり → 内容を編集して OK」では dirty が立たず、
  **プリセットの内容編集は keymap_set を dirty にしない**が維持される。
  一方、1. のリダイレクトや「最初から ON でパス未設定」の経路では値が変わるため永続化される
* **OFF での保存はグローバルへ書くため `hotkey_presets_path` を反映しない**。
  **OFF で保存しても個別パスは消さない**（フラグだけ `false`。再 ON で同じファイルへ戻る）
* **keymap_set の別名保存では個別ファイルを複製して追随させる**。
  新しい保存先の stem から個別パスを再計算し、`hotkey_presets_path` を新パスへ更新する。
  **コピー先に実体があれば複製しない**（それを使う）/ **コピー元が無ければ複製しない**
  （新パスを指すだけで、次のマネージャ確定で作られる）/
  **コピー元が `config` 外なら複製しない**（複製元の解決は**書き込み側と同じ判定**を使う。
  新パスを指すだけで、次の確定で 1. の寄せが効く）/
  **個別指定が OFF なら追随させない**（`hotkey_presets_path` を付け替えない。
  そのため **OFF のまま別名保存して再 ON すると、旧 stem のファイルへ書き**、
  元のセットとの共有〔§5.10.4〕に入り得る）。**複製に失敗した場合は
  keymap_set 本体の保存ごと中止する**（「専用のはずが元と共有」状態を黙って作らない）。
  ここで行うのは**既存ファイルのコピー**であり、**内容を決める書き手はマネージャのまま**
* **同じパスへの通常保存では個別パスを付け替えない**

**プリセットマネージャの UI 契約**

* 切替 UI は**マネージャ内**に置く（「この構成セット専用にする」チェック + **保存先パスの表示**）
* **チェックの確定は OK ボタンで行う**。**キャンセルならフラグ・dirty・ファイル・runtime の
  いずれも変更しない**
* **keymap_set が未保存（パス空）のときは ON にできない**（無効化し理由を表示する）。
  この可否は**保存 / 読込 / 新規作成の後に再評価する**
* **チェックの切替は「次の OK でどこへ書くか」と「編集中の一覧」を同時に切り替える**:
  * **OFF → ON** … 個別ファイルが**読めればその内容へ差し替える** /
    **読めなければ現在の一覧を引き継ぐ**（＝実質のコピー。初回 ON の導線）
  * **ON → OFF** … グローバルが**読めればその内容へ差し替える** /
    **読めなければ組込既定へ差し替える**（**現在の一覧を持ち越さない**）。
    これにより**個別の内容がグローバルへ流出する経路が無くなる**
  * **一覧が編集済みで差し替えが起きる場合は破棄確認を出す**。
    **キャンセルならチェックを元の状態へ戻し、一覧も保存先表示も変えない**。未編集なら確認しない。
    判定は「**直近に読み込んだ一覧**」との比較で行う
  * **読み直しはダイアログ内の表示更新**であり、**runtime へ反映されるのは OK のときだけ**
    （§5.8.8 の P1）
* **ダイアログを開いた時点でも、OFF なら一覧を表示元へ合わせて確定させる**
  （グローバルが読めればその内容 / 読めなければ**組込既定**）。
  **ON では行わない**（「個別が読めなければその時点の一覧を引き継ぐ」を壊さないため）。
  この確定も**ダイアログ内の表示にとどまる**
* **OK の挙動**: ON なら個別ファイルへ書いて runtime へ反映 /
  **OFF なら表示中の一覧をグローバルへ書いて runtime へ反映**する（例外を作らない）。
  ON → OFF でグローバルを読み直せなかった場合は表示中＝**組込既定**が書かれるため、
  **失われた / 壊れたグローバルをここで作り直す導線**になる
* **表示は「保存先」と「一覧の出どころ」の 2 つに分ける**（1 つに混ぜない）。
  **保存先** = 次の OK で書く先で、**チェックの切替に追従する**（フォールバック中でも個別パスを出す）。
  **出どころ** = いま表示している一覧がどこから来たか。出し分けは次のとおり:
  * 個別が読めた … **個別のパス**
  * 個別が読めずグローバルへフォールバック中 … **「グローバルを表示中」**
  * 個別もグローバルも読めない … **「読み込めませんでした（既定を表示中）」**
    （「グローバルを表示中」と誤表示しない）
  * 個別パスが config 外 … **「config 外のファイルを読み込み中・次の保存で管理下へ移る」旨 +
    これから書く既定パス**（「無効」とは表示しない）
  * OFF でグローバルが読めない … **「グローバルを読み込めませんでした。組込既定を表示中
    （OK でグローバルを作成します）」**

#### 5.10.4 契約上の制約（既知・実装は変更しない）

* **破損・不存在（＝「読めない」）のときも、プリセットマネージャの保存はファイルを上書きする**。
  破損内容を退避・警告する仕組みは持たない。**保存前に利用者が退避すること**。
  ただし**個別ファイルへの書き込みでは §5.10.3 の上書き確認が挟まる**
  （保存先が読めない場合も「異なる」として確認する。グローバルへの書き込みは対象外）
* **「読めない」ときの上書き内容は入口経路によって異なる**。置き換えを行わないため runtime は
  **起動時の空データフォールバック（E4）＝空 / Import（E5）＝取り込んだ単一JSON のインライン値 /
  それ以外（E1・E2・E3・L1〜L3）＝組込の既定プリセット**となる。
  その状態でプリセットマネージャを確定すると**その内容でライブラリが確定する**
  （例: 空データ起動のセッションでは**空でライブラリが確定し得る**）。
  * **ただし OFF でマネージャを開いた場合には当てはまらない**。§5.10.3 の UI 契約により
    **開いた時点で表示元（グローバル / 読めなければ組込既定）へ一覧を確定させる**ため、
    runtime が個別由来の一覧を持ったまま OFF になっていても、
    **書かれるのは表示元の内容**になる（ラベルと実体が乖離しない）。
    **この確定は runtime への注入ではなくダイアログ内の表示用再読込**である（§5.8.8 の P1）
* **同一 stem の複数 keymap_set が同じ個別ファイルを共有し得る**（無警告）。
  §5.8 の `_parent_refs`・共有状況判定・誤爆保護は**個別プリセットには効かない**。
  §5.10.3 の上書き確認が止めるのは「**共有が始まる瞬間のデータ損失**」であり、共有そのものは許容する
* **`hotkey_presets_individual` キーを持つ keymap_set で `hotkey_presets_path` を手編集した場合**は、
  **記録済みパスがそのまま個別ファイルの保存先になる**（アプリが書いた値かを値から判別できないため。
  config 外なら §5.10.3 の 1. で既定パスへ寄る）
* **個別指定を OFF へ戻すときにグローバルが読めない場合**は、一覧が**組込既定へ差し替わり**、
  OK で**グローバルが組込既定として作成 / 修復される**。
  このとき**壊れた既存のグローバルファイルは退避されずに上書きされる**（1 点目の既定規則どおり）
* **上書き確認と書き込みの間の競合（別プロセスによる作成・置換）は対象外**とする
  （§5.8.3 の「保存先に実体があれば保存しない」等と同水準の既知の性質）
* **別名保存での複製は keymap_set の保存より前に実行され、保証は best-effort**
  （§5.8.6 と同じ方針）。**複製に成功した後で keymap_set 本体の保存が失敗した場合は巻き戻さない**ため、
  **孤児となった複製ファイル**と、**メモリ上だけ新しい保存先を指す `hotkey_presets_path`** が残る
  （ディスク上の keymap_set は旧パスを指したままなので、**次回起動時の読み込み先は変わらない**）。
  この状態で続けてプリセットを編集して確定すると、**複製の内容と読み込んだ一覧が一致するため
  上書き確認は出ず**、編集は複製側へ書かれる。**keymap_set を保存し直せば新パスが永続化されて解消する**が、
  保存せずに終了すると編集が反映されていないように見える
  （実体は複製側に残る＝データは失われない）。是正は
  [idea_11](../../backlog/idea_11_save_as_preset_copy_rollback.md)（優先度低）
* **上書き確認で「既存を読み込む」を選んだ直後、「一覧の出どころ」の表示は追従しない**
  （個別 / グローバル / 組込既定の 3 分類に「保存先の実体を採用中」が無いため）。
  **対象ファイルは個別指定のチェックと保存先の表示で判別できる**ため、状態を増やさない
* **プリセットの読み出しは同期実行**のため、**到達不能な UNC / 切断されたネットワークドライブ /
  極端に大きい JSON** を指していると読み込み中は UI が待たされる
  （config 外に限らず、trigger_set・keymap の読み出しと同じ性質。非同期化はしない）
* **旧「別ディレクトリ保存」で生成された `<保存先>/hotkey_presets/default.json` は参照されない**。
  当該 keymap_set は `hotkey_presets_individual` キーを持たないため §5.10.1 の移行規則で
  常に OFF となり、残置パスも引き継がれない。必要なら手動でライブラリへ移す
* **Export（単一JSON）はプリセットをインラインで含む**が、Import 時はライブラリが読めれば
  そちらで置き換わるため、**Export ファイル中のプリセットは事実上デッドデータ**になる
  （ライブラリが読めないときだけインライン値が残る）
