## 5. JSON 仕様

### 5.1 重要ルール（後方互換）

* 後方互換必須
* 既存キーの削除禁止
* 既存キーの意味変更禁止
* 未定義キーは無視する

※設計変更タスクの場合は、指示された範囲でのみ変更可能。

**「削除禁止」の例外＝生成停止（能動削除ではない）**: 役目を終えたキーは
**payload の生成を止める**ことで、再保存時に自然に消える形にしてよい。
既存ファイルから**能動的に削除（`pop` 等）はしない**。
**現在、恒久的に生成を止めているキーは無い**（keymap_set の `hotkey_presets_path` は
**個別プリセットの指定**として `hotkey_presets_individual` とともに**常に出力する**。§5.10.1）。
ただし §5.11.3 のドラッグ用 4 キーは **`drag` が false のとき条件付きで出力しない**
（同じく能動削除はしない。条件が変われば再び出力される点が上記の「役目を終えたキー」とは異なる）。
※ §5.9.1 の「hook 3 キーは値が空でも常に出力する」とは扱いが異なる（あちらは削除禁止の原則どおり）。

#### 型不正の共通規則（読込時）

**読込時、文字列を期待するフィールドに非文字列が入っていたら空として扱う。**
**ただし、そのフィールドが空になると要素が成立しない場合は、要素ごと除去する。**

* **空扱い**（要素は残す）… `label` のような付随フィールド、および代替手段を持つ同一性フィールド
  （keymap の `id` はファイル名 stem へフォールバック / trigger の `key` は UI で入れ直せる）。
* **要素ごと除去**… `mappings` の対（target が空なら対応付けが成立しない）/
  `hotkey_presets` の要素（`label` / `value` が非文字列のとき）/
  ファイル名を持たない単一 JSON の `keymaps[]` 要素（`id` が空になると一意化できないため。§5.2）。
* **要素の形そのものが不正な場合も除去**する（`triggers[]` / `keymaps[]` / `actions[]` の非 dict 要素）。
  これは型ではなく形状の話であり、上記の空扱いとは別の判定。
* 配列・辞書を期待するフィールドが別の型なら**空のコンテナとして扱う**
  （`triggers` / `actions` が list 以外なら `[]`、`mappings` が dict 以外なら `{}`）。
* falsy な非文字列（`0` / `false` / `[]` / `{}` / `null`）は元から空扱いであり、本規則で挙動は変わらない。
* **エラーダイアログは出さない**（黙って捨てる）。読込時にファイルは書き換えない。
  ただし捨てた値は、その後の保存操作でファイルから消える（runtime を書き出すため）。
* bool / int のフィールド（`suppress` / `run_to_end` / `run_to_end_delay_ms` / `clicks` 等）は
  本規則ではなく各節の既定値規定に従う。
* 文字列として受け入れた値は trim する。キー名として扱うもの（`key` / `id` / `mappings` の
  キーと値）はさらに小文字化する。
* 孤児棚卸しの候補判定で使う形状検証（[§5.8.9](data_schema/5_08_09_orphan_sweep.md)）は
  **目的が異なる別規定**であり、本規則とは独立に適用される。
* 各節の型欄は本規則を参照する（節ごとに扱いを書き下さない）。

### 5.2 基本構造（単一JSON互換）

```json
{
  "triggers": [...],
  "hotkey_presets": [...],
  "hook_stop_key": "f12"
}
```

* `triggers[].actions` の要素のスキーマは §5.11（アクション要素）
* `triggers[].key` / `triggers[].label` / `keymaps[].id` / `keymaps[].label` の型が不正な場合は
  §5.1「型不正の共通規則」に従う
* ただし **`keymaps[].id` の扱いだけは個別 JSON と異なる**。単一 JSON にはファイル名が無く
  stem へフォールバックできないため、**`id` が空になる要素（非文字列を含む）と `id` が重複する要素は
  除去する**（個別 / split 読込の `_2` 付加による一意化は行わない。§5.6「keymap」）

### 5.3 拡張キー

#### run_to_end

* 型: bool
* 連続実行

#### run_to_end_delay_ms

* 型: int
* デフォルト: 300

| 機能 | 形式 |

#### keymap_set の保存先と「ファイルなし」状態

* keymap_set の既定の保存先は**ディレクトリ `config/user/keymap_sets/`** とする。
  固定ファイル（`default.json`）を既定の保存ターゲットにしない
* 起動時に `config/user/{keymap_sets,keymaps,trigger_sets,hotkey_presets,hotkey_presets/global,sequences}`
  を作成する（`hotkey_presets/global/` はグローバルライブラリ専用の予約ディレクトリ。§5.10.1）。
  **隔離ルート `config/quarantine/` はこのリストに含めない**（§5.8.9 の遅延作成。
  隔離を 1 度も実行していない環境に作らない）。
  **読み込み履歴 `config/keymap_set_history.json` も作らない**（§5.12.4 の遅延作成。
  最初に記録が発生した時点で作る）。
  `config/config.json` 本体は起動時に作らず、**最初に設定が永続化された時点**で作成する
  （keymap_set の保存 / フォントサイズ変更 / 起動時に読む keymap_set の指定 /
  フル表示の境界線のドラッグを離したとき / フル表示のウィンドウ幅を変えたとき）
* **`config/config.json` はフル表示の幅配分の保存値を持つ**（`features.md` §4.6「フル表示の幅配分」）。
  書き込みは起動設定の書き出し経路 1 本を通す（`orphan_sweep_scan_dirs` と同じ機構。keymap_set の保存で
  config.json が書き直されても値は残る）。**キーが無ければ既定で動く**（後方互換）:
  * **`full_view_pane_widths`** = `{"keymap": <int px>, "sequence": <int px>}` — 両端の枠（キーマップ管理 / 出力シーケンス）の
    **希望幅**。トリガー一覧の幅は保存しない。**dict でない / どちらかが欠ける / bool を含む非 int / 0 以下のいずれかなら
    キー全体を無視して既定幅**（エラー表示なし・ファイルは書き換えない）。正の int だが最小幅未満の値は希望幅として保持し、
    表示だけ最小幅へ引き上げる。書き込み契機 = 境界線のドラッグを離したとき（希望幅の組が変わった場合のみ）
  * **`full_view_window_width`** = `<int px>` — フル表示時のウィンドウ幅。**bool を含む非 int / 1 未満なら無視して 780**
    （エラー表示なし・ファイルは書き換えない）。画面幅より広い値は画面幅で開く（ウィンドウ最小幅がそれより広ければ最小幅。保存値は、起動時の更新条件〔`features.md` §4.6〕に当たる場合を除き書き換えない）。
    書き込み契機 = ウィンドウ幅を変えてから 500ms 変化がなかったとき / 起動時に保存値が最小幅に届かず広げたとき（条件は `features.md` §4.6）。
    `full_view_pane_widths` とは別キーで、片方が不正でももう片方は使う
* **`config/config.json` は孤児ファイルの棚卸しの走査ディレクトリ設定
  `orphan_sweep_scan_dirs`（文字列の配列・既定は空）を持つ**（§5.8.9）。
  **書き込みは起動設定の書き出し経路 1 本を通す**（config.json は keymap_set の保存等で
  丸ごと書き直されるため、直接書くと次の保存で無言消滅する。§5.9.4 と同じ機構）。
  値は §5.7 の表記へ正規化し、**非文字列・空文字・重複を除いて保存する**（実在確認はしない）。
  **一覧の編集は棚卸しを実行せずダイアログを閉じた場合も保存する**（設定の編集と棚卸しの実行を分ける。
  UI にもその旨を表示する）
* アプリが保持する現在の keymap_set パスは、次の 3 経路で**空（＝ファイルなし）**になる:
  1. 新規作成した直後
  2. Import（単一JSON）に成功した直後
  3. 起動時に `keymap_set_path` が**未設定 / 不在 / 読込失敗**の場合（無言で空データ起動する）
* パスが空の状態で「保存」した場合は**別名保存**として扱う。
  別名保存ダイアログの初期ディレクトリは `config/user/keymap_sets/`、初期ファイル名は `keymap_set.json`
* パスが空でない場合の「保存」は従来どおり当該ファイルへ上書きする
* **保存では `config/config.json` の `keymap_set_path`（起動エントリ）を更新しない**。起動エントリの変更は
  ファイルメニュー「起動時に読む構成セットを指定…」（`features.md` §4.6）だけが行う。**別名保存でも据え置く**
  * **例外** = 起動エントリが**未設定**、または**起動時に読めなかった**場合は、保存先で更新する
    （自己修復。起動対象を指定しないまま新規作成状態で起動し続けるのを防ぐ）
  * **「読めなかった」は起動時の実読込結果で判定する**（保存時にファイルの実在を確かめ直さない）。
    上記経路 3（未設定 / 不在 / 読込失敗）に当たった起動では、そのセッションの**最初の保存**で
    起動エントリが埋まり、以後は更新しない。**壊れた JSON も自己修復の対象**に含まれる
  * 更新しない場合も `config/config.json` の**他のキーは従来どおり書き直す**
    （据え置くのは `keymap_set_path` の値だけ）
  * **別名保存で起動エントリが指すファイル自身を複製した場合も据え置く**。元ファイルが残るため
    起動エントリは有効なままで、**次回起動は別名保存前のファイルを読む**
* **trigger_set は既定名のレベルで keymap_set ごとに分離する**（§5.6・既定名が keymap_set の
  ファイル名由来）。ただし**既に source_path を持つ子はその保存先を使う**ため常に分離されるとは限らず、
  keymap_set が未設定のときは §5.6 のフォールバック名へ、別名の keymap_set が同一 stem へ丸まる場合は
  同一ファイルへ落ちる。
  **hotkey_presets は keymap_set の子ファイルにしない**（§5.8 の保存計画に載せない）。
  既定は `config/config.json` が指す**アプリ全体のライブラリ**だが、
  **keymap_set ごとの個別指定を持てる**（§5.10）。いずれの場合も
  **keymap_set の保存（保存カスケードを含む）ではプリセットの内容を書き込まない**
  （書き手はプリセットマネージャのみ）。ただし **keymap_set の別名保存では既存の個別ファイルを
  複製する**（内容の生成ではなくファイルのコピー。§5.10.3）。
  **keymap / sequence の既定保存先はセット横断で共有される**（`config/user/keymaps/` /
  `config/user/sequences/` 配下のラベル・id 由来のファイル名）。別々の keymap_set が同名の子を持つと
  保存先が衝突し得るため、誤爆上書きは §5.8 の参照元記録と共有状況判定で防ぐ
* **【実装未追従】** 別名保存でレガシー `<アプリ配置>/settings/` 配下を選んだ場合のみ、選択パスが
  `config/user/keymap_sets/default.json` へ差し替わる実装が残っている
  （[idea_09](../../backlog/idea_09_legacy_settings_save_path_fallback.md)）。**本節の規定が正**であり、
  実装側を追従させる

### 5.5 split 読込

* 通常読込では `keymap_set.json` を直接選択する
* `config/config.json` は起動時に読む `keymap_set_path` を保持する
* `keymap_set.json` は trigger_set / keymap の実体JSONをファイルパスで参照する。
  **hotkey preset は個別指定が ON のときだけ参照する**（`hotkey_presets_individual` が真なら
  `hotkey_presets_path` を個別ファイルとして読む。OFF＝既定では `config/config.json` 起点の
  グローバルを使う。§5.10.2）。
  **`hotkey_presets_individual` キーを持たない既存ファイルは常に OFF として扱い、
  残っている `hotkey_presets_path` も引き継がない**（§5.10.1 の移行規則）
* `keymap_set` の `trigger_set_path` / `active_keymap_path` / `keymaps[].path` /
  `keymaps[].switch_key` / `hotkey_presets_path` の型は **§5.1「型不正の共通規則」に従う**。
  **非文字列は空扱い＝未指定と同じ**（そのファイルを参照しない / スイッチキーを登録しない）
* `keymaps[]` の要素は **dict（`path` / `switch_key` を持つ）と、旧記法の文字列**の両方を受ける
  （文字列は `path` 相当で `switch_key` を持たない）。**dict でも文字列でもない要素、および
  `path` が空になる要素は除去する**
  ※ ここでいう `keymaps[]` は **keymap_set が持つ参照エントリ**であり、§5.1 の
  「`keymaps[]` の非 dict 要素は除去」が指す**単一 JSON / runtime の内容 keymaps**（§5.2）とは別物。
  **参照エントリでは旧記法の文字列を落とさない**（互換のため）
* **`switch_key` はキー名なので trim + 小文字化**、**パスは（読込時の型正規化としては）trim のみで
  小文字化しない**（§5.7。記録時の区切り文字 `/` への正規化は別途 §5.7 が定める）
* `external_keyboard_layouts[]` も同様に、要素は dict（`path` を持つ）と文字列の両方を受け、
  **パスが空になる要素は除去する**（§5.1）

### 5.6 個別JSON

#### trigger_set

* `config/user/trigger_sets/` 配下に保存する
* `triggers[]` は `key` / `suppress` / `sequence_path` を持つ
* `sequence_path` は出力シーケンスJSONへの参照
* `triggers` が **list 以外なら `[]`**、`triggers[]` の**非 dict 要素は除去**する（§5.1）
* **フィールドの型**（不正時は §5.1「型不正の共通規則」に従う）:

  | キー | 型 | 不正時 |
  |---|---|---|
  | `key` | str | **空扱い**（trigger 自体は残す。空 key の trigger は従来どおり残る） |
  | `label` | str | **空扱い** |
  | `sequence_path` | str | **空扱い**（参照なし＝同 trigger のインライン `actions` を使う） |
  | `suppress` | bool | **キーが無ければ true**。値があれば `bool()` で解釈するため **`null` / `0` / `""` / `[]` は false** になる（不正値を既定 true へ倒すのではない） |
  | `run_to_end` | bool | 同上（既定 false） |
  | `run_to_end_delay_ms` | int | 変換不能なら 300（`"500"` のような数値文字列は 500 として受け入れる） |

* **参照先 sequence の `label` も同じ規則で正規化する**。読込時に参照元 trigger の `label` を
  上書きするため、ここを正規化しないと参照先経由で不正な値が入り込む

#### keymap

* `config/user/keymaps/` 配下に保存する
* `id` / `label` / `mappings` を持つ。未定義キーは無視する（§5.1）
* **フィールドの型**（不正時は §5.1「型不正の共通規則」に従う）:

  | キー | 型 | 不正時 |
  |---|---|---|
  | `id` | str | **空扱い** → ファイル名の stem 由来へフォールバック → それも空なら `keymap` |
  | `label` | str | **空扱い** |
  | `mappings` | dict（str → str） | 値（target）が非文字列なら**その対を除去**する |

* `mappings` のキー（source）は JSON 由来のため常に str であり、型の論点にならない
* **個別 / split 読込では** `id` の重複時に `_2` 以降を付けて一意化する
  （単一 JSON では重複要素を除去する。§5.2）。`id` / `mappings` のキー・値は
  trim + 小文字化で正規化し、正規化後に空になる対は除去する
* `mappings` が **dict 以外なら `{}`** として読む（§5.1）。孤児棚卸しの候補判定で使う
  §5.8.9 の形状検証は目的が異なる別規定
* 保存パスの表記は §5.7（`config` 配下なら相対）に従う

#### sequence

* `config/user/sequences/` 配下に保存する
* `label` / `run_to_end` / `run_to_end_delay_ms` / `actions` を持つ
* `run_to_end` / `run_to_end_delay_ms` は UI 上の「連続実行」「間隔(ms)」
* `actions[]` の要素のスキーマは §5.11（アクション要素）
* sequence の新規保存ファイル名は label 由来にし、日本語 label もそのまま候補に使う
* ファイル名では Windows 禁止文字のみ `_` に置換する
* trigger_set の新規保存ファイル名は現在の keymap_set ファイル名由来（拡張子を除いた stem）にする。
  stem は Windows 禁止文字を `_` に置換したうえで、連続した `_` の圧縮・前後の ` ._` の除去・
  予約名（`CON` 等）への `_` 付加を行う。**この処理の結果が空になる場合はフォールバック名**を使う
  （下記の経路別の名前）
* keymap_set が未設定（§5.4 の「ファイルなし」状態）のときのフォールバック名は**経路で異なる**:
  * **構成セットの一括保存**（keymap_set を保存する経路）… `default`（＝
    `config/user/trigger_sets/default.json`）
  * **個別「トリガー一覧を保存」**… `trigger_set.json`
* 既定保存先の決定は**既存ファイルの有無を考慮しない**（衝突を避けて別名へ逃がさない）。
  既存ファイルの保護は §5.8 の共有状況判定と既定選択規則が担う

#### 旧形式互換

* 旧形式の `triggers[].label` / `triggers[].run_to_end` / `triggers[].run_to_end_delay_ms` /
  `triggers[].actions` は読込互換を維持する
* 保存時は trigger_set + sequence の新形式へ寄せる
* 旧形式の `actions[]` の要素も §5.11（アクション要素）に従う

### 5.7 パス保存ルール

* `config` 配下のパスは `config` ルート基準の相対パスで保存する
* `config` 配下ではない外部パスは絶対パスで保存する
* 読込時は絶対パスをそのまま使い、相対パスは `config` ルート基準で解決する
* trigger_set / sequence / keymap 個別保存でも同じルールを適用する
* **記録用の表記（stored）と書き込み用のパス（resolved）を分離する**。runtime が保持する参照パスは
  本節の表記（`config` 配下なら相対）のまま保ち、**ファイルへ書き込む直前に `config` ルート基準で
  絶対パスへ解決する**。解決済みの絶対パスを runtime の参照パスへ書き戻さない
  （相対表記が絶対へ置換されると、次回以降の内外判定と索引が壊れる）
* config 外の絶対パスも**区切り文字は `/` に正規化**して記録する
* 本節は**保存経路・読込経路の両方**に適用する（個別読込で選んだファイルも、config 配下なら相対で記録する）
* **JSON に記録するパス値**の型が不正な場合は §5.1「型不正の共通規則」に従う
  （非文字列は空扱い＝未指定と同じ）。**パスは小文字化しない**（下記の同一性判定で使う
  `normcase` は**比較専用**であり、記録する表記は大文字小文字を保持する）
  runtime 専用の内部キー（`_keymap_source_path` 等・§5.8.2。永続化しない）の**パス値も読込時に本規則に従う**
  （手編集の単一 JSON で非文字列が入っていても空扱い＝未指定と同じ。キーが無ければ補わない）
* **パスの同一性判定は正規化した比較専用の表記で行う**（解決 → `normpath` → `normcase`）。
  ドライブ文字の大小・区切り文字・相対/絶対の差で「`config` の外」と誤判定しないこと。
  正規化した文字列は**比較にのみ使い、保存値・表示・戻り値へ混入させない**

### 5.9 hook キーの全体デフォルトと個別指定

停止キー（`hook_stop_key`）とトグルキー（`hook_toggle_key`）は、**全体デフォルト（`config/config.json`）**と
**keymap_set ごとの個別指定**の 2 系統を持つ。新規作成のたびにキーを設定し直す手間をなくすための規定。
フック実行時の挙動は `key_input.md` §7.6。

#### 5.9.1 データモデル

* **`config/config.json`（全体デフォルト）**: `hook_stop_key` / `hook_toggle_key` を持つ。
  **正規化して保持**し、空文字を許す（**初期値は空**）。未設定のときは空として扱う
* **keymap_set（個別）**: `hook_keys_individual`（bool・**既定 false**）+ 既存キー
  `hook_stop_key` / `hook_toggle_key`
* keymap_set の保存では**この 3 キーを常に出力する**（値が空でも省略しない・§5.1 の既存キー削除禁止）

#### 5.9.2 解決順序（runtime へ載せる時点で確定する）

* 解決は **keymap_set を runtime データへ載せる時点の 1 回**で確定させる。参照するのは
  **§5.9.3 の移行判定を通して確定させた `hook_keys_individual`** であり、
  keymap_set のキーの有無をここで直接見ない
  * 確定値が**真** … keymap_set の個別値をそのまま使う
  * 確定値が**偽** … `config/config.json` の全体デフォルトを runtime の
    `hook_stop_key` / `hook_toggle_key` へ**注入**する
* **注入 API 側の既定**: 新規化・置換された runtime へ注入する経路では、**フラグを持たない runtime を
  OFF とみなす**（既定 `false` を補ってから注入する）。移行判定（§5.9.3）を適用するのは
  **保存済みの keymap_set を読み込む経路**であり、両者を取り違えないこと
  （フラグ無しの runtime へ移行判定を適用すると、注入した全体デフォルトが「個別値あり」と
  誤判定され keymap_set へ焼き付く）
* フック実行層は runtime の値を直読みするため、**常に解決済みの 1 値**だけを見る
  （供給源による分岐をフック側に持たせない）
* 注入は読込だけでなく、**runtime を新規化・置換するすべての入口**に適用する。
  対象経路は **§5.8.8 の入口台帳 E1〜E5**（App 初期化 / 新規作成 / 例を復元 /
  起動時の空データフォールバック / Import）で、**束ねた注入 API 1 本で供給する**。
  適用漏れがあるとその経路だけキーが空になり、フックが無反応になる
* **単独注入が残るのは個別指定 ON→OFF の切替だけ**（§5.9.4）。ここで束ねた API を使ってはならない
* 全体デフォルトの読み出しに失敗した場合は**空（`""` / `""`）へ縮退**する（起動は継続する）

#### 5.9.3 移行規則（後方互換）

`hook_keys_individual` を持たない既存 keymap_set は、次の規則で解釈する:

* フラグが**存在すれば**その値をそのまま使う（`false` とキー無しを区別する）
* フラグが**存在しなければ**、**正規化後**に stop / toggle の少なくとも一方が非空 → **ON**、
  両方空 → **OFF**
* 既存キーは**残す**（削除しない）
* 判定は**冪等**とする。既に ON で両キーが空の状態を OFF へ落とさない
  （§5.9.4 の「ON→OFF での内部保持」が壊れるため）

#### 5.9.4 編集と保存の契約

* **個別指定チェックの操作そのもの**は keymap_set を**未保存（dirty）にする**
  （`hook_keys_individual` は keymap_set に保存される値のため）。
  以下の「dirty にしない」規定は**キーの取得 / クリア**に対するもので、チェック操作は対象外
* **個別指定 ON**: キーの取得 / クリアは keymap_set の個別値を編集し、**値が変わる場合に**
  keymap_set を**未保存（dirty）にする**（クリアは旧値が空なら dirty にしない）
* **個別指定 OFF**: キーの取得 / クリアは **`config/config.json` の全体デフォルトを編集**する
  * 書き込みは**成否を返す**。**成功した場合のみ** runtime / UI 表示を確定する
    （失敗時は旧値を維持し、確定させない）
  * keymap_set は**未保存にしない**（OFF 前の未保存状態を記録し、操作後に復元する）
  * 全体デフォルトの書き込みは**起動設定の書き出し経路 1 本に集約する**。
    別経路で `config/config.json` を read-modify-write すると、次の起動設定書き出しが
    古い在メモリ値で hook キーを消す
* **ON→OFF の切替**: keymap_set の個別値は**内部保持**し、表示・挙動は全体デフォルトへ切り替える。
  **再 ON で復活するのは保存前の同一セッション内のみ**。保持値が無い状態で ON にした場合は
  両キーを `""` にする（全体デフォルト値を個別値として引き継がない＝焼き付きの防止）
* **OFF のまま保存**: 個別値を **`""` にクリア**し `hook_keys_individual: false` で保存する
  （キー自体は残す）。**保存を実行した時点**で内部保持していた個別値も破棄するため、
  保存後は再 ON しても空になる。保存を中止した場合は保持したままとする
* **内部保持の破棄条件**: 保持は**現在の runtime に紐づく**。保存の実行に加えて、
  **runtime を置換・新規化する操作（読込 / 新規作成 / 例を復元）でも破棄**する
  （別の keymap_set を読み込んだ後に前の構成の個別値が復活しないこと）

#### 5.9.5 契約上の制約（既知・実装は変更しない）

* **キーの衝突検証はカレント keymap_set 内に閉じる**。全体デフォルトは他の keymap_set の
  トリガーとは照合されないため、別の keymap_set を読み込むとそのトリガーと重なり得る
  （そのとき停止 / トグルが優先される。`key_input.md` §7.3 の重複禁止はカレント構成内の規定）
* **「明示 `false` + 非空の個別値」を持つ keymap_set** は、読込時に全体デフォルトで上書きされ、
  保存時に空文字化されるため**個別値が失われる**。本アプリはこの組み合わせを生成しないが、
  手編集・別実装由来のファイルでは起こり得る

**keymap_set ごとの個別指定**を持てる。グローバルの参照は `config/config.json` が持ち、
個別指定の有無とパスは keymap_set が持つ。
**個別指定はグローバルの上書きであり、グローバルを置き換えない**（構造は §5.9 の hook キーと同型）。

### 5.11 アクション要素（actions[] の要素）

`actions[]` は §5.2（単一JSON の `triggers[].actions`）・§5.6（sequence の `actions`）・
§5.6「旧形式互換」（旧 `triggers[].actions`）で共通の配列で、要素は dict とする。
要素は**読込時に正規化**し、**dict 以外の要素は除去する**。
正規化は split 読込・個別 sequence JSON の単体読込のいずれの経路にも適用する。
未定義キーは無視する（§5.1）。

#### 5.11.1 種別ごとのキー

| `type` | キー | 意味 |
|---|---|---|
| `hotkey` | `value` / `label` | `value` = 送るホットキー文字列（`ctrl+c` 等）。送信の規定は `key_input.md` §7.7 |
| `text` | `value` / `label` | `value` = 入力する文字列 |
| `mouse_click` | `x` / `y` / `button` / `clicks` / `label`（+ ドラッグ時 `drag` / `to_x` / `to_y` / `drag_speed`） | 画面座標へのクリック、またはドラッグ |

`label` は一覧表示用の任意の文字列。**非文字列なら空扱いで、要素自体は残る**
（§5.1「型不正の共通規則」。要素が除去されるのは**非 dict の場合**のみ）。

`type` / `button` も**非文字列なら空扱い**で、要素自体は残る（§5.1）。**キーが無いときは補わない**
（空文字のキーを足さない）。文字列は trim し、小文字化はしない（判定側が大文字小文字を区別しない）。

**`type` が無い / 空 / 上表以外の値のときは、`value` を文字列として入力する**（`text` と同じ動き。
一覧表示は `value` を表示する）。

#### 5.11.2 mouse_click（クリック）

* `x` / `y` … 画面の絶対座標。`int()` 変換の可否で判定する（`"100"` や `10.9` は受け入れる）。
  欠落 / 変換不能は**実行時エラーとして報告し、何も送らない**
* `button` … `left` / `right` / `middle`（大文字小文字は区別しない）。空 / これ以外の値は `left` として扱う
  （非文字列は §5.1 により空扱い）
* `clicks` … 1 以上の整数。1 未満 / 変換不能は 1 として扱う
* **マウス操作（クリック・ドラッグ）は send guard の対象外**（send guard = 自分が送った入力を自分のフックで
  拾わないためのガード。`codebase_map.md` 参照。キーフックはキーボードのみを見ており、マウス事象を自己受信しないため）

#### 5.11.3 mouse_click（ドラッグ）

| キー | 型 | 既定 | 意味 |
|---|---|---|---|
| `drag` | bool | `false` | true のときドラッグ操作として実行する |
| `to_x` | int | （drag 時必須） | 離す点の X |
| `to_y` | int | （drag 時必須） | 離す点の Y |
| `drag_speed` | int | `1000` | カーソルの移動速度（px/秒）。正の数。**保存は整数**とし、実行は正の実数も受け入れる |

* `drag` が false / 未指定なら**従来のクリックと完全に同じ**（後方互換）
* 真偽判定は `bool(drag)`（`"false"` のような文字列は true になる。手書き JSON の縁辺ケースとして許容）
* `drag` が true のとき `x` / `y` は掴む点、`to_x` / `to_y` は離す点。
  `to_x` / `to_y` の欠落・変換不能は**実行時エラーとして報告し何も送らない**（クリックへフォールバックしない）
* `drag_speed` の欠落・変換不能・0 以下は既定 1000 を使う
* `drag` が true のときは**実行・保存とも** `clicks` を 1 とする（キー自体は残す）。
  古い読み手 / 別実装へ同じ拡張を入れる場合もこれに合わせる（§5.11.5）
* 掴む点と離す点が同一でもエラーにしない（押して離すだけ）
* `drag` が false のときはドラッグ用の 4 キーを**出力しない**（§5.1 の「生成停止」。能動削除はしない）。
  ドラッグ ON で保存したアクションを OFF にして保存し直すと 4 キーは消え、
  `x` / `y` / `button` / `clicks` / `label` は残る

#### 5.11.4 ドラッグの実行規定

* **所要時間 = 掴む点と離す点の距離 ÷ `drag_speed` を 0.15〜5.0 秒へクランプする**。
  下限 = 補間が入らず瞬間移動になるのを避けるため / 上限 = UI スレッドの占有時間を抑えるため。
  クランプが効いた区間では指定した px/秒どおりにならない。上限はカーソル移動へ渡す時間の上限であり、
  実時間の厳密な上限ではない
* **掴む点へ移動 → 押す → 離す点へ所要時間をかけて移動 → 離す**に分解して実行し、
  **例外が起きてもマウスのボタンを必ず離す**
  （押しっぱなしにしない。キー送信の「押した分を逆順に離す」と同じ方針）
* **ドラッグの実行中は pyautogui の FailSafe を無効化し、終了時（例外時を含む）に必ず元の値へ戻す**。
  理由 = 解放の直前に FailSafe 判定が走るため、**離す点が画面の隅だと解放そのものが遮られる**。
  **失うもの = ドラッグ中（最長 5 秒程度）の四隅による緊急停止**。
  **ドラッグ以外のマウスクリックでは FailSafe は従来どおり有効**
* 画面外・負座標は OS のカーソル位置設定に従う（仕様側でクリップしない）

#### 5.11.5 既知の制約（受容）

* ドラッグを知らない読み手（旧ビルド / 別実装）は**掴む位置で単発クリック**になる（`clicks` は 1 固定のため連打にはならない）
* ドラッグ中は UI スレッドが塞がる（最長 5 秒 + 各呼び出し後の待ち）
* **実行中に物理マウスを動かすと離す位置がずれる**（物理入力との競合は制御しない。中断はしない）

### 5.12 構成セットの読み込み履歴（keymap_set_history.json）

構成セット（keymap_set）を**アプリ内の履歴から開き直す**ための記録。
ファイルメニューの「履歴から読み込む…」（`features.md` §4.6）が読み書きする。

#### 5.12.1 ファイルと構造

* 保存先は **`config/keymap_set_history.json`（固定）**。`config.json` と同階層に置き、
  **`config.json` にはキーを追加しない**
* `config/user/` 配下へは置かない（`user/` は子ファイルの置き場で、孤児棚卸しの
  **参照側の走査ディレクトリ**として指定され得るため。§5.8.9）
* **`version` キーは持たない**（他の別ファイル JSON〔hotkey presets〕に揃える）

```json
{
  "recent": [
    { "path": "user/keymap_sets/default.json" }
  ],
  "categories": [
    { "name": "仕事用", "entries": [ { "path": "D:/sets/work.json" } ] }
  ]
}
```

* `recent` — 新しい順の配列。**先頭が最新**。**最大 20 要素**（不在エントリも枠を数える）
* `categories` — ユーザーが作る分類の配列。1 階層のみ（入れ子にしない）。
  保存順は問わない（**表示時に名前の昇順**へ整列する。比較は `casefold`・同値なら保存順）
* `path` — **§5.7 のパス保存ルール**に従う（`config` 配下は相対 / 外は絶対・**小文字化しない**）

#### 5.12.2 型不正の扱い

§5.1「型不正の共通規則」の下位規定。

* `recent` / `categories` / `entries` が list でなければ**空扱い**
* 要素が dict でなければ除去する。`path` が非文字列、または trim して空なら**要素ごと除去**
* 分類の `name` が非文字列、または trim して空なら**分類ごと除去**。
  分類名が重複していたら**先に現れた方を残す**
* `recent` が 21 件以上あったら**読込時に先頭 20 件へ切り詰める**
* **「ファイルが無い」と「あるが読めない」は区別する**。上記の除去は**読めた**場合の規定であり、
  読めなかった場合に空扱いで上書きしてはならない（§5.12.5）
* **未知キーは保持しない**（最上位・エントリ・分類のいずれも、規定したキー以外は読込時に落ち、
  次の書き込みで消える）。§5.1 の「未定義キーは無視する」に対する本ファイル固有の明示規定で、
  読み手がこのアプリだけ・`version` を持たない（§5.12.1）ことを前提とする。
  **キーを増やす場合は本節の改訂が前提**（別実装と同期するなら保持方式の再検討が要る）

#### 5.12.3 記録する契機

**構成セットの読込または保存が成功し、その結果 `keymap_set_path` に空でないパスが確定したとき**、
その**実保存先（正規化後の値）**を記録する。

* 対象 = メニューからの読込 / 履歴ダイアログからの読込 / 起動時に読む構成セットの指定 /
  保存（上書き・別名を問わず**成功時のみ**）
* **記録しないもの** = 起動時の自動読込（成功・失敗を問わない）/ 起動直後の初期代入 /
  新規作成 / Import / 例の復元 / 保存計画のキャンセル / 保存の失敗
* **起動時の自動読込で記録しない理由** = アプリを起動しただけで履歴ファイルが作られるのを避ける
  （§5.12.4 の遅延作成。同一セッション内の後続の読込・保存は通常どおり記録される）
* 記録するのは**保存先の正規化を経た実際の保存先**であり、ユーザーが選んだ生のパスではない

#### 5.12.4 積み方と遅延作成

1. 履歴を**ディスクから読む**（§5.12.5 の結果が「書き込み禁止」なら以降を行わない）
2. §5.7 の保存表記へ正規化したパスを作る
3. **`recent` の先頭が既に同一パスなら、何も書き込まない**。
   判定は**永続化済みの内容**に対して行う（メモリだけ先行更新しない）
4. そうでなければ `recent` から**同一パスの要素をすべて**取り除く
5. 先頭へ新しい要素を挿入する
6. 21 件目以降を末尾から捨てる（**不在エントリも枠を数える**）
7. ファイルへ**原子的置換**で書き出す

* **同一性判定は §5.7 の比較専用表記**（解決 → `normpath` → `normcase`）に従う。
  シンボリックリンクは辿らない（§5.8.9 の方針に合わせる）
* **履歴ファイルは遅延作成**する。起動時のディレクトリ骨格作成（§5.4）の対象に**加えない**。
  最初に記録が発生した時点で作る。手順 3 により、前回と同じ構成セットを開く通常の起動では
  ディスクに触らない

#### 5.12.5 読めないときの退避

| 状態 | 扱い |
|---|---|
| ファイルが**無い** | 空の履歴として扱い、通常どおり書き込む（遅延作成） |
| **あるが読めない**（壊れた JSON / 権限エラー / 最上位が dict でない） | **退避してから空で作り直す** |

* 退避は `config/keymap_set_history.broken.json` へのリネーム。既に存在する場合は
  `keymap_set_history.broken2.json`、`broken3.json` … と連番を増やす。
  **退避先は `broken` 〜 `broken5` の最大 5 個**とし、**5 個すべて埋まっていたら退避しない**
  （無制限に増やさない）。退避しなかった場合は書き込みも行わない
* **退避に失敗したら、その操作では書き込まない**。履歴は**読み取り専用**として扱い、
  履歴ダイアログは編集操作を無効にする（`features.md` §4.6）。
  **判定は操作のたびに行う**（セッション内で保持しない）。退避できない原因が一時的なもの
  （ロック・権限）だった場合、解消後の操作では通常どおり退避と書き込みを試みる。
  **壊れたファイルを保全せずに上書きしない**という不変条件は、この都度判定でも保たれる
* 隔離ルート `config/quarantine/` は使わない（棚卸しの所有領域であり、
  中身は実行単位ディレクトリ + `manifest.json` を前提とするため。§5.8.9 / §5.4）

#### 5.12.6 永続化と UI の順序

* **永続化に成功してから UI を確定する**。分類の追加・名前変更・削除、エントリの削除・分類へのコピーは
  **書き込みが成功した場合のみ**一覧へ反映する（メモリだけ更新して見かけ上成功させない）
* **履歴の読み書きの失敗で構成セットの読込・保存を巻き戻さない**。失敗は通知にとどめる
  （既存経路の通知を上書きしない）
* 履歴自体の永続化処理では **`config/config.json` を書かない**
  （未保存確認から派生する keymap_set の保存が `config.json` を書くのは §5.4 の既存挙動）

#### 5.12.7 分類とエントリの編集

* 分類名は trim して空なら不可。**既存の分類と同名も不可**
  （trim 後の完全一致で判定する。**表示名のため大文字小文字は区別する**）
* **同一の分類内に同じパスを重複して持たない**（同一性判定は §5.12.4 と同じ比較専用表記）。
  重複する追加は**何も書き込まない**
* **「履歴から削除」は選択した 1 ノードだけを除去する**。同じパスが `recent` と分類の
  両方にある場合でも、もう一方は残る
* **履歴からの削除は実ファイルに触らない**（構成セット本体は削除しない）
* **分類の削除は配下のエントリごと**行う
* **不在ファイルのエントリを自動削除しない**（表示で区別する。`features.md` §4.6）

#### 5.12.8 孤児棚卸しとの関係

* 履歴は**参照元ではない**。孤児判定（§5.8.9）の参照集合に履歴の内容を含めない。
  走査範囲・候補側の分類結果は本ファイルの追加で変わらない
* 候補側は固定 4 ディレクトリで設定できないため、履歴ファイルが孤児候補になることはない
