## 5. 実機目視（ユーザー実施 2026-09-15）

結果: **1〜4 は問題なし**。**5・6 は想定した操作自体が UI から実行できず、未実行**（下記）。

1. **アクション編集 → プリセット編集**: アクション編集を掴んで動かしても
   プリセット編集が前面に残るか（**v0.1 で症状が確認された経路**）。
2. **プリセット編集 → 上書き確認**: プリセット編集を掴んで動かしても
   上書き確認が前面に残るか（**未確認のまま実装した経路**）。
3. **既定経路の非退行**: メニューからプリセット編集を直接開いて従来どおり操作できるか。
4. **phase 14 の非退行**: プリセット編集 → プリセット追加を閉じて親のモーダル性が戻るか。
5. **非 LIFO（指摘 1 の確認）**: 上書き確認を出したままプリセット編集を × で閉じ、
   確認が残るか / その後 App を前面に上げたとき確認が隠れないか。
6. **最小化 → 復元（指摘 6）**: 入れ子を開いたまま App を最小化して戻し、モーダル性が保たれるか。

### 5 の扱い（**取り下げで確定・2026-09-15・task_05 で反映済**）

指摘 1 は「`WM_DELETE_WINDOW` 未設定（grep 0 件）＝ × で直接破棄されるので**到達可能**」と
結論したが、**実機では背面の × 自体が押せない**（grab が Tk の入力配送を止めるため、
WM の閉じるボタンまで到達しない）。つまり**暫定仕様 §1-④ の元の根拠「UI からは到達しない」が
実測で裏付けられた**。

- **推奨**: 指摘 1 の「修正して採用（根拠の文言を訂正）」を**取り下げ**、§1-④ の文言は
  **現状維持**。task_05 では根拠に**実機実測（2026-09-15）で到達不能を確認**した旨だけ添える
- 併せて **§1-④ の参照行を更新**する: `test_nested_modal_grab.py:311` は task_03 のテスト追加で
  **`:335`（`test_non_lifo_manager_destroy_does_not_steal_confirmation_grab`）へ移動**している
- この経路を通せるのは**プログラムから破棄するテストだけ**という記述は**そのまま正しい**

### 6 で観測した別問題（本フェーズ外）

Win+D で全ウィンドウを最小化すると、**grab を App 以外（子ダイアログ）が持っている場合に
アプリを再表示できない**。→ [idea_19](../../backlog/idea_19_minimize_restore_with_child_grab.md)。

**phase 16 由来ではない（実機で確定・2026-09-15）**。`codex-adversarial-reviewer` の指摘 high
（「grab の保持者が従来から子」というだけでは断定できない。**phase 16 が変えたのは `transient` の
相手そのもの**）を受けて切り分けを行い、**phase 16 で一切変更していないネスト経路
（プリセット編集 → プリセット追加）でも再現する**ことをユーザーが実機で確認した。
**入れ子で grab を持つ窓がある状態に共通の既存問題**であり、本フェーズの退行ではない。
補足材料 2 つ:

- **Tk レベルの機械的な差は無い**（`.venv` の python で実測）。`b.transient(root)`（変更前の形）と
  `b.transient(a)`（変更後の形）で `root.iconify()` → `deiconify()` を比較したが、
  **どちらも子は withdrawn → normal へ戻り、grab の保持者も保たれる**（差分なし）。
  ただし **Win+D とタスクバーからの復元は再現できていない**（プログラム復元で代替したため）。
- **ネストした `transient` は phase 16 以前から存在する**。プリセット編集 → プリセット追加
  （`dialogs/preset_dialog.py:40` の `grab_modal(self, parent)`）は **`0beb1b4` と現在で同一**で、
  親はプリセット編集ダイアログ。**この経路は phase 16 で一切変更していない**。
