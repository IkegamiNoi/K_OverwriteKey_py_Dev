# task01_measurement.md（phase 83 task_01 の実測記録・2026-11-26）

環境: macOS（Darwin 27.2）・`.venv` の Python（Homebrew `org.python.python`）・**Tk 9.1.0**。
操作は全画面の操作（実際のマウスとキー）で行った（背景操作では Tk の窓へ文字を送れないため）。
計測用スクリプトは scratchpad（リポジトリ外）。

## 1. 素の tkinter の最小構成

D = `grab_set()` した Toplevel（`transient(root)`）。各窓の Entry をクリックして 2 文字打った。

| 窓 | 作り | クリックで入力欄に入るか | 記録（`bind_all`） |
|---|---|---|---|
| A | master = D・transient なし（「?」の経路と同じ作り） | **入らない** | 窓 A に `<FocusIn>` は来る。入力欄への `<ButtonPress-1>` は来ない。キーは窓 A 自身へ届く |
| B | master = D・`transient(D)` | **入らない** | A と同じ |
| C | master = root（メニューの経路と同じ作り） | **入らない** | フォーカスも移らない（キーは直前のフォーカス先へ） |
| D | grab を持つ窓 | 入る | `<ButtonPress-1>` が届く |

追加: A の入力欄へ `focus_force()` してから打つと**入る**。その後に A をクリックしても入力は続く（クリック自体は届かない）。
→ **macOS の Tk 9.1 では、ローカル grab の間、grab を持つ窓以外の Toplevel にはマウスの押下が届かない**（Tk の子孫か・transient かによらない）。キー入力は Tk のフォーカス先へ届く。

## 3. 候補の切り分け

- ① `modal.py` のフォーカス戻し: **主因ではない**。素の tkinter（`modal.py` なし）でも同じことが起きる。実機でキーも入らなかった理由は未特定。§1 ではキーが子の窓へ届いたのに実機では届かなかった食い違いも未説明（`_restore_modal_focus`・初期フォーカスが Notebook であることが関わる可能性）。クリックが届かないことは確かだが、キーが入らないことまでそれで説明できるとは言えない
- ② macOS の窓の扱い: **該当**（Tk 9.1 の Aqua のローカル grab の動きとして確認。ほかの Tk の版でも同じかは未確認）。「transient でない子の窓」に限らず、transient を付けても届かない
- ③ メニュー経由: **該当しない**（Mac ではダイアログの間はメニューを使えない）

## 4. 正本との関係（仕様と実装の乖離・`spec_change_workflow.md` 検出基準 A）

`features.md` §4.6「ヘルプの窓」は、ヘルプを「モーダルにも transient にもしない」とし、「メニューから開いたヘルプは…操作できない（**ダイアログの「?」がこれを補う**）」と定める。
Mac では「?」から開いたヘルプも操作できず、**この補いが成り立っていない**。なお Mac ではダイアログの間はメニュー自体を使えないため、「メニューから開いたヘルプは操作できない」という前提の場面も Windows とは別になる。
Windows では成り立っている（§5・ユーザー確認済み）。

## 5. Windows（ユーザーに依頼）

1. アクションの編集（出力シーケンスの「編集」）を開き、「?」でヘルプを開く
2. 絞り込み欄をクリックして文字を打つ / タブ「QA」をクリック / 見出しを開閉 / ヘルプの閉じるボタン
3. ヘルプを開いたまま、ダイアログ側の入力欄をクリックして操作できるか（行き来できるか）

結果（2026-11-26・ユーザー報告）: 1〜3 とも**できる**（絞り込み欄の入力・タブ・見出しの開閉・閉じるボタン・ダイアログとの行き来）。→ Windows では §4.6 の「補う」が成り立っており、問題は Mac だけ。

## 6. 直し方の案

- **案 A'（推奨）: Mac だけ、ダイアログの「?」から開いたヘルプを `grab_modal(help, parent=dialog)` でモーダルにする**。閉じれば `grab_modal` の仕組みで grab がダイアログへ戻る。Windows の今の動き（ダイアログとヘルプを行き来できる）は変えない。OS の差は `WindowBackend` の契約に 1 つ足して吸収する（phase 80 の `detaches_deep_transients_during_minimize` と同じ形）。
  ヘルプの間はダイアログを操作できない。深さは ダイアログ +1 になり、phase 80 の深さ 3 以上の扱いは Windows だけなので Mac では関わらない。
  仕様変更あり: §4.6「モーダルにも transient にもしない」に Mac の例外を足す（`/spec_update`・ユーザー承認）
- 案 A（両 OS）: 両 OS で同じにする。仕様は単純になるが、Windows で今できている行き来ができなくなる
- 案 B: ヘルプの間は grab を外す。App 本体も操作できてしまい、モーダルの意味が崩れる（非推奨）
- 案 C: Mac では受け入れ、ヘルプの文言で「ダイアログを閉じてから」と案内する。§4.6 の「補う」が Mac で成り立たないことを正本に書く

## 8. 案 D の実測（2026-11-26・Mac・素の tkinter）

案 D = 前面になった窓へ grab を移す（ダイアログとヘルプを行き来できるまま、App 本体は操作できないまま）。
D = grab を持つダイアログ（`transient(root)`）、H = ヘルプ役（master = D・`transient(D)`）。

| 試行 | 合図 | 結果 |
|---|---|---|
| D-1 | 窓の `<FocusIn>` で、その窓へ `grab_set()` | D → H は移れる。**H → D は戻れない**（H が grab を持つ間、D には FocusIn が来ない） |
| D-2 | H の `<Activate>` で H へ・H の `<Deactivate>` で D へ grab | **行き来できる**（下の表） |

D-2 の操作ごとの結果:

| 操作 | 結果 |
|---|---|
| D が前面のとき H の入力欄をクリック（1 回目） | H が前面になり grab が H へ移る。クリック自体は部品へ届かない |
| 続けて H の入力欄をクリック（2 回目）・ボタン | 届く（入力・ボタンとも） |
| H が前面のとき D の入力欄をクリック（1 回目） | H の `<Deactivate>` で grab が D へ戻る。クリック自体は届かないが、D で前にフォーカスがあった欄へキーが入る |
| 続けて D の入力欄をクリック（2 回目） | 届く |
| ROOT（App 本体）の入力欄・ボタンをクリック | **届かない**（ボタンの処理は動かず、キーは D の欄へ入る）→ モーダルの意味は保たれる |

- 窓を切り替えた直後の 1 回目のクリックは前面にするだけで、部品には効かない（Mac で別のアプリの窓をクリックしたときと同じ感覚）
- 実機（`modal.py` の grab の受け渡し・最小化の預かり・フォーカスの戻し）との組み合わせは未確認。ほかのアプリへ切り替えたとき（Cmd+Tab）も H の `<Deactivate>` で grab が D へ戻る見込み（未確認）

## 9. 案 D を transient なしで実測（2026-11-26・task_02 の手順 0・Mac・素の tkinter）

§8 の D-2 から H の `transient(D)` だけを外し、H を D に一部重ねて置いた。操作は §8 と同じ。

| 操作 | 結果 |
|---|---|
| H をクリック（1 回目 → 2 回目）・H のボタン | 1 回目で grab が H へ移り、2 回目から入力とボタンが効く（§8 と同じ） |
| H が前面のとき D をクリック（1 回目 → 2 回目） | H の `<Deactivate>` で grab が D へ戻り、2 回目から効く。**D が H の上に出る**（重なった部分も D が前） |
| ROOT の入力欄・ボタン | 届かない（ボタンの処理は動かず、キーは D の欄へ） |
| ふたたび H をクリック | H が D の上に出て、grab が H へ移る |

→ **transient なしで成り立つ**（正本 §4.6 の「transient にしない」のまま実装へ進める）。

## 10. 案 E（ヘルプを、いちばん手前のダイアログの子へ作り直して付け替える）の実測（2026-11-26・Mac・素の tkinter）

task_02 の目視で見つかった別件（ヘルプを開いたあとに別のダイアログを開くと、Mac・Windows ともヘルプが操作できない）への案。
新しい窓を先に出してから古い窓を消す。引き継ぐ状態 = 位置と大きさ・絞り込みの文字・チェック（見出しの開閉の代わり）・本文のスクロール位置。Mac は案 D の受け渡しも入れる（相手 = その時点の親）。

| 操作 | 付け替えにかかった時間 | 結果 |
|---|---|---|
| App の子のヘルプ（メニュー相当）→ DIALOG_1 を開く | 125 ms | ヘルプが DIALOG_1 の子になり、状態はすべて保たれる。DIALOG_1 が前面。ヘルプはクリック 2 回目から入力できる |
| DIALOG_1 → 入れ子の DIALOG_2 を開く | 150 ms | 同上（DIALOG_2 の子へ） |
| DIALOG_2 を閉じる | 69 ms | DIALOG_1 の子へ戻り、状態は保たれる。**前面に来たのがヘルプ**（DIALOG_1 であるべき。窓を消したあとにフォーカスを戻す順で直せる見込み） |
| DIALOG_1 を閉じる | 66 ms | App の子へ戻る。App 本体もヘルプも操作できる |

- 時間は新しい窓を作って状態を戻すまで（本文 200 行の Text を含む）。古い窓は新しい窓を出したあとで消すので、何も映らない間はない。ただし**ちらつきが目で見て気になるかは、画面の取り込みでは判断できない**（ユーザーの目視が要る・Windows は未実測）
- 窓を切り替えた直後の 1 回目のクリックは前面にするだけ（案 D と同じ）
- 目視用のスクリプト = `spike/help_follow_spike.py`（一時ファイル・目視が終わったら削除する・2026-11-26 ユーザー承認）。閉じたときの前面の順は、窓を消したあとで手前の窓へ戻す形に直してある

## 11. 暫定 63 の前提（A0）の実測（2026-11-26・task_03・Mac・素の tkinter・`spike/help_follow_spike2.py`）

暫定 63 の手順（閉じるときはダイアログを先に破棄 → ヘルプは親と一緒に消える → `after_idle` で持ち主の子として控えから作り直す / 開くときは新しい窓を先に出して古い窓を消す / 持ち主のすぐ下 / フォーカスに触らない）で試した。ダイアログはヘルプに重なる位置に開く。操作は 開く / 入れ子を開く / 入れ子を閉じる / 外側を閉じる。下の表の①②⑤の結果は、記載のない限り 4 つの操作で共通（③は §12 で操作別に記録）。

| 項目 | 結果 |
|---|---|
| ① 閉じたあとの作り直し | **できる**。入れ子を閉じると、消えてから 78〜101 ms で 1 つ前のダイアログの子として出直す。開くときの付け替えは 48〜86 ms |
| ① 状態 | 絞り込み・チェック・位置は保たれる。**スクロール位置は、作り直した窓が初期化の途中で「先頭」を控えに書き込み、控えを上書きして失われた** → 状態を戻し終えるまで控えへの書き込みを止めると保たれる（実装の要件） |
| ② 持ち主のすぐ下 | **窓が表示される前の `lower` は効かない**（重なり順の記録で、作ったヘルプが最前面のまま）。`wait_visibility()` で表示を待ってから `lower(持ち主)` すると、ヘルプはダイアログの下に入る |
| ③ フォーカス | **効かない**。開く・閉じるのどちらでも、新しく出したヘルプを OS が前面の窓（キー窓）にし、キーボードの入力先がヘルプの窓へ移る。そのため、ダイアログを開いた直後に打った文字・入れ子を閉じた直後に打った文字が、どこにも入らない（ダイアログの欄にもヘルプの絞り込み欄にも入らない）。試した手当て: (a) 持ち主の `focus_lastfor()` へ `focus_force` → 持ち主の窓自身に入り、欄には入らない (b) 作り直す直前の入力先へ `focus_force` → 開くときは `after_idle` の時点でダイアログの初期の入力先がまだ効いておらず App 本体が返り、欄に入らない |
| ④ 閉じるときの間 | 78〜101 ms ヘルプが消える（開くときの付け替えは 48〜86 ms）。目で見て気になるかは、Mac は未確認 → task_06 の目視で判断する（暫定 63 §2 確認事項 2）。Windows はユーザーが許容と報告（§12 の末尾） |
| ⑤ ヘルプの操作 | ダイアログの下に入ったヘルプは、見えている部分のクリックで前面に出て操作できる（スクロール可） |

→ 暫定 63 §3.6「付け替えはフォーカスに一切触らない」のままでは、**付け替えのたびにダイアログの入力先が失われる**（受け入れ条件 A14 を満たさない）。task_03 の定義どおりここで止めてユーザーへ相談する（2026-11-26）。Windows は未実測。

## 12. 案 X（付け替えのあと、持ち主が覚えている入力先へ `focus_force` で戻す）の実測（2026-11-27・task_03・Mac・`spike/help_follow_spike2.py`）

ダイアログごとに「最後に入力していた部品」を覚える（開いた直後は初期の入力先・以後は部品の `<FocusIn>` で更新・窓自身へのフォーカスは数えない）。付け替えでは、ヘルプの表示を待って `lower(持ち主)` したあと、持ち主が覚えている部品へ `focus_force` する。持ち主が App のときは戻さない。

| 操作 | 結果 |
|---|---|
| ダイアログ 1 を開いて「d1」と打つ | ダイアログ 1 の欄に入る（付け替えは 66 ms・ヘルプは下） |
| 入れ子のダイアログ 2 を開いて「d2」 | ダイアログ 2 の欄に入る（65 ms・ヘルプは下） |
| ダイアログ 2 を閉じて「k」 | ダイアログ 1 の欄に続けて入る（欄は「d1k」・消えてから 78 ms で出直す・ヘルプは下・ダイアログ 1 が前面の窓） |
| ダイアログ 1 を閉じる | ヘルプは App の子として出直し（85 ms）、状態は保たれる。絞り込み欄に入力できる |
| ヘルプを × で閉じてからダイアログを開く | ヘルプは出てこない（A8） |

→ **案 X で、付け替えのあともダイアログの入力先が保たれる**（A14）。暫定 63 §3.6 の「付け替えはフォーカスに一切触らない」を改める必要がある（2026-11-27 ユーザー承認・暫定 63 v0.5）。

Windows（2026-11-27・ユーザー・同じスクリプトで 1〜6 の手順）: **問題なし**（開いた直後・入れ子を閉じた直後の入力がダイアログの欄に入る・ヘルプはダイアログの下・状態は保たれる・閉じるときの消え方は許容・× で閉じたヘルプは出てこない）。

## 13. task_04・task_05 への引き継ぎ（task_03 の reviewer の指摘・2026-11-27）

1. `wait_visibility()` は `after_idle` の中で入れ子のイベントループを回す → 待つ間に再び付け替えの知らせや利用者の閉じが来ても壊れないよう再入を防ぐ。App やヘルプが最小化・withdraw されている間は表示されず待ちが戻らない恐れ → 待たずに済ませる条件か上限を設ける（A12 と合わせて確かめる・未実測）
2. 状態を戻している間は控えへ書き込まない（スクロールの上書き・§11）
3. 「App が前面にないときは戻さない」（A15）は目視用スクリプトに入っておらず未実測 → task_05 で実装し、task_06 で他のアプリが前面のときを確かめる
4. 最後のダイアログを閉じて持ち主が App に戻ったとき、入力先がヘルプの窓のままになる（§12 の「絞り込み欄に入力できる」はヘルプが前面の窓だったため）→ App 本体へ入力が届くか・絞り込み欄にフォーカスが入ってフックが止まらないかを task_06 で確かめ、必要なら暫定 63 §3.6 を見直す
5. 初期の入力先の経路は本番では `grab_modal` の `focus` 引数（省略時はダイアログ自身）。目視用スクリプトとは経路が違うため、A14 は本番で確かめる。台帳の入力先の更新（窓そのものを数えない）は単体テストを書く
6. 目視用スクリプトにない本番の要素（複数タブ・本文の読込の失敗・ヘルプの最小化・絞り込み欄のフックの停止・`restore_grab` の早期 return・Mac の受け渡しと `focus_force` の組み合わせ = A6）は task_05 のテストと task_06 の目視で扱う
